# G3: половина агентов на вердиктном цикле

Дата подготовки: 2026-11-19.
Гейт: G3 по ADR 0018. Следующий гейт G4 открывает владелец.
Зависимости: T4.4 (G2 canary), T4.7 (учебный откат), T4.2 (SLO). На момент подготовки PR по T4.4 и T4.7 ещё не влиты, поэтому фактические поля разделов «Результат» не заполнены.
Ссылки: ADR 0017, ADR 0018, ADR 0019, ADR 0022, T3.7, T3.8, T4.2, T4.4, T4.7, BEACON-AUDIT §11.

## Суть проверки

По ADR 0018 G3 переводит на вердиктный цикл половину агентов. Выход гейта это неделя активности без инцидентов лестницы и эскалаций либо все эскалации разобраны (BEACON-AUDIT §11). Инцидент это эскалация лестницы, зафиксированная в `beacon_stats` и `ESCALATIONS.md`, включая orphan по ADR 0019.

Вердиктный цикл это шаблоны T3.7 и T3.8: исполнитель сдаёт PR, завершает ход отчётом «waiting, watchID» и просыпается только на keep_working, rebase и retry; оркестратор мержит только после `beacon_get_result` с verdict=ready. Вторая половина агентов продолжает работать через `gh pr checks --watch`.

ADR 0018 запрещает проходить гейт самовольно и требует измерять SLO до перехода на следующий гейт. Решение о переходе на G4 принимает владелец. По ADR 0022 вся проверка идёт в CI через pull request, локально запускать тесты как гейт приёмки нельзя.

## Предусловия

1. T4.4 влит, конфиг и плагин владелец применил сам, три canary-агента работают по новому циклу.
2. Учебный откат T4.7 выполнен до расширения доли агентов. Контрольные суммы каталога состояния совпали, возврат подтверждён пробуждением по вердикту.
3. Известны источники данных: вывод `beacon_stats` и файл `ESCALATIONS.md` из каталога состояния Beacon рядом с `events.jsonl`. Счётчик эскалаций в выводе инструмента лежит в `ladder.escalated`.
4. Известны пути к квитанциям T3.6 и к логу, в котором T3.3 ловит `session.execution.started`.
5. Владелец готов разбирать каждый инцидент и фиксировать решение. Воркер не редактирует `~/.config/opencode`, чужие конфиги и shell rc-файлы.

## Порядок

1. Посчитать число активных агентов N и составить список групп. В группу вердиктного цикла записать `ceil(N / 2)` агентов, остальных оставить на `gh --watch`. Округление вверх гарантирует долю не ниже 50 процентов при нечётном N.
2. Перевести группу на шаблоны T3.7 и T3.8. Перевод делает владелец по ADR 0018. Зафиксировать дату перевода и состав группы.
3. Каждый день недели активности снимать `beacon_stats` и разбор строк `ESCALATIONS.md`. В журнал инцидентов заносить каждую эскалацию лестницы, каждую запись rung 2 и каждый orphan по ADR 0019. Если за день инцидентов нет, записать отдельную строку с пометкой «инцидентов нет». Плановая длительность наблюдения семь календарных дней.
4. Разобрать каждый инцидент вместе с владельцем. В журнале указать ключ эпизода, источник, тип, решение и статус. Неразобранных эскалаций к концу недели быть не должно.
5. Сверить число строк-записей в `ESCALATIONS.md` без учёта заголовка со счётчиком `ladder.escalated` из `beacon_stats`. По T3.10 один эпизод даёт ровно одну строку и одно увеличение счётчика, поэтому расхождение должно быть нулевым.
6. Снять SLO из T4.2 на группе вердиктного цикла до перехода к G4. В отчёт записать дату снятия и три прогона на каждом режиме 15, 30 и 60 Watch.
7. Записать в таблицы ниже период, состав групп, инциденты, сверку, SLO и решение владельца. Поле «Решение владельца по G3» заполняет владелец, а не воркер.

## Ожидаемый результат из расчёта

Расчёт доли. При N активных агентов группа вердиктного цикла равна `ceil(N / 2)`. При N = 15 это 8 агентов на вердиктном цикле и 7 на `gh --watch`. Доля 8 из 15 равна 53 процентам, то есть выше порога 50 процентов.

Расчёт периода. Неделя активности это 7 календарных дней и 7 ежедневных сборов инцидентов. День без инцидентов оставляет строку с пометкой в журнале, поэтому число строк журнала не меньше семи.

Расчёт сверки. По ADR 0017 и T3.10 один эпизод даёт одну строку в `ESCALATIONS.md` и одно увеличение `ladder.escalated`. При отсутствии потерь и повторных записей число строк-записей минус счётчик равно нулю. Orphan-эскалации по ADR 0019 входят в тот же счётчик и тоже требуют разбора.

Расчёт SLO по T4.2, цели до перехода на G4:

| Метрика | Цель |
| --- | --- |
| VmHWM при 60 Watch | менее 100 MB |
| p95 от события CI до квитанции `posted` | менее 15 с |
| Поинты в час | не выше 500, целевое значение 360 |
| Рестарт | не более 5 с |

Ноль процессов `gh --watch` относится к G4 по ADR 0018 и не является критерием G3, поскольку половина агентов остаётся на старом механизме.

Дополнительные ожидания:

- Неразобранных эскалаций в отчёте ноль.
- Каждый инцидент, включая orphan, имеет решение владельца.
- Учебный откат T4.7 выполнен до расширения доли.
- SLO из T4.2 в норме на группе вердиктного цикла.
- Переход на G4 подтверждён владельцем.
