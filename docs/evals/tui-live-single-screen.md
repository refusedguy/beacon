# TUI-LIVE-SINGLE-SCREEN

## Назначение

Eval проверяет живой экран по трём точкам входа, девяти глаголам оператора, отказу verbs `spawn` и `kill`, текстовому выводу без TTY и бюджету памяти. Карточка TU3-03 меняет только этот файл. Production-код, batch-JSON и карточки не меняются.

Зависимости TU3-01 и TU3-02 ещё не влиты в `origin/main` на коммите `dc24b45a`. Три точки входа и одноклавишные verbs поэтому описаны как проверки после их мержа. Этот агент не прогонял сценарий: локальные `go test`, `go build`, `beacon gates` и замеры RSS по правилам репозитория не запускались.

## Точки входа

| Команда | Ожидаемый путь | Состояние на `origin/main` |
| --- | --- | --- |
| `beacon tui` | dispatch вызывает `App.RunLive` | Команды нет. `cmd/beacon/main.go:254` держит только `board`, строка 286 только `up` |
| `beacon up --tui` | флаг `--tui` включает живой экран | Флага нет. `cmd/beacon/up.go:149` объявляет `--interval`, `--once`, `--channels` |
| `beacon board --live` | флаг `--live` включает живой экран | Флага нет. `cmd/beacon/catalog.go:35` описывает `board` без `--live`, `cmd/beacon/board_wire.go:20` вызывает статический `tui.Run` |
| `beacon board` без флага | прежняя таблица карточек | Работает через `cmd/beacon/board_wire.go:20` |

Все три живые команды должны дойти до `internal/tui/app.go:221` `App.RunLive`. Адаптер остаётся в `cmd/beacon` и не импортирует `net/http`. Ребро `cmd -> internal/tui` уже разрешено в `tools/beacon-gates/gate/config/layers.json:21`, матрица слоёв не меняется.

## Глаголы и клавиши

| Клавиша | verb в POST | Квитанция на экране |
| --- | --- | --- |
| `a` | `approve` | строка статуса с результатом `approve` |
| `d` | `reject` | строка статуса с результатом `reject` |
| `c` | `context` | строка статуса с результатом `context` |
| `w` | `rework` | строка статуса с результатом `rework` |
| `p` | `pause` | строка статуса с результатом `pause` |
| `u` | `resume` | строка статуса с результатом `resume` |
| `b` | `unblock` | строка статуса с результатом `unblock` |
| `x` | `cancel` | строка статуса с результатом `cancel` |
| `f` | `force_retry_merge` | строка статуса с результатом `force_retry_merge` |

`r` обновляет экран и не отправляет POST.

Сервер объявляет девять verbs в `internal/infra/httpapi/server.go:1291` `validCommands`, включая `force_retry_merge` в строке 1294. Списки клиента расходятся с сервером: `internal/tui/app.go:110` знает семь verbs без `context` и `force_retry_merge`, `internal/tui/socket.go:69` `DecisionCommands` перечисляет восемь. `internal/tui/board.go:310` `Update` обрабатывает навигацию и ввод `:`, подсказка в строке 535 обещает только `: команда`. TU3-02 правит `board.go` и `app.go`. Этот eval только фиксирует проверки.

Для каждой клавиши выбрать вотч через `SelectedWatch` в `internal/tui/board.go:222`, нажать клавишу и сверить тело POST `/api/v1/human/decide`: поле `command` равно verb из таблицы, поле `watchID` равно выбранному вотчу. Ответ `CommandMsg` из `internal/tui/board.go:66` должен записать в строку статуса `выполнено:` или `отказ:` с текстом ответа сервера.

## Отрицательные проверки

- `spawn` и `kill` отсутствуют в `validCommands`. Отправить каждый как `command`. Сервер возвращает HTTP 400 с текстом `неизвестная команда`, локальный снимок не меняется, строка статуса показывает отказ.
- Неизвестный verb ведёт к тому же отказу без изменения снимка.
- Отказ не меняет список вотчей, блокеры, очередь и хвост событий.
- Подсказка не содержит клавиш для `spawn` и `kill`.
- `maxBodyBytes` в `internal/tui/client.go:31` остаётся равным 1 МиБ. Серверный лимит тела запроса не меняется.

## Память

Цель аудита равна 20-30 МБ RSS на один процесс. Это цель из `docs/research/audit-03-tui.md`, а не измерение этого eval.

Метод замера: поднять живой экран на loopback HTTP с replay, прочитать поле `VmRSS` из `/proc/self/status` после первого кадра и после двухсот обновлений по SSE, перевести kB в МБ делением на 1024. В отчёт записать оба числа, метод, дату, версию Go, целевую платформу, число вотчей и число replay-событий.

Два числа с методом уже записаны в `docs/evals/u01-render-15-watches.md`: 19354 kB (18.9 МБ) после первого кадра и 22118 kB (21.6 МБ) после двухсот обновлений. Замер выполнен 2026-11-22 на Go 1.27.4, linux/amd64, с 15 вотчами. TU3-03 не повторяет тот eval и не делает локального замера.

Ограничители уже лежат в коде: `maxBodyBytes` равен 1 МиБ в `internal/tui/client.go:31`, `eventReplayCount` равен 64 в строке 39, `maxEventLines` равен 12 в `internal/tui/board.go:43`, `outQueue` равен 16 в `internal/tui/socket.go:23`, `maxDedup` равен 256 в строке 26. Ни одно из этих чисел не измерялось этим агентом.

Во время прогона проверить список процессов на `node`, `chrome`, `chromium`, `firefox` и `electron`. Ожидается ноль совпадений. В `go.mod` нет JS-рантайма, браузерного движка и Electron. Отдельного процесса для рендера нет.

## Вывод без TTY

Команда в pipe печатает тот же набор данных текстом и завершается с кодом ноль. На текущем `origin/main` `boardHasTerminal` в `cmd/beacon/board_wire.go:91` проверяет только stdin. `internal/tui/app.go:171` `Render` печатает живой снимок, но ни один dispatch не вызывает этот раннер. TU3-05 владеет правкой fallback, поэтому проверка применяется после мержа TU3-01 и TU3-05.

## Порядок прогона

1. Дождаться TU3-01, TU3-02 и TU3-05 в `origin/main`.
2. Поднять loopback-сервер с тестовым state и включённым replay SSE.
3. Для каждой из трёх точек входа открыть экран и сверить первый кадр: вотчи с вердиктами, воркеры с фазами и ролями, блокеры, очередь, хвост событий, `rssBytes` и `pointStats`.
4. Проверить отсутствие процессов Node.js и браузера.
5. Для каждой из девяти клавиш сверить verb в POST и квитанцию на экране.
6. Выполнить отрицательные проверки с `spawn`, `kill` и неизвестным verb.
7. Снять `VmRSS` после первого кадра и после двухсот обновлений, записать оба числа с методом. Диапазон 20-30 МБ остаётся целью аудита.
8. Повторить команду без TTY, сравнить текст и код выхода.

## Критерии провала

- Хотя бы одна точка входа не доходит до `App.RunLive`.
- Клавиша отправляет не тот verb или не показывает квитанцию.
- Сервер принимает `spawn`, `kill` или неизвестный verb.
- Отказ меняет локальный снимок.
- В выводе появляется процесс Node.js или браузера.
- Свежий замер RSS превышает 30 МБ.
- Вывод без TTY теряет данные или завершается кодом, отличным от нуля.
