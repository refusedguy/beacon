## Методика и ограничения

Websearch вернул HTTP 402, поэтому поиск заменён прямым чтением официальных документов через webfetch. Первичные источники: docs.anthropic.com/code.claude.com, openai.github.io и GitHub OpenAI Swarm, docs.langchain.com, microsoft.github.io/autogen, docs.crewai.com, docs.temporal.io.

В отчёте различаются три вещи: статус задачи как поле, приостановка исполнения и передача управления. Многие системы не имеют статуса задачи вовсе. Там, где статус есть, он часто живёт не в рантайме, а в пользовательском коде. Фразы «не найдено» означают отсутствие в прочитанных первичных документах, а не доказательство отсутствия в продукте.

## Claude Agent SDK и agent teams

Источники: [todo tracking](https://code.claude.com/docs/en/agent-sdk/todo-tracking.md), [agent teams](https://code.claude.com/docs/en/agent-teams.md), [tools reference](https://code.claude.com/docs/en/tools-reference.md).

У TaskCreate, TaskGet, TaskList и TaskUpdate есть явный жизненный цикл. Задача создаётся как `pending`, переводится в `in_progress`, завершается как `completed` и удаляется установкой `status: "deleted"` через TaskUpdate. TaskUpdate меняет статус, зависимости и описание. Статусы приходят в потоке сообщений как вызовы инструментов, поэтому приложение может строить свой прогресс-бар.

В agent teams общий список задач работает иначе. Документ называет три состояния: pending, in progress, completed. Задача может зависеть от других задач и показывается как blocked, пока зависимости не завершены. Команда самостоятельно снимает блок, когда задача-зависимость переходит в completed.

Claim децентрализован. Лид назначает задачу явно, либо тиммейт после завершения текущей задачи берёт следующую неназначенную и разблокированную. Одновременный захват одной задачи предотвращается файловой блокировкой. Заблокированную задачу тиммейт не берёт, но лид или человек может её назначить.

Закрытие инициирует агент через TaskUpdate. Хуки TaskCreated и TaskCompleted могут запретить создание или завершение, выйдя с кодом 2 и отправив объяснение. TeammateIdle с кодом 2 удерживает тиммейта от перехода в простой. Человек может поправить статус вручную, и документ прямо описывает случай, когда тиммейт не отметил задачу завершённой и заблокировал зависимые задачи.

В прочитанных документах нет TTL захвата, нет close reason и нет отдельного статуса duplicate или cancelled. Есть shutdown request с ответом approve или reject, но это протокол завершения сессии, а не статус задачи. Блокировка файлом даёт взаимное исключение без истечения срока, поэтому мёртвый тиммейт оставляет задачу в in_progress.

## OpenAI Agents SDK

Источник: [human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/).

У SDK нет очереди задач и статусов. Единица работы это run, а его состояние хранится в `RunState`. Инструмент объявляет `needs_approval` булевой величиной или функцией. Рантайм приостанавливает run и отдаёт `ToolApprovalItem` в `RunResult.interruptions`. Приложение вызывает `state.approve(...)` или `state.reject(...)` и продолжает через `Runner.run(agent, state)`. Одобрение действует на весь run, включая handoff и вложенный `Agent.as_tool()`.

Закрытие run наступает с финальным ответом. Отклонение возвращает сообщение обратно в run через `tool_error_formatter` или `rejection_message`. Это не closed, а продолжение с другим входом.

Большинство полезных для Beacon деталей находятся в разделе про долгоживущие одобрения. `RunState` сериализуется в базу или очередь. Документ требует, чтобы сервер сам аутентифицировал ревьюера, авторизовал его на конкретный run, проверял идентификаторы ожидающих решений против серверного снимка и выполнял атомарный переход с проверкой владельца. Иначе параллельные или повторные запросы возобновят один снимок дважды.

Отдельно сказано, что одобрение разрешает вызов инструмента, но не даёт ровно одного исполнения. Для побочных эффектов приложение назначает стабильный idempotency key и передаёт его в систему, которая атомарно подавляет повторы. Если такой ключ недоступен, нужно сверить результат с внешней системой до повтора, а при неопределённости записать исход как unknown.

Статусов blocked, duplicate и cancelled нет. Human gate здесь самый зрелый из рассмотренных, но ответственность за идемпотентность лежит на приложении.

## LangGraph

Источники: [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), [persistence](https://docs.langchain.com/oss/python/langgraph/durable-execution).

Задача это узел графа, а не запись со статусом. `interrupt()` внутри узла приостанавливает исполнение, checkpointer сохраняет состояние, и граф ждёт неопределённо долго. Возобновление идёт через `Command(resume=...)` с тем же `thread_id`. Документ называет `thread_id` постоянным курсором: повторное использование продолжает тот же чекпоинт, новое значение создаёт новую ветку.

Payload прерывания доступен в `stream.interrupts` при event streaming и в `result["__interrupt__"]` при `invoke`. Для нескольких параллельных прерываний значения возобновления сопоставляются с `Interrupt.id`. Схема ответа задаётся через `response_schema` на Pydantic, TypedDict или dataclass, и Studio показывает типизированную форму.

Ключевое правило: при возобновлении узел перезапускается с начала, а не с строки вызова `interrupt()`. Побочные эффекты до прерывания должны быть идемпотентными. После долгого простоя нужно перечитать внешнее состояние. Документ рекомендует выносить эффекты в отдельные узлы и не оборачивать `interrupt()` в обычный try/except.

Есть отдельный раздел про одобрение вне графа. Возвращённое значение считается подтверждением возврата оператора, а не самим решением. Задача отправляется в одном узле, её идентификатор сохраняется в чекпоинте, а после возобновления проверяется внешний статус. Если решение ещё не принято, узел вызывает `interrupt()` снова вместо создания новой задачи.

Checkpointer хранит состояние одного потока, store работает между потоками. InMemorySaver теряет данные при рестарте, для продакшена указаны PostgresSaver и SqliteSaver. Статусов claim, blocked и duplicate нет. Роль blocked выполняет ожидание прерывания, роль close завершение графа через END.

## AutoGen core

Источник: [autogen_core API reference](https://microsoft.github.io/autogen/stable/reference/python/autogen_core.html).

В AutoGen core нет задачи как сущности. Есть агент с адресом `AgentId`, рантайм и сообщения. `AgentRuntime.send_message` отправляет напрямую и возвращает ответ. `publish_message(message, topic_id, ...)` рассылает сообщение подписчикам темы и возвращает `None`. В документации прямо сказано, что ответов от публикации не ожидается.

Сигнатура publish важна для сравнения. Параметр `message_id` должен быть уникальным, рекомендуется UUID, а при отсутствии генерируется рантаймом. Это встроенный ключ идемпотентности доставки. Параметр `cancellation_token` отменяет ожидающие вызовы, а `Agent.on_message` может бросить `CancelledError`. Отмена здесь транспортная, а не бизнес-статус задачи.

Жизненный цикл агента описан через `bind_id_and_runtime`, `save_state`, `load_state` и `close()`, который вызывается при закрытии рантайма. `AgentId` уникален внутри рантайма, включая распределённый, и служит адресом для получения сообщений.

Статусов in_progress, blocked, duplicate и close reason нет. Урок для оркестратора: если модель публикации fire-and-forget, дедупликация живёт в идентификаторе сообщения, а не в статусе получателя.

## CrewAI Flows

Источник: [Flows](https://docs.crewai.com/en/concepts/flows).

Flow это событийный граф методов с декораторами `@start`, `@listen`, `@router`. Состояние получает автоматический UUID. `@persist` на классе или методе включает сохранение в SQLite по умолчанию. Есть два режима гидрации: `kickoff(inputs={"id": uuid})` продолжает ту же запись, а `kickoff(restore_from_state_id=uuid)` копирует состояние в новую запись с новым id. Если источник не найден, kickoff молча продолжается с чистым состоянием.

`@human_feedback` с версии 1.8.0 приостанавливает flow и собирает ответ человека. Параметр `emit` задаёт исходы, например `approved`, `rejected` и `needs_revision`. Свободный ответ обрабатывается моделью и сводится к одному из исходов, который запускает соответствующий `@listen`. Есть `default_outcome`, история отзывов в `self.human_feedback_history` и асинхронные провайдеры вроде Slack или webhook.

Закрытие flow наступает, когда завершён последний метод, и его возврат становится результатом `kickoff()`. Статусов задачи, claim, blocked и duplicate нет. Набор исходов `@human_feedback` ближе всего к close reason: решение человека становится именованным исходом с маршрутизацией.

## Temporal

Источники: [workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing), [continue-as-new](https://docs.temporal.io/develop/python/continue-as-new).

Temporal разделяет сообщения по семантике ожидания. Signal это асинхронная запись без ответа. Query это чтение без блокировки и без записи в Event History. Update это синхронная отслеживаемая запись, которую можно проверить до принятия, и отправитель ждёт результата или ошибки. Документ сравнивает их по fire-and-forget, доступности воркера, конкуренции и чувствительности к задержке.

Continue-As-New закрывает текущий run успешно и создаёт новый в той же цепочке. Workflow Id остаётся тем же, Run Id и Event History становятся новыми, состояние передаётся параметрами. Документ называет это чекпоинтом при приближении к лимитам истории и предлагает проверять `workflow.info().is_continue_as_new_suggested()`. Вызов из обработчика signal или update запрещён, нужно дождаться завершения обработчиков в основном потоке.

Кто закрывает: код воркфлоу или внешний клиент через signal и update, а предел истории отслеживает рантайм. Статусов blocked и duplicate в прочитанных разделах нет. Полезный паттерн для Beacon это закрытие с сохранением идентичности и свежей историей вместо бесконечного роста одного Watch.

## OpenAI Swarm

Источник: [README](https://raw.githubusercontent.com/openai/swarm/main/README.md).

Swarm признан учебным проектом и заменён Agents SDK. Два примитива: `Agent` и handoff. Функция возвращает объект `Agent`, и исполнение переходит к нему. Если handoff-функций несколько, используется последняя. Объект `Result` позволяет одной функцией вернуть значение, сменить агента и обновить `context_variables`.

Swarm не хранит состояние между вызовами. `client.run()` возвращает `Response` с сообщениями, последним агентом и контекстом, которые передаются в следующий вызов. Цикл обработки: получить completion, выполнить инструменты, сменить агента, обновить контекст, вернуться, если новых вызовов нет. Параметр `execute_tools=False` прерывает исполнение и возвращает `tool_calls`, что похоже на приостановку до внешнего решения.

Статусов claim, blocked, duplicate и close reason нет. Handoff это передача управления вместе с контекстом, а не смена статуса задачи.

## Сопоставление с Beacon

Уже есть по `AGENTS.md` и локальным аудитам:

- `beacon_task_claim` выдаёт карточку, цель, зависимости, OwnerFiles, режим плана и handoff. Первая выдача ставит `in_progress`, поэтому второй агент не берёт ту же карточку.
- Граф из рёбер `blocks`, `depends-on`, `supersedes` и `related` с отвержением цикла на записи.
- Watch и вердикты: `beacon_watch_pr`, `beacon_get_result`, `beacon_wait_result`, `beacon_ack` с решениями `approve`, `reject`, `blocked:not_mine` и `blocked:resolved`.
- Терминальный `merged` сам переводит связанную карточку в `done` и пишет ссылку на PR.
- `closeReason=head_changed` для преемника Watch при смене head, `BlockerIncident`, бюджет wake, парковка, deferred wiring.

Чего нет:

- Закрытия карточки без PR. Исследовательская или документальная карточка, дубликат и отклонённая human задача не имеют терминального пути.
- Таксономии close reason для карточки с указанием актора и доказательства. Причина закрытия Watch есть, причины закрытия карточки нет.
- Срока захвата. in_progress живёт до мержа или ручного вмешательства. Смерть агента оставляет карточку занятой, как в Claude при задержке статуса.
- Статуса duplicate-of и обработки дубликата через `supersedes`.
- Универсального human gate. Решения approve и reject привязаны к вердикту Watch, а не к закрытию карточки.

## Три механизма с приоритетом

### Приоритет 1. Закрытие карточки без PR с причиной

Добавить терминальное состояние, которое не зависит от `merged`, и обязательные поля `close_reason`, `actor` и `evidence`. Перечень причин: `done_without_pr`, `duplicate_of`, `rejected_by_human`, `superseded`, `abandoned`. Для `duplicate_of` использовать уже существующее ребро `supersedes` и запретить повторный claim дубликата.

Инициатором должен быть оркестратор или человек, но не сам исполнитель по своей карточке. Это сохраняет правило `AGENTS.md` о запрете ручного закрытия исполнителем. Механизм снимает главный пробел и переиспользует `closeReason`, который уже есть у Watch.

### Приоритет 2. Lease на claim с продлением по активности сессии

Записывать при выдаче `claimedAt` и `leaseUntil`. Продлевать срок по наблюдаемой активности сессии, которую читает эскалация доставки. По истечении срока возвращать карточку в pending и публиковать событие. Повторный claim после истечения должен быть идемпотентным по `(cardID, leaseGeneration)`.

Основание: Claude блокирует параллельный захват файлом, но документ описывает задержку статуса и заблокированные зависимости. Beacon сталкивается с тем же при смерти сабента. Стоимость ниже, чем кажется, потому что источник активности уже есть в системе доставки.

### Приоритет 3. Универсальное ожидающее решение с одноразовым потреблением

Вынести approve и reject из `beacon_ack` в отдельную сущность `pendingDecision` с идентификатором, владельцем и версией. Решение принимается только от аутентифицированного ревьюера, проверяется против серверного снимка и потребляется атомарно с проверкой версии. Повторный или параллельный ответ не возобновляет агента дважды.

Это повторяет правила серверной одобрялки OpenAI Agents SDK, идентификаторы прерываний LangGraph и именованные исходы CrewAI. Механизм номер три стоит после первых двух, потому что без close reason и lease нечего передавать человеку на решение.

## Пять находок с источниками

1. В Claude agent teams захват задачи защищён файловой блокировкой, а документ прямо описывает задержку статуса, когда тиммейт не отметил задачу завершённой и заблокировал зависимые. Блокировка без срока не лечит мёртвого владельца. [agent teams](https://code.claude.com/docs/en/agent-teams.md)

2. OpenAI Agents SDK не гарантирует ровно одного возобновления. Гарантию строит приложение: аутентификация ревьюера, проверка идентификаторов против серверного снимка, атомарный переход с проверкой владельца и стабильный idempotency key для побочных эффектов. [human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)

3. LangGraph перезапускает узел с начала при каждом `Command(resume=...)`. Побочные эффекты до прерывания обязаны быть идемпотентными, а возврат из внешней системы одобрения считается подтверждением возврата, а не самим решением. [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

4. AutoGen `publish_message` не ожидает ответа, но требует уникальный `message_id`. В fire-and-forget модели дедупликация живёт в идентификаторе сообщения, а не в статусе получателя. [autogen_core API](https://microsoft.github.io/autogen/stable/reference/python/autogen_core.html)

5. Temporal различает Signal, Update и Query по семантике ожидания и закрывает длинный run через Continue-As-New с тем же Workflow Id и свежей историей. Это готовый аналог для Watch, который не должен расти бесконечно. [message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing), [continue-as-new](https://docs.temporal.io/develop/python/continue-as-new)
