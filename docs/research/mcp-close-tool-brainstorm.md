# Брейншторм: MCP-инструмент закрытия карточек

Дата: 2026-11-21. Режим только чтение. Код, конфиги и карточки не менялись. Тесты, сборки и гейты не запускались. tools.beacon не вызывался. Поиск шёл через rg с явными каталогами. Websearch вернул HTTP 402, поэтому внешние источники не использованы. Все утверждения ниже опираются на файлы репозитория.

## Главные находки

1. Четыре проверки золотого `tools/list` обновляются по-разному. Имена, порядок и классы аннотаций выводятся из `toolDescriptors`. Число байт и SHA-256 пишутся вручную в `contract_test.go`. Десятый дескриптор сам обновит три проверки из четырёх, но без ручной правки двух констант контракт останется красным.

2. Золотой ломается не только от десятого имени. go-sdk выводит `inputSchema` из типа аргументов обработчика. Поле `cardClose` в `AckInput` изменит сериализованный ответ `tools/list` так же, как новое имя. Вариант «без десятого инструмента» через расширение `beacon_ack` не сохраняет побайтовый контракт.

3. Карточка в `docs/tasks` остаётся источником истины. SQLite хранит производный индекс, который CI сверяет с деревом карточек. Закрытие надо писать в markdown-карточку, затем пересобирать индекс. Статусы `blocked` и `duplicate` сегодня не проходят парсер карточек.

4. ADR-цепочка и evals отстают друг от друга. ADR 0094 фиксирует восемь имён и требует отдельного ADR на девятое. ADR 0263 фиксирует семь. ADR 0268 добавил девятое имя и золотой 18212 байт. В `evals/main.go` список `contractTools` содержит восемь имён без `beacon_task_claim`, поэтому eval `02_catalog` на девятиинструментальном сервере красный уже сейчас.

5. В репозитории есть прецедент инструмента вне рекламируемого контракта. `t3_thread_read` имеет обработчик, схему и `AttachThreadRead`, но намеренно отсутствует в `toolDescriptors`. Он не меняет `tools/list`. ADR 0263 запрещает тихую регистрацию вне контракта, поэтому этот путь требует явного решения владельца.

## 2. Проект beacon_task_close

Вход и выход в стиле соседнего `tool_task_claim.go`:

```go
type TaskCloseInput struct {
    CardID      string `json:"cardID" jsonschema:"exact card id to close; required"`
    AgentID     string `json:"agentID" jsonschema:"agent closing the card; required for an in_progress card owned by another agent"`
    Status      string `json:"status" jsonschema:"done, dropped, blocked or duplicate"`
    Reason      string `json:"reason" jsonschema:"short reason recorded in the card; required"`
    DuplicateOf string `json:"duplicateOf,omitempty" jsonschema:"card id this one duplicates; required when status is duplicate"`
}

type TaskCloseOutput struct {
    OK     bool   `json:"ok"`
    CardID string `json:"cardID"`
    Status string `json:"status"`
}
```

Идемпотентность проще всего держать в карточке. Вводим поле `Причина закрытия` и пишем его вместе со статусом. Повтор с тем же `cardID`, `status` и `reason` возвращает `ok=true` без записи. Повтор с другой причиной или другим статусом получает ошибку. Это та же модель, которую `beacon_defer_wiring` использует для ключа `(watchID, reason)` и где повтор возвращает `created=false`.

Валидация на границе обработчика, до записи:

- `cardID` обязателен, автоматический выбор карточки не нужен.
- `status` входит в `{done, dropped, blocked, duplicate}`. Для `duplicate` обязателен `duplicateOf`, и карточка с таким ID должна существовать.
- `reason` не пустой после `TrimSpace`.
- Если найденная карточка имеет `Статус: in_progress` и непустое поле `Агент`, `agentID` обязателен и должен совпадать с владельцем. Иначе закрытие чужой работы возможно без её владельца.
- Для карточки в `todo` требуется непустой `agentID`, но совпадение с владельцем не проверяется.
- Карточка уже в целевом статусе с той же причиной это успешный повтор. Карточка в другом терминальном статусе это ошибка.
- Несовпадение `agentID` и статуса `in_progress` преобразуется в `CodeInvalidInput` или в новый код проекта. Новый код затронул бы `ErrorShape` и `statusByCode` в `schema.go:420`, поэтому для первой версии дешевле обойтись существующими кодами.

Хранение. Markdown-карточка остаётся источником истины. Причина закрытия живёт в новом поле карточки, статус меняется в строке `Статус:`. Писать надо через блокировку и атомарный rename, как делает `FileTaskClaimStore` в `tool_task_claim.go:147`, либо через уже существующий writer `internal/infra/batchapply/apply.go:606`, который сегодня ставит `done` после мержа. Автоматический путь после мержа идёт через `closeLinkedCard` в `internal/infra/cibridge/verdict_applier.go:391` и срабатывает только для `VerdictMerged`. Ещё один готовый writer это `runTaskDone` в `cmd/beacon/task.go:430`. Он берёт flock, требует `--summary` и `--evidence`, пишет поля `Итог` и `Доказательство` и отклоняет повтор на неактивной карточке. Новый инструмент может переиспользовать этот формат вместо нового поля `Причина закрытия`. После записи композиционный корень должен пересобрать индекс командой `beacon index build`, иначе CI найдёт расхождение индекса с деревом карточек.

Побочные эффекты новых статусов. `cardStatuses` в `internal/infra/taskstore/store.go:237` содержит только `todo`, `in_progress`, `done`, `dropped`. Такой же список дублирует `internal/app/taskcli/service.go:80`, а whitelist полей карточки лежит в `store.go:104`. Список из 13 полей продублирован в `tools/beacon-gates/docsgate`. Добавление `blocked` и `duplicate` потребует правки всех этих мест. Перевод в `done` дополнительно разблокирует зависимые карточки через `FileDependencyResolver` в `internal/app/orchestrator/store.go:97`, который считает зависимость выполненной только при `Статус: done`.

Аннотации. Идемпотентный инструмент логично регистрировать как `kindAdditive`: `DestructiveHint: false`, `IdempotentHint: true`. Контрактный тест в `contract_test.go:170` проверяет именно это сочетание. Если владелец решит, что закрытие карточки деструктивно, нужен `kindDestructive` и правка ожидаемой аннотации в том же PR.

Риск для первой версии: статусы `blocked` и `duplicate` расширяют язык карточек и задевают doc gate. Безопаснее начать с `done` и `dropped`, а `duplicate` добавить отдельным решением вместе с определением графового ребра.

## 3. Альтернативы без десятого имени

**a) Поле `cardClose` в `beacon_ack`.** Плюс: число имён остаётся девять. Минусы: `inputSchema` инструмента меняется, поэтому байты и SHA золотого всё равно обновляются. Один вызов получает два разных действия, и аннотацию инструмента нельзя выбрать однозначно. ADR 0094:28 уже отверг такую схему для отложенной проводки и выбрал отдельное имя. Сейчас `beacon_ack` работает с обязательствами Watch, а не с карточками. Evals `r03`, `w21` и `e05` завязаны на поведение ack, и любая правка обработчика повышает риск их переписать.

**b) `beacon_defer_wiring` с параметром `status`.** Плюс: готовая идемпотентность по `(watchID, reason)` и готовый вывод карточки. Минусы: инструмент создаёт карточку `WIRING-<PR>` для неподключённой проводки, а не меняет статус произвольной задачи. Расширение `DeferWiringOutput` изменит схему и золотой. Смешение двух областей мешает владельцу карточки понять, кто отвечает за закрытие.

**c) Фоновая проверка TTL `claimedAt`.** Плюс: контракт MCP не меняется, золотой остаётся побайтово тем же. Минусы: сегодня TTL для выдачи карточек нет. `taskstore` знает только протухшие файловые замки по PID в `store.go:419`. Нужен новый демон, новое событие и правило, которое решит, что делать с живым агентом. У такой карточки не будет `reason` и `duplicateOf`. Штатный путь закрытия по AGENTS.md это мерж PR, при котором Beacon сам ставит `done`. Демон может закрыть карточку, пока агент ещё работает.

**d) Закрытие обычным docs-only PR.** Плюс: контракт, ADR и evals не трогаются. Карточка остаётся источником истины, индекс пересобирается в CI, история причины лежит в самом PR. Минусы: нет атомарной операции для агента, нет проверки владельца в момент записи, возможна гонка с `beacon_task_claim`. Правило «не закрывай карточку вручную» из AGENTS.md сегодня запрещает такой шаг исполнителю, поэтому путь требует решения владельца.

**e) Инструмент вне рекламируемого набора по образцу `t3_thread_read`.** Плюс: обработчик доступен подключившему его корню, а `tools/list` и золотой не меняются. Минусы: ADR 0263 называет тихую регистрацию вне контракта нарушением, а комментарий в `server.go:131` прямо указывает, что десятое имя ломает закреплённый листинг. Нужно явное решение владельца и отдельная запись в документации контракта.

**f) Готовый CLI `beacon task done` и `beacon task needs-input`.** Это уже реализованный путь в `cmd/beacon/task.go:430` и `:493`. Команда `done` ставит `Статус: done`, пишет `Итог` и `Доказательство`, берёт flock и не принимает повтор на неактивной карточке. Без `--evidence` карточка уходит в `needs_input` и остаётся `in_progress`. Контракт MCP не меняется, ADR не нужен. Минус: нет команд для `dropped` и `duplicate`, и право вызова надо ограничить оркестратором или владельцем. Подробный разбор этого пути есть в `docs/research/task-lifecycle-brainstorm.md`.

## 4. Влияние на ADR и evals

ADR 0094 в приёмке говорит, что девятый инструмент требует отдельного решения или ADR. ADR 0263 повторяет это для восьмого и запрещает тихую регистрацию. ADR 0268 добавил девятое имя `beacon_task_claim`, поднял бюджет с 16 KiB до 20 KiB и зафиксировал замер 17922 байт. Десятое имя требует нового ADR, который явно отменяет потолок в девять инструментов. Если появится новый код ошибки, задевается ADR 0009. ADR 0186 направляет новые возможности в HTTP и SSE, поэтому ADR должен объяснить, почему на этот раз выбран MCP.

Evals делятся на две группы. `02_catalog`, `CT01_contract_tools_frozen`, `r10-seven-tools` и `e02-seven-tool-contract` считают имена и требуют обновления. В `evals/main.go:63` сейчас восемь имён, `beacon_task_claim` отсутствует, а `frozenContractToolsHash` равен `b0a23b54...`. Пересчёт хеша по девяти или десяти именам обязателен. `02_catalog` сравнивает ответ живого сервера со списком, поэтому сервер с девятью инструментами уже даёт FAIL. `e05`, `w21` и `r03` не считают инструменты. Они проверяют `hasPendingQuestion`, отклонение старой revision и разницу между plain ack и `blocked:not_mine`. Если `beacon_ack` не трогать, эти кейсы остаются в силе.

Что изменится в золотом:

- Число инструментов: 9 становится 10.
- Число байт: 18212 заменяется на замер из CI. Точное значение заранее не известно. По историческим шагам один инструмент добавляет примерно 1500 до 2500 байт. Ориентир 19700 до 20700 байт.
- SHA-256: меняется обязательно, даже если число байт совпадёт.
- Бюджет: потолок 20 KiB равен 20480 байт. При ориентире выше 20480 его поднимают до 24 KiB в том же ADR.
- Порядок: SDK сортирует имена. `beacon_task_close` идёт после `beacon_task_claim`, так как `claim` меньше `close`, и перед `beacon_wait_result`.

## 5. Рекомендация и план миграции

Для ближайшей потребности рекомендую вариант (f), а для статусов `dropped` и `duplicate` вариант (d). Оба сохраняют golden побайтово, не требуют ADR и оставляют карточку источником истины. Вариант (f) лучше, потому что проверка доказательства и блокировка уже написаны. Если агенту нужна атомарная операция с проверкой владельца, нужен отдельный ADR и десятый инструмент `beacon_task_close` с хранением в markdown. Варианты (a) и (b) не дают выигрыша в контракте. Вариант (c) вводит новый механизм без ясного правила. Вариант (e) годится только после прямого решения владельца.

План миграции для десятого инструмента:

1. Зафиксировать baseline. Измерить дельту `tools/list` в CI на PR, локальные тесты по правилам репозитория не запускать. Записать число и ссылку на замер в карточке.
2. Принять ADR о десятом инструменте. Перечислить статусы, ключ идемпотентности, обязательного владельца, аннотации и источник истины для причины закрытия. Явно обновить счётчик в ADR 0094 и снять противоречие с ADR 0263.
3. Написать `internal/infra/mcp/tool_task_close.go` по образцу `tool_task_claim.go`: вход, выход, порт `TaskCloseStore`, файловый адаптер с блокировкой и атомарной записью. Порт добавить в `Dependencies` рядом с `TaskClaimStore` в `server.go:455`.
4. Добавить дескриптор в `toolDescriptors`, фабрику схемы и хелпер `attachTaskClose`. Ни один существующий дескриптор не трогать.
5. Обновить золотые константы и бюджет по измерению из CI. Обновить `docs/AGENTS.md`, где сейчас перечислены девять инструментов.
6. В evals добавить в `contractTools` и `beacon_task_claim`, и `beacon_task_close`, пересчитать `frozenContractToolsHash`, поправить README и спецификации `r10-seven-tools` и `e02-seven-tool-contract`. Кейсы `e05`, `w21`, `r03` оставить без изменения.
7. Если в первой версии появляются `blocked` или `duplicate`, расширить `cardStatuses`, фильтр `taskcli` и список полей в doc gate в том же PR. Иначе отложить их до отдельного ADR.
8. Прогнать проверки в GitHub Actions на PR. Локально только gofmt на свои Go-файлы, как требует AGENTS.md.

Порядок шагов позволяет остановиться после любого этапа. До шага 5 контракт остаётся красным по золотому, поэтому шаги 2 до 5 идут одним PR.
