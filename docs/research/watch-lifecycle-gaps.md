## Детали по разрывам

### Прерванный ретрай при GC

`GCObligations` в версии PR #1275 выбирает строку по времени закрытия Watch или по времени последней активности обязательства. Список полей в `obligationLastActivity` не содержит `NextRetryAt`, хотя лестница доставки ставит туда момент следующей попытки и хранит историю попыток в `Attempts`. Для обязательства с отсутствующей строкой Watch это даёт удаление строки с живым ретраем. Тихий результат: подписчик не получит повтор, а аудит удаления покажет безобидную причину `gc:missing`.

### Снимок и применение GC

`GCObligations` читает `LiveWatches`, `AllWatches`, архив и таблицу обязательства отдельными запросами к read pool. После построения плана каждая строка удаляется своим вызовом `EraseObligation`, который пишет аудит и делает delete в отдельной транзакции. Между снимком и удалением нет проверки, что Watch всё ещё закрыт, а обязательство не изменилось. Один процесс может удалить обязательство, созданное другим процессом после снимка.

### Подтверждённое обязательство остаётся висящим

`beacon_ack` вызывает `StampClaimed`, который меняет только `ClaimedAt` в payload. Колонка `delivered_at` остаётся нулевой, поэтому `PendingObligations` возвращает строку. Два потребителя этого метода выбирают её как активную: обязательство для human wake в `cmd/beacon/mcp.go` и счётчик активных обязательств при остановке агента в `cmd/beacon/registry_stop.go`. Результат: повторный wake со старым `obligationID` и ложный отказ в остановке.

### Обязательства orphaned подписчика

Фильтр `Bridge.wakeOne` не даёт wake на мёртвую сессию, но не меняет число создаваемых обязательств. `Fanout.ensureObligation` вызывается для всех подписчиков на каждой регистрации. GC из PR #1275 защищает обязательства только живых Watch. Для живого Watch с мёртвым исполнителем получается бесконечный рост таблицы. Синтетическое обязательство `orphan:<watchID>` из `markOrphaned` рано или поздно собирается GC по ветке `missing`, поэтому оно не является постоянной утечкой.

### Поллеры WatchOutcome

PR #1228 закрыл гонку с пулом чтения, добавив ожидание горутин в `Close`. Он не убрал две другие проблемы. Первая: `readWatchOutcome` выбирает единственную строку по ключу без сравнения ревизии, поэтому новый наблюдатель получает уже опубликованный результат. Вторая: число поллеров равно числу вызовов. При массовом ожидании одного worker key LOAD на SQLite растёт линейно. Утечка горутины возможна, если вызывающий передаёт `context.Background()` и не читает канал. Такая горутина живёт до закрытия store.

### Гонка закрытия head

Между `SaveWatch(closed)` и `SaveWatch(next)` в `handleHeadChanged` есть окно. Если в него попадёт `beacon_watch_pr`, `Fanout.Subscribe` не найдёт активный Watch на новый SHA и создаст свой с ID с суфиксом времени. После этого `handleHeadChanged` проверит короткий ID `watch:<repo>:<pr>:<head>`, не найдёт его и создаст второй Watch. Два активных Watch на один алиас дают два набора обязательств и две точки доставки.

### Закрытие без проверки ревизии

`confirmMerge` передаёт в `CloseWatch` только ID. Реализация в `cmd/beacon` читает текущую запись, проверяет статус и пишет три поля. Если параллельный цикл уже закрыл Watch по смене head, поздний merge перезапишет `CloseReason` и `Verdict`. Потеря причины закрытия ломает аудит и может вернуть старый PR в выборку `MergedPR`.

### Общее CI-ождание

`SharedGate.Wait` обещает, что отмена одного участника не трогает раунд. Это верно только для присоединившихся. Лидер передаёт свой ctx прямо в `fn`, поэтому отмена лидера останавливает общую работу и все участники получают его ошибку. Счётчик `waiters` растёт только на входе, то есть `ActiveWaiters` показывает сумму когда-либо присоединившихся. PR #1217 заменил в тесте ожидание по времени счётчиком участников, но код gate не тронул.
