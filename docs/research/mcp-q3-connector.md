# Вопрос 3: почему вызовы tools.beacon поднимают процессы

Отчёт подготовлен 2026-11-21. Режим только чтение. Код, конфиги и процессы не менялись. `tools.beacon.*` не вызывались. `go test`, `go build` и `beacon gates` не запускались. Поиск шёл через `rg` с явными каталогами.

## Короткий ответ

Сам вызов `tools.beacon.*` не создаёт процесс. Code Mode берёт инструмент из зарегистрированного каталога и вызывает его через уже существующий MCP-клиент. Процесс `beacon mcp` поднимается один раз на локацию OpenCode, то есть на каталог, в котором загружен плагин `beacon-project`. Новый процесс появляется при открытии сессии в новом worktree, при переподключении после падения stdio-сервера и при `ctx.mcp.reload()` после смены корня. Дочерний `opencode serve` поднимается внутри стартующего `beacon mcp`, когда `EnsureServer` не находит живую регистрацию. Это реализация конфигурации и плагина, а не свойство протокола MCP.

## 1. Что прочитано

Плагин `.opencode/plugins/beacon-project/*.js`, оба конфига (`beacon-impl/opencode.json` и `~/.config/opencode/opencode.jsonc`), документация плагинов V2 на `opencode.ai/docs/build/plugins/server`, исходники OpenCode в `/home/nbook/opencode` на ветке `dev` от 2026-08-25, код `cmd/beacon` и `internal/infra/opencode`, логи `~/.local/share/opencode/log/opencode.log`, список процессов `ps`, а также соседние отчёты `mcp-q1-startup.md`, `mcp-q2-tools.md`, `mcp-spawn-rootcause.md` и `process-leak-mechanism.md`.

Установленный бинарник OpenCode собран 2026-11-20 из ветки V2. Локальный checkout `/home/nbook/opencode` отстаёт от него на три месяца и не содержит точного кода V2 runtime. Поэтому вывод про Code Mode опирается на документацию V2, на более старый `packages/opencode/src/tool/code-mode.ts`, на логи и на отсутствие следов переподключения в коде плагина. Прямой строки лога, которая связывает конкретный вызов `tools.beacon.*` с конкретным PID, нет. Отсутствие такой строки отмечено и в соседних отчётах.

## 2. Как зарегистрирован MCP-сервер beacon

### 2.1 Статическая запись в проектном конфиге

`beacon-impl/opencode.json:3-14` задаёт локальный stdio-сервер:

```json
"mcp": { "servers": { "beacon": {
  "type": "local",
  "command": ["/mnt/projects/beacon-handoff/beacon-impl/.opencode/bin/beacon", "mcp"],
  "cwd": "/mnt/projects/beacon-handoff/beacon-impl"
} } }
```

Глобальный `~/.config/opencode/opencode.jsonc:3-13` не содержит beacon. Там только удалённый `context7`. Итого сервер зарегистрирован дважды: статически в проектном конфиге и динамически плагином. ADR 0069 в разделе «Отклонённое» прямо требует убрать хардкод `cwd` из `opencode.json`, но файл до сих пор его содержит.

### 2.2 Динамическая регистрация плагином

`beacon-project/index.js:11-27` объявляет `Plugin.define({ id, setup(ctx) })`. В `setup` плагин берёт корень из `projectRoot(ctx)` и выходит, если корня нет. Дальше он вызывает `registerBeaconMcp` и `installProjectContext`, а на выгрузке диспозит регистрации.

`location.js:3-6` поясняет границу. `ctx.location` описывает экземпляр плагина, а не каждую сессию. Источник корня это `ctx.location.project.canonical`, который переживает запуск из worktree.

`mcp.js:6-19` собирает конфиг сервера:

```js
type: "local",
command: [".opencode/bin/beacon", "mcp"],
cwd: root,
environment: { BEACON_PROJECT_ROOT: root },
disabled: false
```

`mcp.js:25-47` применяет его через `ctx.mcp.transform`, а `setRoot` вызывает `ctx.mcp.reload()` только при фактической смене корня.

### 2.3 Жизненный цикл по документации V2

Страница `build/plugins/server` говорит следующее. `setup` выполняется при загрузке плагина. `ctx.location` это расположение экземпляра плагина. Регистрация, удаление и `reload()` помечают реестр изменённым, после чего OpenCode пересобирает домен, повторяя трансформы в порядке регистрации. Для MCP сказано прямо: OpenCode сам согласует жизненный цикл серверов с преобразованным конфигом, `disabled: true` отключает и разрывает соединение, `reload()` повторно применяет трансформы и выравнивает серверы.

Отсюда следует масштаб. Один stdio-процесс на локацию, то есть на каталог, где OpenCode загрузил плагин. Не на инструмент и не на вызов инструмента.

Логи это подтверждают. Строки `225232-225235` показывают `mcp connected server=beacon` для пяти разных `directory` в течение секунды, каждая рядом со строкой `loading plugin ... beacon-project`. Всего за день в логе 64 события `mcp connected server=beacon`, почти каждое со своим `directory`. Это worktrees `t4`, `t6`, `t7`, `z6`, `aa1`, `ab1`, `am1` и другие.

Текущий `ps` тоже показывает одну запись. PID 599570 с командой `.opencode/bin/beacon mcp` живёт около восьми минут, родитель PID 3047150 это долгоживущий `opencode.exe serve --service`. Все вызовы инструментов текущей сессии обслуживает этот один процесс.

## 3. Что на самом деле порождает новые процессы

### 3.1 Новая локация или новый worktree

Главный множитель это параллельные агенты в разных worktree. Каждая сессия в новом каталоге загружает `.opencode/plugins/beacon-project`, плагин регистрирует сервер, OpenCode запускает ещё один `beacon mcp`. Ночная смена спавнит десятки агентов, значит получается десятки процессов. Это совпадает с наблюдением владельца про 22 процесса `beacon mcp` за два часа, но объяснение не в частоте вызовов, а в числе локаций.

### 3.2 Переподключение после смерти stdio-сервера

В логе 34 события `mcp transport error ... server=beacon`. Строки `3664-3673` показывают массовый выход процессов для десятка worktree в одну секунду. Строки `232021` и `232031` показывают два `mcp connected` для одного каталога `worktrees/am1` с интервалом две секунды и разные `connectionID`. Это уже реконнект.

Есть и конкретные ошибки старта. В 14:33 один процесс упал с `beacon mcp: store: migrate: ... table obligations already exists`, другой с `mcp: poller: open /tmp/TestMCPReconnectsAfterAddressChange.../beacon-poller.lock: no such file or directory`. Второй путь указывает на state directory из тестового tmp, то есть два процесса делят одно состояние. Плагин передаёт серверу только `BEACON_PROJECT_ROOT`, но не `BEACON_MCP_REMOTE`. По `mcp.go:464-484` и `1165-1178` это означает локальный режим со своим DB и poller lock на каждый процесс. Конкуренция за один state dir даёт падения и последующие реконнекты.

### 3.3 Дочерний opencode serve

Цепочка старта описана в `mcp-q1-startup.md:53-59` и подтверждена кодом. Каждый процесс `beacon mcp` выполняет `main.go:116-124`, где `wireOpenCodePorts()` вызывает `newOpencodePort()`. Тот в `opencode.go:118-129` читает конфиг и ставит ensurer в `opencode.EnsureServer`. Позже `reconcileWaker` в `mcp.go:1547-1555` через `opencodeWakePorts` в `mcp.go:1516-1542` снова вызывает `newOpencodePort()`. Теперь ensurer уже установлен, поэтому `resolveOpencodeConfig` идёт в `EnsureServer`.

`internal/infra/opencode/server.go:390-429` сначала переиспользует собственную запись с живым PID, затем `service.json`, и только если оба источника недоступны, вызывает `startServer`. Тот в `server.go:103-128` собирает `exec.Command("opencode", "serve", "--hostname", ..., "--port", <random>)`. Так `opencode serve` становится ребёнком `beacon mcp`, а не ребёнком Code Mode.

В текущем коммите 2a3362f1 исправление PR 887 уже применено. У дочернего процесса стоит `Pdeathsig: syscall.SIGTERM`, PID и пароль пишутся в `opencode-serve.json` с режимом 0600, `EnsureServer` проверяет живой PID перед повторным использованием, команда `gc` подключена в `main.go:274`. Сироты должны умирать вместе с родителем, но churn при каждом новом `beacon mcp` остаётся, если живой регистрации нет.

### 3.4 Обновление конфига MCP

`mcp.js:44` вызывает `ctx.mcp.reload()` при смене корня проекта. По документации это пересобирает домен и выравнивает жизненный цикл серверов. Это ещё один источник нового процесса, но он срабатывает редко, только при смене `root`.

### 3.5 Что не порождает процесс

В коде, который удалось прочитать, вызов инструмента не создаёт соединение. В `packages/opencode/src/tool/code-mode.ts:210-230` каталог берётся из `mcp.tools()` и `mcp.clients()`, а вызов идёт через `entry.tool.client.callTool(...)`. Клиент берётся из кэша инстанса. В документации V2 (`packages/codemode/codemode.md:86-114`) сказано, что каждый запрос модели захватывает стабильный снимок инструментов, а вложенные вызовы внутри одного `execute` используют один контекст. Ни в `mcp.js`, ни в `index.js` нет хука на `tool.execute`, который трогал бы MCP.

Отдельно стоит заметить, что обработчики инструментов Beacon тоже не открывают opencode port. Это показано в `mcp-q2-tools.md:9` и `171`. Порт открывает стартовая фоновая логика процесса, а не `tools/call`.

## 4. Прямые ответы на вопрос 2 и вопрос 4

### Про «каждый вызов tools.beacon поднимает процесс»

Такого правила в коде нет. Вызов внутри уже открытой сессии использует существующий stdio-клиент. Процесс появляется, когда OpenCode открывает новую локацию, переподключает упавший сервер или применяет изменённый конфиг. Если владелец видел примерно двадцать вызовов и двадцать процессов, наиболее простое объяснение это двадцать сессий в двадцати worktree, а не двадцать переподключений внутри одной сессии.

С оговоркой. Точный код установленного бинарника V2 недоступен локально, поэтому утверждение про отсутствие per-call reconnect это вывод из документации, логов и более старого исходника, а не прочитанная строка V2 runtime.

### Про вину протокола MCP

МCP не виноват. Протокол stdio действительно означает один процесс на соединение, но одно соединение обслуживает много вызовов инструментов. Размножение идёт от конкретных решений в этом проекте.

Список решений по порядку вклада.

1. Плагин регистрирует локальный stdio-сервер в каждой локации через `ctx.mcp.transform` в `mcp.js:25-37`. Один worktree равен одному процессу.
2. Проектный `opencode.json` оставляет вторую запись того же сервера с абсолютным путём и фиксированным `cwd`.
3. `beacon mcp` при старте вызывает `EnsureServer`, который поднимает `opencode serve` на случайном порту, если нет живой регистрации.
4. Несколько процессов делят один state directory, что даёт ошибки миграции и poller lock, а за ними реконнекты.
5. Оркестратор создаёт много worktree, и каждый из них тянет за собой отдельный экземпляр плагина.

Ни один из этих пунктов не является требованием MCP. Code Mode здесь только каталог и способ вызова инструментов. Управлением процессами занимается OpenCode и код Beacon.

## 5. Можно ли держать один beacon mcp на всю сессию

Внутри одной сессии это уже так. Все вызовы `tools.beacon.*` идут в один процесс, если соединение не упало.

Если цель это один процесс на все сессии и все worktree, конфигом это не решить. MCP-серверы в V2 привязаны к локации. Нужно заменить локальный stdio-сервер одним удалённым. В коде Beacon для этого уже есть путь. `mcp.go:464-484` и `1165-1178` включают тонкий режим `BEACON_MCP_REMOTE`, при котором stdio-процесс не держит DB, а `internal/infra/mcp/client.go:1-2` и `104-168` пересылают каждый `tools/call` по HTTP на сервер Beacon. Адрес берётся из `connection.json`.

Где именно менять.

- `.opencode/plugins/beacon-project/mcp.js:9-20`, функция `beaconServerConfig`. Вместо `type: "local"` с `command`, `cwd` и `environment` нужно вернуть `type: "remote"` с одним фиксированным `url`. Переменную `BEACON_PROJECT_ROOT_ENV` тогда можно убрать или оставить для диагностики.
- `.opencode/plugins/beacon-project/mcp.js:25-47`, `registerBeaconMcp`. Трансформ останется, но ему не нужен `cwd` и `setRoot` с `reload()` при смене корня. Адрес сервера будет общим для всех локаций.
- `beacon-impl/opencode.json:3-14`. Удалить статическую запись `mcp.servers.beacon`, как требует ADR 0069. Иначе останется второй источник локального stdio-сервера.
- `~/.config/opencode/opencode.jsonc` менять не нужно. Запись beacon в глобальный конфиг включит сервер для всех проектов.
- Сервер Beacon должен быть запущен заранее и публиковать `connection.json`. Без него удалённый режим не стартует.

Если замена на remote пока не планируется, самые простые меры такие. Убрать дубль из `opencode.json`. Не вызывать `ctx.mcp.reload()` без смены корня. Дать разным проектам разные state directories, чтобы processes не бились за один poller lock. Оставить `beacon gc --apply` в cron для остатков от старых версий.

## 6. Что осталось непроверенным

Точный код V2 runtime в установленном бинарнике прочитать не удалось. Локальный checkout OpenCode на три месяца старше сборки. Поэтому утверждение «Code Mode не переподключается на каждый вызов» опирается на документацию, на более старый исходник и на логи, а не на прямую трассировку из бинарника.

Прямой строки лога, которая связывает `tools.beacon.*` с PID нового процесса, нет. Есть строки, которые связывают загрузку плагина с `mcp connected` и падение stdio-сервера с реконнектом. Этих событий достаточно, чтобы объяснить число процессов, но не достаточно, чтобы доказать отсутствие редкого per-call reconnect в V2.

Список живых процессов и PID взят в момент проверки и не является измерением за весь период инцидента.
