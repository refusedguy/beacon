# Закрытие карточек без PR: разбор вариантов

Дата: 2026-11-21. Режим: чтение. Код, тесты, сборки, гейты и инструменты Beacon не запускались. Поиск шёл через `rg` с явными каталогами `internal/`, `cmd/`, `docs/`. Попытка внешнего поиска вернула HTTP 402, поэтому внешних источников здесь нет. Все выводы опираются на файлы репозитория с указанием строк.

## Что уже есть в коде

Карточка живёт в `docs/tasks/*.md`. Поля аренды это `Статус`, `Агент`, `Время`. `beacon_task_claim` берёт flock, выбирает карточку со статусом `todo`, пишет `in_progress` через atomic rename и возвращает контекст (`internal/infra/mcp/tool_task_claim.go:150`, `:221`, `:241`, `:380`). Отдельного MCP-инструмента close или release нет.

Путь автоматического закрытия существует. `EvaluatePR` возвращает `VerdictMerged` для состояния PR `MERGED` (`internal/domain/verdict.go:186-193`). Дальше идёт цепочка `applyVerdict` → `applyMerged` → `closeWatch` → `closeLinkedCard` → `CardLinks.CloseMerged` (`internal/infra/cibridge/verdict_applier.go:111`, `:342`, `:385`, `:437`). Порт вызывается только для `merged`, поэтому hold или blocked карточку не трогают.

В продакшене порт `CardLinks` привязан к адаптеру `deferredCardLinks` в `cmd/beacon/mcp.go:47-74`, `:1749`. Адаптер ищет строку в отложенных проводках по `WatchID` и закрывает wiring-карточку `WIRING-<pr>`. Обычные карточки, взятые через `beacon_task_claim`, в этой цепочке не участвуют: вызовов `db.Link` вне тестов в репозитории нет, они есть только в `internal/infra/store/card_links_test.go` и `internal/infra/cibridge/bridge_test.go:1541`. Значит merge PR сам по себе не переводит обычную карточку в `done`, если для неё нет строки в `card_links` или отложенной проводки.

Есть готовый CLI-путь без новых инструментов. `beacon task done <id> --summary ... --evidence ...` ставит `Статус: done` под flock и atomic write, а без `--evidence` переводит карточку в `needs_input` (`cmd/beacon/task.go:430-487`). `beacon task needs-input <id> --question ...` пишет `Состояние: needs_input` и `Вопрос`, оставляя статус `in_progress` (`cmd/beacon/task.go:493-550`). Регулярка `IsID` это `^[A-Za-z][A-Za-z0-9_-]*[.-][0-9]+$` (`internal/infra/taskstore/store.go:92`, `:349`), поэтому ID вида `ARDH-08` и `CLEAN-15` принимаются. Третьего пути сменить статус через CLI нет, `dropped` командой не ставится.

Контракт инструментов зафиксирован побайтно. Девять имён перечислены в `AGENTS.md` и `ADR 0268`. Золотые константы это 18212 байт и SHA-256 `ba0a9f42031cab8ff4733f89a8f6b3d1424be695367cbb6f305a3a0b60865f99` (`internal/infra/mcp/contract_test.go:31`, `:36`). Бюджет ответа 20 KiB, поднят с 16 KiB в ADR 0268. Десятое имя ломает список имён, размер и хэш одновременно. Обновление требует отдельного ADR и правки золотых констант в том же PR, как это сделано для девятого инструмента (`docs/adrs/0268-task-claim-tool.md:23-31`).

`beacon_watch_pr` не умеет работать с карточкой. В `WatchPRInput` нет поля `cardID` (`internal/infra/mcp/tool_watch_pr.go:192-206`). Для ролей executor и fixer инструмент требует ID сессии с префиксом `ses_` и явно отклоняет ID карточки как цель (`tool_watch_pr.go:410-415`). `AGENTS.md` запрещает `notify.target: "<cardID>"` по той же причине.

## Варианты

### Вариант 1. `beacon_task_close(cardID, status, reason)`

Десятый MCP-инструмент с перечислением `done | dropped | duplicate`. Handler проверяет существование карточки, пишет статус и причину под тем же flock, что и claim, и возвращает предыдущий и новый статус. Идемпотентность идёт по ключу `(cardID, status, reason)`: повтор возвращает `created=false` и не меняет файл. Вызывает агент или оркестратор, решение владельца о праве вызова нужно зафиксировать в ADR.

В коде появятся `tool_task_close.go`, порт store, описание и схема вывода в `server.go`, запись в `toolDescriptors`, тесты контракта. Риск для golden `tools/list` высокий: ломаются имя, размер и SHA, нужен отдельный ADR по образцу ADR 0268. Плюс конфликт правил: `AGENTS.md` прямо запрещает закрывать карточку вручную и поручает это Beacon по `merged`. Инструмент легализует ручное закрытие, поэтому его надо выдавать только оркестратору или владельцу, не исполнителю.

### Вариант 2. `beacon_task_release(cardID, agentID)`

Аналог release lease для самой карточки. Снимает `in_progress`, возвращает `todo`, очищает `Агент` и `Время`. Идемпотентность условная: повтор от чужого агента или со старым `claimedAt` отклоняется, как `StaleClaimError` в `internal/app/orchestrator/claim.go:54-70`. Вызывает оркестратор после того, как подтвердил смерть сессии или отказ исполнителя.

API-изменения и риск для golden такие же, как в варианте 1: десятый инструмент, новый ADR, новые константы. Отдельный риск это потеря работы. Возврат в `todo` позволяет другому агенту взять карточку и начать с нуля, а правила перезапуска в `AGENTS.md` запрещают терять работу в worktree. Вариант годится только для карточек без живого worktree и ветки.

### Вариант 3. Переиспользование `beacon_defer_wiring`

Агент вызывает существующий инструмент с причиной блокера и получает карточку `WIRING-<pr>` со статусом `deferred`. Дальше PR по этой карточке при MERGED закрывается через `deferredCardLinks`. Ни один контракт не меняется, риск для golden нулевой, идемпотентность уже есть по `(watchID, reason)` (`internal/infra/mcp/tool_defer_wiring.go:91-134`).

Минус семантический. Инструмент требует положительный `pr` (`:101`), создаёт новую карточку и закрывает её, а не застрявшую. Для «уже влито» или «нужно решение владельца» это подмена предмета. Сгодится только для случая «фикс висит в чужом PR», где новая wiring-карточка действительно описывает отложенную проводку.

### Вариант 4. Watch без PR, только issue

Регистрировать Watch по issue или другой стабильной метке и получать терминальный вердикт извне. Механика Watch и обязательств уже есть, `RegisterSelfWatch` принимает `cardID` как подписчика (`internal/infra/cibridge/read_api.go:21-57`). Но публичный `beacon_watch_pr` требует `pr > 0` (`tool_watch_pr.go:389`), а смена входной схемы или описания инструмента попадёт в побайтный контракт и потребует ADR. Риск средний или высокий. Идемпотентность по ключу Watch сохраняется, но нужен новый ключ для issue-only Watch и новый источник вердикта. Вызывает оркестратор или daemon. Вариант самый дорогой и решает не ту проблему: блокер это не состояние CI, а отсутствие решения.

### Вариант 5. Отдельный docs-only PR с пометкой

Для каждой застрявшей карточки открыть PR, который меняет только её текст, с пометкой в заголовке. После merge сработает штатная цепочка MERGED → done, если карточка связана с Watch. Контракт инструментов не меняется, идемпотентность обеспечивается headSHA Watch по ADR 0019. Вызывает агент через обычный flow.

Риск средний по процессу. Нужны 15 PR, зелёный CI и корректная связка карточки с Watch. В текущем продакшене связки для обычных карточек нет, как показано выше, поэтому merge docs-only PR не гарантирует перевод в `done`. Вариант добавляет шум в историю PR и не годится для owner-decision карточек, пока владелец не ответил.

### Вариант 6. Daemon по TTL `claimedAt`

Фоновая проверка раз в N минут ищет карточки в `in_progress`, у которых `Время` старше порога, и переводит их в `needs_input` или `todo`. Готовые детали есть: поле `Время` пишется при claim, `beacon task lease` уже умеет освобождать файловые аренды (`cmd/beacon/task.go:684-702`), а снятие устаревшей аренды по generation есть в orchestrator. Контракт MCP не трогается, риск для golden нулевой. Идемпотентность надо строить по `(cardID, claimedAt)`, иначе повторный проход затрёт свежий ответ владельца. Вызывает daemon.

Главный риск это ложное срабатывание. Долгая работа, живой worktree и активный Watch не должны считаться застрявшими. Перед записью нужна проверка, что у карточки нет живого PR и свежей активности. Вариант решает симптом, а не причину, поэтому идёт после варианта с исправлением связи карточки и Watch.

### Вариант 7. Ручная правка markdown оркестратором

Оркестратор сам меняет `Статус: done` в файле карточки. Нулевой риск для контракта и полная свобода в выборе статуса, включая `dropped`. Идемпотентности нет, каждый вызов перезаписывает файл. Плюс прямое нарушение `AGENTS.md`: «Закрывать карточку вручную» запрещено, индекс пересобирается только командой `beacon index build`, а прекоммит блокирует устаревший индекс. Вариант против правил и не рекомендуется.

### Вариант 8. Существующий CLI `beacon task done` и `beacon task needs-input`

Не новый инструмент, а уже реализованный путь. `done` требует `--summary` и `--evidence`, пишет поля `Итог`, `Доказательство`, очищает `Состояние` и `Вопрос` (`cmd/beacon/task.go:478-485`). `needs-input` требует `--question` и сохраняет статус `in_progress` (`:531-536`). Оба берут flock и пишут через atomic write. Контракт MCP не меняется вообще. Идемпотентность обеспечивается блокировкой и проверкой `taskActive`: повторный `done` на уже закрытой карточке получает отказ без записи (`:465-467`). Вызывает оркестратор или владелец, но не исполнитель своей карточки.

Единственный минус это отсутствие CLI для `dropped` и `duplicate`. Для таких случаев нужно решение владельца и либо расширение CLI, либо вариант 1.

## Оценка `beacon_watch_pr` на уже влитом PR

Конкретный случай это ARDH-08 и PR #1160. Карточка подтверждает merge 2026-11-21T13:15:13Z, но её статус до сих пор `in_progress` (`docs/tasks/ARDH-08.md:2`, `:20`).

Что произойдёт при вызове `beacon_watch_pr` на #1160. PR в состоянии MERGED даёт `VerdictMerged` без wake (`internal/domain/verdict.go:188-193`). Watch закроется с `closeReason=merged`, подписчики станут finished, оркестратор получит `terminal_ack` (`verdict_applier.go:342-383`, `:468-476`). Дальше сработает `closeLinkedCard`, но только если найдётся связанная карточка.

Сама карточка ARDH-08 не закроется по трём причинам. Первое: `beacon_watch_pr` не принимает `cardID` и не создаёт строку в `card_links`. Второе: ID карточки запрещено передавать в `notify.target` как подписчика, для executor и fixer нужен `ses_...`. Третье: в продакшене `db.Link` для обычных карточек не вызывается, а `deferredCardLinks` ищет только отложенные проводки по `WatchID`.

Итог: вызов закроет Watch и даст оркестратору терминальный сигнал, но не переведёт ARDH-08 в `done`. Дополнительно нужен либо вызов `beacon task done` с доказательством в виде ссылки на #1160, либо исправление связки карточки с Watch. Ещё один нюанс это `headSHA`. Для влитого PR head commit обычно доступен провайдером, и `resolveHead` сможет его получить, но при ошибке разрешения регистрация не состоится (`tool_watch_pr.go:418-421`).

## Рекомендация

Приоритет по порядку.

1. Сейчас, без кода. Оркестратор обрабатывает 15 карточек через существующий CLI. Для «уже влито» и «фикс в чужом PR» использовать `beacon task done` с реальным доказательством из текста карточки. Для «нужно решение владельца» использовать `beacon task needs-input` с конкретным вопросом. Для `dropped` и `duplicate` пока ничего не делать, пока владелец не зафиксирует решение. Не править markdown руками и не ставить десятый инструмент без ADR.

2. Следующий шаг. Один скрипт или runbook, который собирает все `in_progress` карточки старше порога, группирует их по типу блокера и печатает готовые команды. Это левер на 15 повторов, а не 15 ручных правок. Источник данных это `beacon board` и текст карточек, CI сверяет индекс.

3. Корень проблемы. Привязывать карточку к Watch при claim или регистрации, чтобы MERGED действительно закрывал обычную карточку. Сейчас порт `CardLinks` работает только для deferred wiring. Без этого исправления любое будущее «просто посмотреть PR» останется неполным.

4. Расширение CLI. Добавить `beacon task close <id> --status dropped|duplicate --reason ...` в `cmd/beacon/task.go`. Это не меняет `tools/list`, поэтому ADR не нужен. Права оставить оркестратору.

5. Десятый MCP-инструмент только если агенты реально должны закрывать карточки сами. Для этого нужен отдельный ADR, обновление `toolsListByteCount`, `toolsListGoldenSHA256`, списка имён и бюджета в том же PR. По текущему правилу `AGENTS.md` закрытие карточки это решение не исполнителя, поэтому потребность в десятом инструменте не доказана.

6. TTL-reaper и docs-only PR оставить как запасные варианты. Reaper годится после проверки живых Watch и worktree. Docs-only PR добавляет 15 merge ради смены статуса и не исправляет отсутствующую связь.

Примеры команд для первой группы:

`beacon task done ARDH-08 --summary "Общий список полей недостижим между модулями" --evidence "PR #1160 merged 2026-11-21T13:15:13Z, mutual references in store.go:99-103 and docs.go:52-59"`

`beacon task needs-input CLEAN-12 --question "Нужно решение владельца: разрешить отдельный TUI-процесс с ребром cmd к internal/tui и передать cmd/beacon/mcp.go, либо явно отменить проводку WIRING-493"`

Команды должен выполнять оркестратор или владелец с проверкой доказательства, а не агент, который вернул блокер.

## Пять главных выводов

1. Цепочка MERGED → done в коде есть, но в продакшене она закрывает только deferred wiring карточки. Обычная карточка из `beacon_task_claim` не имеет строки в `card_links`, поэтому merge PR не меняет её статус.

2. `beacon_watch_pr` на уже влитом PR закроет Watch и пошлёт `terminal_ack`, но не закроет ARDH-08. Инструмент не принимает `cardID`, запрещает ID карточки в `notify.target` и не создаёт связь с карточкой.

3. Десятый MCP-инструмент ломает побайтный golden `tools/list` на 18212 байт и SHA `ba0a9f...`. По ADR 0268 это отдельный ADR с обновлением золотых констант в том же PR.

4. Готовый путь без новых инструментов уже есть. `beacon task done --summary --evidence` и `beacon task needs-input --question` работают под flock, принимают ID вида ARDH-08 и CLEAN-15 и подходят для 15 застрявших карточек прямо сейчас.

5. Закрытие это действие оркестратора с доказательством, а не исполнителя. Сначала CLI и runbook на 15 карточек, потом исправление связи карточки и Watch, и только потом десятый инструмент или TTL-reaper.
