# Аудит 04. Выбор протокола для управления Beacon

## Граница и отправная точка

Отчёт выбирает канал для каждой возможности Beacon. Он не исправляет расхождение списков инструментов. Карточки AUD-09 и AUD-10 уже ведут эту работу. Здесь они нужны только как источник фактов, и ни один из их OwnerFiles не попадает в новые карточки.

Запрет на дублирование соблюдён. Отчёт не переделывает `newReadOnlyOpencodePort`, `FileTaskClaimStore`, `FileTaskCloseStore`, `card_links`, поддержку ATX-R01 и `FootprintCheck` в `internal/infra/wake/acp.go`.

Базовые замеры взяты из репозитория. Новый замер не снимался, потому что правила агента запрещают локальный `go build`, `go test` и `beacon gates`. Там, где числа нет, эффект помечен как ожидаемый, а не как измеренный.

## а) Что остаётся в MCP, что уходит в CLI и что заменяет push

Разделение идёт по частоте вызова и по цене ошибки. Инструменты, которые меняют состояние цикла внутри хода агента, остаются в MCP. Диагностика уходит в CLI. Ожидание результата заменяется доставкой указателя.

| Инструмент | Канал | Причина |
| --- | --- | --- |
| `beacon_watch_pr` | MCP | Регистрация Watch и подписка идут в одном вызове, `server.go:143-144`. Ошибка неверного watchID ломает весь цикл, нужен типизированный ответ |
| `beacon_ack` | MCP | Идемпотентная запись `claimedAt` и решения `blocked:not_mine`, `server.go:183-187`. Типизированный `decision` подбирается моделью из описания |
| `beacon_cancel_watch` | MCP | Единственный деструктивный инструмент, `server.go:197-201`. Требует явного намерения и точного имени |
| `beacon_task_claim` | MCP | Атомарная выдача карточки, `server.go:224-229`. Гонка двух агентов недопустима |
| `beacon_task_close` | MCP | Закрытие с проверкой владельца, `server.go:233-238`. Идемпотентность по тройке полей описана в `server.go:234-235` |
| `beacon_defer_wiring` | MCP | Возвращает готовый markdown карточки и идемпотентен по `(watchID, reason)`, `server.go:215-220`. Вызывается в точке хода, описанной в `AGENTS.md:109` |
| `beacon_get_result` | MCP | Малый read после пробуждения. Читает вердикт и ставит `readAt`, `server.go:163-164` |
| `beacon_wait_result` | Push вместо long-poll | Держит лизинг 30 минут, `server.go:154-155`. Beacon уже доставляет `watchID`, `obligationID`, `revision` и текст инструкции, `GLOSSARY.md:105-106`. Цикл прямо велит спать, а не опрашивать, `server.go:96` |
| `beacon_list_running` | CLI и SKILL | Диагностика по требованию. В CLI уже есть `beacon inspect`, `beacon watch`, `beacon board`, `cmd/beacon/catalog.go:35,44,51` |
| `beacon_stats` | CLI и SKILL | То же. Дополнительно несёт `graphReady` в строке, `tool_stats.go:461`, что тяжело читать модели |
| `beacon_wake` | Не в каталоге агента | Это канал адаптера, а не инструмент агента. Агент получает wake как вставку в сессию через `session/prompt`, `acp.go:807-813` |

Два пассивных read-инструмента занимают место в каждом `tools/list`. Исторические замеры показывают рост контракта с 17922 до 18212 байт при добавлении одного инструмента, `docs/adrs/0268-task-claim-tool.md:25` и `docs/adrs/0270-task-close-tool.md:9`. Точная экономия от удаления двух описаний требует замера в CI и здесь не заявлена.

`beacon_wait_result` заменяется не удалением чтения, а сменой инициативы. Сервер публикует указатель через Ladder, `GLOSSARY.md:47-49`. Агент просыпается и вызывает `beacon_get_result`. Долгоживущий вызов остаётся только как совместимый режим для клиентов без push-канала.

## б) Zed ACP и AG-UI-like SSE

### ACP уже занял свою нишу

ACP стандартизует связь редактора с агентом по JSON-RPC поверх stdio. Это подтверждает спецификация проекта, https://agentclientprotocol.com/overview/introduction. Beacon реализовал клиентскую сторону полностью.

Список опорных точек:

- `acpRuntimes` в `internal/infra/wake/acp.go:425-430` содержит `opencode acp`, `claude --acp`, `codex acp` и `pi --acp`;
- `ResolveACPRuntimeCommand` в `:451-472` разрешает заменить команду и аргументы, поэтому альтернативные бинарники вроде `claude-agent-acp` или `codex-acp` подключаются без нового протокола;
- `Initialize` в `:713-732` согласует `protocolVersion` и capabilities;
- `DeliverWake` в `:756-776` выбирает `session/load` или `session/new` по capabilities и шлёт `session/prompt`;
- `ACPServer` в `:846-968` закрывает входящую сторону для хоста;
- `mcpServers` в `session/new` и `session/load`, `:780-782` и `:800-802`, уже является мостом к MCP.

Вывод: ACP подходит для доставки wake и не подходит для вызова инструментов Beacon. Это разные направления. ACP связывает хост с агентом. MCP связывает агента с сервисом. Попытка превратить `session/prompt` в вызов инструмента смешает два контракта и уничтожит типизированные схемы. Старый `ACPStdioTransport` в `:118-177` запускает процесс на каждый вызов и сохранён только для старых тестов. Постоянный `PersistentACPClient` в `:496-844` является рабочим путём.

### AG-UI стоит использовать как источник идей, а не как протокол целиком

Спецификация AG-UI определяет типизированные SSE-события с общими полями `type`, `timestamp`, `rawEvent` и `metadata`. Категории событий включают жизненный цикл `RunStarted`, `RunFinished`, `RunError`, поток текста `TextMessageStart`, `TextMessageContent`, `TextMessageEnd`, вызовы инструментов и пару `StateSnapshot`, `StateDelta` на base JSON Patch RFC 6902. Источник: https://docs.ag-ui.com/concepts/events.

В Beacon SSE уже есть транспорт. `Event` в `internal/infra/httpapi/server.go:298-304` несёт `ID`, `Type string`, `At`, `WatchID` и `Payload json.RawMessage`. `handleEvents` в `:899-939` держит соединение и heartbeat. `writeSSE` в `:962-970` кодирует кадр. Реплей по `Last-Event-ID` и параметру `replay` живёт в `:942-960`.

Полный AG-UI потребует отображения `Watch` в `Run`, обязательства в сообщение, вердикта в `RunFinished`. Это дублирует store и Ladder. Достаточно заимствовать два приёма.

Первый приём: дискриминированное имя события. Публиковать имена, выведенные из домена Watch, и проверять их на границе. Неизвестное имя отклонять.

Второй приём: пара `StateSnapshot` и `StateDelta`. Отдавать полный snapshot редко, а между ним слать патчи изменений вердикта и обязательства. Клиент перестаёт перечитывать весь `Snapshot` из `:855-897` после каждого кадра.

Контракт `beacon.human-decide.v1` в `:60-63` показывает, что репозиторий уже умеет версионировать wire-форму. Новый SSE-контракт должен пойти тем же путём, а не ломать существующих подписчиков.

## в) Что не стоит тащить в Go-ядро

### A2A для локального запуска

A2A решает задачу поиска и вызова удалённых агентов разных вендоров через HTTP и AgentCard. У Beacon другие условия. Все акторы живут на одной машине, состояние лежит в SQLite, а доступ к control plane идёт через loopback и bearer-токен, `internal/infra/httpapi/server.go:29-35,725-734`. Watch, Obligation, Verdict и Ladder уже моделируют жизненный цикл и доставку, `GLOSSARY.md:27-49`. A2A добавит второй язык описания задач и вторую модель авторизации. Если удалённая оркестрация когда-нибудь понадобится, адаптер живёт на границе в `cmd` или отдельном infra-пакете. Домен и ядро остаются чистыми.

### Тяжёлый Code Mode внутри Go

Code Mode это приём экономии контекста на стороне модели. Поиск `search({ query: "beacon", namespace: "beacon" })` и вызов `tools.beacon.<name>` описаны в `AGENTS.md:105-107`. Сервер уже отдаёт типизированные инструменты через `toolDescriptor` в `internal/infra/mcp/server.go:129-139`. Встраивание в Go песочницы JavaScript, динамического реестра инструментов или RPC-роутера повторит работу среды агента. Оно также добавит зависимость, которая замыкает цикл, что запрещено в `AGENTS.md:13`. Code Mode остаётся в среде агента. Go остаётся детерминированным ядром с фиксированным контрактом.

### UTCP вместо аутентифицированного шлюза

UTCP это руководство, которое говорит агенту вызывать нативные API напрямую, с нативной аутентификацией. Источник: https://utcp.io/. У Beacon уже есть то, что UTCP заменяет: один loopback-сервер, токен в `connection.json` с режимом 0600, `internal/infra/httpapi/server.go:648-678`, сравнение в константное время в `:725-734`, и один JSON-RPC формат для вызовов, `internal/infra/mcp/client.go:164-230`.

Добавление `/utcp` и CLI call templates создаст второй каталог инструментов и вторую историю авторизации. Текущий дрейф 7/9/10/11 показывает, что один каталог уже расходится. Два каталога разойдутся гарантированно. UTCP не заменяет шлюз Beacon, он его удваивает. Решение: не вносить.

## Связь с существующими карточками

AUD-09 закрывает неполную remote-карту в `internal/infra/mcp/client.go`. AUD-10 обновляет `CycleInstructions` и документацию. Оба остаются владельцами своих файлов и здесь не повторяются.

PROTO-04 фиксирует разделение каналов в шаблонах. PROTO-07 поднимает `graphReady` до типизированного поля. PROTO-08 убирает `registryListSource` из зоны MCP. PROTO-06 фиксирует отказ от A2A, UTCP и тяжёлого Code Mode как dropped.
