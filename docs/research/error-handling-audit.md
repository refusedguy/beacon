# Аудит обработки ошибок, ROP-паттернов и boilerplate

Дата: 2026-11-21. Репозиторий: `beacon-impl`, коммит `d3b1bfb`.

## Как снимался замер

Поиск шёл через `rg` с явными каталогами `internal` и `cmd`, без `grep -r` по корню. Тестовые файлы `*_test.go` исключены. Команды `go test`, `go build` и `beacon gates` не запускались. Ниже все числа получены из исходников, а не из запуска кода.

Масштаб: 177 нетестовых Go-файлов. Проверок `if err != nil` найдено 1290 в 144 файлах. По слоям: `internal/domain` 5, `internal/app` 158, `internal/infra` 803, `internal/tui` 20, `cmd` 304. Вызовов `fmt.Errorf` 984, из них 318 без `%w`. Плоских `_ =` присваиваний 129, из них большая часть это `defer func() { _ = close() }()`. Вызовов `errors.As`/`errors.Is` 150, `errors.Join` 8.

ADR 0009 задаёт курс явно: `(value, error)` плюс `AppError` с кодом и статусом, преобразование в единый shape на границе MCP, тип `Result[T]` не добавлять (`docs/adrs/0009-error-handling.md:7-13`). Фактический код этому следует. Обобщённого `Result[T]` или `Either[T]` в исходниках нет. Единственное упоминание `Result[T]` это комментарий `internal/domain/types.go:511`.

## Находки

### 1. Плотные цепочки проверок в инфраструктуре, 1290 `if err != nil`

Примеры (файл:строка)::

- `internal/infra/store/receipts.go:780-850`, `EnqueueFenced`, 10 проверок в одной функции.
- `internal/app/orchestrator/rebase.go`, `rebaseWatch`, 10 проверок.
- `internal/infra/registry/validate.go:59-121`, `Validate`, 9 проверок.
- `cmd/beacon/inspect.go`, `runInspect`, 9 проверок.

Оценка. Это идиоматичный Go. Каждая проверка возвращает ошибку с контекстом через `%w`, цепочка короткая и читается сверху вниз. Большинство проверок в `infra` это операции с SQL и файлами, где ошибка реально возможна на каждом шаге. ROP-тип здесь убрал бы строки `if err != nil`, но добавил бы обёртки над каждым вызовом `tx.Exec` и `QueryRow`. Читаемость не выросла бы.

Рекомендация. Оставить как есть. Если хочется уменьшить повторение, уменьшать надо не через Result, а через локальные helper'ы внутри пакета `store` для повторяющихся пар `create table + insert`. Это правка на уровне одного пакета, а не новый тип ошибок.

### 2. 39 мест теряют причину ошибки через `%v` вместо `%w`

Список по файлам: `cmd/beacon/agents.go` 16, `internal/infra/opencode/client.go` 10, `internal/infra/wake/telegram.go` 4, `cmd/beacon/attach.go` 4, `internal/infra/wake/acp.go` 2, по одному в `internal/app/orchestrator/daemon.go`, `internal/app/event/bus.go`, `cmd/beacon/observe.go`.

Примеры:

- `cmd/beacon/agents.go:76` и `:80`, чтение и разбор снимка мёртвых аренд через `%v`.
- `internal/infra/opencode/client.go:70`, `:74`, чтение `service.json` и разбор JSON через `%v`.
- `cmd/beacon/attach.go:113`, `:117`, `:130`, `:134`, та же проблема.

Оценка. После `%v` цепочка `errors.Is`/`errors.As` обрывается. В `agents.go:71` перед этим уже стоит `errors.Is(err, os.ErrNotExist)`, то есть автору важен тип ошибки, но следующий вызов его теряет. В `telegram.go:170-188` причина другая: `s.sanitize(err.Error())` намеренно вырезает токен из текста. Здесь потеря цепочки это плата за безопасность, и её надо сохранить.

Рекомендация. В 35 местах, где текст ошибки не очищается, заменить `%v` на `%w`, оставив текст ошибки прежним. В четырёх местах `telegram.go` добавить собственный sentinel `ErrTelegramTransport` и оборачивать его через `%w`, а очищенный текст держать в сообщении. Тогда вызывающий сможет отличить транспортную ошибку, не получив токен.

### 3. `AppError` не хранит причину, а `fanout` превращает ошибку store в текст

Определение: `internal/domain/types.go:512-552`. У `AppError` есть поля кода, сообщения, статуса и два опциональных поля. Метода `Unwrap` нет, поля для cause нет. Потеря примера:

- `internal/domain/fanout.go:94` и `:98`: `NewAppError(CodePersistFailed, err.Error())`. Исходная ошибка store превращается в строку.
- `internal/domain/identity.go:171`, `:178`: `%w: bad payload encoding: %v`, то есть sentinel сохраняется, а причина кодирования нет.

Оценка. Для контракта MCP из шести полей это осознанный компромисс: `AppError` это базовая форма ответа, а не контейнер для диагностики. Но внутри процесса такой компромисс мешает различать `sql.ErrNoRows` и ошибку диска, когда обе приходят как `PERSIST_FAILED`.

Рекомендация. Добавить в `AppError` неэкспортируемое поле `cause error` и метод `Unwrap`, не меняя JSON-представление. Вызовы `NewAppError` останутся совместимыми, а `fanout.go` сможет передать исходную ошибку через новый конструктор. Если владелец считает, что контрактный тип должен остаться плоским, зафиксировать это в ADR 0009 как явное решение.

### 4. Две реализации форма ошибки на HTTP-границе плюс неиспользуемый конвертер MCP

- `internal/infra/server/http/error.go:14-90`: тип `Code`, struct `Error`, `CodeOf`, `WriteError`. Централизованная точка.
- `internal/infra/httpapi/server.go:725-730`: свой `errorBody{Code string, Message string}` и своя функция `writeError`, 12 вызовов в файле. Типы не общие, коды строковые.
- `internal/infra/mcp/schema.go:393-412`: `ToErrorShape` converting `AppError` в форму из шести полей. В продакшен-коде нет ни одного вызова. Функция проверена в `schema_test.go:60-142` и вызывается только из `ToRepairableErrorShape` (`tool_wake.go:443-448`), у которого тоже нет продакшен-вызова, только тесты.
- Сами MCP-хендлеры возвращают сырые ошибки в SDK, например `tool_ack.go:466-475`. Клиент превращает их в протокольную ошибку через `SetError` в `client.go:375-379`.

Оценка. Проверки на границе сконцентрированы хорошо: HTTP и MCP имеют по одной точке, где ошибка превращается в ответ. Проблема в количестве точек: их три, и одна из них не подключена к живому пути. Это повторяющийся код именно на границе, где он допустим, но дублирование типов делает контракт сложнее, чем есть на самом деле.

Рекомендация. Либо подключить `ToErrorShape` в общий адаптер хендлеров MCP и тем самым сделать ADR 0009 исполнимым, либо удалить мёртвый конвертер и честно описать, что хендлеры отдают сырые ошибки SDK. Для HTTP достаточно одного общего типа `Error` и одного `WriteError`; `httpapi.writeError` может делегировать ему без изменения формата ответа.

### 5. ROP-подобные вещи уже есть, и лучше всего они работают в чистых функциях

Хорошие примеры:

- `internal/domain/verdict.go:100-162`, `Evaluate`, и `:170-237`, `EvaluatePR`. Приоритетная таблица решений, early return, каждый возврат несёт вердикт и список wake-целей. Нет ошибок, нет I/O, нет мутаций.
- `internal/domain/verdict.go:570-590`, `CompletionGate`; `:663-710`, `EvaluateExternal`; `:850-864`, `ParseReviewerExitCode`. Один закрытый набор исходов, fail closed.
- `internal/infra/github/errors.go:37-48`, `Result`. Сумма-тип с четырьмя полями: `Err`, `Conflict`, `Retry`, `Backoff`. Потребители читают поля напрямую: `graphql.go:408-423`, `tier2.go:240-254`.
- `internal/infra/channel/reply.go:62-89`, `Outcome`, и `internal/infra/server/eventbus/poison.go:62-99`, `Result`. Чистые функции, возвращают структуру с причиной.

Полу-ROP, который только усложняет:

- `internal/app/orchestrator/orchestrator.go:325-388`: `errs []error` передаётся в helper'ы как `*[]error` (`:399`, `:427`, `:484`, `:529`, `:550`), затем `errors.Join`. Это аккумулирующий writer, описанный вручную. Работает, но сигнатуры helper'ов несут лишний аргумент.
- Аналог в `workload.go:183-195`, `rebase.go:197-205` и `:364-389`, `github/graphql.go:330-358`.

Оценка. Вердикт-функции это то, что от ROP стоит взять: закрытый набор исходов, ранний выход, чистота. Это не обработки ошибок, а моделирование решения, и тип `Result[T]` туда не вписывается. Аккумуляция ошибок через `[]error` и `errors.Join` это идиома Go 1.20+, и замена на monad ничего не упростит.

Рекомендация. Оставить вердикт-движок как есть. В orchestrator можно убрать `*[]error` из сигнатур, если собрать ошибки в возвращаемом `Result` как поле `Errs []error`, но это косметика и отдельная карточка, а не часть аудита ошибок.

### 6. Проглоченные ошибки в бизнес-логике, где это влияет на решение

- `internal/app/orchestrator/checkall.go:827-838`: три `json.Unmarshal` с `_ =` для полей `verdict`, `headSHA`, `revision`, плюс три `json.Marshal` с `_ =`. От прочитанного `verdict` и `headSHA` зависит, будет ли выполнена запись. При битом поле decoder оставляет пустую строку и код уходит по ветке «ничего не менять».
- `internal/app/orchestrator/decision.go:354`: `satisfied, _ = deps.Satisfied(...)`. Ошибка resolver'а трактуется как неудовлетворённая зависимость. Это fail closed, поведение разумное, но молчаливое.
- `internal/infra/server/eventbus/bus.go:96-100`: `deliver` гасит и ошибку подписчика, и панику через `_ = recover()`. В параллельном `internal/app/event/bus.go:282-291` `deliverOne` превращает панику в ошибку. Две шины с разной политикой.

Оценка. Большинство из 129 плоских `_ =` это закрытие файлов и `defer`, где альтернативы нет. Три примера выше влияют на accept/reject решения и заслуживают внимания.

Рекомендация. В `checkall.go` проверять три внутренних `Unmarshal` так же, как проверен внешний на `:822`. В `decision.go` логировать ошибку resolver'а через `observe`, оставив fail closed. Для шин выбрать одну политику и описать её в ADR.

### 7. Паники

- `internal/domain/identity.go:28-32`: `NextRevision` паникует на `maxRevision`, потому что функция возвращает `uint64`, а не ошибку, и нарушение монотонности недопустимо.
- `internal/app/event/bus.go:135-147`: `WithTx` ловит панику, делает rollback и перевыбрасывает её. Корректно.
- `internal/app/event/bus.go:284-291`: `deliverOne` превращает панику подписчика в ошибку. Корректно.

Оценка. Это не случай «паника там, где нужна ошибка». Паника здесь защищает инвариант или не даёт подписчику убить цикл. Единственный спорный случай `NextRevision`: вызывающий не может узнать о переполнении заранее, если только сам не проверит `maxRevision`.

Рекомендация. Оставить панику, но добавить в `NextRevision` комментарий с контрактом для вызывающих и, если ревизии приходят извне, проверять верхнюю границу на входе до вызова. ROP-тип здесь не помог бы: он не делает переполнение возможным.

## Помог бы здесь ROP или Result-тип

Честный ответ: нет, не помог. В этом коде уже есть то ценное, что ROP даёт, а именно ранний выход и закрытые наборы исходов в чистых функциях. Это сделано через обычные Go-структуры в `domain/verdict.go` и `github/errors.go`. Остальное это либо `%w` с `errors.As`, либо `errors.Join` для аккумуляции. Обобщённый `Result[T]` добавил бы обёртку вокруг каждого `tx.Exec`, новую терминологию для чтения кода и расхождение с ADR 0009, который владелец уже принял.

Есть два места, где правда хочется большего: аккумуляция ошибок в orchestrator и конвертация `AppError` в MCP envelope. Первое решается полем `Errs` в уже существующем `Result` DTO, второе подключением уже существующего `ToErrorShape`. Ни одно не требует monad.

## Рекомендации по приоритету

1. Подключить `ToErrorShape` к живому пути MCP или удалить неиспользуемый конвертер. Это уточнит контракт ADR 0009.
2. Заменить `%v` на `%w` в 35 местах из находки 2, сохранив очистку текста в `telegram.go`.
3. Проверить внутренние `json.Unmarshal` в `checkall.go:827-838`, от них зависит запись.
4. Добавить `Unwrap` к `AppError`, чтобы `fanout.go` не превращал причину в строку. Не менять JSON.
5. Объединить два HTTP форма ошибки или явно документировать, почему они разные.
6. Не добавлять `Result[T]`. ADR 0009 уже закрыл этот вопрос, и замер это подтверждает.
