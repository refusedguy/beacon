### test

Шаг `Test root module` занимает 21 с. По логу того же прогона модули не скачиваются ни разу, кэш 189 МБ восстанавливается успешно, и один пакет печатает `(cached)`. То есть старый диагноз про сломанный кэш больше не действует. Остаток времени приходится на пересборку изменённых пакетов: `cmd/beacon` 9,8 с, `internal/app/taskcli` 8,0 с, `internal/infra/mcp` 2,9 с. Внутри пакетов тесты идут последовательно, `t.Parallel()` в репозитории нет. В `taskcli` два теста по 20 раз устраивают гонку за файловым замком с шагом 100 мс, что остаётся вероятной причиной 8 с.

### e2e

Самая дорогая проверка. В наборе семь сценариев с замороженным хешем `85303c45...`, включая живой цикл MCP на реальном opencode 2.3.0. В коде стоят таймауты контекста 15, 30, 60 и 120 с. Джоба имеет `continue-on-error: true` и не входит в набор обязательных проверок `batchapply`. При этом она определяет время, за которое PR получает полный набор проверок. Лимит джобы 20 минут, то есть зависший прогон удерживает критический путь в 14 раз дольше обычного.

### js-test

26 с на джобу, из них 19 с занимает `node --test` по 16 файлам: 13 adapter-тестов, 2 `SKILL_test.js` и 1 тест агента. Зависимостей npm нет, отдельный `setup-node` не нужен. Проверка дешёвая и кэш ей не требуется.

### gates-binary

Работает только при изменении исходников гейтов, `go.mod` или самого workflow. В последние 8 прогонов по этому workflow один провал, остальные успешны. Внутри: пересборка бинарника и побайтовое сравнение с закоммиченным файлом. Само сравнение мгновенное, основное время занимает setup-go и компиляция. Шаг использует встроенный кэш `setup-go` размером около 10 МБ. Это другой механизм, чем `actions/cache` в CI, и запись с 21 ноября 09:44 больше не обновлялась.

### Стоимость самих гейтов

Логика проверок почти бесплатна. `Self-test every gate` и `Run gates on tree` занимают 0 и 1 с. `rules gate` в джобе `rules-broken` тоже 0 с, все 25 с уходят на build. `cardindex` тратит 4 с на self-test и 0 с на сравнение индекса. Из примерно 103 runner-секунд, которые кодо-правка отдаёт проверкам `gates`, `rules-broken`, `cardindex` и `seed-spec`, на работу самих правил приходится меньше 5 с. Остальное это подготовка раннера и компиляция.

## Чего не делать

Не выключать джобы и гейты ради скорости. Набор `build`, `test`, `gates`, `gates-binary` зафиксирован в `internal/infra/batchapply/apply.go` как обязательный для авто-мержа.

Не добавлять `-count=1` в `go test`. Флаг отключает кэш результатов, который теперь работает.

Не отключать встроенный `go vet` через `-vet=off`. Он часть гейта.

Не снижать число последовательностей в property-тестах. Сейчас `invariantChecks = 1000`, по замерам это 0,6-1,5 с, выгоды почти нет.

Не поднимать `-p` и `-parallel` выше числа процессоров раннера. Документация Go предупреждает о падении производительности.

Не запускать замеры локально. ADR 0022 запрещает локальную компиляцию и тесты. Все числа здесь получены из GitHub Actions API и логов.

## Как проверить эффект

Для каждой правки нужен один и тот же порядок проверки. Сначала записать время джоб из API до изменения. После мержа исправления сравнить медиану по 10 прогонам. В логах `Cache Go` должны появиться строки `Cache saved successfully`, а в `Test root module` больше пакетов с `(cached)`. Для `e2e` отдельно сверить, что при выносе в отдельный workflow проверка по-прежнему запускается на PR, меняющем сценарии.

Оценки в таблице помечены как оценки. Измерены только времена джоб и шагов, размер кэша и частота запусков. Гипотеза про 4-5 с в `taskcli` остаётся неподтверждённой до замеров с `-json`.
