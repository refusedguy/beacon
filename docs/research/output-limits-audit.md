# Аудит ограничений вывода и truncate

Дата: 2026-11-21. Репозиторий: beacon-impl, коммит `d3b1bfb1`. Область: каталоги `cmd`, `internal`, `tools`, плюс `docs` для сверки с карточками и ADR. Worktree не читались.

Метод: поиск по явным каталогам (`rg` по `cmd internal tools docs`) и чтение реализаций вместе с тестами. Код не менялся.

## Что найдено по каждому лимиту

### 1. Вырезка failure excerpt в `beacon_get_result`

Место: `internal/infra/mcp/tool_get_result.go:68-74`, `:453-489`, `:534-555`.

Лимит: 2048 байт на одну вырезку и на всю агрегатную строку; 8 аннотаций на проверку (`failureExcerptLimit`, `failureExcerptAnnotationCount`).

Поведение при превышении: `sanitizeExcerpt` сначала удаляет секреты, потом экранирует markup, потом вызывает `clampExcerpt`. `clampExcerpt` отрезает по байтам и откатывается назад до границы UTF-8 (`:546-555`). `attachFailureExcerpts` перестаёт добавлять проверки, когда накоплено 2048 байт (`:478`). Остальные проверки в `failedChecks` остаются, но без текста.

Continuation token: нет. Признака обрезания в ответе нет.

Потеря информации: да. Текст аннотации после 2048 байт и аннотации сверх восьми не попадают в ответ.

Восстановление: частичное. Источник можно вызвать отдельно (`gh run view --log-failed`) или заменить через `SetFailureExcerptSource`. Кэш SQLite хранит уже урезанный текст, поэтому повторный опрос его не восстановит.

### 2. Ограничение по рунам и конверт wake-подсказки

Место: `internal/infra/wake/deliver.go:1170-1204` (`T212clamp`, `T212buildPromptText`). В задаче этот пункт обозначен как clampRunes.

Лимит: 96 рун на каждое из трёх полей (`watchID`, `obligationID`, `verdictRef`), 512 байт на весь конверт `<beacon-event>...</beacon-event>`.

Поведение при превышении: `T212clamp` режет по рунам. Если после JSON-маршалинга строка длиннее 512 байт, код отсекает байты до `limit - len("</beacon-event>")` и приклеивает закрывающий тег (`:1200-1203`).

Continuation token: нет.

Потеря информации: хвосты идентификаторов. Есть риск хуже: байтовый отрез может разрезать multi-byte символ или JSON-строку посередине. Конверт тогда останется валидным по длине, но не разберётся как JSON. Тест `TestT212PromptTextHasIdentifiersOnly` (`:731-763`) проверяет только длину и наличие ключей, не разбор JSON.

Восстановление: полные ID остаются в Watch и в store. Подсказка несёт только указатель.

### 3. `maxRecentWatches = 30`

Место: `internal/infra/httpapi/server.go:46-50`, применение `:832-834`.

Лимит: 30 записей в блоке `recentWatches` снимка.

Поведение при превышении: срез `[:30]`. По контракту провайдер обязан отдавать записи от новых к старым по `ClosedAt` (комментарий `:184-185`), поэтому отбрасывается хвост. Молча.

Continuation token: нет в самом снимке.

Потеря информации: в этом ответе да. В SQLite записи остаются.

Восстановление: да, через постраничный `GET /api/v1/watches` с `nextCursor` (`internal/infra/server/api_watches.go:154-174`).

### 4. `maxAuditRecords = 200`

Место: `internal/infra/httpapi/server.go:52-53`, `:421-429`.

Лимит: 200 записей в процессе.

Поведение при превышении: `recordAudit` оставляет последние 200, старые удаляет из среза.

Continuation token: нет.

Потеря информации: в этом транспорте да. История команд старше 200 через этот endpoint недоступна.

Восстановление: только если те же факты записаны в постоянный audit store; этот срез живой, не из БД.

### 5. ANSI strip и обрезка истории

Место: `internal/infra/wake/deliver.go:1576-1579`, `:1583`, `:1615-1667`.

Лимит: 200 строк и 16 KiB вывода поиска (`historySearchMaxLines`, `historySearchMaxBytes`).

Поведение при превышении: `HistorySearch` снимает SGR и OSC последовательности регуляркой `historyANSI`, затем `clampHistoryOutput` оставляет первые 200 строк и укладывается в 16 KiB. Превышение по строкам или байтам ставит `HistorySearchResult.Truncated = true`.

Continuation token: нет. Есть булево `Truncated`, единственный явный сигнал об обрезании во всём аудите.

Потеря информации: да, но помеченная.

Восстановление: да. Запрос можно повторить с ужестёкшим шаблоном или прочитать файл напрямую; backend (`rg` или `grep -E`) и путь известны вызывающему.

### 6. `beacon logs --tail`

Место: `cmd/beacon/logs.go:23`, `:31-34`; `internal/infra/observe/query.go:76-94`.

Лимит: по умолчанию 100 последних совпавших записей. `--tail 0` означает все. Отрицательное значение отклоняется.

Поведение при превышении: `ReadLogs` оставляет хвост среза (`:92-94`). Предупреждения нет. Дополнительно `bufio.Scanner` имеет предел 4 MB на строку (`:77`), а ошибку сканера код игнорирует (`:89`), поэтому строка длиннее 4 MB пропадает молча.

Continuation token: нет.

Потеря информации: да, без пометки.

Восстановление: да, если пользователь знает про `--tail 0`. Про строки длиннее 4 MB нет.

### 7. Постраничные REST-проекции

Место: `internal/infra/server/api_watches.go:25-27`, `:154-174`; `internal/infra/server/api_audit.go:26-28`, `:202-225`; `internal/infra/server/events.go:39`, `:95`, `:146`.

Лимит: размер страницы по умолчанию 50, максимум 500 для watches и audit. Для потока событий `PageSize = 500`.

Поведение при превышении: возвращается страница и `nextCursor`, если данные остались. Дальнейшие страницы читаются этим курсором.

Continuation token: да, `nextCursor`. Контракт проверяет отсутствие повтора курсора в `internal/infra/mcp/contract_test.go:118-125`.

Потеря информации: только если клиент игнорирует `nextCursor`.

Восстановление: полное при обходе курсора.

### 8. SSE replay

Место: `internal/infra/httpapi/server.go:40-44`, `:887-898`.

Лимит: буфер 256 событий по умолчанию, `replay` не больше 1000.

Поведение при превышении: запрошенное число тихо уменьшается до 1000 (`:895-897`).

Continuation token: есть `Last-Event-ID` для живого потока, но нет признака того, что `replay` был уменьшен.

Потеря информации: старые события недоступны через `replay`.

Восстановление: через позицию в потоке, если клиент её хранил.

### 9. TUI render

Место: `internal/tui/app.go:146-180`.

Лимит: собственного лимита нет. Единственное сокращение: `shortSHA` показывает 7 символов хеша (`:175-179`).

Поведение: `Render` печатает все вотчи, блокеры, эскалации и ошибки загрузки из снимка. Снимок уже ограничен HTTP-слоем в 30 последних вотч.

Continuation token: не нужен.

Потеря информации: только в отображении полного SHA.

Восстановление: полный SHA есть в других представлениях.

### 11. Квитанции

Место: `internal/infra/store/receipts.go:259-329`, `:372-446`; `internal/infra/ladder/transitions.go:137-145`, `:379-384`.

Лимит по размеру не найден. Квитанция это целая строка JSON. Импорт отклоняет строки с лишними данными (`:278-279`) и строки без отметки verified (`:406`), но не ограничивает длину. Ограничение в три попытки относится к повторам доставки, не к размеру вывода.

## Несоответствия код versus карточка/ADR

**t3_thread_read и 30000 символов.** Карточка `docs/tasks/T3.236.md` описывает внешний инструмент, который останавливается около 30000 символов и возвращает `earlierPosition` или `hasMore`, а также поля `createdBy` и `creationSource`. Та же формулировка есть в `docs/tasks/S4.012.md` и `docs/tasks/S6.003.md`. В коде такого инструмента нет. `internal/infra/mcp/server.go` регистрирует ровно восемь инструментов по ADR 0094. Нет ни лимита 30000, ни continuation token, ни provenance полей. S4.012 и S6.003 имеют статус dropped после PR 394, T3.236 остаётся todo с блокером. Это расхождение между спецификацией карточки и реализацией, а не баг в работающем коде. Нужно решение владельца: отдельный ADR на девятый инструмент или переформулировка проверки под восемь существующих.

**R13 page limit warning.** `docs/evals/r13-page-limit-warning.md` требует предупреждение, когда список вернул ровно `limit` строк. В коде реализации нет. REST-проекции сигнализируют только наличием `nextCursor`, а предупреждение не печатают. Списка registry с параметром `limit` в main нет.

**ANSI strip, T3.250.** Карточка `docs/tasks/T3.250.md` и код совпадают. Реализация снимает ANSI и ограничивает вывод по строкам и байтам. Замер в карточке: 18 из 87 байт образца приходились на escape-последовательности.

**Вырезки W11-B.** Схема в `internal/infra/mcp/schema.go:129-133` обещает предел 2048 байт, код даёт 2048. Расхождений нет, но в схеме нет поля-признака обрезания.

## Пять главных находок

1. В трёх местах обрезание молчаливое и без точки продолжения: failure excerpt, wake-конверт, `beacon logs --tail`. Это самый высокий риск.
2. `clampHistoryOutput` выделяется среди всех: он ставит `Truncated = true`. Но даже он не даёт курсора, поэтому продолжение придётся изобретать вызывающему.
3. `maxRecentWatches = 30` теряет данные только в снимке. Постраничный endpoint с `nextCursor` позволяет восстановить всё, если клиент о нём знает.
4. TUI и `tabwriter` не являются лимитами вывода. Их часто упоминают в таком контексте, но они только форматируют или отображают уже ограниченный снимок.
5. Спецификация t3_thread_read на 30000 символов с `earlierPosition`/`hasMore` живёт только в карточках T3.236, S4.012 и S6.003. В коде восьми инструментов её нет. Предупреждение из R13 тоже не реализовано.
