## 1. Что это такое

Z.A.E.B.A.L. это хук для интерактивного кодинг-агента, который реагирует на брань пользователя. Название раскрывается как `Zaebal? Audit. Errors. Break. Analize. Leave no assumption` (`README.md:5-9`, `core/zaebal.py:1-4`). Ядро на Python stdlib, 1389 строк в `core/zaebal.py`, плюс адаптеры под Claude Code, Codex CLI, Kimi CLI и OpenCode. Всего 30 отслеживаемых файлов, около 6300 строк.

Рабочий цикл: пользователь пишет сообщение в чат, адаптер передаёт текст в ядро, ядро нормализует текст, ищет брань в трёх языковых списках (RU/EN/ZH), определяет адресата и тональность, ведёт взвешенную историю по сессии и возвращает в контекст агента протокол уровня L1-L4 (`README.md:104-135`, `core/zaebal.py:214-300`, `:656-676`). L1 просит аудит истории, L2 повторяет его с проверкой предыдущего вывода, L3 останавливает мутации и запускает внешнего аудитора, L4 запрашивает согласие на Swarm Review из 5-7 ревьюеров (`README.md:129-160`, `core/protocol/L1.md` - `L4.md`).

Есть ещё Early Review: по желанию пользователя хук напоминает агенту тихо вызывать read-only чекпоинт после первого существенного изменения, при смене подхода и перед дорогим или необратимым действием (`README.md:253-258`, `core/zaebal.py:1164-1191`, `core/protocol/early-review.md:1-20`).

Ключевое ограничение зафиксировано в README: детектор не находит небранных циклов действий, а общий детектор зацикливания объявлен отдельным продуктом со своей моделью ложных срабатываний (`README.md:357`). Это снимает главный вопрос задания: как заимствовать у Z.A.E.B.A.L. детектор застрявших задач. Такого детектора там нет по прямому решению авторов.

## 3. Разбор по пяти запрошенным направлениям

**Оркестратор агентов и слоты.** В Z.A.E.B.A.L. нет оркестратора. Есть один агент, которому в контекст подсовывают протокол, и опционально холодный CLI-аудитор, который раз за разом анализирует тот же текст. Слотов, выдачи задач и владельцев файлов нет. Beacon в этой части ушёл дальше.

**Worktree и параллельные ветки.** В клоне нет ни одного упоминания `git worktree`. Есть `git_summary` (`core/zaebal.py:969-1002`), который читает status, diff и log для аудита, не меняя дерево. Это средство потенцирования контекста аудитора, а не изоляция работы агентов.

**CI merge.** В клоне нет интеграции с GitHub Actions, PR или merge-очереди. Есть только `.github/workflows/platform-smoke.yml`, который проверяет сам хук на трёх ОС. Механизм слияния в beacon не с чем сравнивать.

**Детекты застрявших задач.** Z.A.E.B.A.L. детектирует только эмоциональный сигнал в сообщении и прямым текстом README отказывается от детектора небранных циклов (`README.md:357`). Beacon использует повтор отказа как переход в `parked`, heartbeat сессии и TTL-реaper. Подход «эскалация по числу ругательств» в контур beacon встроить некуда: сообщения от человека приходят как issue, а решение по ним принимает оркестратор, а не хук на chat.message.

**Перф-замеры.** В репе нет бенчмарков и замера latency. Есть константы `auditor_timeout_sec=90`, размеры хвостов 12000 и 2500 символов (`core/config.json:1-12`) и `time.monotonic()` в блокировке (`core/platform_runtime.py:51-63`). Это параметры, а не измерение. Переносить нечего.

## 4. Что не создаём

Карточек `ZB-01..N` нет. Причины:

1. Все найденные механизмы либо неприменимы в beacon, либо уже реализованы там в более строгой форме. Карточка без измеримого разрыва создаёт работу ради работы.
2. Заявленная цель repo это изменение поведения одного интерактивного агента через текст протокола. Beacon управляет несколькими агентами через события, вердикты и CI. Разная точка управления.
3. Запрет ADR 0022 не позволяет поставить LLM-аудитора между PR и merge, а именно это ядро Z.A.E.B.A.L. и делает.
4. Детектор брани не работает с входными данными beacon:issue, события CI и journal Watch не содержат сообщений чата.
