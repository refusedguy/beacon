# Взятие задачи в работу и закрытие без PR: обзор

Дата: 2026-11-21. Режим: brainstorm, read-only. Код не менялся, гейты не запускались, Beacon не вызывался.

Вопрос: как другие системы отделяют «задача взята в работу» от «задача закрыта», и как закрывать блокеры без PR. Ниже шесть систем, затем механические правила и предложение для карточек Beacon.

## 1. Что у других систем

### GitHub Issues и Projects

Источник: https://docs.github.com/en/rest/issues/issues

Взятие в работу это `assignees`. Назначение не меняет `state`, задача остаётся `open`.

Закрытие разделено на два поля:

- `state` принимает `open` и `closed`.
- `state_reason` принимает `completed`, `not_planned`, `duplicate`, `reopened` или `null`.

Появилось поле `status` со значениями `Backlog`, `Todo`, `In progress`, `In review`, `Done`, `Not planned`, `Duplicate`. Установка `status` сама обновляет `state` и `state_reason`. Если причины не согласованы, API отклоняет запрос. Для `status: Duplicate` обязателен `duplicate_issue_id`, и цель должна существовать. Если записать статус не удалось, API откатывает все изменения полей в этом запросе.

Есть `closed_by` и `closed_at`, то есть кто и когда закрыл. Есть `issue_dependencies_summary` со счётчиками `blocked_by` и `blocking`. Блокировка это отношение между задачами, а не отдельный `state`.

Главное для Beacon: причина закрытия это отдельное обязательное поле, а дубль это не только причина, но и структурированная ссылка на оригинал.

### Linear

Источник: https://linear.app/docs/issue-property

Взятие в работу это `assignee`. Типовой поток: `Backlog > Todo > In Progress > Done > Canceled`. Категории статусов фиксированы: backlog, unstarted, started, completed, canceled, плюс triage как входящий ящик. Команды добавляют свои статусы внутри категории, но порядок категорий менять нельзя.

Дубль это зарезервированный статус `Duplicate`. Система ставит его автоматически, когда задачу отмечают дублем. В карточке появляется баннер и ссылка на каноническую задачу. Переименовать этот статус нельзя.

Блокировка это отношение `Blocked by` / `Blocks`, а не статус. Когда блокирующая задача закрывается, отношение переезжает в раздел `Related`. Есть автосервис `auto-close`, который закрывает давно не обновлявшиеся задачи, и `auto-archive`.

На уровне агентских сессий тот же подход виден в GraphQL-схеме: `AgentSession.status` принимает `pending`, `active`, `stopping`, `awaitingInput`, `complete`, `error`, `stale`, а шаги плана имеют статусы `pending`, `inProgress`, `completed`, `canceled`. Источник: https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql

Главное для Beacon: блокер живёт как отношение с владельцем и lifecycle, дубль живёт как terminal-статус плюс типизированная ссылка.

### Jira

Источники:
https://support.atlassian.com/jira-cloud-administration/docs/what-are-issue-statuses-priorities-and-resolutions/
https://support.atlassian.com/jira-cloud-administration/docs/work-with-issue-workflows/

Взятие в работу это `assignee`. Статусы по умолчанию: `To Do`, `Open`, `In Progress`, `In Review`, `Done`, `Cancelled`, `Rejected`, `Resolved`, `Closed`, `Backlog`. В Jira Service Management есть `Waiting for support`, `Waiting for customer`, `Pending`, `Escalated`.

Переход между статусами делается только через объявленный transition. Transition однонаправленный, для возврата нужен второй. Отдельный loop-переход позволяет открыть экран или вызвать действие, не меняя статус.

Причина закрытия хранится в отдельном поле `Resolution`, которое обычно заполняется при переходе: `Done`, `Won't do`, `Duplicate`, `Cannot reproduce`, `Known error`. О Resolution в документации сказано прямо: это описание того, как работа была завершена. После заполнения ключ задачи в ссылках зачёркивается.

Главное для Beacon: статус и причина завершения это два разных поля, и причина заполняется на переходе, а не позже по памяти.

### Claude Agent SDK, общий список задач

Источник: https://code.claude.com/docs/en/agent-sdk/todo-tracking.md

Инструменты `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, плюс устаревший `TodoWrite`. Жизненный цикл одной задачи:

1. `pending` при создании.
2. `in_progress` при начале работы.
3. `completed` при успешном завершении.
4. `deleted` через `TaskUpdate`, когда задача больше не нужна.

Дополнительных статусов blocked, duplicate или cancelled нет. Зависимости тоже правятся через `TaskUpdate`. Каждая смена статуса видна во внешнем потоке как `tool_use` блок, а приложение correlation ID берёт из `tool_use_result`.

Главное для Beacon: четырех статусов достаточно для потока, но отмена и блокировка не различаются. `deleted` это единственный способ убрать задачу из работы. Для Beacon этого мало, потому что блокер нужно сохранить с причиной и владельцем.

### CrewAI

Источники:
https://docs.crewai.com/en/concepts/tasks
https://raw.githubusercontent.com/crewAIInc/crewAI/main/lib/crewai/src/crewai/task.py

Задача это `Task` с `description`, `expected_output`, `agent`, `context`, `output`. В текущем исходнике поля `status` нет. Состояние выводится из `start_time`, `end_time`, `output` и событий `TaskStartedEvent`, `TaskCompletedEvent`, `TaskFailedEvent`. Есть `retry_count` и `guardrail_max_retries` для повторов guardrail.

Статуса blocked, duplicate или cancelled нет. При ошибке задача пишет `end_time`, посылает `TaskFailedEvent` и выбрасывает исключение. Завершившаяся задача определяется по заполненному `output`.

Главное для Beacon: эту модель копировать не стоит. В ней нет долговременного состояния задачи, а Beacon держит карточку в git и обязан объяснять, почему она закрыта.

### Очереди задач с арендой, пример AWS SQS

Источник: https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html

Получение сообщения это claim. Сообщение остаётся в очереди, но становится невидимым для других потребителей на `visibility timeout`. Значение по умолчанию 30 секунд. `ChangeMessageVisibility` продлевает или сокращает таймаут, а значение 0 немедленно возвращает сообщение в очередь.

Документация прямо рекомендует heartbeat для регулярного продления таймаута. Максимальный срок аренды 12 часов от первого получения, продление не сбрасывает этот предел. После успеха сообщение удаляется явно. Необработанные сообщения уходят в Dead-Letter Queue. Доставка at-least-once, поэтому абсолютной гарантии от повторной обработки нет.

Главное для Beacon: claim с истекающим сроком и heartbeat это рабочий паттерн. Beacon уже использует похожую идею в файловых арендах, но не применяет её к статусу карточки.

## 2. Идеи, которые можно ввести механически

Список того, что реально проверяется кодом или парсером:

1. Lease + TTL. Поле `Время аренды` ставится при claim. Карточка старше TTL считается брошенной. Beacon уже имеет `LeaseTTL = 30 * time.Minute` в `internal/app/taskcli/service.go` для файловых аренд и проверяет его на границе чтения. Переиспользовать то же число и ту же логику для карточек.

2. Heartbeat. Команда продлевает `Время аренды`, не меняя статус. Продление пишется в журнал. По истечении TTL карточка уходит в `todo` или `blocked` с причиной `lease expired`.

3. Обязательная причина закрытия. Парсер отклоняет `done` и `dropped` без поля `Причина` из фиксированного перечисления. Это правило на границе чтения карточки, такое же как сейчас проверка обязательных полей.

4. Блокер с владельцем. Статус `blocked` требует поля `Блокировщик` и причины свободным текстом. Владелец это agent ID, watch ID или ссылка на чужой PR. Разрешение блока возвращает карточку в `todo` и чистит поля, но сохраняет запись в журнале. У Beacon уже есть готовый словарь на уровне Watch: `StatusBlocked`, `blocked:not_mine`, `blocked:resolved`, `BlockerStatusOpen`, `BlockerStatusResolved` и wake для оркестратора. Перенос этого же контракта на карточку стоит дешевле, чем новый механизм.

5. Ссылка duplicate-of. Поле `Дубликат` обязательно тогда и только тогда, когда `Причина: duplicate`. Парсер проверяет, что цель существует, по той же схеме, как `beacon task new` проверяет `Ссылка` на ADR или эпик. Это убирает текущую практику, когда причина дублирования живёт только в тексте раздела `Подтверждение`.

6. Кто и когда закрыл. Поля `Закрыл` и `Время закрытия` заполняются командой закрытия. Сейчас `Агент` и `Время` заполняются при взятии, и этот же шаблон можно повторить.

7. Явная команда закрытия и освобождения. `beacon_task_close` и `beacon_task_release` работают под тем же файловым замком и атомарным переименованием, что и `take`. Идемпотентность по `(cardID, причина, владелец)` не даёт двум агентам записать разные причины для одного закрытия.

8. Наблюдаемость. `internal/app/tasks/card_monitor.go` уже испускает `card.status_changed`. Новые статусы не требуют нового канала уведомлений.

## 3. Сопоставление с текущими карточками Beacon

Источник: docs/beacon-task-cli-spec.md и карточки в docs/tasks/.

Сейчас у карточки четыре статуса: `todo`, `in_progress`, `done`, `dropped`. Обязательные поля: `Тип`, `Статус`, `Фаза`, `Владелец файлов`, `Зависимости`, `Ссылка`, `Цель`, `Контекст`, `Шаги`, `Проверка`, `Приёмка`, `Агент`, `Время`. Дополнительные строки парсер сохраняет.

Что происходит сегодня:

- `beacon_task_claim` выбирает первую карточку `todo` с валидным handoff, проверяет `agentID`, пишет `in_progress`, `Агент` и `Время`.
- `done` появляется после PR и `beacon_watch_pr`.
- `dropped` ставится вручную. Причина живёт свободным текстом в разделе `Подтверждение`. В репозитории есть карточки с причинами «Дублирует BS.31», «conflicts with the seven-tool MCP contract», «dead T2xx design».
- `done` и `dropped` освобождают владельцев файлов. `todo` и `in_progress` считаются занятыми.
- Команды `close` и `release` на уровне карточки отсутствуют.

Чего не хватает:

1. Отдельной причины закрытия. Сейчас `dropped` совмещает дубль, устаревшее решение и отказ владельца, и причина не проверяется.
2. Статуса `blocked`. Блокер на уровне Watch есть, на уровне карточки его нет, поэтому карточка висит в `in_progress` после того, как стало ясно, что PR не будет.
3. Структурированной ссылки на дубль. Текст в `Подтверждение` машина не может проверить.
4. Срока аренды для `in_progress`. Карточка может остаться в работе навсегда после падения агента.
5. Полей `Закрыл` и `Время закрытия`.
6. Явного механизма освобождения карточки без PR.

## 4. Рекомендация

### Минимум, чтобы закрывать блокеры без PR

Статусы: оставить `todo`, `in_progress`, `done`, `dropped` и добавить `blocked`. Пять статусов против четырёх сейчас. `blocked` не terminal: он возвращается в `todo` после разрешения.

Поля карточки, добавляемые к существующим:

| Поле | Когда обязательно | Проверка |
|---|---|---|
| `Причина` | для `done` и `dropped` | перечисление `completed`, `already_landed`, `duplicate`, `not_planned`, `owner_decision`, `obsolete` |
| `Дубликат` | только при `Причина: duplicate` | цель существует в `docs/tasks/` или это существующий PR |
| `Блокировщик` | для `blocked` | непустой agent ID, watch ID или ссылка на PR |
| `Причина блокировки` | для `blocked` | непустой текст |
| `Закрыл` | для `done` и `dropped` | непустой agent ID |
| `Время закрытия` | для `done` и `dropped` | RFC3339 в UTC |

Правила, которые парсер проверяет при чтении и команды при записи:

- `done` или `dropped` без `Причина` это ошибка формата, карточку пропускать нельзя.
- `Причина: duplicate` без валидного `Дубликат` это ошибка.
- `blocked` без `Блокировщик` и `Причина блокировки` это ошибка.
- `beacon_task_close` принимает `in_progress` и `blocked`, записывает `Причина`, `Закрыл`, `Время закрытия` и статус `done` или `dropped`.
- `beacon_task_release` возвращает `in_progress` в `todo`, чистит `Агент` и `Время`, пишет запись в журнал.
- Разрешение `blocked` возвращает карточку в `todo`, чистит поля блокировщика, сохраняет историю.

Для трёх уже существующих блокеров из контекста это даёт такой результат:

- «уже влито»: `dropped`, `Причина: already_landed`, `Дубликат` на PR.
- «решение владельца»: `dropped`, `Причина: owner_decision`, `Закрыл` равен владельцу.
- «чужой PR»: `blocked`, `Блокировщик` равен watch ID чужого PR, позже `release` в `todo`.

### Следующий шаг, если понадобится

Добавить `Время аренды` и `Продлить`. Переиспользовать `LeaseTTL = 30 * time.Minute`. На границе чтения просроченная аренда переводит карточку в `todo` или `blocked` с причиной `lease expired`. Журнал при этом сохраняется целиком, как сейчас в файловых арендах.

## 5. Главные находки

1. GitHub держит причину закрытия отдельно от статуса и требует ссылку на оригинал для дубля. https://docs.github.com/en/rest/issues/issues
2. Linear делает дубль зарезервированным статусом с автоматической ссылкой, а блокировку держит как отношение, которое переезжает в `Related` после разрешения. https://linear.app/docs/issue-property
3. Jira заполняет `Resolution` на переходе, и переход без объявленного правила невозможен. Это готовый аргумент за обязательное поле причины в момент закрытия. https://support.atlassian.com/jira-cloud-administration/docs/what-are-issue-statuses-priorities-and-resolutions/
4. Claude Agent SDK обходится четырьмя статусами, но не различает блокер и отмену. Для Beacon этого мало. https://code.claude.com/docs/en/agent-sdk/todo-tracking.md
5. Очереди с арендой давно используют TTL, heartbeat и явное подтверждение. У Beacon уже есть `LeaseTTL`, но только для файлов, не для карточек. https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html

Дополнительный источник по агентским сессиям Linear: https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql

Дополнительный источник по CrewAI: https://raw.githubusercontent.com/crewAIInc/crewAI/main/lib/crewai/src/crewai/task.py
