# Процедура закрытия застрявших карточек

Runbook для оркестратора. Описывает, как закрыть карточку, у которой не будет терминального вердикта `merged`, и как запросить решение владельца. Команды меняют карточки в `docs/tasks/*.md`. Доставка закрытой карточки в `main` описана ниже. Основание: ADR 0020, ADR 0051, ADR 0094, ADR 0268, ADR 0270.

## Когда применять

Обычную карточку закрывает Beacon: при `verdict=ready` он мержит watch-PR и переводит карточку в `done` со ссылкой на PR. Эту процедуру применяют только когда PR, который дал бы `merged`, не появится и не родит вердикт:

- изменение уже влито в `origin/main`;
- изменение уже есть в другом PR или другой карточке;
- владелец принял решение, которое снимает задачу;
- premise карточки ложна, функциональность уже реализована.

Сигнал приходит от исполнителя вместе с доказательством. Оркестратор читает его через `beacon_get_result` или из отчёта хода. Блокер без проверяемого доказательства не закрывает карточку: оркестратор вызывает `beacon task needs-input` с вопросом.

Процедура не отменяет общий запрет на ручное закрытие при обычном цикле. Beacon по-прежнему закрывает карточки при `merged`. Здесь закрытие делает оркестратор, потому что ждать вердикта не от чего.

## Доставка статуса в main

`beacon task done`, `beacon_task_close` и автозакрытие на merge пишут карточку в рабочем дереве. Ни один из этих путей не создаёт коммит и PR. Пока правку не принёс PR, `origin/main` хранит прежний статус `todo`. CI и оркестратор читают старую карточку.

Замер от `8a766a5d`: 17 карточек имели `done` только в рабочем дереве, всего было изменено 79 файлов `docs/tasks/`. Проверку расхождения выполняют для каждой закрытой карточки до завершения хода.

Выбранный способ доставки это docs-PR по образцу ветки 6b скилла `beacon-executor`. Отдельный коммит оркестратора после `merged` не используется, потому что коммит без PR не проходит CI и не попадает в `main`.

### Проверка расхождения

Команда ловит карточку, у которой статус изменён только в дереве:

```bash
git fetch origin main
git diff --name-only origin/main -- docs/tasks/<CARD>.md
git show origin/main:docs/tasks/<CARD>.md | rg '^Статус:'
rg '^Статус:' docs/tasks/<CARD>.md
```

Первая команда должна вывести `docs/tasks/<CARD>.md`. Статус в дереве должен быть `done`, `dropped`, `blocked` или `duplicate`. Статус `todo` или `in_progress` в `origin/main` означает, что доставка не выполнена. Пустой вывод `git diff` означает, что правка уже в `main` и отдельный PR не нужен.

### PR с закрытой карточкой

1. Закрыть карточку с непустыми `--summary` и `--evidence`. Для `beacon_task_close` те же SHA и номер PR идут в `reason`.
2. Создать worktree: `git worktree add --lock -b fix/close-<CARD> worktrees/close-<CARD> origin/main`.
3. Скопировать закрытую карточку из общего дерева в worktree: `cp <root>/docs/tasks/<CARD>.md <worktree>/docs/tasks/<CARD>.md`.
4. Закоммитить только `docs/tasks/<CARD>.md`, запушить ветку и открыть `gh pr create --base main --head fix/close-<CARD>`. Кода в этом PR нет.
5. Зарегистрировать Watch на PR с `autoMerge: true` по правилам скилла `beacon-executor`. Мерж делает Beacon после зелёных проверок.

Если PR с кодом ещё нет, этот PR остаётся единственным способом доставить статус. В `evidence` указывают полный SHA и результат `git merge-base --is-ancestor <SHA> origin/main` с кодом 0. Номер будущего PR добавлять не нужно. Когда PR с кодом уже есть, его номер пишут в `evidence` и в заголовок PR с карточкой.

Если при регистрации Watch в логе появилось `watch_pr_card_link_missing` или `watch_pr-card-link`, связь «карточка → Watch» не записана. Такой Watch не закроет карточку при `merged`. Закрыть карточку вручную по этой процедуре и доставить её docs-PR. На автозакрытие рассчитывать нельзя.

## Две команды

Обе команды меняют только активные карточки со статусом `todo` или `in_progress`. Карточка в `done` или `dropped` даёт ошибку.

### `beacon task done <id> --summary <строка> --evidence <строка>`

Переводит карточку в `done` и пишет поля «Итог» и «Доказательство». Очищает поля «Состояние» и «Вопрос».

- `--summary` и `--evidence` обязательны как отдельные поля. Итог не заменяет доказательство.
- Если `--evidence` пуст, карточка не закрывается, а уходит в `needs_input` с вопросом «завершение без доказательства: задайте --evidence».
- Если `--evidence` есть, а `--summary` пуст, команда возвращает ошибку и карточку не меняет.
- Успешный вывод в stdout: `<id> done`. Диагностика идёт в stderr.

Пример:

```bash
beacon task done T3.7 \
  --summary "Требование уже закрыто коммитом 4f0e188, отдельный PR не нужен" \
  --evidence "git merge-base --is-ancestor 4f0e188 origin/main -> exit 0; PR #1203; github.com/refusedguy/beacon/pull/1203"
```

### `beacon task needs-input <id> --question <строка>`

Оставляет статус `in_progress`, пишет `Состояние: needs_input` и `Вопрос: <строка>`. Статус остаётся в допустимом множестве, поэтому `beacon task list` и `beacon task take` продолжают работать с карточкой.

- `--question` обязателен. Без него команда возвращает ошибку.
- Успешный вывод в stdout: `<id> needs_input`.

Пример:

```bash
beacon task needs-input T3.7 \
  --question "Владелец решил отложить задачу или закрыть её? Уточните решение и ссылку на него"
```

## Таблица причин

| Причина | Что проверить | Доказательство | Действие |
| --- | --- | --- | --- |
| Уже влито | Коммит с изменением достижим из `origin/main` | `git merge-base --is-ancestor <SHA> origin/main` с кодом 0, полный SHA, номер PR | `done` |
| Дубль или чужой PR | Другая карточка или PR уже несёт то же требование | ID другой карточки или номер PR и SHA коммита | `done` со ссылкой на исходное закрытие |
| Решение владельца | Владелец зафиксировал отказ, отложку или передачу задачи | Ссылка на сообщение владельца с решением | `done`, если решение завершает задачу; `needs-input`, если нужно уточнение |
| Ложная premise | Функциональность уже есть в коде, карточку писали под неё | Путь и символ в `internal/`, при наличии ссылка на ADR | `done` с указанием готовой реализации |

Чужой PR не отдельная строка: это тот же дубль. В доказательство кладут номер чужого PR и SHA его коммита. Оркестратор не открывает свой PR и не пушит повторное изменение.

Если владелец решил отказаться от задачи, она закрывается через `done`: в бинарнике нет отдельной команды `dropped`. Решение владельца уходит в поле «Доказательство». Если формулировка решения неоднозначна, оркестратор выбирает `needs-input` и задаёт конкретный вопрос.

## Whitelist полей закрытия

Закрытие «уже влито» пишет один и тот же набор полей. Этот набор зафиксирован здесь и называется whitelist. Поля и разделы вне whitelist в блок закрытия не добавляются.

| Поле | Что пишется | Источник |
| --- | --- | --- |
| `Статус` | `todo` меняется на `done` | Карточка в PR с закрытием |
| `Ссылка` | Ссылка на PR с кодом вместо ссылки на исследование | PR с кодом |
| `Причина` | Номер PR, полный SHA, команда `git merge-base --is-ancestor <SHA> origin/main` с кодом 0 и оговорка, что дубль кода не писался | SHA и результат команды |
| `Закрыл` | Имя агента или `нет` | Отчёт хода |
| `Время закрытия` | Время в формате `2026-11-22T15:21:13Z` | Отчёт хода |
| `## Подтверждение в main` | Список путей с именами символов и строка о неизменном контракте | `origin/main` |

В разделе «Подтверждение в main» каждая строка даёт путь и имена символов. Номер строки добавляется, только когда его получил инструмент из `origin/main`. Общие слова вместо пути и символа whitelist не разрешает.

Замер от 2026-11-22 по базе `29cda75b`: 161 PR с ровным шаблоном закрытия, средний диф один файл и +7.1/−2.9 строки. Канонический пример это карточка CA-16 в PR #1818 с merge-коммитом `badee108e467c4515d2d97126d35e84891db38b7`. Whitelist повторяет поля этого примера и не добавляет новых полей.

Генератор блока закрытия заблокирован. Инструмент вроде `scripts/close-card.sh` не пишется, пока владелец не примет whitelist отдельным решением. До принятия поля пишутся вручную и просматриваются в теле PR. Проверки, которая запрещает генератор, пока нет. Это открытое ограничение.

## Проверка требования до закрытия

Оркестратор проходит чек до каждой команды закрытия. Вердикт или блокер сами по себе не дают права на закрытие.

1. Требование. Прочитать поля «Цель» и «Приёмка» карточки и сформулировать, что именно должно быть выполнено.
2. Совпадение. Сверить доказательство с этим требованием. Доказательство обязано закрывать требование карточки, а не соседнюю работу.
3. Проверяемость. Убедиться, что доказательство содержит команду с кодом выхода, SHA, номер PR или ссылку на решение. Пересказ без ссылки не считается доказательством.
4. Состояние. Убедиться, что карточка активна и ещё не в `done` или `dropped`.
5. Поля. Подготовить непустые `--summary` и `--evidence`. Это разные поля, и первое не подменяет второе.
6. Власть. Закрывать только карточку, закреплённую за оркестратором. Чужие карточки в несвязанных PR не трогать.
7. След. После `done` сверить, что в карточке появились «Итог» и «Доказательство». После `needs-input` сверить, что появились «Состояние: needs_input» и «Вопрос».

Если любой пункт не проходит, закрытие заблокировано. Оркестратор задаёт вопрос через `needs-input` и ждёт ответа владельца.

## Отличие от блокера main

Блокер main это красная required-проверка на `origin/main`. По нему оркестратор запускает FIX-агента, а не закрывает карточку. Блокер из этой процедуры называется иначе: требование уже выполнено где-то ещё, и чинить нечего. FIX-агент по такому сигналу не спавнится.

Информационные проверки с `required: false` и `continue-on-error: true` не порождают ни FIX-агента, ни закрытие карточки.

## Инструмент `beacon_task_close` и golden `tools/list`

Эта процедура использует CLI `beacon task done` и `beacon task needs-input`. ADR 0270 добавил десятый MCP-инструмент `beacon_task_close`. Он даёт исполнителю один атомарный вызов с ключом идемпотентности `(cardID, status, reason)` и машиночитаемым результатом в том же цикле, где агент вызвал `beacon_task_claim`. CLI остаётся оркестратору для массовой чистки карточек. Инструмент принимает статусы `done`, `dropped`, `blocked` и `duplicate`, обязательный `reason` и поле `duplicateOf` для `duplicate`.

Каждое новое имя меняет публичный контракт MCP. ADR 0094 закрепил восемь инструментов и потребовал отдельного ADR на девятый. ADR 0268 добавил девятый `beacon_task_claim` и поднял бюджет ответа до 20 KiB. ADR 0263 запретил тихую регистрацию обработчика вне контракта. Для десятого имени принят ADR 0270.

Причина в золотом `tools/list`. Контракт в `internal/infra/mcp/server.go` (`ToolNames`) и в `internal/infra/mcp/contract_test.go` (`expectedToolNames` и золотые константы) фиксирует отсортированный список имён, размер сериализованного ответа и его SHA-256. Eval `rs-mcp-tools-list-stable-across-connections` сравнивает два листинга побайтово. Десятое имя меняет список, размер и хэш одновременно. Без ADR это выглядит как тихая регистрация, которую запретил ADR 0263. ADR 0155 и ADR 0156 показывают ту же цену: расширение набора инструментов отклонили в пользу строкового перечисления в `beacon_ack`. ADR 0270 взвесил альтернативу с одним CLI из брейнштормов и выбрал MCP-инструмент, заплатив за обновление золотых констант.

Чтобы добавить одиннадцатый инструмент, снова нужен отдельный ADR и обновление золотого `tools/list` в том же PR.
