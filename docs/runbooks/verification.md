# Проверка работоспособности Beacon

**Режим документа: reference.** Файл даёт справочные сведения о проверках и их наблюдаемых фактах. Первый абзац объявляет режим документа. Правило лежит в `AGENTS.md`, раздел «Режим документа». Пошаговые инструкции собраны в разделе «Запуск» и не смешиваются со справочником без заголовка.

Скрипты в `scripts/` проверяют реальные артефакты. Они не читают self-report
агентов, не доверяют свежим mtime файлов и не считают успешной сборку доказательством
работы. Каждая проверка либо наблюдает факт напрямую, либо завершается ненулевым
кодом.

## Запуск

```bash
bash scripts/verify-beacon.sh
bash scripts/verify-daemon.sh
```

Оба скрипта работают из любого каталога. Корень репозитория они находят по
своему расположению. Переопределение корня: `BEACON_REPO=/path/to/repo`.
 Go
берётся из `GO`, затем из `GO_BIN`, затем из `PATH`. Требуется `python3`.

Каждый запуск создаёт новый каталог в `/tmp/opencode` (или в `$TMPDIR`) и
удаляет его при выходе. Внутри каталога задаются изолированные
`XDG_STATE_HOME`, `BEACON_LOG_FORMAT=text` и `BEACON_LOG_LEVEL=debug`.
Переменные `BEACON_STATE_DIR` и `BEACON_PROJECT_ROOT` сбрасываются, чтобы
проверка шла через обычное определение каталога проекта по `cwd` с `.git`.
Внешние токены GitHub не нужны. `GOPROXY` по умолчанию равен `off`, зависимости
берутся из module cache.

Скрипты перезапускаемы: состояние и логи каждого прогона лежат в отдельном
каталоге, предыдущий прогон не влияет на результат. Код выхода `0` означает,
что все проверки прошли. Код `1` означает, что хотя бы одна проверка провалилась.
Скрипт продолжает работу после отдельного провала и печатает все найденные
проблемы, поэтому по выводу видно полную картину за один запуск.

## Переменные окружения проверки

Полная таблица production-переменных лежит в `README.md`, раздел «Конфигурация: переменные окружения». Скрипты проверки используют только часть из них.

| Переменная | Кто задаёт | Назначение |
| --- | --- | --- |
| `BEACON_REPO` | оператор | корень репозитория для скриптов, по умолчанию каталог скрипта; production Go-код её не читает |
| `GO`, `GO_BIN` | оператор | путь к компилятору, затем `PATH` |
| `GOPROXY` | оператор | по умолчанию `off`, зависимости берутся из module cache |
| `TMPDIR` | оператор | база для каталога каждого прогона, по умолчанию `/tmp/opencode` |
| `XDG_STATE_HOME` | скрипт | изолированный каталог состояния внутри каталога прогона |
| `BEACON_LOG_FORMAT`, `BEACON_LOG_LEVEL` | скрипт | `text` и `debug` для читаемых логов прогона |
| `BEACON_STATE_DIR`, `BEACON_PROJECT_ROOT` | скрипт | сбрасываются, чтобы проверить обычное определение каталога по `.git` |

Внешние токены GitHub не нужны. Скрипт подменяет `gh` заглушкой, поэтому `BEACON_GITHUB_TOKEN` и `GITHUB_TOKEN` остаются пустыми. Их значения и риски описаны в центральной таблице.

## Реестр проверок

Для каждой проверки runbook хранит запись покрытия. Запись содержит файлы и функции, которые проверка наблюдает, границы её применения, команду запуска и commit синхронизации. Commit синхронизации задаёт коммит, на котором проверку последний раз сверили с кодом. Новый commit записывают только после новой сверки.

| Проверка | Файлы и функции | Границы | Команда | Commit синхронизации |
| --- | --- | --- | --- | --- |
| `verify-beacon.sh` | `scripts/verify-beacon.sh`, сборка и тесты `./...`, `beacon mcp`, `beacon_stats`, `beacon metrics`, проект-scoped `beacon.db`, логи, `beacon daemon` | весь репозиторий, изолированный каталог прогона, подменённый `gh` без реальных PR | `bash scripts/verify-beacon.sh` | `935201f757d4bca3f357ec4aaa31baafb63e4a66` |
| `verify-daemon.sh` | `scripts/verify-daemon.sh`, `domain.Evaluate`, `orchestrator.Run`, `SaveWatch`, таблица `orchestrator_merges`, вызовы `gh pr merge` | реальный бинарник и store SQLite, заглушка `gh`, PR 901 и 902, без обращения к GitHub | `bash scripts/verify-daemon.sh` | `935201f757d4bca3f357ec4aaa31baafb63e4a66` |

Проверку нельзя считать актуальной, если покрываемый файл изменился после commit синхронизации. Сначала нужно заново сверить проверку с кодом, затем записать новый commit.

Перед каждым выводом о состоянии проверки нужен негативный контроль. Нужно намеренно изменить контролируемый файл, убедиться, что проверка провалилась, откатить правку и только после этого делать вывод. Проверка без негативного контроля не считается доставленной.

## Premise-check до кодового PR

`scripts/premise-check.sh` это локальная проверка перед открытием кодового PR. Она не входит в `verify-beacon.sh` и `verify-daemon.sh` и не запускает Go-тесты, сборку или гейты. Вход это ID карточки, базовая ветка по умолчанию `origin/main` и путь к бэклогу через `--from-backlog` для карточек вне store.

Скрипт печатает `clean` с кодом 0, `landed` или `duplicate` с кодом 1. Отрицательный вердикт несёт полный SHA и номер открытого PR. Карточка без источника, то есть без файла в `docs/tasks/` и без `--from-backlog`, даёт код 2.

Негативный контроль на базе `79dc1694`: `BP-07` даёт `landed`, `TCG-18` даёт `duplicate`, `CLS-01` из бэклога `06-card-closing.md` даёт `clean`.

## Исходы провалившейся проверки

Провал проверки не равен багу в коде. Каждый провал получает один из четырёх исходов с указанием commit, на котором зафиксировано решение.

| Исход | Что произошло | Что делать |
| --- | --- | --- |
| в синхроне | Проверка совпадает с кодом, провал вызван внешним фактором или временным сбоем окружения | Повторить прогон в новом изолированном каталоге и записать commit повторного прогона |
| обновлена | Дрейф проверки: покрываемый файл или обещание изменилось, описание проверки устарело | Сверить модель с кодом, обновить описание и commit синхронизации в реестре, затем повторить прогон |
| баг в коде | Код нарушает обещание, которое проверка продолжает верно описывать | Исправить код, не трогая свойство и границы проверки, записать commit исправления |
| заблокирована | Провал нельзя отнести ни к одному из трёх исходов без данных, которых сейчас нет | Остановить вывод о состоянии, запросить недостающие данные или доступ и записать commit, с которого проверка заблокирована |

Дрейф проверки и баг в коде различают по источнику изменения. Сначала сравнивают покрываемые файлы и обещание с commit синхронизации из реестра. Если обещание изменилось, это дрейф проверки. Если обещание то же, а код перестал его выполнять, это баг в коде.

Запрещено править свойство или границы проверки ради зелёного прогона. Ослабление допускается только как отдельное изменение обещания с доказательством: в commit указано, какое новое обещание заменяет старое и почему оно слабее. Правка, которая снимает проверку без такого доказательства, проваливает карточку.

Перед повторным прогоном после обновления модель проверки переписывают из кода, а не из старого описания. Затем показывают негативный контроль: намеренно вносят контрольную правку в покрываемый файл, убеждаются, что обновлённая проверка всё ещё падает, откатывают правку и только после этого принимают результат. Обновлённая проверка, которая не падает на контрольной правке, не считается доставленной.

## Критерий теста

Тест проверяет поведение, а не реализацию. Решение принимают через две правки. Их делают до сдачи теста в отдельном каталоге и в рабочую ветку не коммитят.

1. Сломать наблюдаемое поведение. Правка меняет результат или тип ошибки, который видит вызывающий. Тест должен стать красным. Зелёный тест после такой правки не защищает поведение. Его переписывают.
2. Заменить внутренности при том же поведении. Правка меняет функцию или вызов и сохраняет наблюдаемый результат. Тест должен остаться зелёным. Красный тест после такой правки привязан к внутреннему вызову. Его удаляют.

Результат обеих правок записывают рядом с тестом. Указывают, что изменили и какой цвет дал тест. Тест без такой записи не считается проверенным.

Ожидаемое значение выводят из требования. Тест не вычисляет ожидаемое тем же кодом, который проверяет. Тест не проверяет данные, которые сам создал. Такой тест проходит при любом поведении.

Если вызывающий ветвится по типу ошибки, тест проверяет тип ошибки. Проверка факта ошибки или текста сообщения не закрывает этот случай.

## Что проверяет `verify-daemon.sh`

Скрипт проверяет мерж на реальном пути: настоящий бинарник `beacon`, настоящий
store SQLite, настоящий движок вердиктов и настоящий `orchestrator.Run`.
Внешний `gh` подменён локальной заглушкой, которая записывает все вызовы в
журнал. Заглушка сообщает `MERGEABLE` и `CLEAN` для PR 901, `DIRTY` для PR 902
и `state=MERGED` после команды мержа. Команда `gh pr merge` принимается только
без `--auto`: заглушка возвращает ошибку GraphQL для `--auto`, потому что в
этом репозитории `enablePullRequestAutoMerge` выключен. Перед запуском демона
скрипт проверяет, что `gh` из `PATH` разрешается в заглушку. Реальные PR не
мержатся и не закрываются.

Порядок проверки:

1. `domain.Evaluate` на снимке `MERGEABLE` и `CLEAN` должен вернуть `ready`.
   Тот же снимок с `DIRTY` должен вернуть `rebase`. Оба Watch сохраняются в
   настоящий store через `SaveWatch` с вердиктом `ready`. Для PR 902 это
   намеренно устаревший вердикт: заглушка сообщает `DIRTY` на момент мержа.
2. Первый проход `beacon daemon --once` должен вызвать
   `gh pr merge 901 --squash --delete-branch` ровно один раз. Для PR 902
   проверенный merger должен отказать до команды мержа и записать в лог
   `PR 902: merge held: mergeable=MERGEABLE mergeStateStatus=DIRTY`.
3. Второй проход не должен повторить мерж. Это проверяет журнал
   `orchestrator_merges` и отсутствие повторных вызовов `gh pr merge`.
4. В логах не должно быть строки `add the --auto flag`. Заглушка возвращает
   ошибку для команды мержа с `--auto`, поэтому проверка ловит откат к старому
   поведению.
5. В таблице `orchestrator_merges` должна быть запись
   `('watch:verify-ready', 1)` и не должно быть записи про
   `watch:verify-conflict`. Запись появляется только после подтверждения
   `state=MERGED`.

## Что означает результат

`PASS go test ./...` говорит о том, что тесты реально выполнились в изолированном
окружении. `FAIL go test ./...` печатает последние строки вывода, по ним видно
падающий тест.

`MCP_OK server=beacon tools=<число из AdvertisedToolNames> stats_keys=<число>` означает, что дочерний процесс
`beacon mcp` ответил по протоколу и что обработчик `beacon_stats` вернул
ожидаемую структуру. Ошибка `MCPFAIL` указывает конкретный шаг протокола.

`state БД доступна: DB_OK quick_check=ok tables=7` означает, что SQLite открыл
файл в режиме только для чтения и нашел таблицы миграций. Если БД отсутствует,
проверка логов и демона тоже провалится: все они работают с одним каталогом
состояния.

`запуск N создал лог ...` означает, что `setupObserve` открыл новый файл для
каждого процесса. Один и тот же файл на два запуска был бы признаком записи
в общий лог.

`демон сделал N циклов` означает, что строка `event=poll_cycle` появилась в
логе работающего процесса. Её пишет `PollCycleDuration` на каждом проходе
`CloseMerged`. Один цикл был бы недостаточен: проверка требует как минимум
второй проход по тикеру.

`LEDGER_OK rows=[('watch:verify-ready', 1)]` означает, что реальный оркестратор
записал мерж в постоянный журнал и что конфликтующий Watch туда не попал.

## Чек-лист «Beacon здоров»

- `go build ./...` и `go test ./...` проходят без ошибок.
- `beacon mcp` поднимается как отдельный процесс и отвечает на `beacon_stats`.
- В проект-scoped каталоге состояния есть читаемая `beacon.db` с таблицами.
- Каждый запуск CLI оставляет новый лог-файл, и `beacon.latest.log` указывает на него.
- `beacon metrics --format json` возвращает JSON со всеми ожидаемыми счётчиками.
- Демон жив и пишет в свой лог как минимум два цикла `poll_cycle`.
- PR с вердиктом `ready` и `mergeStateStatus=CLEAN` получает одну команду
  `gh pr merge --squash --delete-branch`, подтверждает `state=MERGED` и попадает
  в журнал `orchestrator_merges`.
- Конфликтующий PR не получает команды мержа, получает диагностику `merge held`
  и не вызывает ошибок `--auto`.

## Семь вопросов к измерению производительности

При выводе числа о скорости ответь на семь вопросов из
`pstack/skills/benchmark-checklist/SKILL.md:21-27`. Ответ даёт факт прогона, а не
чтение кода. Число без ответа помечается `inconclusive` и в решение не идёт.

| Вопрос | Команда | Признак провала |
| --- | --- | --- |
| 1. Почему не вдвое? Назови лимитер. | Профиль в отдельном прогоне: `perf stat -d <команда>`, `pidstat -u -p <pid> 1`, `strace -c <команда>`, затем свести горячее место к исходнику. Смотреть и генератор нагрузки. | Лимитер не назван, или профилировщик изменил замеряемый путь, или первым насытился генератор нагрузки. |
| 2. Была ли настройка сторон? | Сравнить окружение и флаги: `env \| rg 'GOGC\|GOMAXPROCS\|CGO_ENABLED'`, команды сборки, версии, данные и температуру кэша. | Одна сторона идёт на настройках по умолчанию. Замер сравнивает конфигурации, а не реализации; победителя из него не выбирают. |
| 3. Не ломает ли предел? | Арифметика по замеру: `nproc`, байты в секунду против полосы диска и сети, операции в секунду против цены операции, выигрыш против времени изменённого куска. | Результат выше предела. Тогда замер измерил кэш, no-op или ошибку. |
| 4. Считает ли ошибки? | Счётчик в скрипте или разбор лога: `rg -c 'level=error' <лог>`, проверка кода ответа и содержимого результата. | Скрипт не считает ошибки или проверяет только наличие ответа, а не его правильность. Отклонения бывают быстрыми, таймауты и повторы медленными. |
| 5. Воспроизводится ли? | `for i in 1 2 3 4 5; do <прогон A>; <прогон B>; done`, затем медиана и размах: `python3 -c 'import statistics,sys;v=[int(x) for x in sys.argv[1:]];print(statistics.median(v),max(v)-min(v))' <значения>`. | Меньше пяти чередующихся прогонов A/B/A/B/A на сторону, нет медианы и размаха или разрыв меньше разброса. |
| 6. Имеет ли значение? | `curl -w '%{time_total}\n' <endpoint>` по пользовательскому пути с теми же данными и параллелизмом, затем доля микро-результата в целом. | Есть только микро-число. Функция, занимающая 1% запроса, не ускорит запрос больше чем на 1%. |
| 7. Была ли работа? | Следы внутри таймируемой области: `wc -l <результат>`, доступ к серверу, число записанных строк и прочитанных байтов. | Ленивый код, таймаут или неиспользованный результат. Число описывает работу, которой не было. |

Прогоны чередуют A/B/A/B/A и более, чтобы прогрев, ленивая инициализация и
кэши не давали преимущества одной стороне. Минимум пять чередующихся прогонов
на сторону. Сообщают медиану и размах. Разрыв меньше размаха не считают
различием. При близком результате используют rank-sum test или статистику
самого harness.

В отчёте сначала verdict: быстрее, медленнее, нет измеримого различия или
inconclusive. Дальше число с единицей, числом прогонов, размахом и лимитером.
`inconclusive` обязателен, если не назван лимитер, сторона шла без настройки
или не проверены вопросы 4 и 7. В теле PR оставляют одно основное число,
остальные прогоны и доказательства кладут в приложенный файл.
