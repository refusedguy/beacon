# Разовая настройка репозитория под инженерные скиллы

Эта инструкция задаёт порядок один раз настроить репозиторий, чтобы конфиг трекера, словарь триажа и доменные документы лежали в дереве. Источник: `skills/engineering/setup-matt-pocock-skills/SKILL.md` из `mattpocock/skills@abeeaf9`. Процедура управляется промптом, а не детерминированным скриптом. Четыре фазы идут по порядку: explore, present, confirm, write.

Выполняйте процедуру один раз перед первым использованием инженерных скиллов. Повторите её, когда меняется трекер задач или нужно начать настройку заново.

## Состояние настройки в beacon

Процедура уже применена 22 ноября 2026 года. Изменение вошло в `origin/main` через PR #1858, коммит `1c152a25045337246cdbd3d469006bd1fb0c6c47`. Повторяйте фазы, только если сменился трекер задач или нужно сбросить конфиг.

## Измерение до выбора

До правки на `origin/main` замер снят командой:

```
git grep -i -c -E 'Agent skills|docs/agents/' -- AGENTS.md README.md GLOSSARY.md docs/templates .opencode docs/design docs/adrs internal cmd tools scripts
```

Результат: два совпадения в `docs/adrs/0035-o-claude-code-mechanics-features.md:21` и `:24`. Оба относятся к формату Agent Skills и профилю сабагента, а не к конфигу репозитория. В `docs/agents/` ноль файлов. В `AGENTS.md` раздела `## Agent skills` нет. Новый конфиг поэтому не дублирует существующий, а файлы `docs/agents/` создаются только при реальной потребности.

## Фаза 1. Explore

Прочитайте состояние репозитория и ничего не предполагайте заранее. Список чтения:

- `git remote -v` и `.git/config`: какой это репозиторий и на каком хостинге.
- `AGENTS.md` и `CLAUDE.md` в корне: есть ли один из них и есть ли в нём раздел `## Agent skills`.
- `GLOSSARY.md` и `GLOSSARY-MAP.md` в корне.
- `docs/adr/` и каталоги `src/*/docs/adr/`.
- `docs/agents/`: есть ли результат предыдущей настройки.
- `.scratch/`: признак того, что локальный markdown-трекер уже используется.
- Установленный скилл `triage`: от этого зависит, выполняется ли секция меток.
- Признаки монорепозитория: `pnpm-workspace.yaml`, поле `workspaces` в `package.json`, заполненные `packages/*` с собственным `src/`. Их отсутствие означает один контекст.

## Фаза 2. Present

Кратко перечислите, что уже есть, а чего нет. Затем проходите секции по порядку: одна секция, один ответ, потом следующая. Начинайте каждую секцию с рекомендованного ответа, чтобы его можно было принять одним словом. Пояснение давайте только там, где выбор действительно разветвляется. Секцию пропускайте целиком, если explore уже ответил на вопрос: секцию меток, когда скилл `triage` не установлен, и секцию доменных доков, когда нет признаков монорепозитория.

- Секция A, трекер задач. Укажите, где живут задачи и какие команды использует агент.
- Секция B, словарь меток триажа. Спросите, оставить ли пять канонических меток: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. Переопределения собирайте только если в трекере уже есть другие имена.
- Секция C, доменные документы. По умолчанию один контекст: `GLOSSARY.md` и `docs/adr/` в корне. Вариант с `GLOSSARY-MAP.md` предлагайте только при признаках монорепозитория.

## Фаза 3. Confirm

Покажите на утверждение черновик блока `## Agent skills` и содержимое файлов `docs/agents/*.md`. Дайте возможность отредактировать текст до записи. Блок содержит три подраздела: `### Issue tracker`, `### Triage labels` и `### Domain docs`. Подраздел `### Triage labels` включайте только когда установлен `triage` и выполнялась секция B.

## Фаза 4. Write

Выберите файл для правки. Если есть `CLAUDE.md`, правьте его. Иначе если есть `AGENTS.md`, правьте его. Если нет ни одного, спросите, какой файл создать. Не создавайте `AGENTS.md`, когда есть `CLAUDE.md`, и наоборот.

Если выбранный файл уже содержит блок `## Agent skills`, обновите его содержимое на месте. Не добавляйте второй блок и не затирайте правки в соседних разделах. Это правило обязательно и на фазе confirm, и на фазе write.

Файлы `docs/agents/` создавайте только под реально используемую конфигурацию. Не делайте пустых заглушек. Для GitHub, GitLab и локального markdown-трекера возьмите за основу seed-шаблоны из каталога скилла. Если секция B выполнялась на GitHub или GitLab, создайте в трекере недостающие метки.

## Конфиг трекера в beacon

В этом репозитории трекер задач живёт в дереве. Задачи лежат в `docs/tasks/` как карточки, а доску показывает `beacon board`. В карточке есть поля `Статус`, `Фаза`, `Тип`, `Владелец файлов`, `Зависимости`, `Ссылка`, `Агент` и `Время`. Агент получает карточку через `beacon_task_claim`, и её статус становится `in_progress`. Индекс в state dir пересобирается командой `beacon index build`, вручную его не правят.

## Отображение пяти состояний триажа на статусы карточек

Пять состояний из `docs/tasks/CMx-09.md` отображаются на статусы карточек так:

| Состояние триажа | Статус карточки | Действие |
| --- | --- | --- |
| `needs-triage` | `todo` | Карточка в очереди, оценка ещё не проведена. Агент её не берёт. |
| `needs-info` | `todo` | Карточка ждёт ответа заявителя. В теле карточки фиксируются вопросы и заметки триажа. |
| `ready-for-agent` | `todo` | Карточка полностью описана. Агент берёт её через `beacon_task_claim`, и статус становится `in_progress`. |
| `ready-for-human` | `in_progress` | Агент держит карточку и останавливается с вопросом к человеку. Карточка не переходит в `done`, пока человек не ответит. |
| `wontfix` | `dropped` | Карточка закрыта с причиной. Beacon не запускает по ней работу. |

Категории `bug` и `enhancement` из CMx-09 не являются отдельными статусами. Их пишут в заголовке или теле карточки. Одна карточка несёт ровно одно состояние триажа. При конфликте состояний задайте вопрос владельцу. Статус `done` проставляет Beacon при слиянии PR, агент его не меняет вручную.
