Goal: a run bound to a PR must follow the PR head instead of looping forever on an observed SHA whose checks were cancelled, and merge.max_auto_rebases must take effect without a daemon restart.
Evidence: on 27 Nov 2026 PR 2845 sat in waiting_ci for more than 100 minutes. state.db showed head_sha and observed_sha c61447c while the PR head was already 9cf67fb; every check on c61447c was cancelled, and the last reconcile decision was needs_rebase at 18:27 UTC. Similar stale runs: 2851 observed b9f0c2 while head was a different SHA, 2842 observed 50241a with 64 commits behind main. The reconciler kept ticking but logged no new reconcile decision. handleNeedsRebase returns early at reconcile_observation.go:75 when obs.HasPending() and at line 78 when sameObservation, before NoteObservation, so a new head with any pending check is never stamped and the run keeps comparing against the old SHA. All these PRs were 30 to 64 commits behind main. Separately, cmd/beacon/main.go:332 and 392 read cfg.Merge.MaxAutoRebases only when services are built; config_watch.go restartFields omits that key and the watcher never rebuilds the Reconciler or Policy, so raising merge.max_auto_rebases from 2 to 12 had no effect until the daemon was killed and respawned at 19:05 UTC.
Steps: in handleNeedsRebase, stamp the observation before any early return, so a changed head is recorded even when a check is pending or the run is behind; keep the existing no-rebase guard so a pending check still does not spend a rebase attempt. Add a test that feeds a new head with a pending check and asserts observed_sha moves and the next tick re-evaluates the real head. Add max_auto_rebases to the runtime config path so a change rebuilds or updates the reconciler and policy without restart, or classify it in restartFields and make doctor name the restart explicitly; add a watcher test that changes only max_auto_rebases and asserts the live cap changes. Keep manual mode and the rebase budget semantics unchanged.
Accept: after a PR force-push the run stamps the new head on the next 30s tick and no longer waits on checks from the old SHA, and a live edit of merge.max_auto_rebases changes the effective cap without killing the daemon.
