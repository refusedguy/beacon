Ссылка:

baseline: 2026-11-21, origin/main 0198f6b. `git grep -n 'maxItems\|maxBytes' origin/main -- internal/infra/mcp/tool_list_running.go internal/infra/mcp/tool_get_result.go internal/infra/mcp/tool_stats.go` даёт 0 совпадений. Единственный байтовый предел в OwnerFiles: `failureExcerptLimit = 2048` в tool_get_result.go:70, он режет только excerpt ошибки. Предела на число записей и на весь ответ нет.
Цель: Ограничить число записей и байт в beacon_list_running, beacon_get_result и beacon_stats инструментальной ошибкой с подсказкой сузить запрос.
Контекст: Premise: проверено 2026-11-21, единого лимита байт в трёх обработчиках нет. baseline: `grep -rn 'maxItems\|maxBytes' internal/infra/mcp/tool_*.go` пусто. Плейбук Block после 60 серверов требует, чтобы инструмент сам проверял размер вывода, пример с файлом больше 400 КБ.
Шаги: Ввести константы лимита записей и байт для каждого обработчика. При превышении возвращать isError с текстом, который называет лимит и показывает способ сузить выборку. Сохранить курсор для list_running. Добавить тесты на ровно лимит, лимит плюс одна запись и пустой результат.
Проверка: gofmt чистый. Тесты в CI. Текст ошибки не содержит живого времени и данных прогона.
Приёмка: Пятнадцать параллельных агентов не могут раздуть контекст большим листингом. Негативный контроль возвращает ошибку и предлагает сузить запрос.

## Решение
- Общий помощник `checkResponseLimits` в tool_list_running.go считает записи и байты закодированного structuredContent. При превышении он возвращает AppError с кодом LIMIT_EXCEEDED. go-sdk превращает такой ответ в isError. Текст содержит только имя лимита, число и подсказку, без времени и данных прогона.
- Лимиты: list_running 200 записей и 256 КБ, get_result 200 failedChecks и 256 КБ, stats 200 loadErrors и 256 КБ.
- list_running считает записи по watches и events. Курсор и терминальный вердикт фиксируются только после прохождения лимитов, поэтому отклонённый ответ не съедает позицию в потоке. Подсказка называет filters.verdict, filters.status и cursor.
- get_result проверяет ответ до штампа readAt. Отклонённый ответ не расходует единственный факт чтения обязательства. Подсказка называет watchID с меньшим числом failedChecks и отмечает, что includeChecks не уменьшает ответ.
- stats не имеет аргументов. Подсказка предлагает сократить число или длину loadErrors в снапшоте.
- Тесты в трёх файлах покрывают пустой ответ, ровно лимит, лимит плюс одна запись, байтовый лимит и isError на MCP-сессии. Дополнительно проверено, что отклонённый list_running сохраняет курсор, а отклонённый get_result не штампует readAt.
- gofmt применён к шести файлам. go test и go build локально не запускались по правилам репозитория, проверка идёт в CI.
- PR: https://github.com/refusedguy/beacon/pull/868, ветка fix/t20.
- Первый прогон CI нашёл неиспользуемую переменную `second` в TestListRunningLimitRefusalKeepsCursor. Теперь тест проверяет, что повторный вызов с тем же курсором не возвращает старые события.
