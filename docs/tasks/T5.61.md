# T5.61. E2E регистрация на живом сервисе
Premise: пересмотр 2026-11-21 снял прежний блокер «нужен живой зонд» в части регистрации адаптера. Registration point по ADR 0088 (строка 11) это вызов beacon_watch_pr до фразы `waiting, watchID`. Хендлер internal/infra/mcp/tool_watch_pr.go:646 берёт sessionID из `_meta["ai.opencode/sessionID"]`, строит Subscriber с Adapter и Target из notify (строки 463-473) и сохраняет его внутри Watch через domain.Fanout.Subscribe и SaveWatch. Факт лежит в beacon.db и читается тем же store.Open, что используют driveReadyVerdict и storedObligation. Живой opencode для этой проверки не нужен. Сценарий runLiveMCPCycle в OwnerFiles карточки уже вызывает watch_pr с role=executor. Добавлены три проверки: assert сохранённого Subscriberа (ID=sessionID, Adapter=opencode, Target=sessionID), негативный контроль (card id в _meta отклоняется, значит сохранённый sessionID не подставлен заглушкой) и приёмка (вызов без executor и без _meta по notify.target работает). Часть карточки про config_id и sync остаётся блокированной, и причина не в живом зонде. Продовый код не пишет config_id при watch_pr: WatchPRExecutor.ConfigID (tool_watch_pr.go:225) объявлен opaque и не влияет на сохраняемый Watch. Две функции, которые пишут config_id и binding, store.RegisterExecutor (registry.go:358) и store.WriteWatchBinding (watch_bindings.go:215), имеют ноль вызовов вне тестов. Команда `beacon registry sync` не подключена: в runRegistry только `case "stop"` (registry_stop.go:221), хотя syncRegistry есть в registry_sync.go:174. Для полной проверки нужны правки чужих OwnerFiles: internal/infra/mcp/tool_watch_pr.go (запись config_id при регистрации), internal/infra/store/registry.go и watch_bindings.go (связка executor, config_id и watch), cmd/beacon/mcp.go (композиция зависимостей), cmd/beacon/registry_stop.go (dispatch sync). Также нужна закрытая или явно снятая зависимость T5.55. Статус todo сохранён. Дубль не создан, набор замороженных сценариев не менялся, правка затронула только OwnerFiles карточки и её карточку.
