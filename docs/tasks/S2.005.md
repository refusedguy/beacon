# S2.005. SSE реплей и Last-Event-ID
Premise: проверено 2026-11-21, требование уже в main. PR #410 (W8-A, loopback HTTP + SSE API inside beacon mcp) внёс реализацию в OwnerFiles. В internal/infra/httpapi/server.go handleEvents сначала подписывается на шину через s.events.Subscribe(), затем отдаёт replay-кадры через s.replay(r), а после них live-кадры, пропуская e.ID <= last, поэтому события между reconnect приходят один раз и в порядке. s.replay(r) читает заголовок Last-Event-ID и вызывает events.Since(id), либо параметр replay и вызывает events.Last(n) с потолком maxReplay=1000. EventBus держит ограниченное кольцо последних событий (defaultEventCapacity=256), откуда идёт replay после обрыва; это и есть буфер live событий. В internal/infra/httpapi/client.go openEvents выставляет Last-Event-ID из c.lastID, а consumeEvents обновляет c.lastID из id кадра, так что повторная подписка продолжается с последнего увиденного seq. Приёмка зафиксирована тестами в main: TestEventsReplayAndLive и TestEventsLastEventID в server_test.go проверяют порядок и отсутствие дублей при replay, TestClientEventsParsesFramesAndSendsLastEventID в client_test.go проверяет Last-Event-ID при resubscribe. Раздел «Подтверждение» уже фиксировал, что после W8-A код лежит в main, а PR #394 был DROPped только потому, что HTTP-транспорт тогда отложили (OPEN_QUESTIONS). Восьмой MCP-инструмент не нужен: это отдельный loopback-транспорт, ADR 0094-seven-tools. OwnerFiles не менял, код не писал, gofmt не применял, правка только текстовая. Статус изменён с todo на done.
