# AT-03. beacon_merge_status: причина, по которой зелёный PR не мёржится
Статус: todo
Фаза: research
Тип: task
Владелец файлов: internal/infra/mcp/tool_merge_status.go, internal/infra/mcp/tool_merge_status_test.go, docs/tasks/AT-03.md
Зависимости: нет
Ссылка: docs/research/research-agent-tooling-gaps.md, разделы 3.1 и 4
baseline: `mergePolicyHold` возвращает четыре класса причины (`internal/infra/cibridge/verdict_applier.go:202-226`). `GetResultOutput` не содержит поля с причиной (`internal/infra/mcp/schema.go:130-178`). `beacon_list_running` отдаёт только сырые флаги `MergePolicyOutput` (`schema.go:298-303`).

Цель: показать агенту вычисленную причину удержания мержа и расход лимитов по конкретному Watch.

Контекст: жалоба «бикон их не мерджит». Мерж действительно есть в `applyMerge` (`verdict_applier.go:399-494`). Он не вызывается, когда включён `requireApproval`, не привязан `Merger`, не разрешён `waitFor` или `waitForMain`, либо Watch запаркован по `wakeCap`. Агент видит `verdict=ready` и общую подсказку «the orchestrator merges» (`tool_get_result.go:424-426`). Причины в контракте нет.

Инструмент (сигнатура):

```go
type MergeStatusInput struct {
    WatchID string `json:"watchID" jsonschema:"Watch to inspect; required"`
}

type MergeStatusOutput struct {
    WatchID          string   `json:"watchID"`
    Verdict          string   `json:"verdict"`
    AutoMerge        bool     `json:"autoMerge"`
    MergerBound      bool     `json:"mergerBound"`
    HoldReason       string   `json:"holdReason,omitempty"`
    BlockerID        string   `json:"blockerID,omitempty"`
    WakeUsed         int      `json:"wakeUsed"`
    WakeCap          int      `json:"wakeCap"`
    RebaseUsed       int      `json:"rebaseUsed"`
    RebaseBudget     int      `json:"rebaseBudget"`
    RetryBudget      int      `json:"retryBudget"`
}
```

Где реализовать: новый `internal/infra/mcp/tool_merge_status.go`. Порт `MergeHoldReader` объявить в `internal/infra/mcp/server.go:404-493` рядом с остальными портами. Адаптор в композиционном корне должен вызывать чистую функцию, извлечённую из `verdict_applier.mergePolicyHold` (`verdict_applier.go:202-226`), чтобы не появилась вторая копия правил. Счётчики брать из готовых источников: `wakeCap` (`wake_dispatcher.go:409-417`), `rebaseAttempts` (`bridge.go:607-625`), `remainingRetryBudget` (`tool_get_result.go:995-1022`). `internal/infra/mcp` не импортирует `internal/infra/cibridge` по ADR 0005, поэтому общую функцию вынести в `internal/domain` или `internal/app` и перевести на неё оба вызова.

Шаги: выделить из `mergePolicyHold` чистую функцию `MergeHold(policy, resolver) string`, хранящую текущие строки причин. Перевести `verdictApplier` на неё. Добавить read-порт, отдающий Watch и счётчики. Handler не должен вызывать GitHub и не должен писать состояние. `HoldReason` пустой только когда мерж разрешён. Для Watch без обязательства агента инструмент всё равно отдаёт статус, в отличие от `get_result`.

Проверка: табличный тест на четыре причины из `mergePolicyHold`: `require_approval`, `resolver_unavailable`, `wait_for:REF`, `wait_for_main:REF`, и на пустую причину при `autoMerge=true` и привязанном `Merger`. Тест с подставным счётчиком показывает `wakeUsed=6`, `wakeCap=6` для запаркованного Watch. Регрессионный тест cibridge подтверждает, что вынесенная функция возвращает те же строки, что и старый путь.

Приёмка: агент видит причину удержания и расход лимитов одним вызовом и прекращает ждать мерж, который заблокирован политикой. Логика вердикта не меняется.
