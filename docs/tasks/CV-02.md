# CV-02. Расписка решения в ответе beacon_ack

Premise: проверено 2026-11-22 по `origin/main` `2d34645b`. Источник: OpenHands `src/components/shared/buttons/conversation-confirmation-buttons.tsx:17-21`, `:38-40`, `:48-51` помечает event id как отправленный до ответа сервера и не даёт повторному нажатию изменить решение. В beacon механизм идемпотентности есть, но агент его не видит.

Разрыв: `AckReceipt` в `internal/infra/mcp/tool_ack.go:169-186` содержит `Resumed`, `ResumeRevision`, `Blocked`, `Unblocked` и `DecisionID`. Тип решения и первая победа описаны в `DecisionRegistry` на `:194-210`. Однако `AckHandler.Handle` в `:540-549` возвращает `OKOutput{OK: receipt.OK}`, а `OKOutput` в `internal/infra/mcp/schema.go:417-418` содержит только поле `ok`. Описание инструмента в `internal/infra/mcp/server.go:188-189` обещает idempotent, но не различает первое решение и повтор. Агент, вызвавший `beacon_ack` с `decision=approve`, не может из ответа понять, возобновил ли он агента или получил no-op.

baseline: `rg -n 'resumed|Resumed|AckReceipt' internal/infra/mcp/schema.go` = 0; `rg -n 'OutputType:.*OKOutput' internal/infra/mcp/server.go` = 2, это beacon_ack и beacon_cancel_watch; `rg -n 'Resumed bool' internal/infra/mcp/tool_ack.go` = 1, строка 179.

Цель: Передавать агенту факт применения решения через ответ MCP-инструмента, сохранив форму обычного ack.
Контекст: Источник: docs/research/comp-devin.md, ADR 0058, ADR 0072 и OpenHands `conversation-confirmation-buttons.tsx`. `AckReceipt` уже содержит факт применения решения, но `OKOutput` возвращает только `ok`, поэтому повтор неотличим от первого вызова.
Шаги: Расширить результат `beacon_ack` необязательными полями `resumed`, `resumeRevision`, `blocked`, `unblocked`. Заполнять их из существующего `AckReceipt`, не меняя логику `DecisionRegistry`. Для вызова без `decision` оставить ответ байт-в-байт прежним. Обновить описание инструмента и схему вывода. Добавить контрактный тест на два последовательных вызова.
Проверка: `gofmt -w` на своих .go, тесты в CI. Тест проверяет `resumed=true` при первом approve и `resumed=false` при повторе. Негативный контроль: plain ack не приобретает новых полей.
Приёмка: Агент различает первое решение и повтор по ответу инструмента, не вычитывая Watch через `beacon_get_result`.
