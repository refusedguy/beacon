Цель: Вычислять вердикт и адресатов пробуждения по таблице §4.6 без вызовов GitHub и состояния.
Контекст: WORKER-PROMPT §4.6 задаёт 10 строк с приоритетом сверху вниз: MERGED/CLOSED, head_changed, DIRTY rebase, BEHIND при requireUpToDate rebase, flaky retry с бюджетом, иной FAILURE keep_working, SUCCESS плюс MERGEABLE плюс CLEAN/HAS_HOOKS/BEHIND без requireUpToDate плюс не draft плюс ignoreReviews или reviewDecision не CHANGES_REQUESTED даёт ready, UNKNOWN watching с REST пином, timeout, иначе watching. Там же: одного SHA недостаточно, re-run сбрасывает suite, кэш без валидации состава suites не даёт ready (невариант 10). ADR 0007 и ADR 0008 размещают функцию в domain.
Шаги: 1. Описать входной снимок CI: rollup, mergeable, mergeStateStatus, reviewDecision, draft, headSHA,Used flaky, дедлайн, флаг валидации suite. 2. Реализовать Evaluate(s Snapshot, p Policy) (Verdict, []WakeTarget) строго в порядке приоритетов таблицы. 3. Добавить фикстуры на каждую строку: fork, missing required, SKIPPED/NEUTRAL, ACTION_REQUIRED/WAITING/QUEUED, DRAFT, BEHIND при двух значениях requireUpToDate, merged/closed, rerequest.
Проверка: Табличный юнит-тест ровно по 10 строкам плюс тесты: ready не выдаётся при невалидном составе suite, watching→watching не меняет revision и не будит, флейк-цикл ограничен бюджетом.
Приёмка: Для каждого набора входных данных результат определяется таблицей §4.6, бесконечный retry по flaky невозможен.
