# T3.249. Transcript rotation
Premise: перепроверено 2026-11-21 по свежему origin/main (4729ae3; база ветки fix/ag4 была 389604e, с тех пор только docs-коммиты перепроверок карточек, код internal/infra/wake не менялся, OwnerFiles карточки не тронут). Функционал transcript rotation в main отсутствует, дубль не создан. Проверил wake delivery и envelope по заданию оркестратора. Доставка wake есть: `OpenCodeDeliverer.Deliver` (:104) через `PromptFunc` (:36, :174) и CLI fallback (:195), плюс `ACPAdapter.Deliver` в `internal/infra/wake/acp.go`, который шлёт текст в существующую сессию через ACP. Envelope wake это `Envelope` (:274) и `T202Envelope` (:686): они кладут в текст пробуждения только whitelisted идентификаторы внутри `<beacon-event>`. Ни один из этих путей не создаёт tmux-сессию, не читает pane и не пишет снимок терминала. Уточнение к прежней формулировке: упоминания transcript в deliver.go и deliver_test.go есть, но они про историю, а не про ротацию. Это `HistorySearch` (T3.250, коммит d3ed935) с тестовым именем `transcript.txt` и комментарий `historyANSI` (:1591) про transcript recorder в terminal capture. Ротации, pipe-pane capture, group by 24 pane и atomic temp plus rename в main нет. `git grep -i 'pipe-pane\|capture-pane' origin/main` даёт совпадения только в самих карточках T3.246 и T3.249, в .go-файлах ноль; ни один .go-файл origin/main не упоминает tmux (`git grep -li tmux origin/main -- '*.go'` = 0 файлов). Карточка предписывает запускать rotation сразу после создания tmux, группировать capture по 24 pane и писать atomically temp plus rename, а проверка требует, чтобы файл содержал хвост сессии, а не полный pipe-pane поток. Для этого нужен живой tmux-раннер с pipe-pane capture и замером потока 1000 строк за 2 с. Фейковый PromptFunc такой зонд не заменяет: он проверяет доставку wake-сообщения, а не захват терминала, и в deliver.go нет точки для работы с pane. Ссылка на ADR 0083 не соответствует теме: документ docs/adrs/0083-events.md описывает обработку событий и полное чтение состояния, а не ротацию транскрипта. По архитектуре capture терминала живёт в слое работы с tmux или сессиями, то есть вне OwnerFiles карточки. Перенос логики ротации в deliver.go создал бы дубль чужого слоя и не закрыл бы приёмку про хвост сессии. Статус todo сохранён, карточка остаётся неподтверждённым спайком до появления живого tmux-зонда или расширения OwnerFiles. OwnerFiles не менял, код не писал, чужие файлы, wiring и .beacon не трогал, правка только текстовая.
