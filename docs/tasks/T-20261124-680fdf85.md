Goal: stop worker sessions from re-running MCP config resolution and binary staleness checks. The operator confirmed that the pooled MCP daemon is inherited from the parent session, so registering Beacon MCP config inside a worker session is redundant and causes visible MCP reconnect lines in the TUI when Dispatch spawns a worker.

Root cause: .opencode/plugins/beacon-project/index.js setup() always calls registerBeaconMcp(ctx, root). That calls beaconServerConfig -> beaconCommand in mcp.js, which runs rebuildLocalIfStale. Every new worker session loads the project plugin, so this runs again and OpenCode re-evaluates MCP configuration even though the worker already inherits the parent connection.

Steps:
1. In .opencode/plugins/beacon-project/index.js, before calling registerBeaconMcp, determine the current session agent. Verify the exact API in /tmp/opencode-2.3.2/packages/plugin/src/tui/context.ts and reuse the approach already used in context.js (eventAgent/resolvedAgent). If the agent is worker or contains "worker", skip registerBeaconMcp entirely and pass a no-op registration object with a dispose() method so the existing cleanup still works.
2. Do not break the operator's build/orchestrator session: in those sessions registerBeaconMcp must behave exactly as today.
3. If beaconCommand is also reached from CliStatusSource in worker sessions, guard that path too or disable the status panel for worker sessions. Do not change behavior for the main TUI panel.
4. Add tests: a fake ctx with agent worker results in zero calls to beaconCommand and zero MCP config registrations; a fake ctx with agent build or orchestrator still registers config; cleanup calls dispose on the no-op.
5. Keep file sizes under 350 lines and node --check / node --test green.
6. Open a PR against main and call beacon_watch_pr with the real run ID and PR number. Do not self-merge.

Accept: only .opencode/plugins/beacon-project/**. No Go changes. No task card edits.
