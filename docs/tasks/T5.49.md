# T5.49. Heartbeat и stale в wake
Premise: проверено 2026-11-21 по свежему origin/main (4943794), дубля нет, но задачу нельзя закрыть внутри OwnerFiles. Карточка просит не будить исчезнувшего исполнителя: запрещать wake для записей stale до успешной сверки и записывать отказ в receipt (ADR 0059, ADR 0095). Часть работы уже в main. PR #353 (commit dbee6d7, T5.30) добавил cmd/beacon/registry_sync.go с функциями classifyStale, reconcileStale, syncRegistry и registryWakeAllowed на строке 210. Функция разрешает wake только при status=active, и TestRegistryWakeAllowed проверяет это. Комментарий в начале registry_sync.go прямо называет T5.49 потребителем guard. Однако граница wake находится в другом пакете. internal/infra/mcp/tool_wake.go не читает статус registry ни в одной строке. AgentDirectory на строке 525 отдаёт только Target, Capabilities и WorktreePath, статуса в нём нет. registryWakeAllowed определена в package main и не имеет ни одного вызова вне теста. Поэтому поведение «не будить stale» в main отсутствует, и дубль создать нельзя. Чтобы запрет заработал, нужны порт статуса в tool_wake.go и вызов guard при обработке wake. Интеграция самого инструмента тоже не завершена: AttachWake на строке 1740 не имеет ни одного вызова вне тестов, а NewServer намеренно не регистрирует beacon_wake. Точка подключения лежит вне OwnerFiles карточки. Приёмка требует живого прогона с сервером, SQLite и stale-записью, чтобы прочитать отказ в receipt. На слабом ПК доступны только текст и gofmt, поэтому go test и живой зонд недоступны. Статус todo сохранён, блокер возвращён оркестратору: нужны расширение OwnerFiles до `internal/infra/mcp/tool_wake.go` (AgentDirectory на строке 525, AttachWake на строке 1740), порт статуса registry в этом пакете и вызов `registryWakeAllowed` в обработчике wake, плюс живой зонд с прочитанным receipt. Код не писал, gofmt не применял, дубль не создал, OwnerFiles не менял, правка только текстовая.
