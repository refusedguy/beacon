baseline: dmux классифицирует четыре состояния: `main_dirty`, `worktree_uncommitted`, `merge_conflict`, `nothing_to_merge`, каждое с флагом `canAutoResolve` (`src/utils/mergeValidation.ts:18-23`, `:249-324`). В `origin/main` нет проверки мержа до вызова API: `precheckRepo` хранит только журнал (`internal/app/taskcli/precheck_repo.go:1-18`), а `mcpPrecheck` проверяет источник init-события (`cmd/beacon/mcp.go:479-521`).

Цель: Узнать до мержа, что мешает влить ветку, и отличить состояние, которое можно исправить автоматически, от требующего человека.

Контекст: `validateMerge` в dmux проверяет чистоту основного репозитория и worktree, наличие коммитов и возможные конфликты, затем возвращает `canMerge` и список проблем (`mergeValidation.ts:249-324`). Файлы, созданные самим инструментом, не считаются грязью: список путей задан отдельно (`:31-39`, `:52-69`). Beacon мержит по `verdict=ready` в `internal/infra/cibridge/verdict_applier.go:421-470`, а единственный автоматический rebase выполняется после устаревшей базы (`:441-450`). Проверки dirty и no-op перед вызовом API нет.

Шаги: Добавить в `internal/app/orchestrator/merge_preflight.go` типы проблемы и чистую функцию, которая принимает уже собранные факты о main, worktree, коммитах и конфликтах. Функция не вызывает git. Покрыть тестами грязного main, незакоммиченных изменений, отсутствия коммитов и конфликта. Список путей, созданных beacon, передавать как параметр.

Проверка: Для входа с грязным main и незакоммиченными изменениями функция возвращает две проблемы с `canAutoResolve=true`. Для входа без коммитов и без изменений возвращается только `nothing_to_merge`. Путь из списка инструмента не попадает в `files`. `canMerge` равен true только при пустом списке.

Приёмка: Причина отказа мержа видна до вызова GitHub API. Автоматически исправимые состояния помечены, остальные уходят исполнителю через существующий вердикт.
