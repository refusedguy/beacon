# Q-A-03. Детект устаревшей базы stale_base вместо keep_working
Premise: проверено на origin/main 28db985 до правки: `grep -rn 'stale_base' internal/domain internal/infra/github` пусто. Базовый коммит cae40f5 (RS2-CMP-01) уже добавил PRState.BaseHeadSHA, VerdictRecheck и передачу базового SHA в merge path. Этот путь срабатывает только при мерже, а карточка требует ребаза до мержа, сразу после починки main. Решение использует три факта одного GraphQL батча: mergeStateStatus=BEHIND несет сигнал behindBy > 0, ref.target.oid базовой ветки дает BaseHeadSHA, а statusCheckRollup базы с ChecksKnown=true показывает, что main зеленый. EvaluatePR возвращает VerdictRebase с причиной stale_base_after_main_fix, только когда все три факта есть и чеки PR красные. OwnerFiles не включает graphql.go и tier1.go, поэтому я не добавил новые поля в GraphQL-документ: оба сигнала уже приходят в батче.
baseline: до правки `grep -rn 'stale_base' internal/domain internal/infra/github` = 0 совпадений. После правки `grep -rn 'stale_base_after_main_fix' internal/domain internal/infra/github internal/infra/cibridge` = 1 (константа в verdict.go), `grep -rn 'BaseHeadSHA' internal/domain/verdict.go internal/infra/cibridge/bridge.go internal/infra/github/batch_provider.go` = 10. Я применил gofmt -w к пяти своим .go-файлам, локально go test и go build не запускал, проверка пройдет в CI на PR.
