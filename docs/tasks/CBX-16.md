Baseline: beads: cmd/bd/ready.go:890-895, --explain обязан видеть статус блокировщиков и готовых, и :646-665, один batch-fetch на собранный набор ID; в beacon graphReadyView в cmd/beacon/inspect.go:69-75 даёт только Ready и Source.

Цель: Давать оператору reasons и раздельные списки блокировщиков вместо одного булева признака готовности.

Контекст: Источник, реальный код beads. runReadyExplain в cmd/bd/ready.go:607-665 собирает готовые и заблокированные карточки, зависимости готовых и циклы, затем одним batch-чтением поднимает статусы всех блокировщиков. explainBlockerIDs на :890-919 берёт блокировщиков заблокированных карточек и цели блокирующих зависимостей готовых карточек, дедуплицирует ID и исключает parent-child и related. Причина, почему готовые карточки всё-таки admission-ются, связана с тем, что ready query admitting card у которой блокирующие цели закрыты или закреплены (:893-895). printReadyItemDependencies на :921-933 печатает разрешённые, закреплённые и открытые зависимости отдельными строками. Разрыв в beacon: cmd/beacon/inspect.go:56-75 отдаёт graphReadyView с двумя полями; cmd/beacon/task.go:46-76 не содержит ready или explain, а runTaskWhy печатает только рёбра.

Шаги: Добавить query ready с объяснением в inspect и в task. Собирать ID блокировщиков и целей блокирующих рёбер одним проходом, дедуплицировать. Исключать parent-child и related из объяснения. Выводить JSON с разделами ready и blocked и тремя списками зависимостей. При ошибке чтения зависимостей объяснение остаётся частичным, но не падает.

Проверка: Измеримая. Две готовые и две заблокированные карточки: JSON содержит 4 записи, каждый blocker ID встречается один раз, parent-child и related не попали. Разделы ResolvedBlockers, PinnedDependencies и OpenDependencies заполнены для готовой карточки с закрытым и закреплённым блокировщиком. Число обращений к store для статусов равно одному. Повторный вызов даёт побайтово тот же JSON.

Приёмка: AN-01 владеет самим ready-запросом; здесь только объяснение. AN-02 и CBX-05 не дублируются.
