## Goal
One process owns beacon.lock and the daemon state files, so a CLI invocation cannot clear another process's diagnostics or race the daemon on startup.

## Evidence
From T-5115e3a5: beacon.lock is taken only by serve and standby MCP, while beacon dispatch, beacon control with no daemon, beacon gc and orchestrator MCP tools write without it. Daemon state files have multiple writers with no cross-process coordination. A loser's write error is cleared by the winner.

## Steps
Make serve the single startup owner of beacon.lock and the daemon state files. Write diagnostics with a process key so a losing opener's error survives. Add tests in cmd/beacon/lock_test.go for two openers against one lock and for process-keyed diagnostics.

## Accept
At most one process owns beacon.lock at a time, and a losing opener's diagnostic is not erased by the winner.
