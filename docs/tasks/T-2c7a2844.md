Goal: make an operation_id survive a daemon restart and an eviction so a retried task mutation cannot write twice.
Evidence: internal/infra/mcp/server.go:103,115,159 keeps opJournal in memory with a 128-entry LRU inside one beacon mcp process. A restart loses every cached result; after 128 other operations an older ID is forgotten and a duplicate call writes again. server.go:159-179 stores a result only when err nil, so a concurrent duplicate of a failed operation gets CodeUnavailable 'did not complete' instead of the real error. TaskCreate with no explicit ID at taskcreate.go:143-146 uses a random factory, while MCP single-card create routes through CreateBatch with content-seeded IDs; the two paths can produce different cards for the same request.
Steps: persist operation results in .beacon/state.db keyed by operation_id with the result payload and error text; read that table before running a mutation and return the stored result or error; keep the in-memory journal as a fast path only; make a failed operation store its real error so duplicate callers receive it; make the plain TaskCreate path use the same deterministic ID derivation as CreateBatch so a retry adopts the card. Add tests covering restart, eviction, failed duplicate and concurrent duplicate.
Accept: the same operation_id returns the same result after a daemon restart and 128 intervening operations, and a failed operation is not re-executed on retry.
