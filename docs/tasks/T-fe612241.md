Goal: let the operator ask why one run is in its current state and get a short answer without correlating timeline, decisions, checks and attempts by hand.
Evidence: the operator reads beacon status --snapshot, or the plugin panel, and manually combines timeline events, decision records, check results and attempt counters. The plugin Why line shows only a short reason string. Two audits proposed the same read-only command. All needed data already exists in RunSnapshot at internal/app/snapshot_types.go, including timeline, decisions, checks and attempt counters, plus MergeDecision.Criterion from the decision log.
Steps:
1. Add a pure function in internal/app that takes a run with its events, decisions and checks and returns short text: current state, time in state, last transition, last verdict and criterion, failed check, attempts against budget, and the control action that applies.
2. Expose it as beacon status --explain <run-id> in cmd/beacon/commands.go. Reject an unknown ID with a clear error. Do not change the snapshot wire shape.
3. Add a narrow read port to Store for one run with its events and last decision; avoid scanning all runs. Use the existing 'at' indexes.
4. Reuse the same text in the notification body if a clean seam exists, but do not change notification delivery semantics in this card.
5. Tests for each run state, including a run with a stale reason, one with a failed check, and one with exhausted attempts. Assert the text contains the actionable control verb.
Accept: an operator returning to an alert can decide in seconds without opening the raw snapshot.
