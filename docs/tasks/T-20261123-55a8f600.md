Context: diagnosis found that each `opencode serve` location calls `registerBeaconMcp` once, which reaches `rebuildLocalIfStale` and spawns `bash scripts/build-beacon.sh --hash`. Each `--hash` spawns three bash processes because of the pipeline. With four open locations that is four or more resolutions per server start, and the log shows 357 plugin loads and 155 beacon MCP connects in two hours. The recorded hash currently equals the computed hash, so no `go build` runs, but the subprocess churn is wasteful. OpenCode v2.3.2 has no binary mtime watch, so rewriting the binary does not restart a running daemon; overwriting it is a hazard, not a fix.

Goal: stop spawning bash on every resolution, and make binary freshness explicit.

Steps:
1. In `.opencode/plugins/beacon-project/mcp.js`, make the build-hash check happen at most once per plugin process. Add a module-level guard in `rebuildLocalIfStale` or cache the resolution per project root.
2. Better: replace `currentBuildHash` with a Node-side `statSync` comparison over `.go` files under `cmd`, `internal` and `pkg`, plus `go.mod`, `go.sum` and `go.work`, against the binary mtime. No subprocess on the common path. Rebuild only when a source is newer than the binary.
3. Keep `scripts/build-beacon.sh` as the explicit freshness operation for a manual attach. Do not add any watcher or automatic daemon restart.
4. Update `mcp_test.js`: assert one resolution does not spawn bash more than once, a newer source triggers a rebuild, and a fresh binary does not. Use fake deps with stat data.
5. Run `node --check` and `node --test` on plugin tests. Open a PR and call beacon_watch_pr with the real run ID and PR number.

Check: starting the plugin for four locations spawns no repeated `--hash` subprocesses, and the binary is rebuilt only when a source file is newer.

Accept: do not reintroduce a watcher, reload or daemon restart. Keep files under 350 lines. Do not edit AGENTS.md or another card.
