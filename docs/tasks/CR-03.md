# CR-03. Отменять продолжение передачи по самому свежему событию

Статус: todo
Фаза: P2
Тип: task
Владелец файлов: internal/app/taskcli/service.go, internal/app/taskcli/service_test.go

Цель: Не предлагать агенту повторить шаги передачи, если после них пришло более свежее событие.

Контекст: В OpenRig `packages/daemon/src/domain/startup-orchestrator.ts:65-78` берёт последнее событие по `seq` и разрешает продолжение только когда это `node.startup_failed` для той же сессии с неотправленным контекстом. `:103-117` считает отсутствующую или повреждённую запись признаком незавершённой работы. `:1111-1116` формулирует правило прямо: более новое событие `pending`, `ready` или `failed` поглощает разрешение, в том числе при потере демона во время доставки, поэтому неопределённая доставка не проигрывается вслепую.

В beacon `internal/app/taskcli/service.go:2522-2543` `RecoverHandoff` читает журнал и возвращает все шаги и `LastSeq` без сравнения с более новым событием. `:2803-2806` хранит ответы `continued`, `inconclusive` и `not-continued`, но не делает из них гейт свежести. Дедупликация wake в `internal/infra/cibridge/wake_dispatcher.go:42-69` привязана к обязательству и не закрывает этот случай. CR-03 не предлагает новый журнал: лимиты 16 записей и 64 КБ уже есть в `service.go:2440-2469`.

Шаги: Добавить чистую функцию, которая по `(taskID, journalSeq, latestEventSeq, sessionID)` решает, разрешено ли продолжение. Вызывать её из `RecoverHandoff` и из пути подтверждения. Связать записи журнала с идентификатором сессии получателя. Обработать отсутствующий или повреждённый seq как отказ в продолжении. Сохранить текущий JSON-контракт `HandoffRecovery` как дополнительные поля.

Проверка: Измеримая. Журнал содержит шаги `a` и `b`, затем приходит событие `continued` с большим seq. Функция возвращает `continue=false` и пустой список шагов для продолжения. Перестановка событий или повреждённый seq тоже даёт `continue=false`. При отсутствии более свежего события поведение совпадает с текущим `RecoverHandoff`.

Приёмка: Существующие тесты `service_test.go:1706`, `:1724` продолжают проходить. Ни один вызов `beacon_ack` не меняет контракт: CR-03 меняет только подстановку блока восстановления.
