# T3.383. CLI beacon workload: сводка бэклога оркестратора
Статус: todo
Фаза: P3
Тип: task
Владелец файлов: internal/app/orchestrator/workload.go, internal/app/orchestrator/workload_test.go, cmd/beacon/workload.go, cmd/beacon/workload_test.go, cmd/beacon/main.go, cmd/beacon/catalog.go
Зависимости: 
Ссылка: ADR 0156
Агент: нет
Время: нет
Цель: Дать оркестратору команду beacon workload со сводкой бэклога по вердиктам и проектам.
Контекст: Оркестратор сейчас считает вердикты вручную и держит список Watch в промпте. ADR 0155 вводит blocked Watch, который нельзя смешивать с retry. Контракт MCP ровно на семи инструментах, поэтому сводка живёт в CLI, а не в восьмом инструменте. beacon_get_result остаётся единственным источником вердикта одного Watch.
Шаги: Добавить чистую функцию Summarize в internal/app/orchestrator/workload.go. Она группирует активные Watch по project key и вердиктам ready, retry, blocked, watching и несёт причину, число failedChecks и счётчик uncovered. В cmd/beacon/workload.go сделать команду beacon workload [--project <key>|--all] [--format table|json]. Без флага читать проект текущего cwd, с --all обойти каталоги <XDG_STATE_HOME>/beacon/projects/* и напечатать строку на каждый проект. Зарегистрировать команду в beacon list и в usageText. Команда не обращается к GitHub и не пишет в store.
Проверка: Табличный и JSON-вывод дают одинаковые счётчики. Blocked Watch не попадает в retry и несёт свою причину. --all разделяет два проекта. Подставной раннер GitHub не получает вызовов. На пустом state команда печатает нули и возвращает код 0.
Приёмка: Команда печатает одну строку на проект с четырьмя счётчиками и отдельной причиной blocked. Каталог beacon list содержит workload. Тест контракта MCP по-прежнему видит семь инструментов.

# T3.383. Метрики CI-моста: poll_cycles и verdict_published
Статус: todo
Фаза: P3
Тип: task
Владелец файлов: internal/infra/cibridge/bridge.go, internal/infra/cibridge/metrics.go, internal/infra/cibridge/bridge_test.go
Зависимости: T3.381
Ссылка: ADR 0186
Агент: нет
Время: нет
Цель: Считать циклы опроса и публикации вердиктов без изменения доменной логики.
Контекст: Bridge.Run тикает каждые 5 секунд, publish меняет вердикт только после Transition. ADR 0056 p6 уже хранит wait samples для beacon_stats.
Шаги: Int64Counter beacon.poll.cycles{component=cibridge} и beacon.verdict.published{verdict}; Float64Histogram beacon.ci.refresh.duration в секундах. Записывать в Refresh и publish, не класть headSHA в лейблы.
Проверка: Два тика дают два poll_cycles; устаревший headSHA не публикует вердикт; 15 Watch дают один refresh-спан и один вызов провайдера.
Приёмка: Вердикт публикуется один раз на пару (watchID, revision), а счётчик не растёт при повторном чтении.
