# SB-13. Отдельный исход для таймаута проверки

Статус: todo
Фаза: P1
Тип: task
Владелец файлов: internal/domain/types.go, internal/domain/verdict.go
Зависимости: 
Ссылка: docs/research/comp-swebench.md, раздел 1, строка «Происхождение кода выхода»; исходники swebench/harness/run_evaluation.py и swebench/harness/constants/__init__.py
Агент: нет
Время: нет
Цель: Отличать проверку, которая превысила бюджет времени, от проверки, которая упала по коду выхода.

Контекст: Источник: `swebench/harness/run_evaluation.py:366-381`, `swebench/harness/constants/__init__.py:42-46`. `exec_run_with_timeout` возвращает вывод, флаг таймаута и время работы. При таймауте грейдер дописывает в лог `Timeout error: N seconds exceeded` и поднимает `EvaluationError` (`:375-381`). Маркер `>>>>> Tests Timed Out` входит в список bad codes в `grading.py:130-140`, поэтому такой прогон не даёт карту статусов. В beacon `CheckState` адаптера GitHub перечисляет `SUCCESS`, `FAILURE`, `ERROR`, `PENDING`, `SKIPPED` и `NEUTRAL` (`internal/infra/github/errors.go:304-315`), но не имеет `TIMEOUT`. `domain.Check` (`internal/domain/types.go:155-161`) хранит произвольную строку состояния, а move-логика читает только `Rollup` и `Failures` (`errors.go:324-331`). Таймаут `beacon_wait_result` живёт в `WaitStopReason` (`internal/infra/mcp/tool_wait_result.go:95-154`) и описывает ожидание, а не проверку. Поиск `git grep -c 'CheckTimeout' -- internal` даёт 0 файлов.

baseline: `rg -c 'TESTS_TIMEOUT|Timeout error' swebench/harness/constants/__init__.py swebench/harness/run_evaluation.py` даёт 4 строки; `git grep -c 'CheckTimeout' -- internal` даёт 0.

Шаги: Добавить состояние таймаута и длительность в наблюдение проверки. Записывать их в доказательство и в отчёт stats как отдельный исход. Не смешивать с `WaitStopTimeout` и его кодом 143. Сохранить текущий fail-closed результат: таймаут по-прежнему блокирует merge. Не менять список обязательных проверок и бюджет повтора.

Проверка: Подать две проверки с кодом 1 и с превышением лимита времени. Сейчас обе читаются как обычный failure. Цель: первая даёт `FAILURE`, вторая даёт `TIMEOUT` с записанной длительностью. Негативный контроль: обычный красный чек не получает признак таймаута, а `beacon_wait_result` по-прежнему возвращает свой прежний `reason=wait_timeout`.

Приёмка: Оркестратор видит, что проверку нужно повторить с большим бюджетом, а не чинить код.
