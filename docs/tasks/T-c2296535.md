Goal: stop batch control calls from returning context deadline exceeded after the cancel has already been saved.
Evidence: Control.Cancel at internal/app/control.go:248-284 saves the closed state, then calls Harness.Stop and Workspace.Remove synchronously through bestEffort at lines 17-21 with the caller's context. controlMany at internal/infra/mcp/tool_control.go:105-113 repeats that per id. Each cleanup can do an HTTP stop and a git worktree remove, so a batch of several runs exceeds the MCP client timeout. The operator sees errors such as Post http://127.0.0.1:7432/api/v1/control context deadline exceeded even though the runs are closed. A cancelled run can also leave a worktree with a stale `initializing` git lock when creation was in flight, which then breaks the next dispatch with cannot remove a locked working tree.
Steps: run cleanup with a detached bounded context that does not inherit the RPC deadline, and do not let it hold the control response; make the cancel response return as soon as the state is saved; keep cleanup best effort and logged; add a test that cancel returns before a slow Stop and Remove finish and that SQLite shows the run closed; add recovery for a worktree left with an initializing lock so a later dispatch can remove it; add a batch test with several slow cleanups that completes within the client timeout.
Accept: a batch cancel of several runs returns per-id results without a deadline error, and a cancelled run never leaves a worktree lock that blocks the next dispatch.
