Goal: make cancel and start converge on a clean unlocked workspace without losing committed worker work, and stop batch control calls from returning a deadline error after the cancel is saved.
Evidence: Control.Cancel saves EvCancel first, then calls Harness.Stop and Workspace.Remove synchronously through bestEffort with the caller's context at internal/app/control.go:14-21 and 253-289. A dirty tree makes Remove return WorkspaceConflict, so cancel reports success while leaving edits behind. No cleanup sweep visits a closed run: the daemon lists active runs only and Reconcile returns noop for terminal runs. The next StartOne calls Create, which refuses to clear code edits at git_worktree.go:220-234, then fails before WorkspacePath is set at dispatcher.go:820, so handleStartFailure cannot force-remove. A killed git worktree add leaves an `initializing` lock that no code unlocks, producing cannot remove a locked working tree. Batch control repeats that per id and exceeds the MCP client timeout, so the operator sees context deadline exceeded even though the runs are closed.
Steps: add a single reclaim helper to GitWorktree.Create that runs before addWorktree, unlocks an initializing lock, keeps the card-only-dirt discard, checks HasChanges for unpushed commits, preserves them, removes the tree and deletes the branch only when no commit would be lost; route Control.Cancel cleanup through the same helper on a detached bounded context so a caller timeout cannot cut it short; keep cleanup best effort and logged; add tests for Create after an initializing lock, ForceRemove preserving an unpushed commit, cancel returning before a slow Stop finishes, and a batch cancel with several slow cleanups.
Accept: a batch cancel of several runs returns per-id results without a deadline error, and a cancelled run never leaves a worktree or lock that blocks the next dispatch while unpushed commits stay reachable.
