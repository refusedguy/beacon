Add a live Beacon status panel to the existing project plugin, inside OpenCode only. Do not create a separate TUI. Design for modularity: define a small JS interface `BeaconStatusSource` with `snapshot(): Promise<{active: Run[], recent: Run[]}>` and provide a CLI implementation that spawns the resolved beacon binary with `status` and `status --recent`, parses JSON, and tolerates `null` for an empty list. The UI must depend only on this interface so another source can be added later. Register a TUI slot with `ctx.ui.slot({ append: 'sidebar.content', render })` from `@opencode/plugin/tui`; render active runs with state, task ID, PR number, short SHA, reason, attempt counters and age, then a separator and recently merged or closed runs. Refresh every few seconds via reactive state without calling `ctx.session.synthetic`, so no chat messages are produced. If a server/plugin RPC bridge is needed to reach the CLI, add it in the server part and consume it from the TUI part; verify the exact API against the installed @opencode/plugin sources instead of guessing. Keep the existing plugin behaviour intact. Add a JS test with a fake source covering active, recent, empty and error states. Run node --check and node --test, open a PR and call beacon_watch_pr.
