Goal: stop the repeated unavailable: update branch: head sha didn't match the current head ref failures.
Evidence: for run-8d3ee7356efaed4540ce35cd on PR 2894 the worker commit was 6c88695f and Beacon's own update created merge commit edd60685. The GraphQL mutation returned the pre-update headRefOid. internal/infra/scm/github.go:525-531 writes that stale value into the PR cache, and etagCache.update at github_etag.go:86-94 keeps the old ETag. The next conditional GET gets 304 and serves the stale head, so Observe reports 6c88695f and reconciler.go passes it as expectedHeadOid. GitHub rejects it against the real head edd60685. The same pattern repeats on seven PRs, 2884 and 2890 through 2894. There was no intervening worker push.
Steps: add an invalidate method to etagCache that deletes the entry under the mutex; replace writePRCache after a successful UpdateBranch with cache invalidation so the next Observe performs an unconditional GET and sees the real head; re-read the PR after the mutation before stamping the run so the recorded SHA is the post-update head; add a test that an update followed by Observe returns the new head and that a second UpdateBranch succeeds with the refreshed expectedHeadOid; note but do not change the analogous stale-validator pattern in Merge and unblockWithRebase.
Accept: after a successful automatic rebase the next tick observes the merge commit SHA and no branch update fails with a head mismatch on that PR.
