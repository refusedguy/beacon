# T0.5. Бинарник beacon-gates с тремя гейтами и self-test

Цель: Собрать один stdlib-бинарь beacon-gates с подкомандами layers-list, layers-ast, capabilities и self-test, который находит посаженное нарушение.

Контекст: ADR 0016 выбрал один бинарник beacon-gates, только стандартную библиотеку, коды выхода 0 зелёный, 1 нашёл нарушение, 2 не смог запуститься, и self-test у каждого гейта. ADR 0005 выбрал вариант 2: слои с зависимостями только внутрь, два независимых гейта на импорты через go list и через go/parser, capabilities гейт на os/exec, файлы и сеть вне internal/infra, расхождение двух гейтов считается ошибкой. Отчёт H §3 называет минимальный стартовый набор именно layers-list, layers-ast и capabilities; go-quality заводится следующим шагом и в этой карточке его нет. Отчёт H §4 задаёт механизм self-test: фикстура в os.MkdirTemp, посаженный дефект проходит через боевой analyse, проверяются код finding и file:line, плюс near-miss, который остаётся зелёным. Проверка одного exit code половинчата. Отчёт H §5 требует код 2 при плохом вызове, неизвестной подкоманде и нечисловом флаге, отсортированный реестр через --list, совпадение имени подкоманды с именем каталога и детерминированный вывод. Флаг --list в beacon-gates остаётся человеческим, машиночитаемый JSON относится к beacon. ADR 0010 требует behavior-тест в каждой задаче и посаженное нарушение у гейта.

Шаги:
1. Создать отдельный модуль tools/beacon-gates без внешних зависимостей. Реализовать общий пакет gate с константами Green, Red и Broken и единый main, который разбирает подкоманду, --list, --help и --self-test.
2. layers-list читает матрицу разрешённых рёбер как данные, получает граф через go list -deps -json ./... и находит пакет без строки в матрице и неиспользуемое разрешение. Порядок пакетов в выводе фиксированный.
3. layers-ast проверяет тот же инвариант по import-блокам через go/parser. При расхождении с layers-list гейт возвращает отдельный код ошибки, а не расхождение мнений.
4. capabilities проверяет через AST вызовы os/exec, файловые вызовы, net/http, net.Dial, plugin, reflect и unsafe вне internal/infra. Две таблицы: убывающая baseline со ссылкой на задачу и permanent с обязательной причиной.
5. Для каждой подкоманды написать selftest.go по образцу отчёта H §4. Посаженный os/exec в internal/domain/plant.go ожидает finding CAP-EXEC-IN-DOMAIN на строке 3, near-miss в internal/infra/allowed.go остаётся зелёным. Проверять код finding и file:line.
6. Прогнать self-test на синтетическом дереве. Реальный прогон трёх гейтов на дереве Beacon отложить до появления каталогов из ADR 0007, как указано в отчёте H §3.

Проверка: `cd tools/beacon-gates && go test ./...` проходит. `beacon-gates --list` печатает три подкоманды. Каждая подкоманда с --self-test печатает `self-test passed: N fixtures` и возвращает 0. Негативные вызовы возвращают 2: нет аргументов, неизвестная подкоманда, нечисловое значение флага. Гейт на фикстуре с посаженным os/exec возвращает 1 и печатает путь, строку и правило.

Приёмка: Один бинарник собирается без внешних модулей. Три подкоманды зарегистрированы один раз каждая. Каждый self-test ловит посаженное нарушение по коду и file:line и пропускает near-miss. Коды выхода 0, 1 и 2 проверены тестами. gofmt и go vet чисты.

Гейт: G1. Не закрывает G1 один, а готовит проверку SLO для shadow-прогона. Условия выхода G1 по ADR 0018: не менее 20 реальных PR, ноль расхождений вердикта с фактом gh, SLO в норме.
