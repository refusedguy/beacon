# CR-02. Подключить защиту worktree по владельцу, а не только по точному HEAD

Статус: todo
Фаза: P1
Тип: task
Владелец файлов: internal/infra/worktree/gc.go, internal/infra/worktree/headguard.go, internal/infra/worktree/grace.go
Зависимости:
Ссылка: docs/research/comp-openrig.md, находка 2; https://github.com/mvschwarz/openrig (коммит 6793401380e3685042ffbe8caa686cb9771bf7ca)
Агент: нет
Время: нет

Цель: Не дать сборщику worktree удалить каталог, который всё ещё принадлежит активному Watch или агенту.

Контекст: В OpenRig `packages/daemon/src/domain/seat-delivery-guard.ts:422-441` берёт лизинги по отсортированным ID до любой мутации и заново проверяет цель после ожидания. `:469-474` требует активный лизинг для смены привязки. `packages/daemon/src/domain/node-launcher.ts:216` проверяет доступность адреса, `:227` резервирует поколение владельца, `:351-385` регистрирует сессию, привязку и событие в одной транзакции. Документ `docs/reference/worktree-builds.md:44-45` требует самопроверки, что worktree резолвит пакеты в своё дерево, иначе сборка может быть зелёной по чужим исходникам.

В beacon `internal/infra/worktree/headguard.go:45-103` уже реализованы четыре правила защиты, включая branch, binding и ancestry, и тест `:37` проверяет ancestry. Но `headguard.go:3-4` прямо говорит, что сборщик вызывает `WatchIDForHead` напрямую. `internal/infra/worktree/gc.go:176-220` проверяет только locked, защищённый каталог, точный HEAD и `git status`. `internal/infra/worktree/grace.go:50-73` повторно читает статус через 30 секунд, но не удерживает лизинг владельца.

Шаги: Передать в `Collect` список `WatchAnchor` и `Runner` для merge-base. Вызвать `GuardWatch` вместо прямого `WatchIDForHead` и записать причину из `HeadGuardAnswer.Reason` в `Kept`. Добавить лизинг владельца на время проверки и удаления, чтобы параллельная смена привязки не могла подменить цель. Сохранить отказ от удаления грязных и заблокированных worktree без `--force`.

Проверка: Измеримая. Для worktree, чей HEAD является потомком записанного headSHA Watch, `Collect` возвращает `Kept` с причиной `head_ancestor`; сейчас такой worktree удаляется. При параллельных `Collect` и `handoff` одного каталога удаление не происходит, пока держится лизинг. Все четыре причины из `headguard.go:31-36` встречаются в отчёте соответствующими тестами.

Приёмка: `WatchIDForHead` остаётся быстрым путём точного совпадения внутри `GuardWatch`. При пустом списке Watch сборщик не удаляет ничего, как и сейчас для пустого `closedWatchID` в `internal/infra/cibridge/worktree_scope.go:53-54`.
