Цель: Не оставлять Watch в готовом состоянии после переходной ошибки `gh pr merge`.
Контекст: В корпусе 25 записей `merge_fail` с `TLS handshake timeout`, 8 с другими сетевыми ошибками, 3 с `Merge already in progress`, 1 `RATE_LIMITED` и 32 без поля `error`. `internal/infra/ghci/provider.go:66` и `:208` считают TLS timeout переходной ошибкой и удваивают задержку для чтения PR. Путь merge в `internal/app/orchestrator/orchestrator.go:516` и `internal/infra/github/batch_provider.go:350` такой защиты не имеет: ошибка попадает в `observe.MergeFailure`, и Watch остаётся готовым к merge.
Шаги: Вынести классификацию переходных ошибок в общую функцию рядом с `internal/infra/ghci/provider.go`. В `mergeOne` повторять merge не более N раз с экспоненциальной задержкой и разбросом, только для TLS timeout, EOF, reset, 502 и rate limit. `Merge already in progress` не считать ошибкой и сразу вызывать подтверждение merge. После исчерпания бюджета писать `observe.Event` уровня WARN с полями `watchID`, `pr` и `event=merge_retry_exhausted`. Добавить eval на три сценария.
Проверка: Eval с одним TLS timeout даёт merge_success. Eval с N переходными ошибками даёт `merge_retry_exhausted`. Непереходная ошибка не повторяется.
Приёмка: Переходная сетевая ошибка не оставляет PR видимо готовым к merge без попытки повтора.
