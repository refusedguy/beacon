Context: `merge.max_attempts` in `internal/infra/config/config.go` defaults to 3, and `internal/infra/sqlite/schema.go` stores `max_attempts` with default 3. Runs are closed with `rebase attempts exhausted` after three automatic rebases. The operator sees rebases fire often even when the active PRs touch independent modules, so a busy main branch burns the whole budget for no reason. Requirement from the operator: allow 10 to 15 attempts.

Goal: raise the limit to 12 and stop rebasing a PR when the new base does not affect its scope.

Steps:
1. Raise the default `merge.max_attempts` from 3 to 12 in `internal/infra/config/config.go`, including the zero-value fallback and the default config literal. Confirm the YAML key `merge.max_attempts` already exposes it; if not, add it.
2. Update `internal/infra/sqlite/schema.go` default for `max_attempts` to 12 so existing databases are consistent. Do not rewrite rows in a migration unless a test requires it.
3. In `internal/app/reconciler.go`, inspect the automatic rebase decision. Avoid a rebase when the incoming base change cannot affect the run's scope, or when the PR is already green against its recorded base. Keep the existing behavior for genuine conflicts.
4. Update `internal/infra/config/config_test.go` and `internal/app/reconciler_test.go` with tests that assert the new default, the YAML override, and that an independent base change does not consume a rebase attempt.
5. Run `gofmt -w` on changed Go files and targeted `go test ./internal/infra/config ./internal/app ./internal/infra/sqlite`.
6. Open a PR and call beacon_watch_pr with the real run ID and PR number.

Check: a fresh config reports 12 attempts, a YAML override still wins, and a run whose scope is untouched by new main commits keeps its rebase count at zero.

Accept: do not change the skip reasons or the control actions. Keep files under 350 lines. Do not edit AGENTS.md or another card.
