# T3.236. Scoped subscription и ограничение размера ответа
Статус: todo
Premise: проверено 2026-11-21, функционал в origin/main отсутствует и не реализуем локально в OwnerFiles. `internal/infra/mcp/server.go` содержит только регистрацию ровно восьми инструментов по ADR 0094: beacon_watch_pr, beacon_wait_result, beacon_get_result, beacon_list_running, beacon_ack, beacon_cancel_watch, beacon_stats, beacon_defer_wiring. Инструмента подписки на поток или t3_thread_read там нет, как нет ограничения ответа ~30000 символов, полей earlierPosition/hasMore, provenance createdBy/creationSource и разделения actor/ingress. Поиск по origin/main нашёл эти имена только в текстах карточек. Родные реализации того же требования в main отказаны: S4.012 (чтение thread по курсору, OwnerFile internal/infra/server/http/history.go) и S4.014 (происхождение сообщений, internal/domain/provenance.go) имеют статус dropped после PR #394: чтение по курсору дублирует beacon_list_running cursor (ADR 0025, 0094), http/history.go отсутствует и HTTP отложен, provenance.go отсутствует, actor/ingress не входят в контракт инструментов (ADR 0094, ADR 0086). Проверка карточки требует живого probe t3_thread_read (обрезание около 30000 символов, earlierPosition или hasMore как точка продолжения, createdBy/creationSource, actor отдельно от ingress). Такого внешнего инструмента и живого потока в этой среде нет: доступны только правка текста и gofmt на слабом ПК. Добавить девятый инструмент в server.go нельзя без нарушения контракта восьми инструментов ADR 0094, а переиспользование курсора beacon_list_running не закрывает фильтрацию по потоку, лимит размера и provenance. Не стал писать спекулятивный код без живой проверки: это повторило бы снятый PR #394 и сломало бы контракт. Статус todo сохранён, карточка остаётся непроверенным спайком до появления живого t3_thread_read probe; блокер возвращён оркестратору. OwnerFiles не менял, код не писал, gofmt не применял, дубль не создал, правка только текстовая.
Блокер: требование карточки не закрывается в контракте восьми инструментов ADR 0094. Проверка просит живой t3_thread_read с обрезкой ответа около 30000 символов, точкой продолжения earlierPosition или hasMore, полями createdBy и creationSource и разделением actor от ingress. Такого имени нет в реестре ADR 0094. Девятый инструмент требует отдельного ADR или решения владельца, как сказано в разделе «Приёмка» ADR 0094. Перенос этих полей в существующие инструменты выходит за OwnerFiles карточки: схемы лежат в schema.go, обработчики в tool_get_result.go и tool_list_running.go, а карточка владеет только server.go. Курсор beacon_list_running продолжает только события Watch по ADR 0025 и не даёт фильтрации по потоку, лимита размера или provenance. Задачи S4.012, S4.014 и S6.003 с тем же требованием имеют статус dropped после PR #394. Без живого probe любой код стал бы спекулятивным дублем снятого PR. Нужно решение владельца: отдельный ADR на девятый инструмент либо переформулировка проверки под поведение восьми инструментов. OwnerFiles и код не менял, добавил только этот блокер.

Цель: Отдавать клиенту только состояние его обязательствов и укладывать ответ в предел модели.
Контекст: T3 подписки отдают состояние одного thread; t3_thread_read останавливается около 30000 символов и возвращает earlierPosition или hasMore.
Шаги: Описать фильтрацию по потоку, курсор, ограничение размера и provenance createdBy и creationSource.
Проверка: Клиент одного потока не получает историю всех потоков; большой ответ имеет явную точку продолжения.
Приёмка: Actor и ingress разделены в каждом результате.
