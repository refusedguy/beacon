baseline: в dmux три режима запуска (`src/utils/hooks.ts:142`, `:209`, `:260`), два из них с таймаутом 30 секунд. В `origin/main` один режим `exec.Command(...).CombinedOutput()` без таймаута (`internal/infra/hookrun/hookrun.go:9-15`).

Цель: Дать каждому событию выбрать режим по смыслу: фоновое уведомление, проверка с таймаутом или гейт с живым выводом.

Контекст: `triggerHook` в dmux запускает `spawn` с `detached: true`, `stdio: 'ignore'` и `unref`, поэтому операция не ждёт скрипт (`hooks.ts:166-200`). `triggerHookSync` использует `execSync` с `timeoutMs` по умолчанию 30000 и возвращает `success`, `output`, `error` (`hooks.ts:209-252`). `triggerHookWithProgress` читает stdout и stderr по строкам, вызывает `onProgress`, завершает процесс по `SIGTERM` и защищает результат флагом `settled` (`hooks.ts:260-389`). Beacon запускает все сценарии одного события последовательно и синхронно через `hookrun.Run` (`service.go:138-143`), при этом таймаут, детач и потоковый вывод отсутствуют.

Шаги: Описать в `internal/infra/hookrun/modes.go` три явных режима и их контракт результата. Сделать запуск через внедрённый раннер, чтобы тесты не поднимали процессы. Покрыть тестами превышение таймаута, порядок строк прогресса и то, что фоновый режим возвращает управление до завершения скрипта. Не трогать `service.go` в этом PR и передать точку подключения владельцу через `beacon_defer_wiring`.

Проверка: Скрипт, спящий 2 секунды, в фоновом режиме не задерживает вызов. В синхронном режиме с лимитом 200 мс вызов возвращает ошибку за время меньше одной секунды. В режиме гейта тест видит все строки вывода и один вызов `SIGTERM`.

Приёмка: Каждое из событий `claimed`, `unblocked`, `closed` может выбрать режим без правки `hookrun`. Ошибка гейта имеет диагностику и не оставляет процесс после таймаута.
