Context: `.beacon/config.yaml` had `on_base_red.mode: notify_orchestrator`. In that mode `internal/app/base_red.go:92-95` only calls `r.notify` and never `ensureFixer`, so `max_fix_attempts: 2` is unused. With no Telegram notifier configured, `notify` is a no-op and the operator receives nothing. PR #2332 (the fix for the broken TUI panel) was blocked with `base_red` when main went red from two funlen lint errors, and nobody was told. The operator requires that a red base branch automatically spawn a fixer agent on main.

Goal: red base always produces a fixer run, never a silent block.

Steps:
1. Change the default `on_base_red.mode` in `internal/infra/config/config.go` from `notify_orchestrator` to `spawn_fixer`. Keep `notify_orchestrator` as an explicit opt-in.
2. Update `.beacon/config.yaml` in the repo if a checked-in example exists. The runtime config in this environment is already set to `spawn_fixer`.
3. In `internal/app/base_red.go`, make the `notify_orchestrator` branch also emit a visible parent-session notification when the notifier is absent, so a silent block is impossible. Keep the fixer path unchanged.
4. Tests in `internal/app/base_red_test.go`: default config spawns a fixer on red base; explicit `notify_orchestrator` still notifies and does not spawn, but produces a session notification; a red base with no notifier never leaves a silent blocked run.
5. Run `gofmt -w`, targeted `go test ./internal/app ./internal/infra/config`.
6. Open a PR and let the reconciler handle it. Do not self-merge.

Check: when a required check fails on main, a fixer run starts automatically within one reconcile tick and the incident records its run ID.

Accept: do not change verdict rules or shell guard. Keep production files under 350 lines. Do not edit AGENTS.md or another card.
