baseline: на базе 2d34645b advertised-набор содержит 10 инструментов (`internal/infra/mcp/contract_test.go:32`). Read-инструментов с входом `repo` и `pr` нет. Значения полей PR уже читает `internal/infra/ghci/provider.go:235-284`. golden `tools/list`: 19680 байт, SHA `1a0bf147…`.

Цель: дать агенту read-инструмент, который возвращает состояние PR и список проверок по `repo` и `pr` без регистрации Watch.

Контекст: агент сегодня вызывает `gh pr view` и `gh pr checks` руками (`internal/infra/ghci/provider.go:237-266`). Единственный путь получить те же данные через MCP это `beacon_watch_pr`, который создаёт Watch и обязательства. Для диагностики чужого PR это лишний побочный эффект. Провайдер `domain.CIProvider` уже умеет делать один batched read.

Инструмент (сигнатура):

```go
type PRStatusInput struct {
    Repo string `json:"repo" jsonschema:"owner/name; required"`
    PR   int    `json:"pr" jsonschema:"pull request number; required"`
}

type PRStatusCheck struct {
    Name       string `json:"name"`
    State      string `json:"state"`
    Conclusion string `json:"conclusion,omitempty"`
    Required   bool   `json:"required"`
    DetailsURL string `json:"detailsUrl,omitempty"`
}

type PRStatusOutput struct {
    Repo             string           `json:"repo"`
    PR               int              `json:"pr"`
    HeadSHA          string           `json:"headSHA"`
    BaseRefName      string           `json:"baseRefName"`
    State            string           `json:"state"`
    IsDraft          bool             `json:"isDraft"`
    Mergeable        string           `json:"mergeable"`
    MergeStateStatus string           `json:"mergeStateStatus"`
    ReviewDecision   string           `json:"reviewDecision"`
    Checks           []PRStatusCheck  `json:"checks"`
}
```

Где реализовать: новый `internal/infra/mcp/tool_pr_status.go`. Порт `domain.CIProvider` уже объявлен в `Dependencies.CI` (`internal/infra/mcp/server.go:404-406`). Дескриптор в `toolDescriptors` рядом с `beacon_list_running` (`server.go:178-186`). Output DTO в `schema.go` рядом с `ListRunningOutput` (`:369-381`). Регистрация `attachPRStatus` по образцу `attachListRunning` (`server.go:701-716`). Остальные точки касания перечислены в документе исследования, раздел 6.

Шаги: описать handler, который проверяет `repo` и `pr` на границе, вызывает `deps.CI.PRState(ctx, repo, pr)` и проектирует `domain.PRState` (`internal/domain/types.go:526-541`) в выходной DTO. Переименовать `HeadRefOid` в `headSHA` только на границе. Собрать `Checks` из `map[string]domain.Check` в отсортированный по имени срез. Не писать ни одного состояния, не создавать Watch и не вызывать `os/exec` в `internal/infra/mcp`. Покрыть тестом на подставном `CIProvider`: пустая карта проверок, проверка с `Required=false`, ошибка провайдера. Общие константы контракта обновлять в том же PR, который сериализует владелец.

Проверка: в CI зелёный контрактный тест с новым размером и SHA `tools/list`, полученным замером в GitHub Actions. Тест обработчика показывает, что ответ содержит ровно поля `domain.PRState`, `checks` отсортированы по имени, а повторный вызов с тем же `repo` и `pr` не создаёт Watch. Число Watch в хранилище до и после вызова одинаково.

Приёмка: агент получает `headSHA`, merge-поля и проверки чужого PR одним вызовом MCP. Команды `gh pr view` и `gh pr checks` для диагностики больше не нужны. Побочных записей в состояние Beacon нет.

Ограничение: инструмент не заменяет Watch как источник вердикта. Проверки в ответе отражают последний read провайдера, а не зафиксированный в Watch снимок.
