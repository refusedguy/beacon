# Контракт проверки правил

Этот файл задаёт семантику вердикта rules gate в Beacon и служит каноническим источником. Workflow, навыки и примеры обязаны следовать этому файлу. Если пример расходится с контрактом, верен контракт.

Контракт опирается на ADR 0240, ADR 0235, ADR 0236 и ADR 0237. Код Harbor в Beacon не переносится.

## Вердикт и блокировка

Rules gate возвращает ровно один вердикт: `PASS`, `WARN`, `FAIL` или `BROKEN`.

`PASS` означает, что найдено хотя бы одно применимое правило, проверка прошла по изменённым файлам или diff, и явных нарушений нет.

`WARN` означает, что проверка не нашла применимых правил, доказательства неоднозначны, изменённых файлов нет или отсутствует дополнительный файл правил. Вердикт `WARN` не блокирует.

`FAIL` означает, что изменённые файлы или diff явно нарушают жёсткое правило. Вердикт `FAIL` блокирует.

`BROKEN` означает, что сам инструмент не смог запуститься или завершить работу: ошибка старта, неизвестная подкоманда, некорректный флаг, внутренний отказ. Код выхода `2` по ADR 0016 всегда даёт `BROKEN`. Это не нарушение правила и не неопределённое сканирование. Вердикт `BROKEN` блокирует.

`FAIL` и `BROKEN` дают `blocking: true`. В вердиктах `PASS` и `WARN` поле `blocking` равно `false`.

Отказ инструмента нельзя выдавать за `WARN` или `PASS`. `WARN` не должен скрывать красную проверку. Команда с кодом выхода `2` даёт вердикт `BROKEN` и блокирует проверку.

Проверка правил не заменяет обзор кода и verify.

## Отдельная обязательная проверка

Отказ инструмента должен падать отдельной обязательной проверкой в CI. Для неё нужна отдельная джоба, которая запускает rules gate и передаёт код выхода без изменений. Код `2` делает джобу красной.

Джоба не должна использовать `continue-on-error: true`, `|| true`, условие `if:` с пропуском при ошибке или преобразование кода `2` в `WARN`. Для кодового PR результат проверки не должен фиксироваться как `skipped` или `neutral`. Джобу не объединяют с общей джобой `gates`, чтобы зелёные проверки не перекрывали отказ инструмента.

Пропуск проверки для PR только с документацией задаётся отдельно через `paths-ignore`. Он не должен скрывать `BROKEN` в кодовом PR.

Порог находок сохраняется. Если сканирование видит меньше находок, чем объявленный порог, проверка добавляет `SCAN-BLIND` и возвращает красный результат. `SCAN-BLIND` добавляется после подавления исключений, поэтому исключение не может его убрать. `SCAN-BLIND` не является `WARN`.

## Привязка нарушений

Каждое блокирующее нарушение привязано к тексту правила и к конкретному файлу или фрагменту diff. Правило, которое звучит как предпочтение, слишком обще или не проверяется уверенно по diff, не поднимается выше `WARN`. Отсутствующие дополнительные файлы правил и частично настроенная иерархия правил дают `WARN`, а не `FAIL`.

## Состав отчёта

Отчёт содержит разделы в следующем порядке:

- общий вердикт
- число проверенных файлов
- результаты проверки правил
- блокирующие нарушения
- предлагаемые исправления
- предлагаемые обновления правил

После человекочитаемого отчёта идёт ровно один финальный fence `aif-gate-result` с JSON. Оркестратор читает последний fence в выводе.

## Машиночитаемый результат

Схема полей определена в ADR 0237. Обязательные поля: `schema_version` со значением `1`, `gate` со значением `rules`, `status`, `blocking`, `blockers`, `affected_files` и `suggested_next`.

Поле `status` и человекочитаемый вердикт используют один верхний регистр: `PASS`, `WARN`, `FAIL`, `BROKEN`. Вердикт отчёта задаёт значение поля напрямую: `PASS` даёт `PASS`, `WARN` даёт `WARN`, `FAIL` даёт `FAIL`, `BROKEN` даёт `BROKEN`. Так machine и human отчёты перечисляют одинаковые значения в одном регистре. ADR 0237 задаёт строчные `pass`/`warn`/`fail`; контракт приводит их к верхнему регистру, добавляя `BROKEN` для отказа инструмента по коду выхода `2` (ADR 0016).

В `blockers` попадают жёсткие нарушения, которые дают вердикт `FAIL`, и отказ инструмента, который даёт вердикт `BROKEN`. Каждая запись содержит `id`, `severity`, `file` и `summary`. Для `BROKEN` запись использует `file` со значением `.` и описывает причину отказа, например код выхода `2`. В `affected_files` попадают проверенные или изменённые пути. Поле `suggested_next` содержит разрешённую команду Beacon или `null`, когда подходящей команды нет.

Пример для вердикта `WARN`:

```aif-gate-result
{
  "schema_version": 1,
  "gate": "rules",
  "status": "WARN",
  "blocking": false,
  "blockers": [],
  "affected_files": [],
  "suggested_next": null
}
```

Пример для вердикта `FAIL`:

```aif-gate-result
{
  "schema_version": 1,
  "gate": "rules",
  "status": "FAIL",
  "blocking": true,
  "blockers": [
    {
      "id": "R-LAYER",
      "severity": "error",
      "file": "cmd/beacon/newcmd.go",
      "summary": "Правило 'cmd/beacon: без os.ReadFile, os.WriteFile, net/http, os/exec' нарушено импортом os/exec"
    }
  ],
  "affected_files": ["cmd/beacon/newcmd.go"],
  "suggested_next": null
}
```

Пример для вердикта `BROKEN`:

```aif-gate-result
{
  "schema_version": 1,
  "gate": "rules",
  "status": "BROKEN",
  "blocking": true,
  "blockers": [
    {
      "id": "R-TOOL-BROKEN",
      "severity": "error",
      "file": ".",
      "summary": "rules gate завершился кодом 2: неизвестная подкоманда"
    }
  ],
  "affected_files": ["AGENTS.md", "docs/RULES-CHECK-CONTRACT.md"],
  "suggested_next": null
}
```

## Граница только для чтения

Проверка правил не изменяет файлы правил и исходники. Отсутствующие дополнительные файлы правил оставляют вердикт `WARN`. Обновление правил идёт через канонические места правил, то есть AGENTS.md и ключ `beacon/survival-rules`, а не через саму проверку.
