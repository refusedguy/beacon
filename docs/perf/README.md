# T4.2. SLO производительности Beacon

Документ фиксирует метрики, методику замера и таблицу результатов. Числа в таблице результатов на момент написания не измерены. Локальные тесты, сборки и замеры как гейт запрещены ADR 0022, поэтому таблица заполняется запуском `tools/perf/measure.sh` в CI после появления демона. Пустые ячейки обозначены прочерком и не являются нулевыми измерениями.

Дата создания документа: 2026-11-19. Карточка: `docs/tasks/T4.2-performance-slo.md`. Ссылка по правилам ADR 0020: ADR 0013.

## Конфигурация замера

Скрипт печатает фактические значения в stderr при каждом запуске и пишет их в `<рабочий каталог>/mode-*/run-*/meta.txt`.

- Дата и время: метка времени в каждой строке таблицы, UTC.
- Контрольная версия: короткий хеш `git rev-parse --short HEAD`, печатается как `commit=`.
- Go: версия из `go version`, `GOOS` и `GOARCH` из `go env`. На момент написания `go.mod:3` задаёт `go 1.26.0`. Фактическая версия toolchain на машине замера может отличаться и берётся из вывода команды.
- Сборка: флаги из ADR 0016, бинарник собирается скриптом, если `PERF_BIN` не указывает готовый файл.
- Фикстуры GraphQL: `internal/infra/github/testdata/pending-states/tier1.json` по умолчанию. Тело содержит `rateLimit.cost`, стоимость одного ответа. Выбор меняется переменной `PERF_FIXTURE`.
- События CI: копия `tests/adapter/fixtures/events.jsonl` в каталог состояния. Меткой события служит поле `at`, `eventAt` или `timestamp`, при их отсутствии mtime файла.
- Seed счётчика: `GET /rate_limit` локального сервера возвращает ненулевое `used`, по умолчанию 137. Ненулевое значение нужно, чтобы проверить условие ADR 0013: после рестарта счётчик не начинается с нуля.
- Режимы: 15, 30 и 60 Watch, по три прогона каждый, девять строк.
- Окно: 2000 мс прогрева и 5000 мс наблюдения на прогон, меняется переменными `PERF_SETTLE_MS` и `PERF_OBSERVE_MS`.
- VmHWM: максимум выборок поля `VmHWM` из `/proc/<pid>/status` за окно наблюдения, один процесс на прогон.
- p95: nearest-rank, 95-й процентиль по разницам между `at` квитанции `outcome=posted` и меткой события с тем же `obligationID`. Квитанции `transport-failed`, `indeterminate` и строки без метки события отбрасываются. Повтор по паре `obligationID`, `attempt` учитывается один раз.
- Латентность модели: отдельный файл `model-wake.jsonl` с полями `wokeAt` и `eventAt`. Скрипт печатает её в `meta.txt` как `model_wake_p95_ms` и в общую таблицу не включает.
- Поинты: сумма `rateLimit.cost` из `graphql-costs.jsonl` сверяется с приростом `used` в снимках `rate-limit.json`. Допуск расхождения 2 поинта на стартовую синхронизацию. Величина `поинтов/час` это экстраполяция суммы на длительность окна наблюдения, а не часовой прогон.
- Рестарт: процесс убивается после окна наблюдения, поднимается повторно, измеряется время до появления файла `ready`. Предел 5000 мс.
- `gh --watch`: проверка `pgrep -fc 'gh pr checks --[w]atch'` во время прогона. Квадратные скобки в шаблоне не дают команде найти саму себя.

## Отчёт по SLO

После таблицы результатов скрипт печатает сводный отчёт по порогам из раздела «Пороги SLO». Отчёт есть и в stdout, и в файле `<рабочий каталог>/slo-report.txt`, чтобы CI мог приложить его к PR.

В отчёте пять строк по числовым метрикам. В каждой строке порог, худшее значение по всем прогонам и статус. Худшее значение это максимум по прогонам для VmHWM, p95 доставки, поинтов в час, рестарта и `gh --watch`. Статус метрики вычисляется из худшего значения и того же порога, который проверен в строке таблицы. Статус принимает одно из трёх значений: `PASS` когда порог соблюдён, `FAIL` когда нарушен, `BLOCKED` когда замер не состоялся и числового значения нет.

Итоговая строка `Итог` равна `PASS`, только когда все прогоны прошли пороги. Наличие строки `BLOCKED` даёт `BLOCKED`, нарушение порога даёт `FAIL`. Сверка `rateLimit.cost` с `used` и продолжение счётчика после рестарта не имеют числовой колонки в отчёте. Они влияют на статус строки таблицы, а через него на итог.

Пороги и логика сравнения заданы константами в начале `tools/perf/measure.sh`: `HWM_LIMIT_KB`, `P95_LIMIT_MS`, `POINT_LIMIT`, `RESTART_LIMIT_MS`. Значение `POINT_TARGET` равно 360 и остаётся целью, а не жёстким порогом. Латентность пробуждения модели хранится отдельно и в отчёт по SLO не входит.

Живой прогон в этой среде недоступен по ADR 0022. Поэтому значения в таблице результатов остаются прочерками до запуска в CI. Контракт замера это пороги, формат артефактов и логика сравнения. Этот контракт проверяется режимом `--self-test` и кодом скрипта без живых замеров.

## Как запустить

```sh
bash tools/perf/measure.sh --self-test
bash tools/perf/measure.sh
```

Первая команда проверяет функции на синтетических артефактах во временном каталоге. Она не трогает репозиторий и не собирает бинарник. Вторая команда собирает бинарник, поднимает фикстурный сервер на `127.0.0.1`, проводит девять прогонов и печатает таблицу. Сырые данные остаются в каталоге под `/tmp/opencode`, путь печатается в конце. Код выхода 2 означает blocked или нарушение порога.

Скрипт ожидает от рантайма одного процесса с режимом нагрузки. По умолчанию он ищет подкоманду `mcp` в каталоге `beacon list --format json` и запускает её с переменными `XDG_STATE_HOME`, `BEACON_PERF_WATCHES`, `BEACON_GRAPHQL_URL` и `BEACON_PERF_SEED_USED`. Если подкоманды нет, можно задать команду через `PERF_LOAD_CMD`. Она получает `PERF_WATCHES`, `PERF_STATE_DIR` и `PERF_GRAPHQL_URL`. Рантайм обязан писать артефакты, перечисленные в заголовке скрипта, и создавать файл `ready` при готовности.

Контракт файлов состояния:

- `receipts/<obligationID>.<attempt>` одна строка JSON вида `{"obligationID":"...","attempt":1,"outcome":"posted","at":"..."}`, формат T3.6 и ADR 0014.
- `events.jsonl` строки с `obligationID` и меткой времени, формат T3.2.
- `graphql-costs.jsonl` строки `{"at":"...","cost":1}`, стоимость берётся из `rateLimit.cost`.
- `rate-limit.json` снимки `{"at":"...","used":137}`, источник `GET /rate_limit`.
- `points.json` снимки `{"at":"...","used":N}` счётчика ADR 0013 до и после рестарта.
- `model-wake.jsonl` строки `{"obligationID":"...","eventAt":"...","wokeAt":"..."}`, только для отдельной метрики.

## Фактические гистограммы в runtime_stats

MCP-сервер сохраняет снимок метрик в `runtime_stats` после каждого цикла. Гистограммы доступны через `beacon inspect`. Команда снятия:

```sh
.opencode/bin/beacon inspect --json | jq '{histograms: .runtimeStats.histograms, poll_cycles_total: .runtimeStats.poll_cycles_total, merge_attempts_total: .runtimeStats.merge_attempts_total, active_watches: .runtimeStats.active_watches, pollerActive: .runtimeStats.pollerActive}'
```

Источник чисел: `docs/research/research-perf-gaps.md`, замер 2. Таблица фиксирует то, что уже работает в рантайме. Она не заполняет девять строк раздела «Таблица результатов» и не меняет пороги T4.2.

| Дата | Гистограмма | Команда | count | sum, с | Среднее, с | Медиана | p95 |
| --- | --- | --- | ---: | ---: | ---: | --- | --- |
| 2026-11-22T12:35:34Z | `poll_cycle_duration_seconds` | `.opencode/bin/beacon inspect --json` | 520 | 605.628146453 | 1.165 | (1, 5] мс | (5, 30] с |
| 2026-11-22T12:35:34Z | `merge_duration_seconds` | `.opencode/bin/beacon inspect --json` | 39 | 308.178452428 | 7.90 | (5, 30] с | (5, 30] с |

Гистограмма хранит накопленные счётчики по бакетам, а не отдельные значения. Поэтому медиана и p95 в таблице заданы интервалом между границами соседних бакетов. Точного перцентиля по этим данным нет. Для `poll_cycle_duration_seconds` 154 из 520 циклов попадают в ≤1 мс, 271 в ≤5 мс, 477 в ≤5 с, 519 в ≤30 с. Отсюда медиана в (1, 5] мс и p95 в (5, 30] с. Для `merge_duration_seconds` все 39 наблюдений больше 5 с, 38 из них попадают в ≤30 с, поэтому и медиана, и p95 лежат в (5, 30] с. Среднее равно sum, делённому на count, и не зависит от ширины бакетов.

В том же снимке `wake_duration_seconds` имеет count 1 и sum 0.095488737 с. Одно наблюдение попадает в бакет ≤0.1 с. Для перцентилей данных недостаточно, поэтому метрика в таблицу не включена.

Предложенные пороги:

- p95 цикла: 5 с. По границе бакета замер 2026-11-22 попадает в (5, 30] с и превышает порог. Пока гистограмма хранит только бакеты, порог достаточно сравнить с границей, точное значение p95 не нужно.
- Среднее мержа: 10 с. Замер 7.90 с укладывается в порог. Среднее вычислено из sum и count, поэтому его сравнивают с числом напрямую. Границы бакетов показывают, что все 39 мержа больше 5 с.

Эти пороги относятся к двум гистограммам и не входят в раздел «Пороги SLO». Каждый новый замер добавляет новую строку с датой. Старые строки не перезаписывают.

## Порядок заполнения таблицы

1. Дождаться появления демона и артефактов контракта в `main`.
2. Запустить `bash tools/perf/measure.sh` в CI, приложить stdout PR или записать его в этот файл.
3. Перенести девять строк и значения `meta.txt` в таблицу, заменив прочерки на числа и дату.
4. Сверить с порогами раздела «Пороги SLO». Только после этого передать числа в T4.3 как критерии выхода G1 по ADR 0018.

## Журнал попыток

Для задачи оптимизации метки исполнитель ведёт журнал попыток. Он хранится в файле `decision.tsv` рядом с артефактами замера, и исполнитель читает его перед каждой попыткой. Файл `decision.tsv` не совпадает с `decisions.tsv` из шаблона исполнителя. Там шесть колонок для решений по задаче, здесь девять колонок для замеров. Одна попытка меняет ровно одно условие и даёт один замер. По результату замера исполнитель оставляет изменение или откатывает его. Выигрыш по чтению кода не считается результатом.

Журнал содержит девять колонок: `id`, `hypothesis`, `change`, `before`, `after`, `delta`, `tests`, `verdict`, `note`. Строка хранит номер попытки, гипотезу, единственное изменение, метку до и после, разницу, результат regression gate, вердикт и короткую заметку. Число колонок одинаково во всех строках.

Условие останова состоит из двух полей: цель и минимум попыток. Цель описывает движение метки выше шума. Минимум попыток это нижняя граница числа итераций. Удачная ранняя попытка не заканчивает прогон. Исполнитель делает не меньше минимума попыток, даже если первая попытка дала выигрыш. Приёмка даётся только при движении метки выше шума и зелёном regression gate. При любом другом исходе изменение откатывается целиком. Одно принятое исправление даёт один коммит.

Стенд замера может не заметить малое изменение. Перед прогоном исполнитель доказывает чувствительность стенда и фиксирует его конфигурацию. В каждую строку журнала он записывает счётчик ошибок и количество выполненной работы. Попытка без этих двух чисел в приёмку не идёт.

Источник: `pstack/skills/poteto-mode/playbooks/hillclimb.md:5-15`, карточка CP-20. Журнал не меняет таблицу результатов раздела «Таблица результатов» и не добавляет локальные замеры.

## Замер пересборки индекса карточек (PF-04)

Дата: 2026-11-22. Команда: `time .opencode/bin/beacon index build --root <worktree>`. Бинарник `.opencode/bin/beacon` собран 2026-11-22 в 15:20 по локальному времени.

Корпус: 1413 карточек, 1048 зависимостей, 3019 владельцев. Пять прогонов подряд дали 101, 106, 119, 121 и 135 мс. Медиана равна 119 мс.

Замер включает запуск процесса, поэтому он завышает чистую длительность `RebuildDir`. Поле `ImportStats.Duration` и колонка `duration_ms` в выводе `beacon index build` дают длительность самой пересборки без запуска процесса. Команда печатает то же число карточек, что и корпус выше.
