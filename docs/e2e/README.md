# E2E-прогон Beacon на реальных процессах

## Команда

```bash
bash tests/e2e/run.sh
```

Эквивалентно:

```bash
/tmp/opencode/go126/bin/go test -tags=e2e ./tests/e2e -count=1 -v
```

Файл `e2e_test.go` имеет build tag `//go:build e2e`. Обычный `go test ./...` пропускает его, поэтому в CI без opencode корневой тест не падает.

Токен GitHub не нужен: тест не делает запросов к GitHub. Владелец запускает локально. В CI тот же вызов живёт в отдельном workflow `.github/workflows/e2e.yml` с `continue-on-error: true`: прогон не блокирует merge. Workflow ставит Go из `go.mod`, Node 26.x и бинарник opencode v2.3.0 из платформенного npm tarball.

## Три инструмента, и никаких самописных клиентов

| Что проверяется | Инструмент |
| --- | --- |
| MCP `initialize`, `tools/list`, `tools/call` | официальный `github.com/modelcontextprotocol/go-sdk/mcp` клиент с `CommandTransport`: бинарник поднимается как subprocess, client сам ведёт handshake по stdio |
| `/api/plugin` и `/api/session` живого сервера | `opencode api --server http://127.0.0.1:PORT GET /api/plugin` и остальные вызовы того же CLI; пароль передаётся через `OPENCODE_PASSWORD` |
| `/api/event` | тот же `opencode api ... GET /api/event` запускается и проверяется на факт `session.execution.started`, но в v2.3.0 CLI не отдаёт тело SSE (0 байт), поэтому это ограничение инструмента фиксируется отдельной строкой лога и не выдаётся за пройденную проверку |
| составитель протокола | MCP Inspector CLI `npx --yes @modelcontextprotocol/inspector@2.5.0 --cli <binary> --method initialize --format json`, опционально |

Самописного JSON-RPC-клиента, `curl` и `fetch` в e2e нет. Inspector в этой среде за 60 с вывода не дал, поэтому по умолчанию пропускается; включение: `BEACON_E2E_INSPECTOR=1 bash tests/e2e/run.sh`. Основной MCP-клиент — go-sdk, а не Inspector.

## Что запускается по-настоящему

| Проверка | Внешний источник факта |
| --- | --- |
| `beacon mcp` отвечает на `initialize`, отдаёт каталог `AdvertisedToolNames` и отвечает на `tools/call` | go-sdk `CommandTransport`, отдельный процесс |
| opencode v2.3.0 грузит плагин | `GET /api/plugin` живого `opencode serve`: `source.type=local`, `features.server=true`, `state.status=active` |
| указатель в `events.jsonl` будит сессию | `prompt.ok delivery=steer` в логе плагина и `session.execution.started` в подписке плагина (`ctx.event.subscribe` внутри живого opencode) |
| квитанция записана | `state/beacon/receipts/<id>.wrote` и строка `state=posted` в `receipts.jsonl` |
| негативный контроль | вместо рабочего обработчика ставится `fixtures/beacon-bridge-stub.js`; та же проверка обязана провалиться |

## Карта возможностей и полнота прогона

Таблицы выше описывают инструменты и отдельные проверяемые факты. Они не заменяют карту пользовательских возможностей. Карта лежит в `tests/e2e/features/README.md`. Для каждой возможности beacon там отдельный файл с путём доступа от лица пользователя, командами прогона и наблюдаемым конечным состоянием. В карту входят Watch, claim карточки, wake сессии и мерж по `ready`. Приём взят из `pstack/skills/create-verification-skill/SKILL.md`, раздел feature map.

Прогон считается полным, когда каждая возможность из карты проверена живым запуском по её пользовательскому пути. Внутренний вызов или прямой сеттер не считается проверкой. Прогон, который трассирует только один удобный вход, неполон, даже если все его проверки зелёные. Возможность, которой нет в карте, тоже делает прогон неполным. Её сначала добавляют в карту и проверяют живым запуском, а не убирают из прогона.

## Честные ограничения

1. **Плагин репозитория будит сессию.** `runWakePositive` и полный цикл грузят `.opencode/plugins/beacon-bridge.js` из корня репозитория. Плагин читает `events.jsonl`, хранит курсор и вызывает `ctx.session.prompt` с delivery `steer`. Копия `tests/e2e/fixtures/beacon-bridge.js` из спайка T0.3 остаётся в дереве, но больше не подтверждает пробуждение. Негативный контроль ставит `fixtures/beacon-bridge-stub.js` вместо плагина репозитория.
2. **Общий каталог задаёт контракт инструментов.** `mcp_go_sdk_CommandTransport` сверяет `tools/list` с `AdvertisedToolNames` из `internal/infra/mcp/server.go` и проверяет протокольный round trip. `live_opencode_full_mcp_cycle` вызывает реальные обработчики `beacon mcp` через go-sdk и берёт из ответов `watchID`, revision и вердикт.
3. **`beacon mcp` сейчас уже в main** (PR #40 влит). Тест собирает бинарник из корня репозитория и объясняет это в логе. Переменная `BEACON_MCP_SRC` позволяет указать другой checkout. Если `cmd/beacon/mcp.go` нигде нет, тест падает с явным сообщением.
4. **`opencode api` не умеет читать SSE.** Проверено на живом сервере 2.3.0: `opencode api GET /api/event` за 7 с вернул 0 байт, тогда как прямой поток отдавал `server.connected` и heartbeat. Заглушки здесь нет: тест запускает CLI, фиксирует отсутствие кадров отдельной строкой лога и не считает SSE доказанным. Факт пробуждения доказывается подпиской плагина, квитанцией и `prompt.ok`.

## Переменные окружения

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `GO_BIN` | Go 1.26 для сборки beacon и запуска теста | `/tmp/opencode/go126/bin/go`, иначе `go` из PATH |
| `BEACON_MCP_SRC` | checkout с `cmd/beacon/mcp.go` | `worktrees/w43`, затем корень репозитория |
| `OPENCODE_BIN` | бинарник opencode | `opencode` из PATH |
| `OPENCODE_EXPECT_VERSION` | подстрока ожидаемой версии | `2.3.0` |
| `OPENCODE_SKIP_VERSION` | `1` отключает проверку версии | не задана |
| `BEACON_E2E_INSPECTOR` | `1` включает опциональный Inspector | не задана, Inspector пропускается |

Изоляция: каждый прогон создаёт каталог `/tmp/opencode/beacon-e2e-*` с отдельными `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` и `OPENCODE_CONFIG`; во временном проекте делается `git init`, без чего opencode не считает его проектом и не грузит плагин. Настоящий `auth.json` копируется в изолированный data-каталог, чтобы `session.prompt` мог обратиться к провайдеру; содержимое файла в лог и в репозиторий не попадает. В конфиге выставлен `experimental.location_idle_timeout: false`, иначе плагин выгружается после простоя.

## Негативный контроль

Автоматический тест `negative_control_stub_handler_must_fail` ставит `fixtures/beacon-bridge-stub.js` вместо плагина репозитория и требует, чтобы та же самая функция проверки, которая зелёная на плагине репозитория, вернула ошибку. Дополнительно он требует отсутствия квитанции и prompt. Если заглушка проходит проверку, прогон красный и e2e не считается рабочим.

## Аудит прогона

Аудит проверки заканчивается одним из трёх исходов: чисто, изменено, заблокировано. Аудит, в котором нет ни одного исхода, не считается завершённым.

- **Чисто.** Все проверки прошли, расхождений с картой возможностей нет. Правки не нужны.
- **Изменено.** Найдено расхождение, и правка внесена в этом проходе. На один проход приходится один PR исправлений. Несколько правок входят в тот же PR.
- **Заблокировано.** Прогон не удалось завершить по причине вне зоны прохода. Причина и наблюдаемые факты попадают в отчёт.

Расхождение между картой возможностей и поведением сначала классифицируют. Причиной бывает дрейф документации или баг продукта. Пока причина не названа, карту не меняют и расхождение не списывают на ограничение инструмента.

Инварианты живого прогона:

- Перед первым управлением экземпляр проходит health-check. После каждого провала health-check повторяют, и только затем выполняют следующее управление.
- Доказательства проверяют по пути после уборки. Путь к квитанции, логу или иному артефакту совпадает с путём из отчёта.
- Мусор неудачной итерации убирают до начала следующей. Следующий прогон стартует в чистом изолированном каталоге.

## Что не проверяется

- Реальный GitHub и изменение статуса CI. Демон опроса в e2e заменяет `cycleDaemon`: он считает вердикт из наблюдаемых фактов через движок домена с проверкой ShipFacts (ADR 0061 п. 2) и атомарно пишет результат в store.
- Бизнес-результат обработчика в `mcp_go_sdk_CommandTransport`: `tools/call beacon_list_running` проверяет только протокольный round trip. Полный цикл читает реальные ответы обработчиков.
- Ответ модели. Для факта пробуждения достаточно `session.execution.started`; провайдер в изолированном окружении может отвечать ошибкой, как зафиксировано в `tmp/p0-wake/Results.md`.
