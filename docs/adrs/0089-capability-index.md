# ADR 89: Производный индекс возможностей

Статус: accepted

## Контекст

ADR 0037 выбирает получателя события по совпадению объявленных возможностей, а не по имени сессии. Overstory показал риск: после init capabilityIndex остаётся пустым при непустом roster, и подбор по возможностям перестаёт работать. Ручное ведение индекса в YAML расходится с реестром executors из ADR 0100.

## Решение

Индекс возможностей производный. Ядро строит его из roster реестра executors при каждом upsert и не хранит его руками в конфиге. При upsert записи поле agent_capabilities заполняется из capabilities этой записи. Удалённый executor убирается из индекса.

Проверка двухсторонняя. Каждое объявление в roster должно дать запись в индексе, и каждая запись индекса должна ссылаться на известного executor. Пустой индекс при непустом roster это ошибка конфигурации. Индекс, ссылающийся на неизвестного агента, тоже ошибка. Сообщение об ошибке называет поле и имя агента.

Ядро не хранит имена агентов в индексе. Ключ индекса это capability, значение это непрозрачный идентификатор executor. Имя сессии остаётся ключом доставки на границе и не участвует в выборе. Получатель выбирается только по возможностям по ADR 0037.

## Последствия

Индекс всегда отражает текущий roster и пересобирается при изменении реестра. Рассинхрон виден до начала подбора, а не как молчаливый пустой результат. Карточки T5.23 и T5.24 строят индекс и проверяют его в обе стороны. Eval r09 проверяет оба направления, включая негативный контроль со ссылкой на неизвестного агента. Число MCP-инструментов остаётся равным семи, контракт ADR 0003 и 0009 не меняется. Реестр из ADR 0100 остаётся единственным источником возможностей, дублирования списка имён в ядре не появляется.
