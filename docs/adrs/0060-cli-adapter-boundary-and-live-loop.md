# ADR 0060. Граница CLI-адаптера и живой контур управления

Статус: accepted

## Контекст

Проектное предложение `docs/design/opencode-cli-manager.md:3` описало CLI-менеджер поверх OpenCode, но оставило открытым решение владельца о границе между JS-плагином и Go-адаптером в CLI (`docs/design/opencode-cli-manager.md:95`). ADR 0029 зафиксировал это напряжение в `docs/adrs/0029-cli-manager-over-opencode-service.md:11` и тоже не закрыл вопрос. Предложение обсуждает установленный бинарник `opencode v2.3.0` (`docs/design/opencode-cli-manager.md:3`) и маршруты текущей ветки `dev`, для которых есть расхождение с v1-документацией (`docs/design/opencode-cli-manager.md:29`).

Проверка на живой среде 20 ноября 2026 года, opencode v2.3.0 с фоновым сервисом на `http://127.0.0.1:49374`, опровергла две детали предложения. Вызов `opencode api app.agents` из псевдокода `docs/design/opencode-cli-manager.md:61` возвращает `UnknownError: Operation not found: app.agents`. Вызов `opencode api session.list` работает и возвращает JSON с полями `id`, `parentID`, `agent`, `model`, `title`, `time.busy`, `time.idle`, `time.outcome` и `location.directory`.

Вторая проверка на той же среде уточнила транспорт. `opencode api` это ограниченная обёртка. Она знает `session.list`, но не знает `app.agents`, `GET /api/event` и `session.status`. Прямой HTTP-запрос к адресу из `$XDG_STATE_HOME/opencode/service.json` с Basic-авторизацией `opencode:<password>` работает. `GET /api/agent` вернул 200 с JSON `{"location":{"directory":"..."},"data":[]}`, то есть в текущем каталоге агентов нет. `GET /api/config` и `GET /api/session` вернули 200 со списком сессий. `GET /api/event?types=session.status` удерживал соединение открытым дольше 3 секунд без данных. Для живого SSE-потока это нормальное поведение, а не ошибка. Источник транспорта и список агентов в этом ADR выбраны по результатам проверки, а не по тексту предложения.

Сейчас `cmd/beacon/main.go:78` содержит dispatch для `agents`, `watch` и `attach`. `cmd/beacon/watch.go:23` делает ровно один снимок, один вызов `session.list` и печатает таблицу. Флаг `--interval` в нём зарезервирован и не запускает цикл (`cmd/beacon/watch.go:171`). Вызовы внешних процессов идут через тип `runner` из `cmd/beacon/main.go:42` и подменяются в тестах.

Владелец принял решение по открытому вопросу и по контуру управления. Этот ADR фиксирует принятое решение. ADR 0006, 0017, 0024, 0025, 0026 и 0029 не переписываются. Пункт ADR 0029 об отказе от собственного спавна уточняется только для случая, когда фоновый сервис не зарегистрирован. Пункт о доступности `opencode api` для всех вызовов уточняется по результатам живой проверки.

## Решение

1. **CLI-адаптер это слой представления, а не второй протокольный мост.** Он не говорит по ACP или MCP как равный участник и не переводит протокол ядра. Для чтения сервера он использует тонкий HTTP-клиент к адресу из `$XDG_STATE_HOME/opencode/service.json` с Basic-авторизацией `opencode:<password>`. Клиент ходит только к этому адресу и только в уже существующее HTTP API opencode. Обёртка `opencode api` остаётся доступной для одиночных вызовов вроде `session.list`, но не становится единственным транспортом и не используется для SSE. Переход в TUI идёт через `runner` и `opencode --server <url> --session <id>`. Ядро остаётся на MCP. Go-код в `internal/domain`, `internal/app` и `internal/infra/mcp` не содержит имён агентов и вызовов OpenCode. ADR 0006 и ADR 0024 не нарушаются. Новый протокольный мост не появляется: opencode уже говорит по HTTP и мы не изобретаем ACP. Мост агентов по-прежнему живёт рядом с `.opencode/plugins/beacon-bridge.js`. Клиент живёт в `cmd/beacon`, читает готовый HTTP API того же сервиса и не переносит код OpenCode в ядро. Этим снимается открытый вопрос из `docs/design/opencode-cli-manager.md:95` и `docs/adrs/0029-cli-manager-over-opencode-service.md:11`.

2. **Единый живой вид работает по событиям.** `beacon watch --live [--interval]` заменяет single-shot режим. Команда подписывается через тонкий HTTP-клиент на `GET /api/event?types=session.status,session.execution.started`. Открытое соединение без данных, включая паузу больше 3 секунд, считается нормой. На каждом событии команда перечитывает снимок Beacon через `SnapshotReader`, а список сессий и статусы через `GET /api/session` того же клиента, затем печатает JOIN-таблицу `WATCH | VERDICT | REVISION | SESSION | AGENT | OPENCODE STATE | ATTENTION`. Соединение строк идёт по непрозрачному sessionID из `_meta` `ai.opencode/sessionID` (`internal/infra/mcp/meta.go:8`). Колонка `AGENT` берётся из поля `agent` ответа `session.list`. Это первичный источник списка агентов. Дополнительные источники это `GET /api/agent` и вывод `opencode agent list`. Вызов `opencode api app.agents` в v2.3.0 недоступен и не используется. Готовность берётся из вердикта Beacon, а не из `idle` OpenCode (ADR 0017 и ADR 0026). `OPENCODE STATE` остаётся справочной колонкой со значениями `idle`, `retry` или `busy`. `ATTENTION` заполняется эвристикой ADR 0058 п6. После обрыва SSE клиент делает переподключение, заново читает снимок и статусы и не нагоняет прошедшие события, потому что поток не хранит историю (ADR 0025). Флаг `--interval` задаёт период предохранительного перечитывания снимка, а не замену подписки. Свой TUI или веб-интерфейс не создаётся. Результат работы это таблица и переход через `beacon attach`.

3. **Спавн идёт через HTTP API OpenCode.** `beacon spawn <taskID> [--agent id]` создаёт сессию запросом `POST /api/session` через тот же клиент с `parentID` оркестратора, полем `agent` и metadata, которая связывает сессию с watch Beacon. Затем команда отправляет промпт в `POST /api/session/:sessionID/prompt`. Агента задают при создании сессии, не в теле prompt: в текущем маршруте v2 поля `agent` там нет (`docs/design/opencode-cli-manager.md:28`, `docs/design/opencode-cli-manager.md:113`). Порт не хардкодится. Если registration-файл `$XDG_STATE_HOME/opencode/service.json` есть, клиент берёт оттуда `url` и `password`. Если файла нет, команда спавнит `opencode serve` на свободном порту с паролем через `OPENCODE_SERVER_PASSWORD` и таймаутом готовности 30 секунд по образцу t3code (`docs/design/opencode-cli-manager.md:15`). Транспорт `--stdio` не используется.

4. **Обратная связь замыкается командой `beacon deliver <watchID>`.** Когда вердикт Beacon становится `ready` или `needs_input`, команда пишет WriteToolResult в живую сессию через `POST /api/session/:sessionID/prompt`. Результат честно различает `delivery=steer`, `delivery=queue` и `delivery=unsupported` по ADR 0026. Очередь не выдаётся за доставку в текущий ход, а `unsupported` не считается успехом. Повтор допускается только для `transport-failed` по ADR 0017 с тем же obligationID. Неопределённый исход и квитанции `posted` повторов не дают. Поле `delivery` печатается вместе с идентификатором watch. Если появится инструмент `beacon_wake` из ADR 0026, команда передаст доставку ему и сохранит тот же контракт.

5. **`beacon attach <session>` остаётся переходом в обычный TUI.** Команда читает адрес из `service.json`, запускает `opencode --server <url> --session <sessionID>` через `runner` и завершается. Управление получает обычный TUI OpenCode. Менеджер код не пишет и свой интерфейс не держит.

6. **Performance-границы фиксируются как бюджет.** Один статический бинарник до 100 MB. HTTP-клиент строится на stdlib `net/http`, без сторонних зависимостей, и работает только с адресом из `service.json`. `session.list` кэшируется с TTL, чтобы цикл по событиям не делал лишний запрос на каждое событие. SSE-читатель имеет ограниченный буфер и переподключение без нагона истории: после обрыва состояние перечитывается, отложенные события не проигрываются. Бюджет 100 MB это ограничение для будущих карточек, не измеренный результат.

## Причина

ADR 0024 (`docs/adrs/0024-one-bridge-per-protocol.md:7`) определяет мост как перевод шести операций ядра в CLI, HTTP API или ACP и требует, чтобы мост жил рядом с адаптером (`docs/adrs/0024-one-bridge-per-protocol.md:9`). ACP описывает `session/new`, `session/prompt` и другие методы, но не решает вопросы worktree, очередей follow-up и артефактов (`docs/adrs/0024-one-bridge-per-protocol.md:13`). CLI не становится вторым мостом: он не переводит протокол ядра и не реализует ACP. Он вызывает HTTP API, который opencode уже открывает сам. ADR 0006 (`docs/adrs/0006-opencode-adapter-boundary.md:7`) выносит код OpenCode из ядра в один JS-плагин, и эта граница сохраняется в `internal`. Клиент живёт в `cmd/beacon` как слой представления. Ядро говорит только MCP. Поэтому новый тонкий HTTP-клиент не отменяет ни «один мост на протокол», ни вынос адаптера из ядра. Отличие от моста в том, что клиент не переводит шесть операций ядра и не подменяет протокол, а читает готовый API того же продукта.

Предложение считало `opencode api` достаточным интерфейсом: `docs/design/opencode-cli-manager.md:13` перечисляет команды `service` и `api`, а `docs/design/opencode-cli-manager.md:35` прямо называет `opencode api session.list` и `opencode api 'GET /api/event'`. Живая проверка показала, что обёртка ограничена: она знает `session.list`, но не знает `app.agents`, `GET /api/event` и `session.status`. Маршруты `GET /api/session` и `POST /api/session` описаны в [session.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/session.ts) и [server.mdx](https://github.com/anomalyco/opencode/blob/dev/services/site/src/docs/v1/content/server.mdx). Прямой HTTP с Basic-авторизацией к тем же маршрутам работает, поэтому выбран он. Расхождение v1 и v2 для prompt разобрано в `docs/design/opencode-cli-manager.md:29`, поэтому агента задают при создании сессии.

Псевдокод `docs/design/opencode-cli-manager.md:61` использует `opencode api app.agents`, но на живой среде v2.3.0 этот вызов вернул `UnknownError: Operation not found: app.agents`. Зато `GET /api/agent` через тонкий клиент вернул 200 с пустым `data` в текущем каталоге, а `GET /api/config` вернул 200. Первичный источник агентов это поле `agent` из `session.list`. Дополнительные источники это `GET /api/agent` и разбор вывода `opencode agent list`, который предложение упоминает в `docs/design/opencode-cli-manager.md:33`. Текущий вызов в `cmd/beacon/agents.go:195` поэтому подлежит замене в отдельной карточке.

`GET /api/event` это живой SSE-поток с параметром `types`, без повтора прошедших событий ([event.ts](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/event.ts), [client docs](https://opencode.ai/docs/build/client/#stream-events)). Beacon зафиксировал это ограничение в ADR 0025 (`docs/adrs/0025-status-and-cursor.md:11`). На живой среде `GET /api/event?types=session.status` держал соединение дольше 3 секунд, не закрывая его. Это нормальное ожидание события, а не таймаут ошибки. Событие `session.status` эфемерно, а терминальные исходы приходят в `session.execution.*` ([session-status-event.ts](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/session-status-event.ts)). Готовность задачи берётся из вердикта Beacon (`internal/infra/mcp/server.go:38`, `docs/design/opencode-cli-manager.md:47`), поэтому `idle` не может быть сигналом готовности.

Registration-файл `$XDG_STATE_HOME/opencode/service.json` содержит `url`, `pid`, `version` и приватный пароль, а `Service.discover()` читает его и делает health-probe, но не спавнит процесс ([service.ts](https://github.com/anomalyco/opencode/blob/dev/packages/client/src/effect/service.ts), [troubleshooting](https://github.com/anomalyco/opencode/blob/dev/services/site/src/docs/content/troubleshooting.mdx), `docs/design/opencode-cli-manager.md:11`). Проверка подтвердила Basic-авторизацию `opencode:<password>` и поля `url` и `password` в файле. Поэтому основой остаётся фоновый сервис. Если его нет, путь спавна описан в t3code: свободный порт через `findAvailablePort(0)`, пароль, таймаут 30 секунд и строка готовности в stdout ([opencodeRuntime.ts:80](https://github.com/pingdotgg/t3code/blob/eee05575ebd514db36f61d7eb05d2258a10c96bd/apps/server/src/provider/opencodeRuntime.ts#L80), [opencodeRuntime.ts:651](https://github.com/pingdotgg/t3code/blob/eee05575ebd514db36f61d7eb05d2258a10c96bd/apps/server/src/provider/opencodeRuntime.ts#L651), [opencodeRuntime.ts:664](https://github.com/pingdotgg/t3code/blob/eee05575ebd514db36f61d7eb05d2258a10c96bd/apps/server/src/provider/opencodeRuntime.ts#L664)). Хардкод порта `4096` запрещён (`docs/design/opencode-cli-manager.md:111`).

Честная доставка follow-up зафиксирована в ADR 0026 (`docs/adrs/0026-honest-followup-delivery.md:7`): `steer`, `queue` или `unsupported`, без выдачи очереди за текущий ход. ADR 0017 (`docs/adrs/0017-wake-ladder.md:7`) разрешает повтор только для `transport-failed` и запрещает его для неопределённого исхода. Проектное предложение требует, чтобы CLI показывал вердикт Beacon, а не `idle` (`docs/design/opencode-cli-manager.md:47`), и не писал свой TUI (`docs/design/opencode-cli-manager.md:99`).

## Последствия

- Менеджер не пишет код. CLI остаётся тонким слоем над HTTP API opencode и печатает таблицу. Код OpenCode не переезжает в `internal/domain`, `internal/app` или MCP-инструменты.
- ADR 0029 сохраняет силу для трёх существующих команд. Собственный спавн `opencode serve` допускается только как fallback, когда `service.json` отсутствует. Другие пункты ADR 0029 не меняются.
- `beacon watch --live` становится долгоживущим процессом. SSE идёт через `GET /api/event`. После обрыва клиент переподключается и перечитывает снимок, а не воспроизводит историю. Пауза в потоке без данных не считается ошибкой. `--interval` не превращает подписку в polling.
- Список агентов берётся из поля `agent` ответа `session.list`. `GET /api/agent` и `opencode agent list` остаются дополнительными источниками. Вызов `opencode api app.agents`, который сейчас использует `cmd/beacon/agents.go:195`, удаляется карточкой по миграции.
- `beacon spawn` и `beacon deliver` появляются в dispatch `cmd/beacon/main.go` и в тексте usage. `beacon attach` сохраняет текущий контракт перехода в TUI.
- Из решения выходят карточки по правилам ADR 0020. Карточки этим ADR не создаются. Владельцы файлов для будущих карточек:
  - `cmd/beacon/opencode.go` и `cmd/beacon/opencode_test.go`: чтение `service.json`, тонкий HTTP-клиент с Basic-авторизацией, fallback-спавн, SSE-читатель с буфером и переподключением, запуск `opencode --server --session`.
  - `cmd/beacon/watch.go` и `cmd/beacon/watch_test.go`: цикл по событиям, JOIN с колонками `WATCH | VERDICT | REVISION | SESSION | AGENT | OPENCODE STATE | ATTENTION`, перечитывание снимка после обрыва.
  - `cmd/beacon/agents.go` и `cmd/beacon/agents_test.go`: замена `opencode api app.agents` на поле `agent` из `session.list`, дополнительные источники `GET /api/agent` и `opencode agent list`, сохранение attention и handoff. Имена агентов в ядро не попадают.
  - `cmd/beacon/spawn.go` и `cmd/beacon/spawn_test.go`: создание сессии с `parentID`, `agent` и metadata, отправка промпта, проверка отсутствия `agent` в теле prompt.
  - `cmd/beacon/deliver.go` и `cmd/beacon/deliver_test.go`: WriteToolResult по вердикту `ready` или `needs_input`, честное `delivery`, повтор только для `transport-failed`.
  - `cmd/beacon/main.go` и `cmd/beacon/main_test.go`: dispatch и usage для `spawn`, `deliver`, `--live`, `--interval`. `cmd/beacon/attach.go` и `cmd/beacon/attach_test.go` сохраняют переход в обычный TUI.
- Проверка карточек: HTTP-клиент ходит только по адресу из `service.json` и не знает протоколов агентов, в ядре нет имён агентов, `opencode api app.agents` не вызывается, `beacon watch --live` обновляется по SSE и перечитывает снимок после обрыва, `beacon deliver` печатает `delivery` и не ретраит неопределённый исход.

## Отклонённое

Собственный TUI или веб-интерфейс. `opencode serve` уже отдаёт веб-интерфейс, а `opencode --session <id>` открывает обычный TUI (`docs/design/opencode-cli-manager.md:99`). Задача CLI это таблица и переход в сессию.

Второй протокольный мост или широкий HTTP-клиент. Клиент из п1 это чтение уже существующего HTTP API opencode по адресу из `service.json`. Он не реализует ACP, не переводит шесть операций ядра и не знает протоколов других агентов. Широкий клиент к любым сервисам или свой протокол сдвинул бы границу ADR 0024 и вернул бы OpenCode-код в Go-ядро, чего запрещает ADR 0006.

`opencode api` как единственный транспорт. Обёртка не знает `app.agents`, `GET /api/event` и `session.status`. Одиночные вызовы через неё возможны, но SSE и полный набор маршрутов идут через тонкий HTTP-клиент с Basic-авторизацией.

ACP как равный мост. CLI не переводит шесть операций ядра в ACP и не становится вторым мостом рядом с плагином. opencode уже говорит по HTTP, новый протокол изобретать не нужно.

Опрос сервера в цикле вместо SSE. `/api/event` отдаёт живые события, а история не хранится (`docs/design/opencode-cli-manager.md:101`). После обрыва состояние перечитывается, а пропущенные события не нагоняются. Пауза в открытом SSE-потоке это норма, а не сигнал к опросу.

`opencode api app.agents` как источник списка агентов. Живая проверка v2.3.0 вернула `UnknownError: Operation not found: app.agents`, поэтому псевдокод из `docs/design/opencode-cli-manager.md:61` устарел. Первичный источник это поле `agent` из `session.list`, дополнительные это `GET /api/agent` и `opencode agent list`.

Задание агента в теле prompt. Поле `agent` отсутствует в текущем маршруте v2 (`docs/design/opencode-cli-manager.md:113`). Агента задают при создании сессии через `POST /api/session`.

Признание `session.idle` готовностью задачи. `idle` означает только конец хода (`docs/design/opencode-cli-manager.md:103`). Готовность приходит из вердикта Beacon.
