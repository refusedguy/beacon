# ADR 0049. Шесть фич из отчёта AG-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AG «AG-волна: новые проекты» ([AG, строка 1](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L1)). Идеи собраны в разделе «Фичи» ([AG, строки 103-111](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L103)) и подтверждены описаниями проектов в разделе «Новые проекты» ([AG, строка 7](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L7)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0048 и 164 карточках из `docs/tasks/`. Лестница пробуждения, аренда, вердикт и идемпотентность уже есть: ADR 0017 задаёт ступени пробуждения, T3.51 и T3.97 задают fencing и базовую аренду, ADR 0045 с T3.67 и T3.68 задают вердикт и чтение ref, ADR 0028 задаёт идемпотентность и квитанции. Поэтому эти темы здесь не повторяются. Несколько пунктов похожи на существующие по имени, но различаются по уровню. Watcher в фиче 1 это внешний скрипт, а не ступень лестницы ADR 0017. Фича 3 уточняет транзакционную границу записи токена, а не добавляет ещё один монотонный token поверх T3.51. Фича 4 даёт один метод суммарного вердикта и кеш прочитанного, а не чтение ref из T3.68 и не нормализацию текущего запуска проверки из ADR 0048. Фича 5 задаёт метрические условия гейта, а не булеву формулу `ship` из T3.67. Фича 6 задаёт владельцев аренды и правило продления, а не саму аренду с TTL из T3.97. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Watcher по событию вместо опроса моделью. Внешний дешёвый скрипт проверяет условие задачи и будит сессию только когда условие стало истинным. Агент не тратит вызовы модели на повторное чтение статуса. Watcher не добавляет ступень в лестницу ADR 0017 и не заменяет доставку follow-up из ADR 0026.

2. Динамическая инъекция MCP-серверов и хуки жизненного цикла инструмента. Beacon подключает MCP-сервер в рантайме по объявленному контракту и вызывает хуки до вызова инструмента, после вызова и на остановку. Хуки получают `tool_call_id` и результат вызова. Подавление дублей по `tool_call_id` не входит в этот ADR, потому что идемпотентность и квитанции зафиксированы в ADR 0028.

3. Fence token и enqueue в одной транзакции. Beacon записывает fence token в той же транзакции, в которой ставит задачу в очередь и меняет данные задачи. Отставший воркер после потери лизы не перезаписывает более свежую работу, потому что токен и задача появляются вместе. Это уточнение транзакционной границы, а не ещё один монотонный token поверх T3.51.

4. Суммарный вердикт CI одним методом и кеш прочитанного. Адаптор GitHub даёт один метод, который возвращает суммарный вердикт коммита по всем проверкам. Прочитанный REST-список с заголовком `Authorization` переиспользуется. Если список не изменился, повторного запроса нет. Правило описывает метод и кеш. Оно не меняет чтение ref из T3.68 и таблицу решений в `internal/domain/verdict.go`.

5. Вердикт из двух условий. Для проверки с измеряемой величиной флаг выставляется только когда медианное отношение не ниже порога и p-value ниже alpha. Если выполнено одно из двух условий, флаг не выставляется. Это правило для метрик гейта, а не замена формулы `ship` из T3.67.

6. Аренда с владельцами и монотонным продлением. У аренды есть список `holders`. Продление на короткий срок никогда не сокращает срок, который уже выдан. Протокол служит для reclaim ресурса агента или worktree. Базовая аренда с TTL и fencing из T3.97 не меняется.

## Причина

1. existence-master/Sentient это локальный ассистент для долгих задач, где watcher это маленький скрипт по расписанию, который будит модель только когда что-то изменилось ([AG, строка 9](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L9), [Sentient](https://github.com/existence-master/Sentient)). Дешёвый внешний скрипт проверяет условие и будит сессию по событию ([AG, строка 10](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L10)). В Beacon агент сам опрашивает статус, а ADR 0017 описывает ступени пробуждения, но не дешёвого внешнего watcher'а. Берётся watcher по событию, а не Python, Electron, AGPL с CLA, голос и интеграции с Gmail и Slack ([AG, строка 11](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L11)).

2. iOfficeAI/aionrs это CLI-агент на Rust, который добавляет MCP-серверы во время работы ([AG, строка 15](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L15), [aionrs](https://github.com/iOfficeAI/aionrs)). Инъекция идёт через JSON stream protocol. Рядом лежат хуки `pre_tool_use`, `post_tool_use` и `stop` ([AG, строка 16](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L16)). ADR 0003 и ADR 0024 фиксируют MCP-библиотеку и один мост на протокол, но не инъекцию в рантайме и не хуки. Берутся инъекция и хуки, а не готовый агент со своим циклом, провайдерами и TUI ([AG, строка 17](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L17)).

3. stablemates/workhorse держит устойчивую очередь задач внутри PostgreSQL и использует fence tokens при захвате задачи ([AG, строка 21](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L21), [workhorse](https://github.com/stablemates/workhorse)). Воркер, который проснулся после потери лизы, не может перезаписать более свежую работу. Enqueue идёт в той же транзакции, что и изменение данных ([AG, строка 22](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L22)). T3.51 задаёт монотонный token в claim, но не границу транзакции между токеном и задачей. Берётся атомарность записи, а не PostgreSQL с его таблицами и публичная бета 0.x ([AG, строка 23](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L23)).

4. cplieger/forgeapi даёт один Go-API для pull request, issue, merge и checks на GitHub, GitLab, Gitea и Forgejo с общими типами результатов ([AG, строка 27](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L27), [forgeapi](https://github.com/cplieger/forgeapi)). `Checks.CommitStatus` возвращает суммарный вердикт коммита, а `RerunFailedChecks` перезапускает упавшие проверки. Клиент темпится под rate limit и переиспользует прочитанное, поэтому неизменённый REST-список с заголовком `Authorization` стоит ноль запросов ([AG, строка 28](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L28)). Это бьёт по проблеме 5400 GraphQL-запросов в час. T3.68 читает ref одним читателем вместо 15 опросов, но не даёт одного метода вердикта и кеша прочитанного. Берутся метод и кеш, а не клиентская библиотека, которая в non-goals прямо исключает polling-цикл и приём webhook ([AG, строка 29](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L29)).

5. ofershap/benchgate даёт недостающий exit code для benchstat, сравнивает два файла `go test -bench` и роняет CI при статистически значимой регрессии ([AG, строка 33](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L33), [benchgate](https://github.com/ofershap/benchgate)). Флаг выставляется только когда медианное отношение не ниже порога и p-value ниже alpha ([AG, строка 34](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L34)). T3.67 фиксирует формулу `ship ⇒ build ∧ audit ∧ (tdd ∨ trivial)`, но не задаёт порог и значимость. Берётся пара условий, а не узкая специализация на бенчмарках Go и один проход без слежения за PR ([AG, строка 35](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L35)).

6. andrius/dev-lease это TTL-лизы для локальных стеков Docker Compose, заточенные под git worktrees и агентов ([AG, строка 45](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L45), [dev-lease](https://github.com/andrius/dev-lease)). У каждой аренды есть `holders`, а короткий `extend` никогда не сокращает уже выданный срок ([AG, строка 46](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L46)). T3.97 даёт аренду worktree с TTL и fencing, но не модель владельцев и не правило продления. Берутся владельцы и монотонное продление, а не Docker socket и отдельный контейнер-свипер ([AG, строка 47](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L47)).

## Последствия

- Из каждого пункта выходит одна небольшая карточка в `docs/tasks/` по правилам ADR 0020. Карточки этим ADR не создаются и будут созданы отдельными задачами. Владельцы файлов для будущих карточек:
  - Фича 1: `cmd/beacon/watch.go`, `internal/infra/mcp/tool_wake.go`, `internal/infra/ladder/transitions.go`, `internal/infra/taskstore/store.go`, `internal/domain/types.go` и тесты к ним.
  - Фича 2: `internal/infra/mcp/server.go`, `internal/infra/mcp/schema.go`, `internal/infra/mcp/meta.go`, `internal/domain/types.go`, `cmd/beacon/mcp.go` и тесты к ним.
  - Фича 3: `internal/infra/mcp/tool_claim.go`, `internal/infra/taskstore/store.go`, `internal/infra/store/db.go`, `internal/infra/store/atomic_write.go`, `internal/domain/types.go` и тесты к ним.
  - Фича 4: `internal/infra/github/rest.go`, `internal/infra/github/cache.go`, `internal/infra/github/tier2.go`, `internal/domain/verdict.go`, `internal/infra/github/fixtures_contract_test.go` и тесты к ним.
  - Фича 5: `internal/domain/verdict.go`, `internal/domain/verdict_test.go`, `internal/domain/types.go`, `internal/infra/mcp/tool_stats.go`, `cmd/beacon/doctor.go` и тесты к ним.
  - Фича 6: `internal/infra/mcp/tool_claim.go`, `internal/infra/taskstore/store.go`, `internal/infra/store/db.go`, `internal/domain/types.go`, `cmd/beacon/task.go` и тесты к ним.
- Проверка карточек: внешний watcher будит сессию по событию и не добавляет ступень в лестницу ADR 0017; MCP-сервер подключается в рантайме, а хуки вызываются до вызова инструмента, после вызова и на остановку; fence token и enqueue попадают в одну транзакцию, а воркер с устаревшим токеном не перезаписывает задачу; один метод возвращает суммарный вердикт, а неизменённый список не вызывает повторного запроса; флаг по величине и значимости не выставляется, если не выполнено одно из двух условий; продление аренды не сокращает выданный срок, а список владельцев сохраняется.
- ADR 0001-0048 с T0.2, T3.51, T3.67, T3.68, T3.96 и T3.97 не переписываются. Watcher из фичи 1 не меняет лестницу ADR 0017 и доставку ADR 0026. Инъекция и хуки из фичи 2 не меняют MCP-библиотеку ADR 0003, один мост ADR 0024 и квитанции ADR 0028. Транзакция из фичи 3 не отменяет монотонный token T3.51. Метод и кеш из фичи 4 не меняют чтение ref T3.68 и нормализацию из ADR 0048. Пара условий из фичи 5 не заменяет формулу T3.67. Владельцы и продление из фичи 6 не отменяют аренду T3.97. Один мост на протокол из ADR 0024, изоляция worktree из ADR 0021 и проверка только в CI из ADR 0022 дополнительной не становятся.

## Отклонённое

Брать проекты целиком. Причины из отчёта сводятся к языку и размеру, внешней инфраструктуре, привязке к чужому харнессу и узкой задаче ([AG, строки 145-153](/home/nbook/Projects/tmp/beacon-research/AG-wave.md#L145)). Beacon требует Go, размер менее 100 MB и глобальную установку в `~/.config/opencode`. Ни один из шестнадцати проектов не годится как целый продукт.

Включать в этот ADR остальные идеи из раздела «Фичи» AG. Менеджером в волну отобраны шесть пунктов выше. Десять кандидатов не вошли. Набор статусов вместо зелёного тика (AG:110), связка сессии и worktree с возобновлением (AG:112), атомарный захват подтверждения (AG:113), holder процесса отдельно от демона (AG:114), подтверждённая доставка и dead-letter (AG:115), подписанный wake с подавлением поздних дублей (AG:116), SQLite WAL и ledger чеков (AG:117), правило «ошибка не отравляет ключ» (AG:118), цепочка чеков через `previous_receipt_hash` (AG:119) и одноразовая capability с отменой (AG:120). Часть из них пересекается с уже принятыми решениями об идемпотентности ADR 0028, доставке ADR 0026, квитанциях T3.96 и аренде T3.97. Остальные менеджером в эту волну не отобраны. Берётся контракт дешёвого внешнего watcher'а, который будит сессию по событию. Не берётся sentinel между агентом и MCP-серверами с плагинами под чужие харнессы.

В контракт переносятся правила шести фич, не эти числа. Правило «ноль запросов» в фиче 4 задаёт переиспользование прочитанного ответа, а не измеренную пропускную способность.
