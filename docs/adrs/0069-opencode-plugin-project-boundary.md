# ADR 0069. Плагин OpenCode как граница проектного контекста

Статус: accepted

До этого ADR проектность Beacon задавалась двумя хардкодами. В конфиге OpenCode сервер Beacon получал фиксированный `cwd`. Функция `stateDir()` в `cmd/beacon/doctor.go` выводила проект из `os.Getwd()` и наличия `.git`. В worktree это ломается: `ctx.location.directory` указывает на каталог worktree, а канонический корень проекта другой. Два проекта в одном сервере OpenCode получают один MCP-сервер и один контекст сессий.

Решение опирается на документацию OpenCode V2, прочитанную 20 ноября 2026 года: [Building plugins](https://opencode.ai/docs/build/plugins) и [Server plugin API](https://opencode.ai/docs/build/plugins/server), разделы Context, MCP, Sessions и Hooks.

## Решение

1. Границей проекта становится локальный плагин. Он лежит в `.opencode/plugins/` и загружается автоматически. Серверная часть экспортируется через `.` или `./server` и определяется как `Plugin.define({ id, setup(ctx) })` из `@opencode/plugin`. Глобальный `opencode.json` больше не задаёт сервер Beacon через `mcpServers` с фиксированным `cwd`.

2. Единственный источник корня проекта это `ctx.location.project.canonical`. Документация описывает `ctx.location` как место загрузки экземпляра плагина: `directory`, необязательный `workspaceID` и объект `project` с полями `id`, `directory`, `canonical`. Документация отдельно предупреждает, что это местоположение экземпляра плагина, а не местоположение каждой сессии или каждого события. Перед записью в сессию плагин проверяет её принадлежность проекту через `ctx.session.list({ directory: ctx.location.directory })` или `ctx.session.get({ sessionID })`.

3. Плагин регистрирует MCP-сервер Beacon через `ctx.mcp.transform`. Документация разрешает управлять MCP только трансформами: `editor.set`, `editor.update`, `editor.remove`, `editor.list`, `editor.get`. Корень проекта передаётся серверу как его рабочий каталог, равный `ctx.location.project.canonical`. Если выбранная форма конфигурации локального сервера не имеет поля `cwd`, корень передаётся явным аргументом или переменной окружения, которую читает Go-сервер. Плагин выставляет `disabled: false` и вызывает `ctx.mcp.reload()` после изменения входных данных.

4. Контекст проекта попадает в сессию через `ctx.session.instructions.entry.put({ sessionID, key, value })`. Такая запись отображается как блок `<context key="...">`, обновляется на следующей границе шага и не ставит сообщение в очередь. Под фиксированными ключами лежат открытые карточки и `AGENTS.md`. Хук `ctx.session.hook("context", ...)` добавляет текст в `event.system` только для исходящего вызова к модели. Хук `ctx.session.hook("prompt", ...)` работает до admission и может добавить `AGENTS.md` через `event.prompt.files`. Prompt-хуки повторяемы и не являются границей ровно один раз, поэтому побочные эффекты в них не пишутся.

5. Go-сторона перестаёт угадывать проект. `stateDir()` получает корень явно от плагина вместо `os.Getwd()` и проверки `.git`. Явный `BEACON_STATE_DIR` и legacy-путь вне проекта остаются для CLI по ADR 0011.

## Причина

Плагины в `.opencode/plugins/` загружаются автоматически, а локальный каталог без `package.json` использует файлы `index` или `server` в корне ([Load](https://opencode.ai/docs/build/plugins#load)). Это даёт точке входа стабильное место без правки глобального конфига.

`ctx.location.project.canonical` доступен и в Promise-, и в Effect-плагинах ([Context](https://opencode.ai/docs/build/plugins/server#context)). Канонический корень переживает запуск из worktree, поэтому он определяет проект, а не текущий каталог процесса.

MCP-серверами плагин управляет только трансформами. Запись `disabled: true` отключает сервер и разрывает соединение, `disabled: false` включает его, а `reload()` повторно применяет трансформы и выравнивает жизненный цикл серверов ([MCP](https://opencode.ai/docs/build/plugins/server#mcp)). Конфигурация с фиксированным `cwd` этого механизма обходит.

Записи `instructions.entry` рендерятся как `<context key="...">` и объявляются об обновлении на следующей границе шага без очереди сообщений ([Sessions](https://opencode.ai/docs/build/plugins/server#sessions)). Хуки `context` меняют только исходящий вызов и не меняют сохранённую историю. Хуки `prompt` идут в порядке регистрации после готовности плагинов локации сессии, работают до admission и могут добавить файлы ([Hooks](https://opencode.ai/docs/build/plugins/server#hooks)). Повтор уже доставленного промпта не запускает хуки заново, а параллельные отправки могут вызвать их несколько раз, поэтому постоянный контекст хранится в `instructions.entry`, а не в эффектах хука.

## Последствия

- Из решения выходят три карточки со статусом `todo` и ссылкой `ADR 0069`. Владельцы файлов указаны в самих карточках.
  - T3.176, каркас V2-плагина и граница проекта. Владельцы: `.opencode/plugins/beacon-project/package.json`, `.opencode/plugins/beacon-project/index.js`, `.opencode/plugins/beacon-project/location.js`, `tests/adapter/beacon-project-location.test.js`.
  - T3.177, регистрация MCP-сервера Beacon через `ctx.mcp.transform`. Владельцы: `.opencode/plugins/beacon-project/mcp.js`, `tests/adapter/beacon-project-mcp.test.js`, `cmd/beacon/doctor.go`, `cmd/beacon/state_dir_test.go`.
  - T3.178, загрузка проектного контекста в сессии. Владельцы: `.opencode/plugins/beacon-project/context.js`, `tests/adapter/beacon-project-context.test.js`.
- Проверка карточек. Плагин загружается из `.opencode/plugins/` без правки глобального конфига. В worktree MCP-сервер получает корень канонического проекта, а не каталог worktree. Контекст сессии содержит открытые карточки и `AGENTS.md` только для сессий этого проекта и не дублируется при повторе промпта.
- ADR 0001-0068 не переписываются. ADR 0011 сохраняет каталог состояния, ADR 0019 и ADR 0021 сохраняют жизненный цикл Watch и изоляцию через worktree, ADR 0022 оставляет проверки в CI.
- Тесты этого ADR не запускались, код не менялся. В PR на реализацию каждой карточки агент приводит команду прогона и фактический вывод.

## Отклонённое

Не оставлять хардкод `cwd` в `opencode.json` и не расширять `stateDir()` ради каждого нового проекта. Подход требует ручной правки конфига при каждом worktree и не различает проекты в одном сервере.

Не писать самописный MCP-клиент или второй мост поверх плагина. Документация даёт `ctx.mcp` и трансформы, а `stateDir()` в Go должен получать корень явно.

Не подменять постоянный контекст разовым промптом. Промпт попадает в сохранённую историю и дублируется при повторной отправке.

Не читать `ctx.location` как местоположение каждой сессии. Документация прямо ограничивает его экземпляром плагина, поэтому принадлежность сессии проверяется отдельно.
