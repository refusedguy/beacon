# ADR 0055. Шесть фич из отчёта AM-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AM «AM волна: новые проекты по восьми темам Beacon» от 20 ноября 2026 года ([AM, строка 1](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L1)). Поиск шёл через `gh api search/repositories` по восьми темам с фильтром `pushed:>=2026-01-01`, всего 235 уникальных кандидатов; исключены репозитории из отчётов A-AL в этой папке, дата коммита взята из `commit.author.date`, а не из `pushed_at`; в выборку вошли 19 проектов, у каждого есть коммит в 2026 году ([AM, строка 5](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L5)). Фичи взяты из раздела «Фичи», пункты 1, 2, 3, 7, 9 и 17 ([AM, строки 108-146](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L108)), а также из итога отчёта ([AM, строка 206](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L206)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0054 и 171 карточке из `docs/tasks/`. Идемпотентность, interrupted-результат, состояния аренды и wake уже зафиксированы: ADR 0028 задаёт идемпотентность по `clientRequestId`, T3.23 `RejectDuplicate` и `idempotency_key`, T3.64 `indeterminate` результата задачи, T3.94 STALE-колонку в `beacon agents`, ADR 0017 лестницу пробуждения, ADR 0048 событие в контексте агента, ADR 0045 приоритетную очередь вопросов. Поэтому эти темы здесь не повторяются. Несколько новых пунктов похожи на существующие по имени, но различаются по уровню. Фича 1 это оборванный вызов инструмента и idempotent send по `requestId`, а не результат задачи `indeterminate` из T3.64. Фича 2 это фиксированный job ID, а не ключ попытки из T3.23 и не `clientRequestId` из ADR 0028. Фича 3 это старт ровно один раз по событию, а не вердикт как событие в контексте из ADR 0048. Фича 4 это явные состояния аренды для reclaim и строгий код выхода, а не колонка вывода из T3.94. Фича 5 это очередь внимания по сессиям, а не способ доставки follow-up из ADR 0026 и не приоритеты вопросов из ADR 0045. Фича 6 это отдельный дочерний агент для idle wait, а не ступень лестницы ADR 0017. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Отдельный результат `interrupted` и idempotent send по `requestId`. Когда рестарт обрывает вызов инструмента, Beacon возвращает `interrupted`, а не перезаписывает результат молча и не заставляет агента повторять вызов вслепую. Отправка вызова идемпотентна по `requestId`: повтор после рестарта не запускает bash с сайд-эффектом второй раз, а возвращает прежний исход или состояние `interrupted`. Это исход вызова инструмента на уровне выполнения. T3.64 называет `indeterminate` результат задачи, когда действие выполнено, а ответ потерян. Здесь фиксируется оборванный вызов, и агент сам решает, что делать.

2. `idempotency_key` превращается в фиксированный job ID. Ключ идемпотентности определяет постоянный идентификатор задачи. Политика `RejectDuplicate` запрещает второй запуск с этим ключом, а не возвращает уже существующую задачу как при повторе из T3.23. Запуск с тем же job ID признаётся попыткой дублирования и отклоняется. Это фиксированный ID задачи, а не ключ попытки из T3.23 и не `clientRequestId` из ADR 0028, который гасит повторы `wait_result`, `steer` и `ack`.

3. `SetWorkflowID(event_id)` и durable notifications с таймаутом в дни. Beacon использует идентификатор события как workflow ID, поэтому старт по одному и тому же событию происходит ровно один раз. Уведомления о результате долговечны и имеют таймаут, измеряемый днями, а не секундами ожидания соединения. Это старт по событию, а не вердикт CI, вставленный в контекст агента как факт в ADR 0048, и не команда, отправленная за агента.

4. Явные состояния аренды worktree и строгий код выхода. Слот аренды находится в одном из состояний `leased`, `in-use`, `dirty`, `unverified` и `locked`. Возврат слота сообщается разными кодами выхода: отдельно «событие обработано и аренда освобождена», отдельно «аренда ещё жива и слот не освободился». Состояния предназначены для reclaim, а не для вывода в CLI. T3.94 добавляет STALE-колонку в `beacon agents` как отображение, здесь фиксируется машина состояний и пригодный для сценариев код выхода.

5. Очередь внимания inbox. Сессии живут в очереди с переходами blocked → finished-unseen → working → idle → settled. Сессия в `settled` поднимается снова, когда в ней появилась новая работа, а история чата открывается заново вместо создания новой сессии. Beacon различает «завершено» и «завершено, но пришло новое событие». Это очередь внимания по сессиям, а не способ доставки follow-up из ADR 0026 и не приоритетная очередь вопросов к человеку из ADR 0045.

6. Idle wait как отдельный дочерний агент. Ожидание простоя выделяется в дочернего агента, который спит без расхода токенов и просыпается мгновенно, когда приходит новая задача. Родительская сессия не держит длинный вызов и не опрашивает источник по интервалу. Это граница дочернего процесса, а не ветвление лестницы пробуждения из ADR 0017: лестница решает, как доставлять и когда эскалировать, а здесь решается, кто именно ждёт.

## Причина

1. disler/durable-pi это durable-агент, который живёт на устройстве, а клиенты только смотрят и управляют; SQLite хранит историю, входящие задачи, чектпоинты и состояние до того, как что-то показывается ([AM, строка 24](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L24), [durable-pi](https://github.com/disler/durable-pi/blob/main/README.md#what-is-a-durable-agent)). Без отдельного результата агент молча повторяет bash с сайд-эффектом ([AM, строка 114](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L114), [API](https://github.com/disler/durable-pi/blob/main/README.md)). T3.64 называет `indeterminate` результат задачи, когда действие выполнено, а ответ потерян, но не различает вызов инструмента, оборванный рестартом. Берутся `interrupted` и idempotent send, а не требования Node 24, `just`, zsh, OpenRouter ключ, веб-хаб и агенты на нескольких устройствах ([AM, строка 168](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L168)).

2. nicogranuja/durable-mcp это MCP-сервер, где долгая задача сразу возвращает job ID, а Temporal держит состояние, ретраи и отмену ([AM, строка 94](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L94), [durable-mcp](https://github.com/nicogranuja/durable-mcp/blob/main/README.md)). Политика `RejectDuplicate` запрещает запустить задачу второй раз, когда `idempotency_key` превращается в фиксированный job ID ([AM, строка 142](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L142), [Architecture](https://github.com/nicogranuja/durable-mcp/blob/main/README.md#architecture)). T3.23 при повторе возвращает уже существующую задачу, ADR 0028 гасит повтор MCP-команд менеджера. Ни одно не запрещает второй запуск задачи целиком. Берутся фиксированный ID и политика отклонения, а не обязательный сервер Temporal и незавершённый статус проекта с непройденным чек-листом идемпотентности, валидации и авторизации ([AM, строка 196](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L196)).

3. dbos-inc/dbos-transact-py это лёгкие durable workflows на Postgres, где аннотации превращают функции в чектпоинтируемые шаги, рядом durable очереди, уведомления и события ровно один раз ([AM, строка 54](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L54), [dbos-transact-py](https://github.com/dbos-inc/dbos-transact-py/blob/main/README.md#what-is-dbos)). `SetWorkflowID(event_id)` даёт идемпотентный старт ровно один раз по событию, а durable notifications живут с таймаутом в дни или недели ([AM, строка 126](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L126), [Exactly-Once Event Processing](https://github.com/dbos-inc/dbos-transact-py/blob/main/README.md), [Durable Notifications](https://github.com/dbos-inc/dbos-transact-py/blob/main/README.md)). ADR 0048 кладёт вердикт CI в контекст агента событием и запрещает промпт за агента, но не решает, что идентификатор события является ключом старта. Берутся событийный ID и долгий таймаут уведомления, а не Postgres-only Python SDK без встроенного SQLite ([AM, строка 180](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L180)).

4. kunchenguid/treehouse это пул переиспользуемых git worktree с арендами, где агент получает изолированное окружение сразу ([AM, строка 44](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L44), [treehouse](https://github.com/kunchenguid/treehouse/blob/main/README.md)). Состояния слотов `leased`, `in-use`, `dirty`, `unverified` и `locked` идут вместе с командой `return --if-clean`; Beacon должен отвечать разными кодами выхода для «event обработан» и «аренда ещё жива» ([AM, строка 122](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L122), [состояния слотов](https://github.com/kunchenguid/treehouse/blob/main/README.md)). T3.94 добавляет в `beacon agents` колонку STALE для показа, но не задаёт машину состояний и не различает коды выхода. Берутся состояния для reclaim и строгий exit code, а не 74-килобайтный README с APFS-клонами и anonymous lock протоколом ([AM, строка 176](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L176)).

5. douglascorrea/herdr-agent-inbox это инбокс для кодинг-агентов с заголовками сессий, очередью внимания blocked → finished-unseen → working → idle → settled и историей чатов, которые открываются заново ([AM, строка 19](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L19), [herdr-agent-inbox](https://github.com/douglascorrea/herdr-agent-inbox/blob/main/README.md#what-you-get)). Сессия уходит в settled, но сама возвращается наверх, когда в ней снова появилась работа ([AM, строка 112](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L112), [Inbox triage](https://github.com/douglascorrea/herdr-agent-inbox/blob/main/README.md#what-you-get)). ADR 0026 описывает способ доставки follow-up, ADR 0045 задаёт приоритеты вопросов к человеку. Ни одно не хранит состояние внимания самой сессии и не различает завершённую сессию от завершённой с новым событием. Берётся семантика автооткрытия, а не плагин к TUI herdr на Python stdlib без API ([AM, строка 166](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L166)).

6. open-inspect/background-agents это фоновый кодинг-агент, которого запускают из веба, Slack, GitHub PR, Linear или вебхука, он работает в песочнице и открывает PR ([AM, строка 14](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L14), [background-agents](https://github.com/open-inspect/background-agents/blob/main/README.md#overview)). Для Beacon это idle wait в отдельном дочернем агенте с мгновенным пробуждением по новой задаче, а не ступень лестницы ADR 0017: там ветвление по исходу доставки, здесь владелец ожидания. Берётся граница дочернего агента, а не большой TypeScript-сервис с веб-UI, моделью ownership и single-tenant режимом ([AM, строка 164](/home/nbook/Projects/tmp/beacon-research/AM-wave.md#L164)).

- Проверка карточек: оборванный рестартом вызов возвращает `interrupted`, а повтор с тем же `requestId` не запускает сайд-эффект второй раз; повторный старт с тем же `idempotency_key` отклоняется как `RejectDuplicate` и не создаёт вторую задачу; старт по одному `event_id` происходит ровно один раз, а уведомление живёт с таймаутом в дни; слот аренды проходит состояния `leased`, `in-use`, `dirty`, `unverified`, `locked`, а при живой аренде возвращается отдельный код выхода; сессия в `settled` поднимается по новому событию и открывает прежнюю историю чата; дочерний агент idle wait спит без опроса и просыпается сразу при новой задаче.
- ADR 0001-0054 c T3.23, T3.64, T3.94, T3.97, T3.109, ADR 0015, 0017, 0020, 0021, 0025, 0026, 0028, 0031, 0045, 0048 и 0053 не переписываются. `interrupted` фичи 1 не подменяет `indeterminate` T3.64 и `clientRequestId` ADR 0028. Фиксированный ID фичи 2 не отменяет ключ попытки T3.23. Старт по `event_id` фичи 3 не меняет событие в контексте из ADR 0048 и доставку ADR 0026. Состояния фичи 4 не дублируют STALE-колонку T3.94, аренду T3.97 и heartbeat T3.109. Очередь фичи 5 не заменяет приоритеты ADR 0045 и курсор ADR 0025. Дочерний агент фичи 6 не добавляет ступень в лестницу ADR 0017 и не меняет долгий HTTP idle из ADR 0053. Один мост на протокол из ADR 0024, изоляция worktree из ADR 0021 и проверка только в CI из ADR 0022 дополнительной не становятся.
