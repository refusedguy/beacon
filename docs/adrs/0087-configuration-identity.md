# ADR 0087. Идентичность конфигурации и псевдонимы

Статус: accepted

## Контекст

ADR 0086 разделяет авторский конфиг и состояние реестра. Нужно зафиксировать, как авторский файл определяет идентичность конфигурации проекта. OpenRig строит идентификатор из отсортированного списка участников вида `pod.member=runtime`.

Watch хранит `config_id`. Если конфиг меняется, идентичность меняется. eval r06 требует, чтобы старый watch сохранял `config_id` A, а регистрация с B отклонялась. Для этого нужен детерминированный идентификатор и стабильный digest.

## Решение

Configuration ID это детерминированная строка пар `id=runtime`, построенная по roster авторского файла.

Каждый участник roster даёт одну пару `<id>=<runtime>`. Пары сортируются по `<id>` в лексикографическом порядке, а не по runtime. Пары соединяются запятой без пробелов. Пробелы внутри `id` и `runtime` запрещены. Формат строки:

`id1=runtime1,id2=runtime2,...`

Псевдонимы не входят в ID. Presets и `recommended` хранятся отдельно от configuration ID и ссылаются на уже существующий ID. Псевдоним обязан указывать на существующий ID. `recommended` указывает ровно на один ID. Переименование псевдонима или смена `recommended` не меняют configuration ID.

Пример. Roster содержит участников `opus=claude-code`, `gpt=codex` и `ci=stub`. Сортировка по `id` даёт порядок `ci`, `gpt`, `opus`. Канонический ID:

`ci=stub,gpt=codex,opus=claude-code`

Любой порядок подачи участников даёт ту же строку. Это и есть проверка канонического порядка.

Configuration ID пригоден для digest. ID это читаемый идентификатор roster. Digest это стабильный хеш полного авторского файла. Канонический JSON сериализуется с отсортированными полями, затем по нему считается SHA-256. Одинаковый порядок полей даёт одинаковый digest. Изменение roster меняет digest. Watch сравнивает digest при регистрации, поэтому конфиг B даёт другой digest и отклоняется, а старый watch сохраняет `config_id` A.

## Последствия

- Генератор ID сортирует пары по `id`, соединяет их запятыми и запрещает пробелы.
- Digest считается по каноническому JSON с отсортированными полями и SHA-256.
- Presets и `recommended` живут отдельно от ID и содержат ссылку на существующий ID.
- Изменение roster меняет и ID, и digest. Изменение псевдонима меняет ни то, ни другое.
- eval r06 проверяет, что старый watch сохраняет `config_id` A после смены конфига на B.
