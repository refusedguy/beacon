# ADR 0056. Шесть фич из отчёта AN-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AN «AN волна: новые проекты по восьми темам Beacon» от 20 ноября 2026 года ([AN, строка 1](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L1)). Поиск шёл через `gh api search/repositories` по восьми темам и смежным формулировкам, всего 30 поисковых запросов с фильтром `pushed:>=2026-01-01`, получено 745 уникальных `owner/repo`; из отчётов A-AM извлечено 780 уникальных пар и убраны все совпадения, осталось 631; дата коммита проверена через `commit.author.date`, а не через `pushed_at`, коммит в 2026 году подтверждён у 627; после поименной проверки вошли 21 проект, это больше минимума в 12 ([AN, строка 5](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L5)). Фичи взяты из раздела «Фичи», пункты 1, 2, 3, 16 и 17 ([AN, строки 160-176](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L160)), а telemetry ожидания из раздела «Перформанс» и итога ([AN, строка 186](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L186), [AN, строка 228](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L228)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0055 и 171 карточке из `docs/tasks/`. Durable task handle, WAL, идемпотентность и лестница пробуждения уже зафиксированы: T3.113 задаёт handle фоновой задачи, T1.8 атомарную запись вердикта в транзакции, ADR 0028 и T2.22 идемпотентность по `clientRequestId`, ADR 0017 и T3.80 лестницу пробуждения и `wake_between`. Поэтому эти темы здесь не повторяются как новые. Несколько новых пунктов похожи на существующие по имени, но различаются по уровню. Фича 1 это протокольный контракт `tasks/get` с TTL и уведомлениями, а не внутренний handle из T3.113. Фича 2 это порядок записи WAL перед ответом «принято», а не просто транзакция из T1.8. Фича 3 это активная детекция дубля промпта на входе, а не ключ запроса из T2.22 и ADR 0028. Фича 4 это батч событий в одно пробуждение, а не разброс пробуждений по времени из T3.80. Фича 5 это позиция SEQ в CLI `wait`, а не курсор событий MCP из ADR 0025. Фича 6 это метрика ожидания в stats, а не порог лимита из T3.52. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Контракт `tasks/get` официального расширения `io.modelcontextprotocol/tasks`. Сервер возвращает `task_id` сразу, соединение не держится, а клиент следит за прогрессом и забирает результат позже. В контракт входят TTL задачи и уведомления о прогрессе и результате. Это протокольный контракт долгой задачи на уровне MCP, а не внутренний handle фоновой задачи из T3.113, который решает, как Beacon хранит и отдаёт результат своего watch. Хранилище, очередь и доставку событий Beacon оставляет за собой.

2. Write-ahead log перед ответом «принято». Состояние задачи пишется на диск до того, как CLI сообщит клиенту, что задача принята. Если ответить раньше записи, то после рестарта клиент опрашивает ID, которого нет на диске. Это именно порядок WAL относительно ответа, а не атомарная транзакция из T1.8: T1.8 фиксирует вердикт, обязательство и wake-intent в одной записи, но сам по себе не задаёт точку ответа «принято».

3. Активное обнаружение дублирующего промпта плюс мгновенный `operationId` на входе. Команда, запускающая долгую работу, сразу выдаёт идентификатор операции и проверяет, не запущен ли уже равный промпт. Повторное обращение возвращает существующий `operationId` вместо второй задачи. Это детекция дубля по содержимому промпта, а не ключ идемпотентности запроса `clientRequestId` из T2.22 и ADR 0028, который гасит повторы MCP-команд после обрыва соединения.

4. Батчинг событий за 200 мс в одно пробуждение. События, пришедшие в одном окне 200 мс, сливаются в один wake сессии. Это защита от шторма уведомлений, когда лог сыплет строками. Здесь решается кратность пробуждения, а не разброс пробуждений по времени: `wake_between` из T3.80 защищает от thundering herd и сдвигает пробуждения во времени, но не сливает несколько событий в одно.

5. Ожидание с позицией в журнале: `wait --after SEQ`. CLI возобновляет ожидание строго после SEQ и возвращает только события с позицией больше SEQ. Позиция живёт в журнале задач Beacon и не требует опроса. Это SEQ в команде CLI wait, а не курсор событий MCP из ADR 0025, который задаёт, какой статус и какую позицию отдавать подписчику через протокол.

6. Телеметрия ожидания в stats. Beacon добавляет метрику простоя: долю времени, потраченного на ожидание CI, и среднее число одновременно работающих воркеров. Метрика показывает простой там, где сейчас видны только активность и пороги лимитов. Это измерение ожидания, а не пороги 75 и 90 процентов из T3.52, которые предупреждают о приближении к лимиту плана и не говорят, сколько времени агенты ждут.

## Причина

1. modelcontextprotocol/ext-tasks это официальное расширение MCP `io.modelcontextprotocol/tasks` на базе SEP-2663: сервер возвращает durable task handle, клиент следит за прогрессом и забирает результат позже ([AN, строка 11](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L11), [README](https://github.com/modelcontextprotocol/ext-tasks/blob/main/README.md#why-tasks)). Проект на TypeScript, 66 звёзд, Apache-2.0, последний коммит cc9aaac от 4 ноября 2026 года из commits API ([AN, строки 12-13](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L12)). Отсюда берётся контракт `tasks/get` с TTL и уведомлениями, чтобы CLI возвращал `task_id` сразу и не держал соединение ([AN, строка 15](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L15), [AN, строка 160](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L160)). T3.113 описывает внутренний handle wait output notify и не задаёт протокольный контракт с TTL. Берётся контракт, а не спецификация и эталонный TypeScript-пакет целиком: хранилище, очередь и доставку событий придётся писать самим ([AN, строка 16](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L16), [README](https://github.com/modelcontextprotocol/ext-tasks/blob/main/README.md#schemas)).

2. AndresSaa/mcp-durable-tasks это библиотека для MCP-сервера, где `WalTaskStore` пишет задачу на диск до возврата из `createTask()`, и `tasks/get` отвечает после краша ([AN, строка 21](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L21), [README](https://github.com/AndresSaa/mcp-durable-tasks/blob/main/README.md)). Проект на TypeScript, 0 звёзд, MIT, последний коммит 7166378 от 11 ноября 2026 года ([AN, строки 19-20](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L19)). Отсюда берётся порядок записи: состояние задачи должно лежать на диске до ответа «принято», иначе после рестарта клиент опрашивает несуществующий ID ([AN, строка 22](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L22), [AN, строка 161](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L161), [README, Two limits to know first](https://github.com/AndresSaa/mcp-durable-tasks/blob/main/README.md#two-limits-to-know-first)). T1.8 уже требует мутации на диске до ответа клиенту, но в контексте вердикта, обязательства и wake-intent в одной транзакции; здесь фиксируется точка ответа «принято» именно для создания задачи. Берётся порядок WAL, а не однопроцессная модель: второй процесс на том же каталоге портит лог, живой воркер привязан к процессу, а версия 0.5.0 обещает ломающие изменения до 1.0 ([AN, строка 23](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L23), [README, Status](https://github.com/AndresSaa/mcp-durable-tasks/blob/main/README.md#status)).

3. aresyn/codex-control-plane-mcp это MCP-сервер, который превращает Codex Desktop в durable-воркера, сразу выдаёт `operationId` или `workflowId`, ведёт историю и Plan Mode и защищает от дублей промпта ([AN, строка 28](/home/nbook/Projects/tmp/beacon-research/AN-wave.md#L28), [README](https://github.com/aresyn/codex-control-plane-mcp/blob/main/README.md)).   - Фича 4: `internal/infra/ladder/transitions.go`, `internal/infra/ladder/escalation.go`, `internal/infra/mcp/tool_wake.go`, `internal/infra/store/observability.go`, `cmd/beacon/watch.go` и тесты к ним.
  - Фича 5: `cmd/beacon/watch.go`, `cmd/beacon/commands.go`, `cmd/beacon/task.go`, `internal/app/taskcli/service.go`, `internal/infra/store/db.go` и тесты к ним.
  - Фича 6: `internal/infra/mcp/tool_stats.go`, `internal/infra/store/observability.go`, `internal/infra/store/db.go`, `cmd/beacon/agents.go` и тесты к ним.
- Проверка карточек: `tasks/get` возвращает `task_id` сразу, соединение не держится, TTL и уведомления описаны в контракте; состояние задачи лежит на диске до ответа «принято», и после рестарта опрос по выданному ID находит задачу; повтор равного промпта возвращает прежний `operationId` и не создаёт вторую задачу; события в окне 200 мс дают одно пробуждение сессии; `wait --after SEQ` возвращает только события после SEQ; stats показывает долю ожидания и среднее число воркеров отдельно от порогов лимитов.
- ADR 0001-0055 c T3.113, T1.8, T2.22, T3.80, T3.52, ADR 0015, 0017, 0020, 0021, 0022, 0024, 0025, 0028 не переписываются. Протокольный контракт фичи 1 не подменяет внутренний handle T3.113. Порядок WAL фичи 2 не отменяет транзакцию T1.8 и хранилище ADR 0015. Детекция дубля фичи 3 не заменяет `clientRequestId` T2.22 и ADR 0028 и не меняет ключ попытки T3.23. Батч фичи 4 не добавляет ступень в лестницу ADR 0017 и не сдвигает пробуждения как `wake_between` T3.80. Позиция SEQ фичи 5 не меняет курсор ADR 0025 и доставку ADR 0026. Метрика фичи 6 не трогает пороги T3.52. Один мост на протокол из ADR 0024, изоляция worktree из ADR 0021 и проверка только в CI из ADR 0022 дополнительной не становятся.
