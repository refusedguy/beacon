# ADR 156: Orchestrator workload

Статус: accepted

## Контекст

Оркестратор цикла Beacon принимает решения по Watch, но сегодня не числится их подписчиком. Он держит список Watch в промпте и считает вердикты вручную. Когда меняется ревизия или появляется blocked Watch из ADR 0155, этот список расходится с store. Оркестратор видит старый `retry` и отправляет исполнителя чинить чужую поломку.

Часть задачи уже закрыта существующими механизмами. `beacon_get_result` выдаёт вердикт одного Watch и штампует `readAt` на обязательстве подписчика. Роль `orchestrator` есть в словаре ролей домена. `Fanout.Subscribe` добавляет подписчика и идемпотентно продлевает его обязательство. Daemon уже регистрирует оркестратора на Watch, которые нашёл `checkall`, но не на всех активных Watch проекта. Команда `beacon watch` показывает вотчину, но не даёт сводки по вердиктам и проектам.

Контракт MCP зафиксирован ровно на семи инструментах в `internal/infra/mcp/contract_test.go`. Восьмой инструмент ломает этот контракт и бюджет `tools/list` в 64 KiB. Сводку нельзя добавить как MCP-инструмент.

## Решение

Оркестратор становится обычным подписчиком Beacon с ролью `orchestrator`. Он регистрируется через тот же `beacon_watch_pr` и тот же `Fanout.Subscribe`, что и исполнитель, под стабильным ID `beacon-orchestrator`. Отдельного списка Watch и отдельной таблицы состояний нет. Источник правды для оркестратора это store проекта.

Авто-подписка живёт в проходе daemon. На каждом проходе daemon читает `ActiveWatches()` и для каждого Watch без подписчика с ролью `orchestrator` вызывает register-порт с ролью `orchestrator` и notify `opencode:beacon-orchestrator`. Повтор вызова с тем же Watch и подписчиком продлевает существующее обязательство и не двигает ревизию. Watch, появившийся между проходами, получает обязательство на следующем проходе. Лимит в 50 Watch на подписчика сохраняется. При превышении daemon логирует пропуск и показывает такой Watch в сводке как `uncovered`, чтобы непокрытый Watch не выглядел готовым.

Вердикт одного Watch оркестратор читает только через `beacon_get_result`. Для blocked Watch из ADR 0155 ответ содержит `verdict=blocked`, причину и `failedChecks` из снимка CI. Перед спавном FIX-агента и перед мержем оркестратор сверяет revision ответа с ревизией Watch. Сводка не подменяет чтение вердикта.

Сводка бэклога живёт в CLI `beacon workload [--project <key>|--all] [--format table|json]`. Команда читает state проекта и группирует активные Watch по проекту и вердикту: `ready`, `retry`, `blocked`, `watching`. С флагом `--all` она обходит каталоги `<XDG_STATE_HOME>/beacon/projects/*` и печатает строку на каждый проект. Без флага читается проект текущего cwd. Вердикт `blocked` идёт отдельной строкой с причиной и числом `failedChecks`, его не смешивают с `retry`. Команда не обращается к GitHub и не меняет состояние. Восьмого MCP-инструмента нет, тест контракта не меняется.

Чистая функция сводки лежит в `internal/app/orchestrator`. Её вызывает и CLI, и проход daemon. Daemon пишет ту же сводку в лог после `checkall`, `orchestrate` и `close-merged`. Перед проходом `orchestrate` daemon гарантирует, что у каждого активного Watch есть обязательство оркестратора. Описание Watch принимается по `beacon_get_result`, а не по строке лога.

## Последствия

Оркестратор перестаёт держать бэклог в голове. Число Watch по вердиктам приходит из store и совпадает с тем, что видит исполнитель. Исполнитель и оркестратор остаются разными подписчиками с разными обязательствами, wake шлётся по adapter из реестра.

ADR 0155 получает наблюдаемое место в сводке. FIX-агент запускается по причине и `failedChecks` blocked Watch, а не по общему счётчику retry. Оркестратор видит число Watch, заблокированных чужими проверками, до чтения деталей.

Новых ролей, MCP-инструментов и миграций нет. Авто-подписка использует существующие таблицы обязательств и биндингов. `contract_test.go` по-прежнему ожидает семь инструментов. Единственная новая команда это `beacon workload`, она попадает в каталог `beacon list`.

Сводка это снимок на момент чтения. Между чтением сводки и действием ревизия может измениться, поэтому перед мержем и спавном обязателен `beacon_get_result` со сверкой revision. Лимит в 50 Watch на подписчика означает, что в большом проекте часть Watch останется без обязательства оркестратора. Daemon обязан показать их в `uncovered`, а не выдавать сводку как полную.
