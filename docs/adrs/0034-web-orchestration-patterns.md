# ADR 0034. Четыре фичи из отчёта M-web-orchestration-patterns

Статус: accepted

Этот ADR фиксирует четыре фичи из отчёта M «Паттерны оркестрации агентов из первичных источников» от 19 ноября 2026 года, разделы 5 и 6, строки 90-151 ([M-web, строка 90](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L90)). Ни одна из четырёх фич не разложена в ADR 0001-0033. Владелец велел принять их без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код и тесты в этой задаче не трогаются.

## 1. Рубрика результата и отдельная проверка результата

Решение. Задача получает рубрику из проверяемых критериев до начала прогона. Факт завершения прогона и результат проверки по рубрике становятся двумя разными состояниями. Проверку ведёт отдельный grader в собственном контекстном окне, который не зависит от решений основного агента. Grader возвращает объяснение по каждому критерию, и это объяснение уходит агенту на следующую итерацию. Число итераций ограничено, по умолчанию три, максимум двадцать. Результат проверки принимает значения `satisfied`, `needs_revision`, `max_iterations_reached`, `failed` или `interrupted`. Терминальный вердикт задачи выставляется по проверке результата, а не по статусу прогона. Признак завершённости составной: все видимые прогоны получили `workflow_run.status_ended`, после чего пришёл `session.status_idle` с `stop_reason: end_turn` не из-за нашего прерывания ([M-web, строка 92](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L92), [M-web, строка 94](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L94)).

Причина. Документ Anthropic прямо пишет, что прогон может завершиться `completed`, хотя работа на его потоках провалилась или поток не удалось создать. Чтобы найти неудавшуюся работу, нужно читать события каждого потока ([Anthropic, Define outcomes](https://platform.claude.com/docs/en/managed-agents/define-outcomes), [Anthropic, Workflow runs](https://platform.claude.com/docs/en/managed-agents/workflow-runs)). Отчёт повторяет это правило для Beacon: зелёный CI не доказательство, нужен набор критериев и отдельная проверка ([M-web, строка 98](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L98), [M-web, строка 125](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L125), [M-web, строка 143](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L143)). ADR 0022 описывает только проверку в CI и не отвечает на вопрос, сделана ли работа.

Последствия. Появляется поле рубрики в задаче и отдельная запись результата проверки рядом с терминальным вердиктом из ADR 0019 и 0025. Статус `completed` сам по себе не закрывает задачу. Число MCP-инструментов остаётся равным семи, ADR 0003 и 0009 не меняются. Владельцы файлов для будущей карточки: `internal/domain/types.go`, `internal/domain/verdict.go`, `internal/infra/mcp/schema.go`, `internal/infra/mcp/tool_get_result.go`, `internal/infra/store/db.go` и тесты к ним.

Отклонённое. Считать успехом статус `completed` или зелёный CI без проверки по рубрике. Поручить проверку основному агенту в том же контексте, где он принимал решения. Формулировать критерии после прогона: так проверка подгоняется под уже полученный результат.

## 2. Аутентификация одобрения перед применением

Решение. Перед применением одобрения ядро проверяет рецензента, авторизует его на конкретный прогон и сверяет идентификаторы решений с ожидающими решениями на сервере. Только после трёх проверок одобрение меняет состояние задачи. Снимок, присланный клиентом вместе с одобрением, не становится источником истины. Список ожидающих решений ядро читает из своего хранилища. Секреты в сериализуемом состоянии не хранятся без нужды ([M-web, строка 149](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L149), [M-web, строка 147](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L147)).

Причина. OpenAI описывает именно такой порядок для долгоживущих одобрений: аутентифицировать рецензента, авторизовать его на прогон, сверить идентификаторы решений с ожидающими на сервере и только потом применять одобрение ([OpenAI, Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)). Снимок `RunState` содержит контекст приложения, метаданные и состояние одобрений, поэтому его нужно считать сохранёнными данными и не принимать от клиента как есть ([OpenAI, Run state](https://openai.github.io/openai-agents-python/ref/run_state/), [M-web, строка 42](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L42)). ADR 0028 задал идемпотентность по `clientRequestId`, но не решал вопрос, кто имеет право одобрить конкретный прогон.

Последствия. В контракт `ack` входит проверка рецензента и привязка решения к прогону, а список ожидающих решений читается из хранилища до записи одобрения. Отклонённое или неавторизованное одобрение не меняет состояние и не снимает ожидание человека из ADR 0028. Число MCP-инструментов не меняется. Владельцы файлов для будущей карточки: `internal/infra/mcp/tool_ack.go`, `internal/infra/mcp/server.go`, `internal/domain/identity.go`, `internal/infra/store/receipts.go`, `internal/infra/store/db.go` и тесты к ним.

Отклонённое. Доверять снимку и идентификатору решения, присланным клиентом. Проверять только рецензента, но не привязывать одобрение к конкретному прогону. Хранить секреты или полный контекст приложения в снимке рядом с одобрением.

## 3. Метка версии агента рядом со снимком и одобрением

Решение. Каждый сохранённый снимок и каждое отложенное одобрение несут метку версии агента на момент сохранения. Метка фиксирует модель, промпт и набор инструментов, которые создали снимок. Когда одобрение лежит долго, чтение старого снимка идёт по его метке, а не по текущей конфигурации агента ([M-web, строка 151](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L151)).

Причина. OpenAI рекомендует хранить версию агента рядом со снимком, если одобрения могут лежать долго: после смены модели, промпта или инструментов нужно знать, как читать старый снимок ([OpenAI, Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)). У Anthropic похожая привязка к версии агента есть в списках `predefined_agents` ([Anthropic, Multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration), [M-web, строка 151](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L151)). Без метки долго ожидающее одобрение применяется к снимку, который текущая версия агента уже не понимает.

Последствия. В схему состояния задачи и в запись ожидающего одобрения добавляется поле версии агента. При смене модели, промпта или инструментов старые записи сохраняют свою метку и читаются по ней. ADR 0012 о версионировании и redaction не отменяется: метка описывает агента, а не версию корпуса. Владельцы файлов для будущей карточки: `internal/domain/types.go`, `internal/infra/taskstore/store.go`, `internal/infra/store/db.go`, `internal/infra/mcp/tool_ack.go`, `internal/infra/mcp/schema.go` и тесты к ним.

Отклонённое. Определять версию снимка по текущей конфигурации агента в момент чтения. Хранить метку только в настройках агента и не копировать её в запись одобрения. Считать, что одобрения всегда приходят быстро, поэтому версия не нужна.

## 4. Дедупликация вебхуков по `event.id` и чтение состояния из GET/Snapshot

Решение. Каждое входящее событие вебхука имеет идентификатор доставки `event.id`. Повтор с тем же `event.id` отбрасывается до начала обработки. Состояние задачи после события берётся из GET-запроса к ресурсу или из авторитетного снимка, а не из порядка прихода событий. Событие несёт тип и идентификатор, а не полный объект состояния. Доставка повторяется до трёх раз с задержкой от 5 до 120 секунд, порядок доставки не гарантирован, после третьей неудачи событие выбрасывается без сигнала, а ответ 3xx отключает подписку ([M-web, строка 74](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L74), [M-web, строка 82](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L82), [M-web, строка 106](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L106)).

Причина. Повторная доставка это норма вебхуков Anthropic, и повтор приходит с тем же `event.id` ([Anthropic, Subscribe to webhooks](https://platform.claude.com/docs/en/managed-agents/webhooks)). Поскольку порядок не гарантирован, состояние нельзя выводить из последовательности событий. Отчёт прямо называет чтение состояния через GET вместо порядка событий ([M-web, строка 74](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L74), [M-web, строка 117](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L117), [M-web, строка 138](/home/nbook/Projects/tmp/beacon-research/M-web-orchestration-patterns.md#L138)).

Это не дубли двух прежних решений. Курсор из ADR 0025 служит для продолжения чтения потока и не идентифицирует доставку вебхука. `clientRequestId` из ADR 0028 служит ключом для команд клиента и не имеет отношения к повторной доставке события от сервера. Здесь ключ именно `event.id` вебхука, и чтение состояния идёт из GET/Snapshot, а не из позиции в потоке. Обработчик остаётся внутри одного моста на протокол по ADR 0024.

Последствия. В хранилище появляется индекс уже обработанных `event.id`, отдельный от индекса `clientRequestId` и от курсора. Адаптер после события читает текущее состояние из GET или снимка и пишет его как факт, а не как шаг в порядке событий. Повторная доставка не меняет состояние и не создаёт вторую работу в задаче. Число MCP-инструментов и правила проверки в CI не меняются. Владельцы файлов для будущей карточки: `internal/domain/identity.go`, `internal/infra/mcp/server.go`, `internal/infra/mcp/schema.go`, `internal/infra/store/db.go`, `internal/infra/store/receipts.go`, `internal/infra/taskstore/store.go`, `cmd/beacon/watch.go` и тесты к ним.

Отклонённое. Использовать курсор из ADR 0025 или `clientRequestId` из ADR 0028 как ключ дедупликации вебхука. Восстанавливать состояние по порядку прихода событий или по самому свежему событию в пачке. Доверять данным, которые событие принесло с собой, и не делать GET. Считать каждую из трёх доставок новым событием с новым эффектом.
