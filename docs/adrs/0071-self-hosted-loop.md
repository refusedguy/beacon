# ADR 71: Self-hosting the development loop

Статус: accepted

## Контекст

Оркестратор раньше пользовался циклом разработки как внешним сервисом: карточки писал вручную, Watch регистрировал вручную, вердикт смотрел в `gh pr checks`, а пробуждение сессии считал побочным эффектом MCP. Нужен контур, в котором оркестратор проходит тот же путь собственными инструментами и оставляет проверяемые внешние факты на каждом шаге.

## Решение

Оркестратор сам пользуется своей разработкой: (1) `cmd/batch-apply` создаёт карточки из research JSON, (2) Beacon MCP регистрирует реальный Watch, (3) CI-мост сам пишет `verdict=ready` в store, (4) `beacon_get_result` и `beacon_ack` читают и подтверждают факт, (5) `opencode api POST /api/session/{id}/prompt` с `delivery=steer` будит сессию по настоящему watchID. Вердикт берётся только из store через `beacon_get_result`, а не из idle-отчёта и не из ручного опроса CI. Это продолжение ADR 0022, ADR 0028, ADR 0074 и ADR 0075.

## Последствия

Доказательство прогона: карточка T3.226 создана тулзой, Watch `watch:refusedguy/beacon:286:177bf240...` перешёл в `ready` при `revision=1`, `beacon_ack` вернул `ok:true`, wake зафиксирован сообщением `msg_1f72fc9f...`. Каждый шаг цикла подтверждается внешним фактом: созданная карточка, вердикт в store, квитанция прочтения, ответ wake. Внутренние массивы фейка и словесные отчёты verdictом не считаются. Ограничение: локальный MCP без CI-адаптера не пишет вердикт, поэтому self-hosting требует включённого моста и подключённого store.
