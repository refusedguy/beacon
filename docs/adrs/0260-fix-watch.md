# ADR 260: Лимит FIX-агентов на заблокированный Watch

Статус: accepted

## Контекст

Оркестратор получает blocked:not_mine и спавнит FIX-агента. Если фикс не удался, PR закрыт без мержа и оркестратор получает повторный пинг, он спавнит следующего фиксера. Без границы цикл бесконечен: каждый проваленный фикс даёт новый PR и новый wake, а Watch остаётся заблокированным.

## Решение

Счётчик fix-попыток хранится в Watch.Blocked.FixAttempts в domain и проецируется в BlockedInfo оркестратора. При каждом новом фиксере с fixFor, равным этому Watch, вызывающий код увеличивает счётчик и сохраняет Watch; доменный хелпер Watch.RecordFixAttempt возвращает копию с инкрементом и не мутирует источник. Decide проверяет блокировку первым: при FixAttempts >= 3 он возвращает NOTIFY_ORCHESTRATOR с причиной escalate_human вместо BLOCKED_FIX_AGENT. Меньше трёх попыток по-прежнему дают BLOCKED_FIX_AGENT с причиной, blockedBy и failedChecks. Счётчик живёт на записи блокировки, поэтому EventUnblock, очищающий Blocked, сбрасывает бюджет и следующий блок начинается с нуля.

## Последствия

Лимит проверяется в чистой функции Decide, без побочных эффектов и без импорта domain в оркестратор (ADR 0005). Тесты decision_test.go покрывают 0-2 попытки, достижение лимита и значения выше, независимость разных Watch и то, что снятый блок больше не эскалируется. Интеграционные зависимости: код спавна фиксера (RoleFixer/fixFor) обязан вызывать RecordFixAttempt и сохранять Watch; проекция в cmd/beacon/orchestrate.go обязана копировать FixAttempts в BlockedInfo оркестратора. Пока эти два места не подключены, production-путь не видит счётчик, но чистое решение остаётся корректным и протестированным.
