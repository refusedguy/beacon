# ADR 0045. Шесть фич из отчёта AB-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AB «AB-волна: новые проекты вне отчётов A–AA» от 20 ноября 2026 года. Идеи собраны в разделе «Фичи» ([AB, строка 88](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L88)) и подтверждены разделами конкретных проектов. Здесь зафиксированы только те фичи, которых нет в ADR 0001-0044 и 151 карточке из `docs/tasks/`. Fencing, аренда, replay, идемпотентность, completion gate и handoff journal уже зафиксированы в предыдущих решениях и карточках, поэтому здесь не повторяются. Несколько новых пунктов похожи на существующие по имени, но различаются по уровню. Фильтр событий в фиче 1 отличается от T3.48, где возврат уже идёт по событию: здесь добавляется явный отбор kinds и ключ идемпотентности на старте ожидания. Порог в фиче 2 это время синхронного вызова, а не поле `delivery` из ADR 0026. Правило в фиче 3 это проверка перед переиспользованием worktree, а не сама аренда из ADR 0044. Сигнал в фиче 4 это размер и содержимое уведомления, а не ветвление лестницы ADR 0017 и не способ доставки ADR 0026. Подпись в фиче 5 привязывает содержимое вердикта к ключу, а не заменяет проверку рецензента из T3.32. Команда в фиче 6 печатает цепочку блокировок в CLI, а не меняет статус карточки. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Событийный `job_wait` с фильтром событий и ключом идемпотентности. Один вызов ожидания принимает фильтр по видам событий `progress`, `checkpoint` и `completed` и возвращается по первому подходящему событию, а не по таймауту опроса логов. На старте ожидания вызыватель передаёт idempotency key, поэтому потерянный ответ не создаёт вторую задачу при повторе. Фильтр и ключ на старте это дополнение к T3.48: там возврат уже идёт по событию, здесь добавляется явный отбор kinds и защита повторного старта. Ключ гасит старт ожидания, а не повтор команд `wait_result`, `steer` или `ack` из ADR 0028.

2. Единый порог превращения синхронного вызова в тикет. Один и тот же порог времени для всех длинных синхронных MCP-вызовов: по умолчанию 30 секунд, максимум 120. Когда вызов его превышает, он возвращает тикет с job id вместо того, чтобы висеть в соединении. Дальнейшее ожидание идёт по тикету. Порог это время, а не способ доставки: ADR 0026 задаёт честное поле `delivery`, но не говорит, когда вызов обязан стать тикетом.

3. Правило безопасного переиспользования worktree. Worktree можно переиспользовать или удалить только когда одновременно выполняются четыре условия: путь существует, дерево чисто, `ahead_commits() == 0`, а аренда либо освобождена, либо старше TTL. Неопределённый счётчик (`-1`) считается работой, а не чистым деревом. Это предикат перед действием, который читает уже существующую запись аренды из ADR 0044, а не новое определение аренды. «Чисто» и «доставлено» остаются разными фактами: чистое дерево без подтверждённой доставки результата не разрешает удаление.

4. Маленький wake-сигнал со ссылкой на долговечную запись. Сигнал пробуждения несёт только маршрутизацию и указатель на долговечную запись. Тело сообщения в сигнал не входит, агент сам тянет запись с сервера. Размер сигнала ограничен, и он не дублирует данные из записи. Лестница ADR 0017 определяет ветвление и требует, чтобы повтор нёс указатель, а ADR 0026 определяет способ доставки. Здесь фиксируется содержимое сигнала: он маленький и без тела вне зависимости от ветви лестницы и режима доставки.

5. Подпись вердикта ревью. Каждый вердикт ревью подписывается ключом ed25519. Перед подписью запись приводится к каноническому виду по RFC 8785, чтобы один и тот же смысл давал одни и те же байты. Сервер хранит точные подписанные байты и проверяет подпись по ним при каждом чтении. Гейт отклоняет вердикт без корректной подписи, поэтому подделка от имени агента не проходит. Подпись подтверждает содержимое записи, а не личность одобрившего: проверка рецензента и ID решения из T3.32 остаётся отдельным шагом. Внешние проверки и их exit-коды из ADR 0044 тоже не меняются.

6. `beacon why <task>` печатает цепочку блокировок. Команда CLI для задачи печатает путь блокировки, а не одно слово `blocked`. Для каждого шага цепочки видно, кто его держит и через какое ребро установлена связь. Поддерживаются ребра `depends-on`, `conflicts-with`, `part-of`, `derived-from`, `supersedes` и `same-as`. Вывод строится по графу, а не по тексту статуса, поэтому карточка со словом `blocked` без цепочки не считается объяснённой.

## Причина

1. vanth ждёт `progress`, `checkpoint` или `completed` одним вызовом, держит состояние в SQLite WAL и доставляет пробуждение через адаптеры `local_command`, `codex_thread`, `opencode_thread` и `webhook` ([AB, строка 90](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L90), [README.md#L13-L18](https://github.com/holdfast-labs/vanth/blob/master/README.md#L13-L18), [README.md#L325-L334](https://github.com/holdfast-labs/vanth/blob/master/README.md#L325-L334)). Там же указан idempotency key на старте, чтобы потерянный ответ не создавал вторую задачу ([AB, строка 90](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L90), [README.md#L40-L45](https://github.com/holdfast-labs/vanth/blob/master/README.md#L40-L45)). Beacon уже возвращается по событию по T3.48, но не различает kinds и не защищает повторный старт ожидания. Берётся контракт фильтра и ключа, а не рантайм vanth с его SQLite WAL и четырьмя адаптерами.

2. leandc возвращает job id после 30 секунд по умолчанию, с максимумом 120 ([AB, строка 94](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L94), [README.md#L164-L165](https://github.com/asif-r-porosh/leandc/blob/main/README.md#L164-L165)). Длинная команда не висит в вызове MCP. В Beacon есть честная доставка из ADR 0026 и идемпотентность из ADR 0028, но нет одного порога, который переводит синхронный вызов в тикет. Берётся порог и вид тикета, а не инструмент `run` leandc и не его набор из пяти инструментов.

3. worktree-lease различает «чисто» и «доставлено» и разрешает переиспользование только при существующем пути, чистом дереве, `ahead_commits() == 0` и освобождённой или просроченной аренде ([AB, строка 96](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L96), [README.md#L51-L76](https://github.com/exisz/worktree-lease/blob/main/README.md#L51-L76)). Неопределённый счётчик `-1` считается работой. ADR 0044 задаёт аренду worktree с владельцем, TTL и fencing-токеном, но не говорит, когда арендованный worktree можно удалить. Берётся предикат перед действием, а не менеджер аренд worktree-lease.

4. aweb посылает сигнал пробуждения без тела сообщения: событие несёт маршрутизацию, а агент тянет долговечное сообщение с сервера ([AB, строка 100](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L100), [README.md#L54-L56](https://github.com/awebai/aweb/blob/main/README.md#L54-L56)). ADR 0017 уже требует, чтобы повтор нёс указатель на запись, а ADR 0026 требует честно называть способ доставки. Ни одно из двух решений не ограничивает размер самого сигнала и не запрещает класть тело в уведомление. Берётся контракт размера и содержимого сигнала, а не сервер aweb с его хранилищем сообщений.

5. Switchboard подписывает каждую запись агента ключом ed25519, канонизирует её по RFC 8785 и хранит точные подписанные байты для повторной проверки ([AB, строка 102](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L102), [README.md#L55-L58](https://github.com/Tsadoq/switchboard/blob/main/README.md#L55-L58)). T3.32 проверяет рецензента и ID решения по sessionID, но не привязывает содержимое вердикта к ключу. Внешний вердикт из ADR 0044 пишет exit-коды проверок на диск, но не подписывает запись. Берётся схема подписи и хранение байт, а не проверка через `ssh-keygen -Y verify` и не сервер Switchboard.

6. Weft печатает путь блокировки, а не слово «blocked», и использует ребра `depends-on`, `conflicts-with`, `part-of`, `derived-from`, `supersedes` и `same-as` ([AB, строка 111](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L111), [README.md#L47-L61](https://github.com/mparrett/weft/blob/main/README.md#L47-L61), [README.md#L74-L76](https://github.com/mparrett/weft/blob/main/README.md#L74-L76)). Beacon показывает статус задачи, но не объясняет, кто держит каждый шаг. Берётся форма вывода цепочки, а не графовое хранилище weft и не его шесть типов рёбер как обязательная схема базы.

Числа в разделе «Перформанс» AB-отчёта это заявления авторов проектов ([AB, строка 122](/home/nbook/Projects/tmp/beacon-research/AB-wave.md#L122)), в контракт Beacon они не переносятся.

  - Фича 3: `internal/domain/types.go`, `internal/infra/taskstore/store.go`, `internal/app/taskcli/service.go`, `cmd/beacon/agents.go` и тесты к ним.

  - Фича 5: `internal/domain/verdict.go`, `internal/infra/store/atomic_write.go`, `internal/infra/mcp/meta.go`, `internal/infra/mcp/contract_test.go`, `internal/app/taskcli/service.go` и тесты к ним.
  - Фича 6: `cmd/beacon/why.go`, `cmd/beacon/commands.go`, `cmd/beacon/task.go`, `internal/domain/types.go` и тесты к ним.
- Проверка карточек: вызов `job_wait` возвращается по первому событию из фильтра, а повторный старт с тем же ключом не создаёт вторую задачу; синхронный вызов сверх порога возвращает тикет с job id и не висит в соединении; worktree с `-1`, с ahead_commits или с живой арендой не переиспользуется; wake-сигнал не содержит тела сообщения и несёт указатель на запись; гейт отклоняет вердикт с неверной подписью или после изменения байт; `beacon why` печатает цепочку с держателями каждого шага, а не слово `blocked`.
- ADR 0015, 0017, 0018, 0020, 0021, 0025, 0026, 0027, 0028, 0029, 0034, 0037, 0038, 0042, 0043 и 0044 с T3.25, T3.32, T3.48, T3.51, T3.67 и T3.88 не переписываются. Фильтр из фичи 1 дополняет возврат по событию T3.48, порог из фичи 2 не меняет способ доставки ADR 0026, предикат из фичи 3 читает аренду ADR 0044, сигнал из фичи 4 не меняет лестницу ADR 0017, подпись из фичи 5 не подменяет проверку рецензента T3.32, а команда из фичи 6 только печатает цепочку в CLI.

## Отклонённое

Сводить фильтр из фичи 1 к T3.48. Там возврат уже идёт по событию, но нет отбора kinds и ключа на старте. Ключ из фичи 1 не подменяет `clientRequestId` из ADR 0028, который гасит повтор команд, а не старт ожидания.

Сводить порог из фичи 2 к ADR 0026 или к ADR 0028. ADR 0026 честно называет способ доставки, ADR 0028 гасит повтор команды. Ни один не определяет время, после которого вызов обязан стать тикетом с job id.

Подменять предикат из фичи 3 арендой из ADR 0044. Аренда даёт владельца, TTL и fencing-токен. Предикат отвечает на другой вопрос: можно ли теперь удалить или переиспользовать этот worktree. Чистое дерево без доставленного результата не достаточно.

Сводить wake-сигнал из фичи 4 к правилу повтора из ADR 0017. В ADR 0017 говорится, что повтор несёт указатель на запись. Здесь фиксируется размер и отсутствие тела у самого сигнала, включая первый вызов и любую ветвь лестницы. Способ доставки из ADR 0026 при этом не меняется.

Подменять подпись из фичи 5 аутентификацией одобрения из T3.32 или внешним вердиктом из ADR 0044. T3.32 проверяет sessionID рецензента, ADR 0044 запускает проверки снаружи и пишет их exit-коды. Подпись ed25519 привязывает содержимое самой записи вердикта к ключу и позволяет повторно проверить точные байты.

Сводить `beacon why` к слову `blocked` в статусе или к общему графу зависимостей. Одно слово `blocked` не объясняет, кто держит шаг, а полный граф не является ответом CLI. Команда печатает только путь блокировки с держателями шагов.

Брать код проектов из отчёта без проверки лицензии. В решении переносится контракт каждой из шести фич, а не рантаймы vanth, leandc, worktree-lease, aweb, Switchboard и weft.

Включать в этот ADR остальные идеи из раздела «Фичи» AB. Менеджером в волну отобраны шесть пунктов выше.
