# ADR 0044. Шесть фич из отчёта AA-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AA «AA-волна: новые проекты вне отчётов A-Z» от 20 ноября 2026 года. Идеи собраны в разделе «Фичи» ([AA, строка 139](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L139)) и подтверждены разделами конкретных проектов. Здесь зафиксированы только те фичи, которых нет в ADR 0001-0043 и 145 карточках из `docs/tasks/`. Fencing при аренде задачи уже в T3.51 и ADR 0037, формула вердикта в T3.67, completion gate с proof в T3.88, структурированная передача между агентами в T3.25, backpressure по квоте GitHub API в T3.54, идемпотентность одной команды по `clientRequestId` в ADR 0028. Несколько новых пунктов похожи на существующие решения по имени, но различаются по уровню. Handle в фиче 1 это идентификатор задачи с подписью, а не fencing-токен из T3.51 и не ключ идемпотентности из ADR 0028. Аренда в фиче 2 держит весь worktree, а не задачу, как T3.51. Внешний вердикт в фиче 3 запускает проверки, которые агент не писал, и пишет их exit-коды на диск, а формула из T3.67 и proof из T3.88 остаются внутренними для агента. Журнал в фиче 4 ограничен по размеру и восстанавливается на старте, а передача из T3.25 задаёт пять полей преемника. Уведомление в фиче 5 об одном событии конца фоновой задачи, а ADR 0028 гасит повтор команды. Проверка в фиче 6 идёт до отправки задачи, а backpressure из T3.54 срабатывает при ответе GitHub API. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Непрозрачный подписанный handle задачи. Задача получает непрозрачный handle с подписью HMAC-SHA256. Handle несёт идентификатор задачи, но не даёт прав: доступ к задаче проверяется отдельно по владельцу. Handle переживает рестарт процесса без in-memory словаря, поэтому любой экземпляр может продолжить задачу по тому же handle. Фиксируется формат handle и разделение handle от авторизации, а не протокол A2A или MCP конкретного продукта. Handle это идентификатор, а не fencing-токен T3.51 и не `clientRequestId` из ADR 0028.

2. Аренда worktree с владельцем, TTL и fencing-токеном. Worktree сдаётся в аренду целиком. Запись аренды содержит владельца, время истечения и монотонный fencing-токен. По истечении TTL аренда считается свободной, а владелец со старым токеном не может записать результат в этот worktree. Это аренда самого worktree, а не аренда задачи из T3.51: там токен защищает переназначенную задачу, здесь он защищает право писать в каталог. Изоляция worktree из ADR 0021 остаётся на месте, добавляется только владелец со сроком.

3. Внешний вердикт с доказательствами на диске. После ответа агента Beacon сам запускает объявленные проверки, которые агент не писал, читает их exit-коды и пишет вердикт вместе с доказательствами на диск. Вердикт показывает, какие проверки прошли, а какие нет, и не зависит от того, что агент сообщил о своей работе. Это внешняя проверка результата, а не вкомпилированная формула из T3.67 и не proof агента из T3.88: там решение принимается внутри домена задачи, здесь запускаются стороны проверки и сохраняются их exit-коды.

4. Bounded handoff journal с восстановлением на старте. После каждого шага Beacon атомарно дописывает запись в журнал handoff с жёстким лимитом размера. Самые старые записи отбрасываются при переполнении, а на старте процесс читает журнал и подставляет блок восстановления. Журнал хранит факты о пройденных шагах и не заменяет структурированную передачу из T3.25 с её пятью полями intent, evidence, patch_plan, verification_plan и risk_notes. Ограничение размера и блок восстановления это новое состояние между передачами, которого в T3.25 нет.

5. Exactly-once уведомление о конце фоновой задачи. Фоновая задача посылает уведомление о завершении ровно один раз. Уведомление несёт стабильный идентификатор события, поэтому приёмник отличает повторную доставку после падения от нового события и не удваивает эффект. CLI не теряет и не дублирует извещение о конце задачи. Это одно уведомление, а не команда: `clientRequestId` из ADR 0028 гасит повтор вызова `wait_result`, `steer` или `ack`, здесь же гасится повтор извещения о завершении.

6. Проверка квот до отправки задачи. Перед отправкой задачи Beacon проверяет живые квоты модели и не тратит попытку на уже исчерпанный план. Проверка стоит до отправки и возвращает причину отказа, а не откладывает уже запущенный вызов. Backpressure из T3.54 реагирует на исчерпание квоты GitHub API при ответе и откладывает запуски, здесь же квота проверяется на входе в отправку задачи.

## Причина

1. mcp-studio-tasks подписывает непрозрачный task handle ключом HMAC-SHA256 и отделяет handle от авторизации владельца ([AA, строка 143](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L143), [таблица возможностей](https://github.com/akmalkhaniub/mcp-studio-tasks#capabilities-implemented)). a2a-mcp-bridge держит всё состояние задачи в запечатанном `taskId`, поэтому handle переживает рестарт процесса без in-memory словаря и базы ([AA, строка 143](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L143), [README](https://github.com/aarushitandon0/a2a-mcp-bridge#readme)). Beacon хранит задачи в SQLite по ADR 0015, но сам формат handle с подписью и отдельной проверкой прав пока отсутствует. У обоих проектов нет лицензии, поэтому берётся формат, а не код, и не берутся протоколы A2A 1.0 и спецификация MCP `2026-07-28`.

2. laneq сдаёт задания в аренду с fencing-токенами, и старый воркер не может записать результат после истечения аренды ([AA, строка 144](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L144), [README](https://github.com/aaronhhsi/laneq#readme)). singular-lite записывает аренду worktree с владельцем, TTL и одним правилом приёмки, которое хост проверяет сам ([AA, строка 144](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L144), [README](https://github.com/xiperinc/singular-lite#readme)). fleet держит аренду и worktree в SQLite-ledger ([AA, строка 144](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L144), [README](https://github.com/lfkdsk/fleet#readme)). T3.51 защищает задачу после переназначения, но не ограничивает право писать в сам worktree. Берётся контракт аренды worktree, а не отдельный сервис laneq и не трёхуровневый движок singular-lite.

3. claw-orchestrator считает прогон завершённым только когда объявленные проверки, которые агент не писал, прошли снаружи, и записывает вердикт с доказательствами ([AA, строка 145](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L145), [README](https://github.com/Enderfga/claw-orchestrator#readme)). verdict даёт оценку доказательности каждой находки ([AA, строка 145](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L145), [README](https://github.com/stainless-code/verdict#readme)). agent-hooks задаёт типизированный конверт вердикта с явной версией спецификации ([AA, строка 145](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L145), [спецификация](https://github.com/responsibleai/agent-hooks/blob/main/spec/0.1/AGENT-HOOKS-0.1.md)). multi-agent-review добавляет fail-closed семантику, когда пустая панель никогда не даёт чистый вердикт ([AA, строка 145](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L145), [README](https://github.com/riekelt/multi-agent-review#readme)). Beacon сейчас принимает вердикт по формуле T3.67 и proof T3.88, но не запускает проверки вне агента. Берётся гейт внешних проверок и запись exit-кодов, а не кросс-движковый рантайм целиком.

4. CoalHearth после каждого шага атомарно пишет журнал и на следующем старте подставляет блок восстановления ([AA, строка 146](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L146), [README](https://github.com/TheColliery/CoalHearth#readme)). sessionFlow ссылается на событие-источник в каждом утверждении пакета handoff ([AA, строка 146](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L146), [README](https://github.com/HarryHeYu/sessionFlow#readme)). deja-vu переносит цель, решения и незакрытую работу между агентами ([AA, строка 146](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L146), [README](https://github.com/vshulcz/deja-vu#readme)). T3.25 описывает содержимое одной передачи, но не хранит историю шагов с лимитом и не восстанавливает её на старте. Берётся bounded журнал и recovery, а не хуки Claude Code с лимитом 4 МиБ и не индексатор с чужим хранилищем.

5. realtasks посылает уведомление ровно один раз по завершении фоновой команды ([AA, строка 147](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L147), [README](https://github.com/st0nie/realtasks#readme)). relay-queue даёт получателю стабильный event ID, чтобы повторная доставка после падения воркера не удвоила эффект ([AA, строка 147](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L147), [README](https://github.com/amgazal/relay-queue#readme)). ADR 0028 решает идемпотентность команды, а здесь теряется и дублируется извещение о конце задачи. Берётся стабильный идентификатор уведомления, а не PostgreSQL-очередь и подписанные вебхуки relay-queue.

6. swrm проверяет живые квоты моделей перед отправкой задачи, чтобы не тратить попытку на исчерпанный план ([AA, строка 150](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L150), [README](https://github.com/surlymochan/swrm#readme)). T3.54 откладывает запуск при исчерпании квоты GitHub API, то есть работает с ответом внешнего API. Проверка квоты модели стоит до отправки и не зависит от ответа. Берётся preflight check, а не планировщик swrm с привязкой к Pi, DeepSeek и cursor-agent.

Числа в разделе «Перформанс» AA-отчёта это заявления авторов проектов ([AA, строка 152](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L152)), в контракт Beacon они не переносятся.

  - Фича 3: `internal/domain/verdict.go`, `internal/infra/store/atomic_write.go`, `internal/infra/store/archive.go`, `internal/app/taskcli/service.go`, `internal/infra/mcp/contract_test.go` и тесты к ним.
  - Фича 4: `internal/domain/types.go`, `internal/infra/store/atomic_write.go`, `internal/infra/store/db.go`, `internal/app/taskcli/service.go`, `cmd/beacon/main.go` и тесты к ним.
  - Фича 5: `internal/domain/fanout.go`, `internal/infra/mcp/server.go`, `internal/infra/store/receipts.go`, `internal/app/taskcli/service.go` и тесты к ним.
  - Фича 6: `internal/infra/github/points.go`, `internal/infra/mcp/tool_claim.go`, `internal/app/taskcli/service.go` и тесты к ним.
- Проверка карточек: подписанный handle не даёт доступа без проверки владельца и переживает рестарт; владелец со старым fencing-токеном не пишет в worktree после истечения TTL; вердикт пишется на диск только с exit-кодами внешних проверок; журнал handoff не превышает лимит и подставляет блок восстановления на старте; уведомление о конце фоновой задачи приходит один раз и повторная доставка не удваивает эффект; задача с исчерпанной квотой не отправляется и получает причину отказа до старта.
- ADR 0001, 0015, 0020, 0021, 0028, 0032, 0037, 0038, 0040, 0042 и 0043 с T3.25, T3.51, T3.54, T3.67 и T3.88 не переписываются. Handle из фичи 1 остаётся идентификатором, аренда из фичи 2 защищает worktree, внешние проверки из фичи 3 не меняют формулу вердикта, журнал из фичи 4 не заменяет передачу с пятью полями, уведомление из фичи 5 не подменяет идемпотентность команды, а проверка из фичи 6 не меняет backpressure по квоте GitHub API.

## Отклонённое

Сводить подписанный handle к fencing-токену T3.51 или к `clientRequestId` из ADR 0028. Токен T3.51 защищает переназначенную задачу, ключ ADR 0028 гасит повтор команды, а handle только называет задачу и требует отдельной проверки прав.

Считать аренду задачи из T3.51 арендой worktree. Разные объекты: первая не даёт старому воркеру изменить задачу, вторая не даёт старому владельцу писать в каталог после истечения TTL.

Подменять внешний вердикт формулой T3.67 или proof из T3.88. Оба решения принимаются внутри агента, а здесь проверки запускаются снаружи и их exit-коды пишутся на диск.

Сводить bounded журнал к передаче из T3.25. Пять полей преемника описывают одну передачу, а журнал с лимитом размера хранит шаги и восстанавливает их на старте.

Сводить уведомление о конце фоновой задачи к идемпотентности из ADR 0028. Там ключ гасит повтор команды `wait_result`, `steer` или `ack`, здесь стабильный идентификатор гасит повтор извещения о завершении.

Подменять preflight check backpressure из T3.54. T3.54 реагирует на исчерпание квоты GitHub API при ответе, а проверка из фичи 6 стоит до отправки задачи и не ждёт ответа.

Брать код проектов без лицензии. В отчёте AA таких шесть: [mcp-studio-tasks](https://github.com/akmalkhaniub/mcp-studio-tasks#capabilities-implemented), [a2a-mcp-bridge](https://github.com/aarushitandon0/a2a-mcp-bridge#readme), [laneq](https://github.com/aaronhhsi/laneq#readme), [multi-agent-review](https://github.com/riekelt/multi-agent-review#readme), [relay-queue](https://github.com/amgazal/relay-queue#readme) и [jobq](https://github.com/aleks-drozy/jobq#readme) ([AA, строки 56, 62, 68, 92, 104, 110](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L56)). Лицензия не указана, поэтому переносится только идея на уровне контракта.

Брать код [singular-lite](https://github.com/xiperinc/singular-lite#readme). Проект под GPL-3.0 ([AA, строка 20](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L20)), и для использования его кода в Beacon нужна проверка совместимости лицензий. Берётся только формат записи аренды.

Брать рантаймы из отчёта целиком. claw-orchestrator это кросс-движковый рантайм с ACP и spend caps, verdict публикует отзыв и SARIF, CoalHearth привязан к хукам Claude Code, relay-queue тянет PostgreSQL и подписанные вебхуки, swrm привязан к Pi, DeepSeek и cursor-agent. Beacon нужен только контракт каждой из шести фич.

Включать в этот ADR две оставшиеся идеи из раздела «Фичи» AA: in-band прогресс ([AA, строка 148](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L148)) и один GraphQL-батч по репозиториям ([AA, строка 149](/home/nbook/Projects/tmp/beacon-research/AA-wave.md#L149)). Менеджером в волну отобраны шесть пунктов выше.
