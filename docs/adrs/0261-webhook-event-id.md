# ADR 261: Журнал webhook-доставок с ключом event_id

Статус: accepted

## Контекст

GitHub отдаёт `X-GitHub-Delivery` как GUID, уникальный для события, и повторяет тот же заголовок при ручном redelivery. Без журнала одна доставка может породить два wake, а повтор с устаревшим телом может откатить уже достигнутый статус. ADR 0149 описывает webhook как подсказку, но не фиксирует, где хранится факт доставки. ADR 0015 требует одной транзакции и UNIQUE-индекса для ключа идемпотентности.

## Решение

Добавить таблицу `webhook_events` с первичным ключом `delivery_id` и колонками `event`, `action`, `repo`, `pr`, `head_sha`, `watch_id`, `revision`, `status`, `received_at` и `outcome`. В primary key пишется `IdempotencyKey('github-delivery', deliveryID)` из домена, поэтому ключ детерминирован и не пересекается с ключами запуска задачи, клиентского запроса или уведомления о завершении. `RecordDelivery` создаёт таблицу при первом использовании и вставляет строку через `INSERT OR IGNORE` в одной транзакции вместе с чтением результата. Повтор того же `delivery_id` не добавляет строку и не меняет сохранённые статус и outcome: `DeliverySeen` возвращает первую запись. Конфликтующее тело помечается как `Conflict`, но всё равно возвращает сохранённый outcome.

## Последствия

Одна доставка GitHub соответствует ровно одной строке журнала, а redelivery возвращает первый результат. Статус не откатывается повторной доставкой с устаревшим телом. Запись переживает рестарт: второй процесс открывает тот же файл и видит зафиксированную строку через отдельный пул чтения. Таблица создаётся на первом использовании, отдельного файла миграции нет. Домен получает только константу пространства имён `github-delivery`; весь SQL остаётся в infra-store.
