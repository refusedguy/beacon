# ADR 0054. Шесть фич из отчёта AL-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AL «AL-волна: новые проекты» ([AL, строка 1](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L1)). Поиск шёл 12 тематическими запросами `gh api search/repositories` с фильтром `pushed:>2026-01-01`. Из 127 кандидатов вне списка исключений через commits API проверены 33, в волну вошли 16 проектов с коммитом в 2026 году. Дата коммита взята из `GET /repos/{owner}/{repo}/commits?per_page=1`, а не из `pushed_at`; ни один из 16 проектов не встречается в старых отчётах ([AL, строка 3](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L3), [AL, строка 5](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L5)). Фичи взяты из пунктов 3, 8, 12 и 13 раздела «Фичи» ([AL, строки 159-169](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L159)) и из описаний проектов wcp, sqlite-task-queue и backend-job-queue ([AL, строки 32, 41, 113](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L32)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0053 и 171 карточке из `docs/tasks/`. Fencing, идемпотентность, аренда и verdict уже есть: T3.116 держит fence token и enqueue в одной транзакции, T3.117 строит verdict из двух условий, T3.14 объединяет очередь и события в одной транзакции, T3.60 паркует провал в `parked` без слепого ретрая, T3.97 даёт аренду worktree с TTL и fencing, ADR 0028 задаёт идемпотентность по `clientRequestId`. Поэтому эти темы здесь не повторяются. Несколько фич похожи на существующие по имени, но различаются по уровню. Фича 1 это команда восстановления из сохранённого состояния, а не сама аренда T3.97. Фича 2 это номер попытки в каждой мутации, а не fence token в одной транзакции T3.116. Фича 3 это отказ судить по размеру выборки, а не формула verdict из двух условий T3.117. Фича 4 это конкретный SQL-приём захвата, а не транзакция очереди и событий T3.14. Фича 5 это явные состояния dead-letter и backoff, а не парковка провала T3.60. Фича 6 это один канонический checkout, а не аренда отдельного worktree T3.97. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. `wcp task recover <id>` возвращает одно безопасное следующее действие из сохранённого состояния. Команда читает состояние задачи и называет единственный шаг, который можно выполнить сейчас, вместо выдачи полной истории или списка вариантов. Если эпоха в запросе устарела, команда отвергает действие даже в том случае, когда diff всё ещё применяется. Сохранённое состояние остаётся источником решения, а не текущий вид diff в дереве. Это команда восстановления, а не аренда T3.97.

2. Каждая смена состояния обязана нести номер попытки из `claim()`. Номер попытки выдаётся при захвате задачи и переносится в каждую последующую мутацию состояния. Потребитель с номером старой попытки не может закрыть задачу новой генерации, даже если его вычисление завершилось и результат корректен. Запись с несовпадающим номером отклоняется. Это номер попытки в каждой мутации, а не fence token T3.116, который связывает токен и enqueue в одной транзакции.

3. Отказ судить при выборке меньше минимального обнаруживаемого эффекта. Гейт не выставляет зелёный verdict, если размер выборки не позволяет обнаружить эффект нужной величины. В этом случае возвращается ERROR, а не зелёный статус и не зелёный verdict. Порог считается от минимального обнаруживаемого эффекта, а не только от величины оценки. Это отказ verdict, а не дополнительный флаг и не формула из двух условий T3.117.

4. Атомарный захват через `UPDATE ... RETURNING` на стандартном SQLite. Захват задачи выполняется одним выражением `UPDATE ... RETURNING` без расширений SQLite и без внешнего брокера. Конкурентные воркеры не могут взять одну и ту же строку: каждая транзакция видит либо необработанную задачу, либо уже захваченную. Приём работает на стандартной библиотеке SQLite. Это конкретный SQL-приём захвата, а не транзакция очереди и событий T3.14.

5. Dead-letter и backoff как явные состояния задачи. Мёртвое письмо и отложенный повтор фиксируются в самой модели задачи отдельными состояниями, а не только счётчиком ретраев. Переход в dead-letter означает, что задача больше не берётся автоматически. Backoff задаёт время, когда задача снова станет доступна, и это время читается из состояния, а не вычисляется адаптером по числу попыток. Это мёртвые письма и отложенный повтор как состояния, а не `parked` T3.60, где провал ждёт человека без ретрая.

6. Один канонический checkout. Агенты пишут только в изолированные worktree. Каждый worktree берётся атомарным лизингом с эпохой, а канонический checkout остаётся общим и не становится местом записи. Эпоха в лизинге позволяет отличить живую аренду от устаревшей. Это канонический checkout с изоляцией записи, а не аренда worktree с TTL и fencing T3.97.

## Причина

1. KilianTheMagnificent/wcp это протокол на стандартной библиотеке Python, который держит один канонический checkout, а агенты пишут только в изолированные worktree ([AL, строка 112](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L112), [wcp](https://github.com/KilianTheMagnificent/wcp)). Фича для Beacon это `wcp task recover <id>`: одно безопасное следующее действие из сохранённого состояния, при этом устаревшая эпоха отвергается, даже если diff применяется ([AL, строка 168](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L168), https://github.com/KilianTheMagnificent/wcp). Аренда T3.97 описывает захват worktree, но не описывает, что возвращает команда восстановления после сбоя и как она отвергает устаревшую эпоху. Берём команду recover, а не только POSIX и `fcntl.flock`, отсутствие Windows, 0 звёзд и проверку хуков только для Claude Code ([AL, строка 202](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L202)).

2. 593682963wd-wq/durable-task-queue это локальная SQLite-очередь с дедупом по идентификатору сообщения, монотонными номерами попыток и изоляцией задач с неизвестным результатом после обрыва ([AL, строка 122](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L122), [durable-task-queue](https://github.com/593682963wd-wq/durable-task-queue)). Фича для Beacon это требование нести номер попытки из `claim()` в каждой смене состояния, поэтому старый потребитель не закрывает новую генерацию задачи ([AL, строка 169](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L169), https://github.com/593682963wd-wq/durable-task-queue). T3.116 связывает fence token и enqueue в одной транзакции, но не описывает номер попытки как обязательное поле каждой мутации. Берём номер попытки в мутациях, а не китайский README, вырезанные отправители, SDK, keychain и desktop-контроль ([AL, строка 203](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L203)).

3. IlaKhan17/proofstep это CI-гейт для агентов, который оценивает траекторию вызовов инструментов по YAML-политикам, и exit code совпадает с вердиктом дашборда ([AL, строка 76](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L76), [proofstep](https://github.com/IlaKhan17/proofstep)). Фича для Beacon это отказ судить, если размер выборки меньше минимального обнаруживаемого эффекта, с возвратом ERROR вместо зелёного статуса ([AL, строка 164](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L164), https://github.com/IlaKhan17/proofstep). В отчёте пример: базовая оценка 0,8239, кандидат 0,8077, n=40, p=0,350, минимальный обнаруживаемый эффект 0,1007; порог даёт exit 0, порог плюс статистический тест даёт exit 2 ([AL, строка 181](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L181)). T3.117 выводит verdict из величины и значимости, но не останавливает оценку, когда выборка слишком мала, чтобы эффект вообще был обнаружен. Берём отказ verdict, а не версию 0.1.0, нестабильные схему и API, PostgreSQL и MinIO ([AL, строка 198](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L198)).

4. sandynana0828/sqlite-task-queue это очередь на стандартной библиотеке SQLite с атомарным захватом через `UPDATE ... RETURNING`, лизингом, перехватом задач мёртвых воркеров, backoff и dead-letter ([AL, строка 32](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L32), [sqlite-task-queue](https://github.com/sandynana0828/sqlite-task-queue)). Фича для Beacon это захват одной транзакцией `UPDATE ... RETURNING` под WAL плюс `heartbeat()` для длинных задач ([AL, строка 159](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L159), https://github.com/sandynana0828/sqlite-task-queue). T3.14 объединяет очередь и события в одной SQLite-транзакции, но не задаёт способ атомарного захвата строки. Берём SQL-приём, а не демонстрационный проект с README на 42 строки, без API и полноценного набора тестов и с неопределённой лицензией в метаданных GitHub ([AL, строка 193](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L193)).

5. maddoxk/backend-job-queue это SQLite в WAL-режиме с пулом tokio-воркеров и axum API, который даёт at-least-once с лизингом, приоритетами, cron и dead-letter ([AL, строка 41](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L41), [backend-job-queue](https://github.com/maddoxk/backend-job-queue)). Фича для Beacon это явные состояния dead-letter и backoff в модели задачи, а не только счётчик ретраев. Рядом стоит `claim_next`, который в одной транзакции берёт или ожидающую задачу, или задачу с истёкшим лизингом от упавшего воркера ([AL, строка 160](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L160), https://github.com/maddoxk/backend-job-queue). T3.60 паркует провал в `parked` без ретрая, но не описывает мёртвое письмо как состояние и не хранит время отложенного повтора в задаче. Берём состояния dead-letter и backoff, а не сервер на sqlx, axum и tokio, слой HTTP и дашборд ([AL, строка 194](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L194)).

6. Протокол wcp держит один канонический checkout, а агенты пишут только в изолированные worktree с атомарными лизингами и эпохами ([AL, строка 113](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L113), https://github.com/KilianTheMagnificent/wcp). Для Beacon это значит, что канонический checkout остаётся одним и не принимает запись от агентов, а каждая изолированная копия берётся атомарным лизингом с эпохой. Тот же проект даёт фичу 1, но здесь берётся другая сторона протокола: не команда recover, а правило записи и владения checkout. T3.97 даёт аренду worktree с TTL и fencing одному агенту, но не вводит понятие одного канонического checkout для всех. Берём канонический checkout и эпохи, а не привязку к POSIX и `fcntl.flock` ([AL, строка 202](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L202)).

## Последствия

- Из каждого пункта выходит одна небольшая карточка в `docs/tasks/` по правилам ADR 0020. Карточки этим ADR не создаются и будут созданы отдельными задачами. Владельцы файлов для будущих карточек:
  - Фича 1: `cmd/beacon/task.go`, `internal/app/taskcli/service.go`, `internal/domain/types.go`, `internal/infra/taskstore/store.go`, `internal/infra/store/receipts.go` и тесты к ним.
  - Фича 2: `internal/domain/types.go`, `internal/domain/transition.go`, `internal/infra/taskstore/store.go`, `internal/infra/mcp/tool_claim.go`, `internal/infra/mcp/tool_ack.go` и тесты к ним.
  - Фича 3: `internal/domain/verdict.go`, `internal/domain/types.go`, `internal/infra/mcp/tool_get_result.go`, `internal/app/taskcli/service.go` и тесты к ним.
  - Фича 4: `internal/infra/taskstore/store.go`, `internal/infra/taskstore/store_test.go`, `internal/infra/store/db.go` и тесты к ним.
  - Фича 5: `internal/domain/types.go`, `internal/domain/transition.go`, `internal/infra/taskstore/store.go`, `internal/infra/store/db.go` и тесты к ним.
  - Фича 6: `internal/domain/types.go`, `internal/infra/mcp/tool_claim.go`, `internal/infra/store/db.go`, `cmd/beacon/watch.go` и тесты к ним.
- Проверка карточек: `wcp task recover <id>` возвращает одно действие из сохранённого состояния и отвергает устаревшую эпоху даже при применяемом diff; мутация с номером попытки из старого `claim()` не закрывает задачу новой генерации; гейт возвращает ERROR и не ставит зелёный verdict, когда выборка меньше минимального обнаруживаемого эффекта; два воркера не захватывают одну строку через `UPDATE ... RETURNING` на стандартном SQLite; задача в dead-letter не берётся автоматически, а backoff читается из состояния задачи; все агенты пишут в изолированные worktree, а канонический checkout остаётся одним и не принимает запись.
- ADR 0001-0053 с T3.14, T3.60, T3.97, T3.116 и T3.117 не переписываются. Команда recover фичи 1 не меняет аренду T3.97. Номер попытки фичи 2 не заменяет fencing T3.116. Отказ verdict фичи 3 не меняет формулу T3.117. SQL-приём фичи 4 не отменяет транзакцию T3.14. Состояния фичи 5 не дублируют `parked` T3.60. Канонический checkout фичи 6 не отменяет аренду T3.97. Идемпотентность ADR 0028, журнал ADR 0011, доставка ADR 0026, курсор ADR 0025, лестница ADR 0017 и проверка только в CI из ADR 0022 дополнительной не становятся.

## Отклонённое

Брать проекты целиком. Причины из отчёта сводятся к чужому рантайму, лицензиям, платформе и широкой поверхности ([AL, строки 189-206](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L189)). Beacon требует Go, один локальный бинарник и глобальную установку в `~/.config/opencode`. Ни один из шестнадцати проектов не годится как целый продукт. Отдельно не берутся GPL-проекты: P-ai с GPL-3.0, десктопом на Tauri и Vue и привязкой к WeChat, Feishu, DingTalk и QQ ([AL, строка 191](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L191), https://github.com/kawayiYokami/P-ai), а также chat-with-cli с GPL-3.0, early alpha `v0.1.0-alpha.5`, публичным релеем по умолчанию и OAuth вместе с Computer Use в одном бинарнике ([AL, строка 192](/home/nbook/Projects/tmp/beacon-research/AL-wave.md#L192), https://github.com/ifloppy/chat-with-cli). Их лицензия несовместима с дистрибуцией Beacon, а идеи сжатия сессии и долгоживущей PTY-задачи в эту волну не отобраны.

Включать в этот ADR остальные идеи отчёта. Менеджером отобраны пункты 3, 8, 12 и 13 раздела «Фичи» и два приёма из описаний проектов wcp, sqlite-task-queue и backend-job-queue. Не отобраны: P-ai со сжатием длинной сессии (AL:157, https://github.com/kawayiYokami/P-ai); chat-with-cli с PTY-задачей и чекпоинтом (AL:158, https://github.com/ifloppy/chat-with-cli); backend-job-queue с `claim_next` (AL:160, https://github.com/maddoxk/backend-job-queue); agents-lobby с побуждением по событию (AL:161, https://github.com/kgsvirus/agents-lobby); hermes-subagent-signal с подписанным URL (AL:162, https://github.com/DadaDevelopment/hermes-subagent-signal); proofcheck с картой diff-доказательств (AL:163, https://github.com/bhaskargurram-ai/proofcheck); lodeline с `--fail-on high` и отдельным кодом выхода 4 (AL:165, https://github.com/Ju571nK/lodeline); drover с fenced `LakeOutboxExporter` (AL:166, https://github.com/arniesaha/drover); worktree с доказательством восстановимости по точным ref-ам (AL:167, https://github.com/beyond10x/worktree); Asyncflow с уникальным индексом на `idempotency_key` и `SKIP LOCKED` (AL:170, https://github.com/eduardomartim/Asyncflow); agent-sessions со счётчиком квоты (AL:171, https://github.com/jazzyalex/agent-sessions); agent-snapshot-resume с `asr selfcheck` (AL:172, https://github.com/jxtse/agent-snapshot-resume). Часть из них пересекается с уже принятыми решениями, остальные менеджером в эту волну не отобраны.

Повторять уже принятые решения под новыми именами. Fencing и enqueue зафиксированы в T3.116, verdict из двух условий в T3.117, очередь и события в одной транзакции в T3.14, парковка провала в T3.60, аренда worktree с TTL в T3.97, идемпотентность в ADR 0028. Фичи этого ADR работают на других уровнях: команда recover с эпохой, номер попытки в каждой мутации, отказ verdict по выборке, SQL-приём захвата, dead-letter и backoff как состояния, один канонический checkout для всех агентов.
