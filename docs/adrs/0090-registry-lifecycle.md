# ADR 0090. Состояния registry и вердикты Watch

Статус: accepted

## Контекст

Реестр исполнителей и вердикты Watch живут в разных слоях. Реестр описывает, доступен ли исполнитель и жив ли его сеанс. Вердикт описывает готовность PR. ADR 0014 отделил факт доставки от прочтения, а ADR 0025 отделил текущий статус от истории событий. Три оси уже существуют отдельно: состояние сеанса, квитанция доставки и вердикт Watch. Карточки P5 добавляют реестр без объединения этих осей.

Отчёт `waiting, watchID` означает конец хода исполнителя по шаблону `executor-task.md`. Он не говорит о готовности PR. Состояние `session.idle` тоже означает конец хода, а не готовность. Если считать idle готовностью, оркестратор сольёт PR до проверок.

## Решение

Реестр хранит состояние исполнителя. Вердикт хранит готовность PR. Одно состояние не выводится из другого. Изменение реестра не меняет вердикт, а смена вердикта не меняет реестр.

### Состояния registry

- `active`. Сеанс из `session_id` жив, heartbeat свежий. Исполнитель может получить wake.
- `stale`. Сеанс из реестра не найден среди живых сеансов. Wake запрещён до успешной сверки `registry sync` (T5.30, T5.49). Запись сохраняется, чтобы не терять адрес.
- `stopped`. Исполнитель остановлен явно командой `registry stop` (T5.56). Wake запрещён.

Запись создаётся до ответа `watch_pr` (T5.34). Ключ записи это `session_id`, а не имя агента (T5.33). Переход в `stale` не удаляет запись и не меняет вердикт.

### Вердикты Watch

Вердикт читается только через `beacon_get_result`. Множество вердиктов задано шаблоном исполнителя и не зависит от реестра:

- wake дают `keep_working`, `rebase`, `retry`.
- wake не дают `ready`, `watching`, `merged`, `closed`, `timeout`.

`ready` требует прочтения вердикта и решения оркестратора (T3.8). Один лишь статус `idle` или отчёт `waiting` вердикт `ready` не создаёт.

## Правила разделения

1. Отчёт `waiting, watchID` не меняет состояние registry. Он фиксирует конец хода и не записывает вердикт.
2. Доставка (`posted`, `claimed`, `read` по ADR 0014) не меняет ни состояние registry, ни вердикт. `beacon_ack` и `beacon_get_result` лишь фиксируют прочтение.
3. Переход registry в `stale` или `stopped` не переписывает вердикт Watch. Вердикт меняется только по своему жизненному циклу через чтение проверок PR (ADR 0004, ADR 0019).
4. Отсутствие wake у записи `stale` это отказ доставки, а не вердикт `retry`. Отказ попадает в квитанцию.
5. Готовность колонки в `beacon watch` берётся из вердикта, а состояние сеанса из `session.status` (T5.47).

## Последствия

- Реестр показывает доступность исполнителя и адрес для wake. Он не показывает готовность PR.
- Вердикты не переписываются при смене состояния registry и при смене квитанции доставки.
- Столбец готовности в CLI заполняется из `beacon_get_result`, а не из `session.idle`.
- Сверка после рестарта (ADR 0095) переводит запись в `stale`, но оставляет вердикт нетронутым.
- Оркестратор мержит только после прочитанного `verdict=ready` и зелёных проверок, независимо от состояния registry.
