# ADR 0037. Шесть фич из отчёта T-next-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта T «Новая волна конкурентов Beacon: 17 репозиториев» от 19 ноября 2026 года, пути и ссылки проверены 20 ноября ([T, строка 1](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L1)). Идеи разложены по разделам новых проектов и сведены в список «Фичи» ([T, строка 248](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L248)). Здесь зафиксированы только те, которых нет в ADR 0001-0036 и 96 карточках из `docs/tasks/`. Атомарный claim уже описан в T3.27, живость по PID в T3.44, ревизия в `ack` в T3.45, append-only журнал в T3.43, поэтому они сюда не входят. Владелец велел принять оставшиеся идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Подбор агента по возможностям. Каждая сессия объявляет набор возможностей. Ядро выбирает получателя освободившегося события по совпадению объявленных возможностей, а не по списку заранее заданных имён. Имя сессии остаётся ключом доставки, но перестаёт быть критерием выбора.
2. `wait_result` возвращается по событию или границе одобрения. Вызов ждёт наступления события или точки, где требуется одобрение, и возвращается сразу в этот момент. Интервал опроса не служит причиной возврата. Лестница пробуждения из ADR 0017 сохраняется: исход доставки по-прежнему определяет подтверждение, повтор и эскалацию. Меняется только момент возврата `wait_result`, а не маркеры лестницы и не байты ответа из ADR 0036 пункт 2.
3. WARNING о совместном gate. Когда несколько активных юнитов ждут одну и ту же дорогую команду, например один CI, ядро печатает предупреждение и сериализует ожидание в одном месте. Один общий gate даёт одно ожидание, а не 15 независимых таймеров. Фантомные таймауты перестают выглядеть как дефект кода.
4. Failure contract вызова hook адаптера. Если адаптер пробуждения завершился ошибкой, вызов hook возвращает код 0 и пустой stdout, а причина пишется в лог. Сломанный адаптер не роняет сервер и не прерывает остальные 14 ожиданий. Это контракт самого вызова hook со стороны Go-ядра, а не fail-open JS-плагина из ADR 0006 и карточки T3.5.
5. Fencing token при аренде. Каждое назначение задачи получает монотонно растущий токен. Перед изменением задачи воркер предъявляет токен, и ядро отклоняет изменение, если токен устарел. Отставший воркер не меняет задачу, которую переназначили после рестарта демона.
6. Пороги предупреждения по лимитам плана. Жёлтый порог на 75%, красный на 90%. Счётчики лимитов читаются раз в 10 минут без модельных запросов. При 15 ожиданиях агент видит предупреждение до отказа, а не в момент отказа.

## Причина

1. CSOAI-ORG/agent-delegation-mcp объявляет capability-based agent matching ([T, строка 20](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L20), [README](https://github.com/CSOAI-ORG/agent-delegation-mcp/blob/main/README.md)). Beacon держит 15 агентов и сегодня выбирает получателя по имени сессии. Подбор по возможностям снимает жёсткую привязку к именам.
2. agentoven возвращается на границе одобрения в `wait_for_recipe_run`, а не по таймауту ([T, строка 46](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L46), [README, Multi-Agent Recipes](https://github.com/agentoven/agentoven/blob/main/README.md#multi-agent-recipes)). Та же семантика нужна `wait_result`: вернуть управление, когда событие наступило, а не когда прошли лишние 10 секунд опроса.
3. flywheel печатает shared-gate warning, когда два активных юнита объявили одну дорогую команду в `gate:` ([T, строка 87](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L87), [README, Why flywheel](https://github.com/suzworx/flywheel/blob/main/README.md#why-flywheel)). Автор зафиксировал фантомные таймауты в field run на 99 запусках воркеров и 44 задачах до 7 воркеров параллельно ([T, строка 283](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L283), [README, Why flywheel](https://github.com/suzworx/flywheel/blob/main/README.md#why-flywheel)). Для 15 агентов Beacon общий CI даёт ту же картину.
4. graymatter завершает ошибочный hook кодом 0 с пустым stdout ([T, строка 115](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L115), [README, Observability](https://github.com/angelnicolasc/graymatter/blob/main/README.md#observability)). Для Beacon это контракт вызова адаптера пробуждения: отказ одного адаптера не должен ронять сервер и остальные ожидания. Отличие от ADR 0006 и T3.5: там fail-open относится к JS-плагину и всей сессии OpenCode, здесь к вызову hook в Go-ядре.
5. bead-rs использует монотонно растущий fencing token, чтобы отставший воркер не менял уже переназначенную задачу ([T, строка 227](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L227), [README, Coordinating a fleet](https://github.com/jedarden/bead-rs/blob/main/README.md#coordinating-a-fleet)). После рестарта демона старый вызов `wait_result` может ещё вернуться, и токен не даст ему изменить новое состояние.
6. TaskHub показывает жёлтый порог на 75% и красный на 90%, читая лимиты раз в 10 минут без модельных запросов ([T, строка 199](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L199), [README, Plan limits in Codex](https://github.com/FelixMUrphy/TaskHub/blob/main/README.md#plan-limits-in-codex)). Beacon ведёт 15 ожиданий и должен предупредить о приближении к лимиту заранее. Число 10 минут здесь уставка чтения счётчика, а не замена событийной модели. Код TaskHub не берётся: лицензия PolyForm Shield запрещает конкурентный продукт ([T, строка 195](/home/nbook/Projects/tmp/beacon-research/T-next-wave.md#L195), [README, License](https://github.com/FelixMUrphy/TaskHub/blob/main/README.md#license)).

## Последствия

- Из каждого пункта выходит одна небольшая карточка в `docs/tasks/` по правилам ADR 0020. Карточки этим ADR не создаются и будут созданы отдельными задачами.
  - Фича 1: `internal/domain/types.go`, `internal/app/taskcli/service.go`, `cmd/beacon/agents.go`, `internal/infra/mcp/tool_claim.go` и тесты к ним.
  - Фича 2: `internal/infra/mcp/tool_wait_result.go`, `internal/infra/mcp/schema.go`, `internal/domain/transition.go`, `internal/infra/ladder/transitions.go`, `internal/infra/mcp/contract_test.go` и тесты к ним.
  - Фича 3: `cmd/beacon/watch.go`, `internal/infra/mcp/tool_watch_pr.go`, `internal/domain/transition.go`, `internal/infra/store/observability.go` и тесты к ним.
  - Фича 4: `internal/infra/mcp/tool_wake.go`, `cmd/beacon/agents.go`, `internal/infra/mcp/server.go` и тесты к ним.
  - Фича 5: `internal/domain/types.go`, `internal/infra/store/db.go`, `internal/infra/taskstore/store.go`, `internal/infra/mcp/tool_claim.go`, `internal/infra/mcp/tool_ack.go` и тесты к ним.
  - Фича 6: `internal/infra/mcp/tool_stats.go`, `internal/infra/store/observability.go`, `internal/domain/types.go`, `cmd/beacon/main.go` и тесты к ним.
- Проверка карточек: получатель события выбирается по объявленным возможностям и не меняется при переименовании сессии; `wait_result` возвращается в момент события или одобрения, а лестница ADR 0017 по-прежнему фиксирует исход доставки; при двух активных юнитах на одном CI печатается WARNING и ожидание идёт через одну точку; сломанный hook адаптер даёт код 0, пустой stdout и причину в логе, остальные ожидания продолжаются; вызов с устаревшим fencing token не меняет переназначенную задачу; при 75% и 90% лимита появляется предупреждение, а чтение счётчика не вызывает модель.
- Число MCP-инструментов остаётся равным семи, ADR 0003 и 0009 не меняются. Лестница из ADR 0017 сохраняется: новая семантика возврата не меняет подтверждения, повторы и эскалации. Байтово стабильный ответ из ADR 0036 пункт 2 сохраняется: граница возврата не переставляет поля. Fail-open плагина из ADR 0006 и T3.5 сохраняется: контракт hook его не заменяет. Fencing token из фичи 5 и ревизия задачи из T3.45 это разные ключи, они применяются последовательно. Один мост на протокол из ADR 0024, изоляция worktree из ADR 0021 и проверка только в CI из ADR 0022 дополнительной не становятся.

## Отклонённое

Хардкодить имена сессий при выборе получателя. Список из 15 агентов придётся править при каждом изменении состава.

Возвращать `wait_result` по истечении интервала опроса. Агент получает управление раньше события и начинает лишний опрос.

Убирать лестницу ADR 0017 ради прямой отправки по событию. Исход доставки всё ещё определяет повтор и эскалацию.

Дать каждому из 15 агентов отдельный таймер на общий CI. Появятся фантомные таймауты, которые читаются как дефект кода.

Ронить сервер или остальные ожидания при отказе hook адаптера. Отказ не должен выходить наружу ненулевым кодом и содержимым stdout.

Считать fencing token версией задачи из T3.45 или ключом доставки из ADR 0034. Токен это номер аренды, ревизия это версия состояния, `event.id` это ключ доставки.

Брать код TaskHub, его polling как архитектуру или тайминг GIF из bead-rs как перформанс. Лицензия TaskHub запрещает конкурентный продукт, а 0.2 с против 0.4-0.6 с в bead-rs это длительность анимации, а не замер кода.
