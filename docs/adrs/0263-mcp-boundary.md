# ADR 263: Граница MCP в десять инструментов

Статус: accepted

## Контекст

Публичный контракт зафиксирован в `internal/infra/mcp/server.go` (`toolDescriptors` и производный от него `ToolNames`) и в `internal/infra/mcp/contract_test.go` (`expectedToolNames`). Тест сравнивает отсортированные имена, требует схему вывода для каждого инструмента, ограничивает сериализованный `tools/list` ответ 20 KiB и сверяет его размер и SHA-256 с золотыми константами. В пакете есть обработчик wake, но `NewServerWithDeps` его не регистрирует: `AttachWake` не вызывается. Инструменты `beacon_task_claim` и `beacon_task_close` зарегистрированы через `toolDescriptors`. ADR 0186 уже решил, что новые возможности идут через REST, SSE и внутренние сервисы, а не через расширение набора инструментов без отдельного решения.

## Решение

MCP это проекция состояния сервера, а не его владелец (ADR 262). Контракт содержит ровно десять имён: `beacon_ack`, `beacon_cancel_watch`, `beacon_defer_wiring`, `beacon_get_result`, `beacon_list_running`, `beacon_stats`, `beacon_task_claim`, `beacon_task_close`, `beacon_wait_result`, `beacon_watch_pr`. Порядок не является частью контракта, тест сравнивает отсортированные списки. Цикл агента живёт в `CycleInstructions` при handshake в `internal/infra/mcp/server.go`, а не в отдельном инструменте.

Схемы ответов выводятся из Go-типов в `internal/infra/mcp/schema.go`, а не пишутся вручную. Аннотации честные: `beacon_list_running` и `beacon_stats` read-only, `beacon_cancel_watch` единственный destructive, `beacon_task_claim` меняет состояние карточки один раз и не помечает идемпотентность, остальные additive, потому что пишут `readAt`, `claimedAt` или намерение. `beacon_get_result` выдаёт имена проверок, заключения, ссылки и машиночитаемое `nextAction`, но не логи и не полный вывод проверок. `beacon_ack` пишет только намерение и не возвращает вердикт. Оба факта, прочтение и принятие обязательства, идут через `ObligationStamper` (`internal/infra/mcp/tool_get_result.go`, `internal/infra/mcp/tool_ack.go`).

Новый инструмент требует отдельного ADR, правки `toolDescriptors` и пересчёта золотого ответа `tools/list` в `contract_test.go`. Без этого возможность остаётся доступной через loopback HTTP и SSE (`internal/infra/httpapi/server.go`) или внутренний сервис. Тихая регистрация обработчика вне контракта запрещена. ADR 0094, ADR 0268 и ADR 0270 фиксируют принятые решения для восьмого, девятого и десятого имён.

## Последствия

Цикл агента остаётся стабильным, а тест контракта ловит лишнее имя и раздутие схемы до того, как клиент увидит изменение. Клиент не может завести второе состояние через MCP: все десять инструментов работают с портами, которые внедрил сервер. Часть функций остаётся доступной только через HTTP и SSE, что является сознательным trade-off ради неизменного контракта. Одиннадцатый инструмент требует смены контракта и нового золотого замера, а не локальной правки хендлера. Поскольку `NewServerWithDeps` не вызывает `AttachWake`, живая проверка доставки из ADR 0026 через базовый контракт MCP недоступна. Эту проверку заменяют модульные тесты `internal/infra/mcp/tool_wake_test.go`, которые подключают инструмент через `AttachWake` с подставным отправителем. Регистрация wake в контракте потребует отдельного ADR и пересчёта золотого замера.
