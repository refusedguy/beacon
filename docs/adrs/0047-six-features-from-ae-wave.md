# ADR 0047. Шесть фич из отчёта AE-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AE «AE-волна: новые проекты для Beacon» от 20 ноября 2026 года ([AE, строка 1](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L1)). Идеи собраны в разделе «Фичи» ([AE, строка 27](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L27)) и подтверждены таблицей проектов ([AE, строки 11-25](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L11)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0046 и 157 карточках из `docs/tasks/`. Идемпотентность, fencing, подписанный вердикт, completion proof и handoff уже зафиксированы в предыдущих решениях и карточках, поэтому здесь не повторяются. Несколько новых пунктов похожи на существующие по имени, но различаются по уровню. Правила в фиче 1 это проверка на MCP-сервере до смены статуса, а не правило в промпте и не порядок создания карточки из ADR 0020. Флаг в фиче 2 это свойство тихого сообщения, а не способ доставки из ADR 0026 и не одно из восьми состояний квитанции из ADR 0043. Парсер в фиче 3 разбирает внешний вердикт ревьюера, а не называет indeterminate результат потерянного ответа из T3.64 и не подписывает байты вердикта из ADR 0045. Лимит в фиче 4 задаёт границу одного наблюдения готовности, а не порог синхронного вызова из T3.103. Хэш в фиче 5 привязывает доказательство к содержимому артефакта, а не фиксирует наличие proof из T3.88. Поля в фиче 6 это три признака владельца worktree с boot id и отдельный вердикт `unverifiable`, а не три сигнала детекции смерти из T3.86. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Граф задач в MCP-сервере с правилами в YAML. Сервер хранит граф и до смены статуса задачи проверяет, что обязательные заметки заполнены, а зависимости закрыты. Правила лежат в YAML и читаются сервером, а не живут в промпте модели. Смена статуса без прохождения проверки отклоняется на границе сервера. Проверка не меняет порядок создания карточек из ADR 0020 и не переписывает модель статуса из ADR 0025. Она добавляет валидацию перед переходом в уже существующие статусы.

2. Флаг `no-wake` для тихих сообщений. Сообщение с этим флагом попадает в очередь целевой сессии, но не будит её. Принятие в очередь не считается прочтением. Квитанция остаётся на стадии доставки до явного чтения. ADR 0026 отвечает, как доставить сообщение (`steer`, `queue`, `unsupported`), а флаг отвечает, будить ли сессию. Восемь состояний квитанции из ADR 0043 не переписываются, флаг только удерживает пробуждение.

3. Строгий парсер вердикта. Парсер разбирает ответ внешнего ревьюера и возвращает код 0 для approve, код 3 для changes requested и код 4 для неясного ответа. Неясный ответ считается отказом. Блокирующее решение всегда побеждает. Если ревьюер оставил блокировку, вердикт не смягчается никаким другим сигналом. Парсер не подменяет T3.64, где indeterminate означает «действие выполнено, ответ потерян», и не меняет подпись вердикта из ADR 0045.

4. Ограничение одного наблюдения MCP в 50 секунд. Один вызов ожидания готовности наблюдает не дольше 50 секунд, чтобы уложиться в 60-секундный лимит клиента. Если готовность не наблюдена, ответ об ошибке несёт `jobId` в `error.details`, и клиент продолжает наблюдение с этим идентификатором. Ограничение задаёт границу одного наблюдения, а не порог синхронного вызова из T3.103. Таймаут не даёт права запускать работу заново.

5. Привязка требования к SHA-256 артефакта. Каждое требование в гейте готовности несёт SHA-256 того артефакта, который проверяется. Пересборка меняет хэш и делает старые доказательства просроченными без ручного напоминания. T3.88 фиксирует наличие proof, а здесь proof связывается с содержимым. Доказательство от старой сборки не принимается для новой.

6. Три поля владельца worktree и вердикт `unverifiable`. Владелец слота описывается тремя полями: `pid`, время старта из поля 22 `/proc/<pid>/stat` и boot id. Boot id отличает перезапуск машины от повторного использования pid. Если данных не хватает, парсер возвращает отдельный вердикт `unverifiable`. Такой вердикт считается живым владельцем, слот не забирается, а попытка возврата получает собственный код отказа. Это усиливает T3.86, где три сигнала детекции смерти не включают boot id.

## Причина

1. jpicklyk/task-orchestrator держит граф задач в MCP-сервере и блокирует переход, если не заполнены обязательные заметки или не закрыты зависимости, а правила задаются YAML ([AE, строка 31](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L31), [task-orchestrator](https://github.com/jpicklyk/task-orchestrator)). В Beacon задачи и статусы уже живут в SQLite по ADR 0015 и ADR 0025, но правила перехода живут в инструкции модели. Берётся серверная проверка перед сменой статуса и правила в YAML, а не Kotlin-рантайм task-orchestrator с Docker, своим графом и схемой без пробуждения сессии ([AE, строка 59](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L59)).

2. leeguooooo/open-cross-session различает доставку в очередь и прочтение и несёт флаг `no-wake` для тихих сообщений ([AE, строка 32](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L32), [open-cross-session](https://github.com/leeguooooo/open-cross-session)). ADR 0026 честно называет способ доставки, ADR 0043 различает восемь состояний квитанции, но ни одно не удерживает пробуждение для тихого сообщения. Берётся флаг и правило «в очередь не значит прочитано», а не протокол между продуктами с Ed25519, X25519 и AES-256-GCM и плагином для каждого харнеса ([AE, строка 60](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L60)).

3. tonydzi/verdict-contract превращает ответ AI-ревьюера в строгий exit-код, считает неясный ответ отказом и даёт набор из 42 контрпримеров, а блокировка всегда побеждает ([AE, строка 33](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L33), [verdict-contract](https://github.com/tonydzi/verdict-contract)). T3.64 называет indeterminate результат, когда действие выполнено, а ответ потерян. Здесь другой случай, парсер разбирает текст внешнего вердикта. Берутся коды 0, 3, 4 и правило «неясное значит отказ», а не оценка текста ответа вместо статусов GitHub Checks ([AE, строка 61](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L61)).

4. 777genius/agent-wait-on ограничивает один вызов наблюдения 50 секундами под клиент с лимитом 60 секунд и сохраняет `jobId` в `error.details`, если готовность не удалось наблюдать ([AE, строка 35](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L35), [agent-wait-on](https://github.com/777genius/agent-wait-on)). T3.103 задаёт порог синхронного вызова 30/120 секунд в `cmd/beacon/mcp.go`, но не границу одного наблюдения и не возвращает `jobId` при неудаче. Берутся лимит наблюдения и поле `error.details`, а не форк agent-exec с зависимостью от Universal Agent Plugins и Node при установке ([AE, строка 63](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L63)).

5. mthburnsbarber-web/done-gate привязывает каждое требование к SHA-256 того пакета, который отправляется, и пересборка сама делает старые доказательства недействительными ([AE, строка 36](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L36), [done-gate](https://github.com/mthburnsbarber-web/done-gate)). T3.88 даёт completion gate с proof, но proof привязан к задаче, а не к содержимому артефакта. Берётся хэш артефакта в каждом требовании, а не Node.js-утилита, которая не запрашивает GitHub Checks и не знает о задачах и сессиях ([AE, строка 64](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L64)).

6. JesseRWeigel/wtpool хранит три поля владельца: pid, start time из поля 22 `/proc/<pid>/stat` и boot id, а при нехватке данных возвращает отдельный вердикт `unverifiable`, который считается живым владельцем ([AE, строка 37](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L37), [wtpool](https://github.com/JesseRWeigel/wtpool)). T3.86 уже реализовал детекцию смерти по трём сигналам, но без boot id и без отдельного вердикта. Берутся три поля и `unverifiable`, а не пул только для Linux без MCP и внешних событий ([AE, строка 65](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L65)).

Числа в разделе «Перформанс» AE-отчёта это заявления авторов проектов ([AE, строка 47](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L47)), в контракт Beacon они не переносятся.

## Отклонённое

Сводить правила из фичи 1 к промпту. Правило в промпте модель может проигнорировать, а серверная проверка до смены статуса не даёт перейти в новое состояние с незаполненными заметками. ADR 0020 задаёт, когда карточка создаётся, а не когда задача может сменить статус.

Подменять флаг из фичи 2 способом доставки ADR 0026. ADR 0026 отвечает, как отправить сообщение. Флаг `no-wake` отвечает, будить ли целевую сессию. Сообщение может быть доставлено в очередь и при этом не прочитано и не разбудило сессию.

Сводить парсер из фичи 3 к T3.64 или к подписи вердикта ADR 0045. T3.64 называет indeterminate потерянный ответ после выполненного действия. Подпись привязывает байты вердикта к ключу. Ни одно не разбирает текст ответа ревьюера и не превращает неясный ответ в отказ с кодом 4.

Подменять лимит из фичи 4 порогом T3.103. T3.103 ограничивает синхронный вызов 30 или 120 секундами в CLI. Лимит 50 секунд ограничивает одно наблюдение внутри MCP-вызова и возвращает `jobId`, чтобы клиент продолжил с того же задания.

Сводить хэш из фичи 5 к proof T3.88. T3.88 фиксирует, что доказательство есть. Хэш артефакта фиксирует, что доказательство относится к текущей сборке. Proof от старой сборки не принимается после пересборки.

Подменять поля из фичи 6 детекцией T3.86. Три сигнала T3.86 не различают перезапуск машины и повторное использование pid. Boot id и вердикт `unverifiable` закрывают этот случай. При нехватке данных слот не забирается.

Брать числа из раздела «Перформанс» AE-отчёта как обязательные показатели Beacon. Значения не воспроизведены автором отчёта. У ajinb/durable-agent-loop таблица SIGKILL даёт 20, 6, 3 и 0 дублей из 30 убийств и средние лишние токены 17 967, 6 167, 1 233 и 1 233, медиана записи 3,02 мс на Apple M3 ([AE, строка 49](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L49), [blog](https://cloudandsre.com/blog/durable-execution-for-agents-sigkill-test/)). У agent-wait-on границы 10, 30 и 50 секунд это проектные лимиты, не замер пропускной способности ([AE, строка 50](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L50)). verdict-contract сообщает 42 контрпримера, 205 строк и пять способов ошибочного APPROVE, но прогон четырёх тестовых файлов отмечен только автором ([AE, строка 51](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L51)). agent-idempotency-guard заявляет 20 тестов и TTL 24 часа ([AE, строка 52](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L52)), agent-mobile-device-lease проверяет владельца раз в секунду и убивает команду через 750 мс после SIGTERM ([AE, строка 53](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L53)). taskflow заявляет «sub-ms slots» без таблицы измерений ([AE, строка 54](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L54)). Остальные семь проектов замеров скорости не публикуют, а пример done-gate 2 из 72 требований это демо-данные ([AE, строка 55](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L55)). В контракт Beacon переносятся правила шести фич, не эти числа.

Брать код проектов из отчёта без проверки лицензии. Из шести отобранных проектов task-orchestrator, open-cross-session, verdict-contract, agent-wait-on, done-gate и wtpool имеют MIT ([AE, строки 13-19](/home/nbook/Projects/tmp/beacon-research/AE-wave.md#L13)). В решении переносятся контракты шести фич, а не рантаймы этих проектов.

Включать в этот ADR остальные идеи из раздела «Фичи» AE. Менеджером в волну отобраны шесть пунктов выше. Семь кандидатов не вошли: agent-exec с контрактом `wait` и jobId (AE:34), taskflow с append-only журналом CRC32 (AE:38), agent-wakeup с probe `wait`/`notify`/`wake` (AE:39), durable-agent-loop со стабильным идемпотентным ключом (AE:40), agent-idempotency-guard с каноническим JSON и отпечатком SHA-256 (AE:41), agent-mobile-device-lease с арендой процесса (AE:42) и merge-guard с привязкой одобрения к head SHA (AE:43). Идемпотентность, fencing, подписанный вердикт, completion proof и handoff уже есть в ADR 0001-0046 и карточках, поэтому эти идеи не дублируются.
