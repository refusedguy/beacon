# ADR 0048. Шесть фич из отчёта AF-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта AF «AF волна: новые проекты» от 20 ноября 2026 года ([AF, строка 1](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L1)). Идеи собраны в разделе «Фичи» ([AF, строки 249-268](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L249)) и подтверждены описаниями проектов в разделе «Новые проекты» ([AF, строка 7](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L7)). Здесь зафиксированы только те фичи, которых нет в ADR 0001-0047 и 158 карточках из `docs/tasks/`. Fencing, аренда, идемпотентность, вердикт, reclaim и GraphQL-батч уже зафиксированы: T3.51 и T3.97 отвечают за fencing, T3.53 за аренду, ADR 0028 за идемпотентность, ADR 0045 и T3.64 за вердикт, T3.65 за reclaim, ADR 0004 и T0.2 за GraphQL-батч. Поэтому эти шесть тем здесь не повторяются. Несколько новых пунктов похожи на существующие по имени, но различаются по уровню. Вердикт в фиче 1 сводит сырой `statusCheckRollup` к текущему запуску каждой проверки, а не меняет таблицу решений в `internal/domain/verdict.go` и не добавляет батч ADR 0004. Событие в фиче 2 вставляется в контекст агента как факт, а не как промпт от имени агента, и не подменяет доставку ADR 0026. Handle в фиче 3 это контракт фоновой задачи с `wait(timeout)`, `output(offset)` и уведомлением о завершении, а не способ подписи из T3.96 и не байт-стабильный ответ `wait_result` из ADR 0036. Команда `gc` в фиче 4 очищает аренды и талоны, а не забирает worktree по признаку мёртвого владельца из AF:257 и T3.65. `UNKNOWN` в фиче 5 это исход мутирующего вызова, а не результат задачи из T3.64 и не причина останова `unknown_submission` из ADR 0046. Очередь в фиче 6 задаёт приоритеты и автоматический переход, а не прерывание ожидания из ADR 0028. Владелец велел принять отобранные идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Вердикт CI по текущему запуску каждой проверки. Адаптер GitHub сводит `statusCheckRollup` не к сырому агрегату, а к вердикту текущего запуска каждой проверки. Проверка, которую перезапустили и которая стала зелёной, побеждает старый красный результат в сырых данных. Сводка живёт в адаптере и не меняет таблицу решений в `internal/domain/verdict.go`, порядок батча ADR 0004 и схему ответа.

2. Вердикт CI как событие в контексте агента. Beacon кладёт вердикт CI в контекст агента событием вместе с текстом ошибки. Агент видит причину провала сам. Beacon не отправляет промпт за агента и не меняет его ход. Событие не меняет способ доставки follow-up из ADR 0026 и не добавляет ступень в лестницу ADR 0017.

3. Handle долгой задачи. Beacon выдаёт handle фоновой задачи. `wait(timeout)` возвращает `waited_ms` и флаг `timed_out`, `output(offset)` читает вывод по смещению байт, а о завершении задачи приходит уведомление. Подпись handle из T3.96 остаётся отдельным механизмом целостности. Здесь фиксируется контракт ожидания и чтения вывода, а не способ подписи и не ответ `wait_result` из ADR 0036.

4. Очистка аренд и талонов отдельной командой. CLI получает команду `gc`, которая удаляет просроченные аренды, мёртвые PID и устаревшие талоны очереди. Применение происходит отдельным действием, команда сообщает, что удалено. Команда не заменяет reclaim worktree с dry-run из AF:257 и T3.65 и не меняет TTL аренд из T3.97.

5. `UNKNOWN` как отдельный исход мутации. Исход мутирующего вызова, который нельзя подтвердить, записывается как `UNKNOWN`. Агент не повторяет вызов вслепую, а получает задачу сверки состояния. Это исход tool call на уровне выполнения. Он не совпадает с результатом задачи `indeterminate` из T3.64 и с причиной останова `unknown_submission` из ADR 0046 фичи 3.

6. Приоритетная очередь вопросов к человеку. Вопросы к человеку живут в одной очереди сессии с приоритетами urgent, high, medium и low. После ответа на один вопрос Beacon автоматически переходит к следующему по приоритету. Очередь хранится как состояние сессии, а не как флаг досрочного возврата из ADR 0028.

## Причина

1. fmguerreiro/prstate нормализует состояние PR по трём осям: вердикт CI, неотвеченные люди, незакрытые находки ботов ([AF, строка 103](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L103), [prstate](https://github.com/fmguerreiro/prstate)). Сырые данные GitHub показывают старый красный результат, даже если проверку перезапустили и она стала зелёной ([AF, строка 105](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L105)). В Beacon батч читает `statusCheckRollup` по ADR 0004 и T0.2, а движок вердикта решает по нормализованному состоянию, но выбор текущего запуска каждой проверки не зафиксирован. Берётся сведение к текущему запуску, а не только читающая библиотека с raw GraphQL и авторизованным `gh` ([AF, строка 107](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L107), [install](https://github.com/fmguerreiro/prstate#install)).

2. gerricchaplin/pr-pulse показывает в Claude Code вердикт готовности к слиянию, прогресс проверок и вставляет известие о провале CI в следующий промпт ([AF, строки 111-113](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L111), [pr-pulse](https://github.com/gerricchaplin/pr-pulse#claude-aware)). ADR 0026 честно называет способ доставки follow-up, а ADR 0017 задаёт ступени пробуждения, но ни одно не кладёт вердикт в контекст агента как событие с текстом ошибки. Берётся событие без промпта за агента, а не TUI-плагин для Claude Code ([AF, строка 117](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L117), [README](https://github.com/gerricchaplin/pr-pulse#readme)).

3. emiliano-go/opencode-bgj даёт MCP-сервер инструменты запуска долгих shell-задач и слежения за ними без блокировки хода агента ([AF, строка 53](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L53), [opencode-bgj](https://github.com/emiliano-go/opencode-bgj)). Инструменты `bgj_start` и `bgj_wait` принимают таймаут, `bgj_wait` возвращает `waited_ms` и `timed_out`, а `bgj_output` читает вывод по смещению байт ([AF, строка 55](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L55), [таблица инструментов](https://github.com/emiliano-go/opencode-bgj#tools)). В Beacon есть подписанный handle из T3.96 и long-poll `wait_result` из ADR 0036, но нет контракта фоновой задачи с чтением вывода по смещению. Берётся контракт handle, wait и output с уведомлением, а не сервер, заточенный под плагины OpenCode ([AF, строка 57](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L57)).

4. rock3r/atc координирует эмуляторы и тяжёлые сборки между агентами без демона, через аренды, очередь ожидания и снимки ([AF, строка 153](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L153), [atc](https://github.com/rock3r/atc#overview)). Команда `atc gc` подчищает просроченные аренды, мёртвые PID и устаревшие талоны очереди, а `atc renew` задаёт TTL ([AF, строка 155](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L155), [commands](https://github.com/rock3r/atc#development)). В Beacon аренды и талоны уже живут в `tool_claim.go` и хранилище, но нет одной команды очистки. Берётся отдельная команда `gc`, а не поддержка Android, iOS и Gradle, Bazel, Xcode ([AF, строка 157](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L157)).

5. Success6666/agent-runtime-governance реализует Action Commit Safety: выполняется именно одобренный вызов, а неопределённый исход мутирующего инструмента записывается как `UNKNOWN` и не ретраируется вслепую ([AF, строка 233](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L233), [AF, строка 235](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L235), [README](https://github.com/Success6666/agent-runtime-governance#readme)). T3.64 называет `indeterminate` результат задачи, когда действие выполнено, а ответ потерян. ADR 0046 фича 3 называет `unknown_submission` причину останова `wait`. Здесь другой уровень: исход самого мутирующего вызова. Берётся запись `UNKNOWN` и задача сверки, а не Python-рантайм с OPA, аудитом и OpenTelemetry ([AF, строка 237](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L237)).

6. usestring/gate-inbox держит одну приоритетную очередь для всех агентов, которые ждут человека: ответил на один вопрос, на очереди следующий ([AF, строка 183](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L183), [gate-inbox](https://github.com/usestring/gate-inbox#readme)). Очередь ожидания это состояние сессии с приоритетом urgent, high, medium и low и автоматическим переходом к следующему сеансу ([AF, строка 185](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L185)). ADR 0028 прерывает ожидание по `hasPendingQuestion` и `pendingApproval`, но не задаёт порядок вопросов. Берутся приоритеты и правило «ответ привёл к следующему», а не чтение tmux-pane и зависимость от tmux 3.1+ ([AF, строка 187](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L187), [install](https://github.com/usestring/gate-inbox#install)).

Числа в разделе «Перформанс» AF-отчёта это заявления авторов проектов ([AF, строка 270](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L270)), в контракт Beacon они не переносятся. У atc критические секции меньше 20 мс, это не замер пропускной способности ([AF, строка 276](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L276)). У governance замеры сделаны на одном хосте с Python 3.12 ([AF, строка 279](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L279)). У pr-pulse интервалы опроса вызваны отсутствием webhook в локальном плагине ([AF, строка 285](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L285)).

## Отклонённое

Брать prstate целиком. Библиотека только читает состояние и требует raw GraphQL и авторизованный `gh`. Вся интеграция с агентами остаётся за её пределами ([AF, строка 107](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L107)). Beacon берёт только сведение `statusCheckRollup` к текущему запуску каждой проверки.

Отправлять промпт за агента. pr-pulse вставляет известие о провале CI в следующий промпт пользователя ([AF, строка 113](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L113)), но Beacon работает через свой адаптер и не пишет сообщения от имени агента. В контекст кладётся событие с текстом ошибки, ход агента остаётся за ним.

Сводить handle из фичи 3 к подписанному handle T3.96. Подпись решает целостность непрозрачного идентификатора. Контракт из фичи 3 решает, как ждать задачу, читать вывод и узнать о завершении. Это разные вопросы, и один не заменяет другой.

Сливать `gc` из фичи 4 с reclaim worktree из AF:257. Reclaim забирает worktree у мёртвого владельца после dry-run ([AF, строка 257](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L257), T3.65). Команда `gc` удаляет просроченные аренды и талоны. Первое меняет владельца ресурса, второе убирает просроченные записи.

Сводить `UNKNOWN` из фичи 5 к T3.64 или к причине из ADR 0046. T3.64 называет результат задачи, когда действие выполнено, а ответ потерян. ADR 0046 называет причину останова `wait` для неизвестной заявки. Ни одно не классифицирует исход мутирующего вызова и не выдаёт задачу сверки вместо повтора.

Сводить очередь из фичи 6 к прерыванию ожидания ADR 0028. ADR 0028 заставляет `wait_result` вернуться раньше таймаута, когда агенту нужен человек. Он не задаёт приоритеты вопросов и не переводит сессию к следующему вопросу после ответа. Очередь хранит состояние, а не один флаг.

Брать числа из раздела «Перформанс» AF-отчёта как обязательные показатели Beacon. Отчёт прямо помечает, что цифры заявлены авторами и не воспроизведены ([AF, строка 270](/home/nbook/Projects/tmp/beacon-research/AF-wave.md#L270)). В контракт переносятся правила шести фич, не эти числа.

Включать в этот ADR остальные идеи из раздела «Фичи» AF. Менеджером в волну отобраны шесть пунктов выше. Восемь кандидатов не вошли. Аренда с heartbeat и `STALE_LEASE` (AF:256), reclaim worktree с dry-run (AF:257), идемпотентность через токен одобрения и канонический хеш (AF:261) и один GraphQL-запрос с адаптивным интервалом (AF:264) уже есть в ADR 0001-0047 и карточках, поэтому не дублируются. Шесть маршрутов реакции на событие вместо флага пробуждения (AF:259), восстановление задачи после истечения аренды `firing → due` (AF:260), crash-test инструментов как контрактный тест (AF:263) и явная привязка PR к worktree и агенту через `refs/pull/N/head` (AF:266) менеджером в эту волну не отобраны.
