# ADR 0043. Шесть фич из отчёта Z-wave

Статус: accepted

Этот ADR фиксирует шесть фич из отчёта Z «Z-волна: 18 новых проектов» от 20 ноября 2026 года. Идеи собраны в разделе «Фичи» ([Z, строка 171](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L171)) и подтверждены разделами конкретных проектов. Здесь зафиксированы только те фичи, которых нет в ADR 0001-0042 и 140 карточках из `docs/tasks/`. Fencing и аренда уже в T3.51 и ADR 0038 пункт 1, идемпотентность по `clientRequestId` в ADR 0028, replay сценария в ADR 0042 пункт 6, дедлайн в ADR 0042 пункт 1, completion gate с proof в ADR 0042 пункт 4, способ доставки `steer`, `queue` и `unsupported` в ADR 0026. Несколько новых пунктов похожи на существующие решения по имени, но различаются по уровню. Чекпоинт в фиче 1 запоминает прогресс ожидания, а replay из ADR 0042 пункт 6 проверяет отсутствие второго эффекта. Сериализация в фиче 2 упорядочивает применение событий к задаче, а ревизия из ADR 0036 пункт 5 отбрасывает старое состояние. Восемь состояний в фиче 4 описывают жизнь одного сообщения, а способ доставки из ADR 0026 описывает, как оно отправляется. STALE-колонка в фиче 5 только читает реестр и не инвалидирует аренду. Возобновление в фиче 6 продолжает ту же сессию после таймаута, а дедлайн из ADR 0042 пункт 1 завершает задачу. Владелец велел принять оставшиеся идеи без дополнительных вопросов, поэтому статус `accepted`. По ADR 0020 карточки создаются только из принятого ADR. Карточки этим ADR не создаются, код, карточки и тесты в этой задаче не трогаются.

## Решение

Beacon получает шесть механизмов. Они описаны на уровне контракта и не привязаны к конкретному продукту.

1. Чекпоинт шагов ожидания. `wait_result` делит ожидание на шаги и записывает номер последнего завершённого шага в SQLite вместе с состоянием задачи. После рестарта ожидание продолжается с записанного шага, а не начинает опрос заново. Запись шага и сохранение состояния задачи идут в одной транзакции по ADR 0015. Это прогресс одного ожидания, а не подавление повтора команды из ADR 0028 и не проверка отсутствия второго эффекта из ADR 0042 пункт 6.

2. Сериализованная обработка событий одной задачи. Все события, которые относятся к задаче, проходят через одну очередь и применяются по одному, даже если наблюдателей несколько. Два наблюдателя CI, которые пишут статус одновременно, не перезаписывают друг друга: результат второго применяется к результату первого. Ключ сериализации это идентификатор задачи. `event.id` из ADR 0034 различает повторные доставки одного события, ревизия из ADR 0036 пункт 5 отбрасывает устаревшее состояние, а здесь события упорядочиваются до применения.

3. Long-poll канал вне MCP-хода. Ожидание события выносится из вызова `wait_result` в отдельный канал, который держит открытым внешний процесс CLI. Ход модели завершается сразу, а событие приходит как ответ на уже открытый запрос. Канал работает поверх существующего хранилища и не добавляет брокера. Время жизни Watch из ADR 0019 и честная доставка из ADR 0026 сохраняются: меняется только место, где висит ожидание, а не маркеры лестницы. Из llm-bus берётся идея протокола, код не берётся по причине лицензии AGPL.

4. Восемь состояний доставки. Квитанция сообщения вместо одного флага «отправлено» несёт одно из восьми состояний: `spooled`, `pending`, `held`, `pushed`, `push-unreachable`, `read`, `refused`, `expired`. Состояния различают сообщение, которое лежит на диске, ждёт отправки, удержано, отправлено, отправлено в недостижимый канал, прочитано, отклонено получателем и истекло. Три состояния из ADR 0014 и способ доставки из ADR 0026 остаются: `steer`, `queue` и `unsupported` отвечают на вопрос как отправить, а восемь состояний отвечают на вопрос в какой точке жизни сообщение находится. Лестница ADR 0017 читает новые состояния как входные данные.

5. STALE-колонка в `beacon agents`. Реестр агентов получает отдельную колонку для задач в работе без живой аренды. Такая задача показывается отдельно от активных, с возрастом с момента истечения аренды. Колонка только читает состояние и не меняет аренду, не инвалидирует её и не запускает захват. Fencing T3.51 и трёхсигнальная детекция смерти из ADR 0042 пункт 2 остаются механизмами инвалидации и захвата, а здесь добавляется видимость мёртвых аренд.

6. Возобновление по сохранённому `session_id`. Задача получает `session_id` до старта, и идентификатор сохраняется в хранилище вместе с задачей. Когда задача убита по таймауту, `beacon attach` открывает сохранённую сессию и продолжает работу в ней, а не создаёт новую. Дедлайн из ADR 0042 пункт 1 по-прежнему завершает задачу, но не стирает идентификатор сессии. ADR 0029 описывал `attach` как открытие уже существующей сессии в TUI; здесь добавляется продолжение задачи после таймаута через сохранённый идентификатор.

## Причина

1. go-workflows пишет чекпоинты шагов в уже используемую SQLite и после рестарта продолжает `wait_result` с последнего записанного шага ([Z, строка 177](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L177), [README:85](https://github.com/cschleiden/go-workflows/blob/main/README.md#L85)). Движок требует детерминизма кода, запрещает `select` и обход map и даёт Temporal-совместимый рантайм ([Z, строка 16](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L16)). Beacon нужен только сервис ожидания, поэтому берётся контракт чекпоинта, а не движок. ADR 0015 уже определяет SQLite как хранилище, поэтому новый сервер не вводится.

2. durable-actors строит модель «один актор на задачу» с сериализованной обработкой событий, где параллельные обновления статуса не перезаписывают друг друга ([Z, строка 179](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L179), [README:29](https://github.com/TerseAI/durable-actors/blob/main/README.md#L29)). Несколько наблюдателей CI пишут в одного актора ([Z, строка 33](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L33)). Рантайм на Rust с SDK только для Python и TypeScript, WebSocket-транспортом и деплоем на GCP не подходит ([Z, строка 34](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L34)). Beacon пишет на Go и общается по MCP, поэтому берётся порядок применений, а не акторный рантайм.

3. llm-bus держит длинный HTTP-опрос открытым до появления работы и выносит ожидание из MCP-инструмента, который блокирует ход модели ([Z, строка 180](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L180), [README:79](https://github.com/danieldoderlein/llm-bus/blob/main/README.md#L79)). Сейчас `wait_result` занимает ход модели на всё время ожидания. Проект под AGPL-3.0 и требует Node 22 с PostgreSQL 16 ([Z, строка 39](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L39), [README:43](https://github.com/danieldoderlein/llm-bus/blob/main/README.md#L43)), поэтому берётся только идея отдельного канала.

4. agent-loom различает восемь состояний квитанции: `spooled`, `pending`, `held`, `pushed`, `push-unreachable`, `read`, `refused`, `expired` ([Z, строка 182](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L182), [README:29](https://github.com/osteele/agent-loom/blob/main/README.md#L29)). В Beacon сейчас один флаг отправки не различает сообщение в spool и сообщение, которое получатель отказался читать. Push работает только через специфические каналы Claude Code и требует Node 22.18 ([Z, строка 61](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L61)), поэтому берётся набор состояний, а не почтовая система.

5. dibs показывает в `watch` отдельный lane STALE для задач в работе без живой аренды, с возрастом с момента истечения ([Z, строка 183](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L183), [README:76](https://github.com/abevz/dibs/blob/main/README.md#L76)). В таблице фич отчёта фича отнесена к `beacon agents`, где живёт реестр ([Z, строка 183](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L183)). Демон dibs работает на одной машине и не синхронизирует аренды между хостами ([Z, строка 70](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L70)), Beacon берёт только представление. ADR 0029 уже определяет `beacon agents` как команду, которая печатает список агентов.

6. agent-dispatch заранее выдаёт `session_id` на каждый dispatch, поэтому задачу, убитую по таймауту, можно продолжить в той же сессии ([Z, строка 188](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L188), [README:221](https://github.com/ginkida/agent-dispatch/blob/main/README.md#L221)). Сейчас таймаут обрывает задачу, и `attach` по ADR 0029 не знает, какую сессию открыть. Жёсткая привязка к Claude Code CLI и потеря обновления конфига после 10 секунд ожидания блокировки не берутся ([Z, строка 115](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L115)).

Числа в разделе «Перформанс» Z-отчёта это заявления авторов проектов ([Z, строка 200](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L200)), в контракт Beacon они не переносятся.

  - Фича 4: `internal/domain/types.go`, `internal/infra/store/receipts.go`, `internal/infra/mcp/tool_get_result.go`, `internal/infra/mcp/tool_ack.go`, `internal/infra/ladder/transitions.go`, `internal/infra/store/observability.go` и тесты к ним.

- Проверка карточек: после рестарта `wait_result` продолжается с последнего записанного шага, а не с начала; два наблюдателя, которые пишут статус одной задачи одновременно, оставляют оба обновления в порядке применения; ход модели завершается до прихода события, а ответ приходит в открытый канал; квитанция различает восемь состояний, и `refused` не считается прочитанной; `beacon agents` показывает задачу без живой аренды в отдельной колонке с возрастом и не меняет аренду; после таймаута `beacon attach` открывает сохранённую сессию и продолжает задачу в ней.
- ADR 0001, 0014, 0015, 0017, 0019, 0020, 0026, 0028, 0029, 0034, 0036, 0037, 0038, 0042 и T3.51 не переписываются. Набор MCP-инструментов остаётся прежним: меняется место ожидания и содержание квитанции, а не число инструментов. Три состояния из ADR 0014, способ доставки из ADR 0026, `event.id` из ADR 0034, ревизия из ADR 0036 пункт 5 и дедлайн из ADR 0042 пункт 1 остаются на своих местах. Ключи разные: шаг ожидания фичи 1 фиксирует прогресс, идентификатор задачи фичи 2 упорядочивает события, открытый запрос фичи 3 удерживает ожидание вне хода модели, состояние фичи 4 описывает сообщение, возраст аренды фичи 5 только показывает задачу, а `session_id` фичи 6 возвращает агента в ту же сессию.

## Отклонённое

Сводить чекпоинт к `clientRequestId` из ADR 0028 или к replay из ADR 0042 пункт 6. Первый гасит повтор одной команды, второй проверяет отсутствие второго эффекта, а здесь сохраняется прогресс незавершённого ожидания.

Брать акторный рантайм durable-actors целиком. Он на Rust с SDK для Python и TypeScript, а Beacon пишет на Go и общается по MCP. Берётся только порядок обработки событий одной задачи.

Брать код llm-bus. Проект под AGPL-3.0 и тянет Node 22 с PostgreSQL 16, что несовместимо с моделью поставки Beacon. Берётся только идея long-poll канала вне MCP-хода.

Приравнивать восемь состояний к способам доставки из ADR 0026. `steer`, `queue` и `unsupported` отвечают на вопрос как отправлять, а состояния квитанции отвечают на вопрос где сообщение находится. Заменять ими лестницу ADR 0017 тоже нельзя: лестница читает состояния как входные данные.

Изменять аренду из STALE-колонки или дублировать трёхсигнальную детекцию из ADR 0042 пункт 2. Колонка только показывает задачи без живой аренды, а инвалидация остаётся за fencing T3.51.

Считать `attach` из ADR 0029 достаточным для задачи после таймаута. Без сохранённого `session_id` команда откроет новую сессию, а не продолжит прерванную.

Брать hangar-ai/hangar в эту волну. Репозиторий содержит только релизы, гайд и сайт, исходный код не публичен ([Z, строка 218](/home/nbook/Projects/tmp/beacon-research/Z-wave.md#L218), [README:34](https://github.com/hangar-ai/hangar/blob/main/README.md#L34)).
