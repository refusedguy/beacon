# Выбор области архитектурного обзора

Статус: контракт проекта. Источник: `mattpocock/skills@abeeaf9`, `skills/engineering/improve-codebase-architecture/SKILL.md:20-35`. Обоснование разрыва: `docs/research/comp-matt-skills.md`. Карточка: `docs/tasks/CMx-06.md`.

Этот документ задаёт порядок выбора области перед архитектурным обзором. Обзор не начинается с полного сканирования репозитория. Сначала определяется область, затем читается контекст зоны, и только после этого сабагент обходит код. Глобально установленный скилл `improve-codebase-architecture` не является контрактом проекта. На него нельзя сослаться из ревью, он не попадает в `skills-lock.json` и исчезает при смене машины. Правило живёт здесь и проверяется вместе с репозиторием.

## Разрыв, который закрывает документ

Базовое измерение до выбора сделано по `origin/main` `0ce4ba29`, как записано в карточке:

```
git grep -i -c -E 'hot spot|горяч.*точк|deletion test' -- AGENTS.md README.md GLOSSARY.md docs/templates .opencode docs/design docs/adrs internal cmd tools scripts   # 0
```

В `docs/research/` лежат разовые аудиты. Ни один документ не задаёт порядок выбора области и обязательный проход по истории до сканирования. `docs/design/module-depth.md` и карточка `CM-03` задают сам deletion test, а не выбор области. CMx-06 закрывает этот разрыв.

## Два входа в обзор

Обзор начинается с одного из двух входов. Выбор входа делается до чтения кода.

1. **Направление от владельца.** Владелец назвал зону, модуль или файл. Эта зона и становится областью обзора. История коммитов в этом случае не нужна для выбора.
2. **Вывод по истории коммитов.** Владелец не назвал направление. Тогда область определяется по реальной истории изменений, а не по полному сканированию.

Второй вход работает по принципу YAGNI: внимание отдают тому, что действительно менялось, а не всему дереву подряд.

## Выбор области по истории

Когда направления нет, выполняется проход по истории за большой отрезок:

```
git log --oneline
```

Путь, число и отрезок фиксируются до запуска. Результатом прохода является список путей с числом попаданий. Каждый путь получает счётчик по числу коммитов, в которых он всплыл. Этот список показывается владельцу до обхода кода. Пока список не показан, обход не начинается.

Порядок действий для второго входа:

1. Зафиксировать отрезок истории и команду `git log --oneline`.
2. Собрать список путей с числом попаданий.
3. Показать список до обхода кода и получить согласие владельца на область.
4. Перейти к чтению контекста зоны.

Если владелец уточнил направление после показа списка, область меняется по первому входу.

## Чтение контекста до обхода кода

Перед обходом кода читаются источники зоны:

1. `GLOSSARY.md` проекта, чтобы использовать принятые термины и не изобретать новые имена.
2. ADR затронутой зоны из `docs/adrs/`, чтобы не предлагать решение, которое уже отклонено или принято.

Ссылки на прочитанные ADR попадают в отчёт обзора. Обход без прочитанного глоссария и ADR зоны проваливает карточку.

## Обход в сабагенте со свежим контекстом

Обход кода отдаётся сабагенту со свежим окном контекста. Общий контекст не используется: сабагент не несёт находки предыдущих шагов и не подталкивается к ним. В бриф сабагента входят выбранная область, список путей с числом попаданий, прочитанные термины и ссылки на ADR.

Сабагент ищет пять видов трения.

| Вид трения | Как выглядит | Что проверить |
| --- | --- | --- |
| Разброс понимания по мелким модулям | Одна мысль размазана по многим маленьким файлам, и чтобы её понять, нужно собрать их в голове | Сколько файлов нужно прочитать, чтобы ответить на один вопрос о поведении |
| Мелкий модуль с интерфейсом сложнее реализации | Публичный контракт больше и сложнее, чем то, что модуль делает внутри | Число и сложность экспортируемых элементов относительно поведения модуля |
| Чистые функции, вынесенные ради теста | Функция существует только ради удобства теста и не несёт доменного смысла | Есть ли вызывающий вне тестов и можно ли вернуть код на место |
| Утечки через seam | Внутреннее состояние или деталь реализации проходит через границу модуля | Что тест или вызывающий знает о внутреннем устройстве модуля |
| Непроверяемые места | Поведение нельзя проверить тестом без хрупкого mock или прямого чтения внутреннего состояния | Можно ли проверить поведение через публичный интерфейс |

Каждое подозрение проверяется deletion test из `docs/design/module-depth.md` и карточки `CM-03`. Модуль мысленно удаляется. Если сложность исчезает вместе с ним, модуль был проходным слоем и подлежит удалению. Если сложность появляется снова в вызывающих, модуль зарабатывает своё место. Число строк реализации и интерфейса глубину не измеряет.

## Проверка

- Файл существует и содержит оба входа: направление от владельца и вывод по `git log --oneline`.
- `git grep -c 'git log --oneline' -- docs/design/architecture-scan.md` больше 0.
- Зафиксировано, что результат прохода по истории это список путей с числом попаданий и что он показывается до обхода кода.
- Есть требование прочитать `GLOSSARY.md` и ADR зоны до обхода.
- Названы все пять видов трения.
- Есть указатель на deletion test в `docs/design/module-depth.md` и на карточку `CM-03`.
- Обход идёт в сабагенте со свежим контекстом.
- Код и ADR не тронуты.

Обзор без списка hot spot по истории или без пяти видов трения проваливает карточку. Измерение до выбора зафиксировано нулевым поиском.
