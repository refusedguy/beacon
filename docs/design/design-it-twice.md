# Проектирование интерфейса тремя расходящимися вариантами

Статус: контракт проекта. Источник: `mattpocock/skills@abeeaf9`, `skills/engineering/codebase-design/SKILL.md:114`, `skills/engineering/codebase-design/DESIGN-IT-TWICE.md:9-44`. Обоснование разрыва: `docs/research/comp-matt-skills.md`. Карточка: `docs/tasks/CMx-04.md`.

Этот документ задаёт приём DESIGN-IT-TWICE: несколько радикально разных интерфейсов проектируются параллельно, затем выбирается один. Глобально установленный скилл `codebase-design` не является контрактом проекта. На него нельзя сослаться из ревью, он не попадает в `skills-lock.json` и исчезает при смене машины. Правило живёт здесь и проверяется вместе с репозиторием.

Приём описывает только генерацию альтернатив и выбор одной из них. Критерии глубины готового интерфейса задаёт CM-03 в `docs/design/module-depth.md`. Этот документ не повторяет тест удаления, проверку интерфейса как тестовой поверхности и счёт адаптеров. Он отвечает на другой вопрос: какие варианты вообще стоит рассмотреть, прежде чем применять критерии CM-03.

## Разрыв, который закрывает документ

Базовое измерение до выбора сделано по `origin/main` `0ce4ba29`, base карточки:

```
git grep -i -c -E 'design it twice|DESIGN-IT-TWICE|radically different' -- AGENTS.md README.md GLOSSARY.md docs/templates .opencode docs/design docs/adrs internal cmd tools scripts   # 0
```

Повтор на текущей base `87f60b6b` дал тот же нулевой результат, код выхода 1. Ни один активный артефакт не задаёт порядок параллельного проектирования интерфейсов. `docs/design/module-depth.md` описывает deletion test, число адаптеров и негативный контроль, но не описывает генерацию альтернатив. `AGENTS.md:139-149` спавнит агентов по свободным слотам, а не по конкурирующим интерфейсам. Измерение зафиксировано нулевым поиском, решение принимается на нём.

## Подготовка problem space до спавна

Перед запуском сабагентов автор пишет объяснение задачи для человека. Это не предложение интерфейса, а рамка, в которой сабагенты будут работать. В объяснение входят три вещи:

1. Ограничения, которым должен удовлетворять любой новый интерфейс.
2. Зависимости, от которых интерфейс зависит, с указанием категории по `DEEPENING.md`.
3. Примерный набросок кода, который делает ограничения конкретными. Набросок не является проектом интерфейса.

Автор показывает объяснение человеку и сразу переходит к спавну. Человек читает и думает, пока сабагенты работают параллельно.

## Четыре независимых брифа

Запускаются параллельно три или четыре сабагента в свежих окнах контекста. Общий контекст не используется, чтобы один сабагент не подталкивал другого к чужой находке. Каждый получает отдельный технический бриф с путями файлов, деталями связности, категорией зависимости по `DEEPENING.md` и описанием того, что находится за seam. В бриф входят словарь `SKILL.md` и словарь `GLOSSARY.md`, чтобы сабагенты называли вещи одинаково. У каждого брифа своё ограничение:

| Бриф | Ограничение |
| --- | --- |
| 1 | Минимизировать интерфейс: не более трёх точек входа, максимум выгоды на каждую. |
| 2 | Максимизировать гибкость: поддержать много вариантов использования и расширение. |
| 3 | Оптимизировать под самого частого вызывающего: сделать стандартный случай тривиальным. |
| 4 | Построить интерфейс вокруг портов и адаптеров для зависимостей между seam. |

Третий и четвёртый брифы обязательны, когда у кандидата есть частый вызывающий или зависимость пересекает seam. Меньше трёх альтернатив приёмом не считается.

## Пять выходов каждого сабагента

Каждый сабагент возвращает пять блоков. Неполный вывод не идёт в сравнение.

1. Интерфейс: типы, методы, параметры, инварианты, порядок вызовов и режимы ошибок.
2. Пример вызова, показывающий, как вызывающий пользуется интерфейсом.
3. Что реализация прячет за seam.
4. Стратегия зависимостей и адаптеры по `DEEPENING.md`.
5. Компромиссы: где выгода интерфейса высокая, где тонкая.

## Сравнение по трём осям

Варианты показываются по очереди, затем автор сравнивает их прозой. Сравнение идёт по трём осям:

| Ось | Вопрос к варианту |
| --- | --- |
| Depth | Сколько выгоды даёт интерфейс на единицу того, что вызывающий должен выучить. |
| Locality | Где концентрируется изменение при смене требования. |
| Размещение seam | Где проходит граница и что за ней спрятано. |

Оси не объединяются в одну оценку. Вариант может выиграть по depth и проиграть по locality. Такое расхождение записывается, а не сглаживается.

## Результат это рекомендация

После сравнения автор даёт собственную рекомендацию: какой вариант сильнее и почему. Если элементы разных вариантов сочетаются, автор предлагает гибрид и называет источник каждого элемента. Автор выражает твёрдое мнение. Список вариантов на выбор без рекомендации проваливает приём.

Глубину выбранного интерфейса автор проверяет по `docs/design/module-depth.md` и карточке `docs/tasks/CM-03.md`. Проверки CM-03 здесь не дублируются.

## Указатели, не переписываем

- `docs/design/module-depth.md` и `docs/tasks/CM-03.md` задают критерии глубины и негативный контроль. Не переписываем, только ссылаемся.
- `docs/tasks/CMx-04.md` хранит измерение до выбора и критерии приёмки. Не переписываем.
- `skills-lock.json` хранит список зафиксированных скиллов. Приём живёт в этом файле, а не в глобальном скилле.

## Проверка

- Файл существует, названы четыре ограничения, пять выходов и три оси сравнения.
- `git grep -c 'DESIGN-IT-TWICE' -- docs/design/design-it-twice.md` больше 0.
- Есть рекомендация с объяснением или гибрид, а не меню на выбор.
- Меньше трёх альтернатив, отсутствие оси depth, locality или размещения seam, отсутствие рекомендации проваливают карточку.
- Код и ADR не тронуты.
