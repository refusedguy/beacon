# Beacon как фабрика агентов

Документ применяет словарь `software-factory` к beacon на уровне сервисов и задач. Источник словаря: `mattpocock/skills@abeeaf9`, `skills/in-progress/software-factory/SKILL.md`. Работа записана в карточке `docs/tasks/MSK-01.md`.

Определения цикла лежат в `GLOSSARY.md`, правила агента в `AGENTS.md`. Здесь их содержание не повторяется. Watch, Verdict, Obligation, BlockerIncident и RoleFixer сохраняют свои значения из глоссария.

Фабрика превращает тикеты, PR и расписания в слитый код. Beacon ведёт два контура. Контур PR читает GitHub, считает вердикт, доставляет wake и мержит. Контур карточек выдаёт задачи через `beacon_task_claim` и спавнит FIX-агентов. Оба контура пишут в хранилище состояния на SQLite, устроенное по `README.md`, раздел «Из чего состоит Beacon».

## Сервисы

Каждый сервис это слот с продуктом. Один продукт может занять несколько слотов.

| Сервис | Продукт в beacon | Подтверждение |
| --- | --- | --- |
| Ticket tracker | GitHub Issues | Люди подают issue и обсуждают работу в комментариях. Очередь задач лежит в `docs/tasks/`, оттуда её раздаёт `internal/infra/mcp/tool_task_claim.go`. |
| Ticket source | GitHub Issues, созданные человеком | Внутри фабрики билеты заводит `beacon_defer_wiring`: карточка `WIRING-<pr>` для работы в чужих OwnerFiles (`docs/templates/executor-task.md`). |
| Git host | GitHub | Ветки, PR и обзоры. Адаптер `github.BatchProvider` из `internal/infra/github` читает проверки батчем и мержит (`README.md`, раздел «Из чего состоит Beacon»). |
| Orchestrator | beacon | `cmd/beacon orchestrate` и `cmd/beacon daemon`, контур `internal/app/orchestrator`. Состояние Watch и инцидентов лежит в SQLite. |
| Runner | Сессия OpenCode в git worktree | Плагин `.opencode/plugins/beacon-bridge.js` подключает сессию к MCP-серверу и доставляет wake. Ветка и worktree описываются в `docs/templates/executor-task.md`. |
| Observability platform | Нет, сознательный отказ | Состояние читают `beacon inspect`, `beacon watch`, `beacon board` и `beacon logs --tail 40 --errors` (`AGENTS.md`). Экспорт OTLP есть в `internal/infra/observe/otel.go`, но `BEACON_OTEL_ENABLED` по умолчанию выключен и ни один прогон его не читает (`README.md`). |

Отказ от observability-платформы означает, что прогон не пишет в неё решение. Человеческий интерфейс остаётся в issue и PR, а состояние системы лежит в каталоге state. Если человеку нужно понять прогон, он читает PR, карточку и вывод диагностических команд.

## Задачи

Задача это работа, объявленная один раз и запускаемая много раз. Прогон это одно выполнение задачи на runner от триггера до конца. Ниже для каждой из пяти задач beacon отвечены пять вопросов словаря.

### Наблюдение Watch

Прогон считает вердикт для одной ревизии Watch.

| Вопрос | Ответ |
| --- | --- |
| Что запускает | Цикл `ReconcileLoop` опрашивает GitHub раз в 30 секунд через `BEACON_CI_POLL_INTERVAL` (`README.md`). Дополнительный триггер это регистрация Watch через `beacon_watch_pr`. |
| Что делает и какие сервисы читает и пишет | Читает Git host через `github.BatchProvider`: статусы проверок и свежий `mergeable` через REST. Читает хранилище: Watch, подписчиков и политики. Пишет вердикт и ревизию через `internal/domain/verdict.go:EvaluatePR` и переходы `internal/domain/transition.go`. Не пишет в GitHub и не меняет карточки. |
| Что запускает дальше | Опубликованный вердикт создаёт обязательство и запускает доставку wake. Вердикт `ready` при включённом `autoMerge` запускает прогон мержа. |
| Где возвращается человек | Человек комментирует PR или пушит новый коммит. Смена `headSHA` закрывает текущий Watch и открывает новый. Для чтения состояния есть `beacon inspect` и `beacon watch` (`AGENTS.md`). |
| Что мешает двум прогонам делать одно | Watch привязан к `(repo, pr, headSHA)`. Одинаковый вердикт не меняет состояние, смена вердикта увеличивает ревизию на единицу (`internal/domain/transition.go`, `transitionVerdict`). Каждый проход цикла получает собственный `cycleID` (`GLOSSARY.md`, ReconcileLoop). |

### Доставка wake

Прогон доставляет указатель на результат в живую сессию.

| Вопрос | Ответ |
| --- | --- |
| Что запускает | Обязательство на новой ревизии Watch. |
| Что делает и какие сервисы читает и пишет | Читает хранилище: `subscriber.adapter`, `target`, обязательства и состояние лестницы. Пишет отметки `readAt` и `claimedAt`. Отправляет указатель сессии OpenCode через реестр wake и плагин `.opencode/plugins/beacon-bridge.js` (`README.md`, раздел «Из чего состоит Beacon»). |
| Что запускает дальше | Прогон исполнителя в своей ветке и его отчёт оркестратору. Подтверждение `beacon_ack` отмечает обязательство как взятое. |
| Где возвращается человек | Вердикты `needs_input`, `parked` и политики ожидания останавливают прогон. Решение приходит от человека в PR или в сессии. Обычный прогон не ждёт человека: он заканчивается фразой `waiting, <watchID>` (`docs/templates/executor-task.md`). |
| Что мешает двум прогонам делать одно | Обязательство выводится из `(watchID, revision, subscriberID)` (`GLOSSARY.md`, Obligation). `beacon_get_result` ставит `readAt`, `beacon_ack` ставит `claimedAt`. Лестница не повторяет доставку с исходом `posted`, повторяет `transport-failed` и не повторяет `indeterminate`. |

### Разбор блокеров

Прогон выясняет, лежит ли падение проверки в main, и ограничивает число попыток починки.

| Вопрос | Ответ |
| --- | --- |
| Что запускает | Падение проверки, которое уже есть на базовой ветке, или `beacon_ack decision="blocked:not_mine"` от исполнителя. |
| Что делает и какие сервисы читает и пишет | Читает Git host: имя проверки и PR. `github.BatchProvider` добавляет алиас для пары `(repo, baseRef)`, чтобы отличить падение на базе (`README.md`). Читает хранилище: `BlockedInfo` и `BlockerIncident`. Пишет инцидент, счётчик `FixAttempts` и подписчика с ролью `fixer` и полем `fixFor` (`GLOSSARY.md`). |
| Что запускает дальше | Прогон FIX-агента в его ветке и PR. После мержа этого PR сигнал `blocked:resolved` снимает блок с Watch. |
| Где возвращается человек | После трёх попыток `MaxFixAttempts` оркестратор эскалирует к человеку (`internal/app/orchestrator/decision.go:51`) и печатает список «ждут решения владельца» (`AGENTS.md`). |
| Что мешает двум прогонам делать одно | Инцидент ищется по `(repo, baseRef, signature)`, поэтому несколько Watch делят одну запись. Регистрация роли `fixer` требует `fixFor` с идентификатором заблокированного Watch. Счётчик `FixAttempts` растёт на каждой выдаче и сравнивается с лимитом в `internal/app/orchestrator/decision.go`. |

### Мерж

Прогон сливает зелёный PR и закрывает Watch.

| Вопрос | Ответ |
| --- | --- |
| Что запускает | Вердикт `ready` и включённый по умолчанию `MergePolicy.AutoMerge` без `requireApproval`, `waitFor` и `waitForMain` (`README.md`, раздел «Авто-мерж»). |
| Что делает и какие сервисы читает и пишет | Читает батч GitHub и свежий `mergeable`, читает политику из хранилища. Вызывает `github.BatchProvider.MergePRWithState`, подтверждает мерж вторым чтением и закрывает Watch (`internal/infra/cibridge/verdict_applier.go`, `applyMerge` и `closeWatch`). |
| Что запускает дальше | Оркестратор переводит карточку в `done` и освобождает слот. Мерж в GitHub запускает проверки на `main`. |
| Где возвращается человек | Политики `requireApproval`, `waitFor` и `waitForMain` удерживают мерж (`README.md`). Человек читает PR до мержа, а найденное им превращается в новые проверки. |
| Что мешает двум прогонам делать одно | Watch в статусе `closed` не мержится повторно. `closeWatch` проверяет, что ревизия не сдвинулась, а успешный мерж фиксируется один раз на ревизию (`docs/design/watch-state-machine.md`, инвариант `NoDoubleMerge`). |

### Выдача задач

Прогон отдаёт одну карточку исполнителю вместе с контекстом из handoff.

| Вопрос | Ответ |
| --- | --- |
| Что запускает | Оркестратор спавнит исполнителя с идентификатором карточки. Один отчёт `report_to_orchestrator` заполняет один слот новым спавном (`AGENTS.md`, раздел «Оркестратору: заполнение слотов»). |
| Что делает и какие сервисы читает и пишет | Читает карточки в `docs/tasks/` и граф из рёбер `blocks`, `depends-on`, `supersedes` и `related` (`AGENTS.md`). Пишет `in_progress`, `Агент` и время выдачи. Выбор и запись идут в одном критическом участке под `flock` с атомарной заменой файла (`internal/infra/mcp/tool_task_claim.go`). |
| Что запускает дальше | Прогон исполнителя в своём worktree и ветке. Вердикт `merged` переводит карточку в `done` и записывает ссылку на PR (`AGENTS.md`). |
| Где возвращается человек | Человек правит карточку или открывает issue. Карточки со статусом `dropped` в работу не берутся (`AGENTS.md`). Решение, которое может принять только человек, уходит в список «ждут решения владельца». |
| Что мешает двум прогонам делать одно | `flock` и атомарная замена не дают двум агентам получить одну карточку. Повторный `claim` той же карточки под другим `agentID` запрещён (`docs/templates/executor-task.md`). |

## Источники билетов

Для каждого источника билета нужен ответ, что мешает завести его дважды.

Человек открывает issue в GitHub. Beacon не отсекает дубли на входе. Дубль предотвращает человек, который ищет существующую issue до создания. Эта проверка лежит вне фабрики.

Внутри фабрики билеты заводит `beacon_defer_wiring`. Повторный вызов с той же парой `(watchID, reason)` возвращает ту же карточку и не создаёт вторую (`docs/templates/executor-task.md`).

## Тормоза

Каждый триггер ускоряет прогоны. Три тормоза ограничивают эту скорость.

1. Автоматические проверки. GitHub Actions прогоняет их на каждом PR. Локально `go test ./...`, `go build ./...` и `beacon gates` запрещены, полный прогон делает CI (`AGENTS.md`). Вердикт считает `internal/domain/verdict.go:EvaluatePR`. Проверка с `required: false` или `continue-on-error: true` информационная и не блокирует мерж (`GLOSSARY.md`).
2. Автоматический обзор. Контракт двух осей, Standards и Spec, лежит в `docs/design/review-axes.md`. Обзор читает diff по `AGENTS.md` и карточке. Найденное возвращается исполнителю как `keep_working` и не меняет чужие OwnerFiles.
3. Человеческий обзор. Человек читает PR до мержа. Найденное им становится новой автоматической проверкой или более точным обзором, а политика `requireApproval` удерживает мерж (`README.md`).

Скорость поднимают по одному триггеру и с человеческим обзором на каждом PR. Цикл FIX-агентов ограничен `MaxFixAttempts = 3` в `internal/app/orchestrator/decision.go:51` и `defaultMaxFixAttempts = 3` в `internal/infra/store/blockers.go:30`. После трёх попыток Watch эскалируется к человеку.
