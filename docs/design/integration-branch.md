## Когда волна требует общей ветки

Оркестратор создаёт интеграционную ветку один раз до спавна исполнителей, когда выполняется любое из двух условий.

1. Волна реализует один спец, а карточки образуют граф задач с рёбрами блокировки и frontier. Отдельные PR не дают required-CI зелёным до последнего шага контракта, как описано в `docs/tasks/CM-04.md`.
2. Несколько исполнителей меняют пересекающиеся OwnerFiles, и сборка любого PR отдельно от других даёт конфликт или красный required-CI.

Одна карточка, непересекающиеся OwnerFiles и зелёный CI каждого PR отдельно не требуют интеграционной ветки. В этом случае сохраняется обычный путь `beacon-executor`: ветка от `origin/main`, свой worktree, PR, Watch.

Интеграционная ветка живёт отдельно от `main`. Авто-мерж Beacon по `verdict=ready` (ADR 0072) по-прежнему применяется к PR в `main`. Роль merger-сабагента относится к влитию в интеграционную ветку, а не к мержу в `main`.

## Проверка bases перед началом и перед отчётом

Каждый implementer проверяет основание своего worktree сам. Проверку не делегируют оркестратору или merger-сабагенту.

Перед началом работы:

1. Убедиться, что текущая ветка основана на интеграционной: `git merge-base --is-ancestor <integration-tip> HEAD`. Код выхода 0 означает верное основание.
2. Если команда вернула ненулевой код, сбросить ветку на вершину интеграционной ветки до первой правки.
3. Зафиксировать `<integration-tip>` в отчёте о старте, чтобы проверка была воспроизводимой.

Перед отчётом о завершении:

1. Подтянуть вершину интеграционной ветки в свою ветку: `git fetch origin <integration> && git merge origin/<integration>`.
2. Разрешить конфликты в своём worktree и оставить required-CI зелёным.
3. Отправить PR и сообщить оркестратору новые значения frontier, если карточка их сдвинула.

Отсутствие проверки bases до старта или перед отчётом проваливает карточку волны. Сабагент со свежим контекстом получает основание через указатель на интеграционную ветку, а не через копию чужих правок. Обмен данными между сабагентами идёт через указатели на спец, карточки, research-заметки и коммиты.

## Merger-сабагент

Слияние в интеграционную ветку делает отдельный merger-сабагент. Оркестратор не мержит вручную, а implementer не мержит чужую ветку.

Триггер роли: implementer сообщил о завершении, PR прошел required-проверки, и в графе есть готовая к влитию вершина.

Обязанности merger-сабагента:

1. Влить ветку завершившего implementer в интеграционную ветку, по одной карточке за шаг.
2. Проверить required-CI на вершине интеграционной ветки после каждого влития.
3. Сообщить оркестратору новый frontier, чтобы он запустил следующих implementer в том же ходе по правилу «один сигнал равен одному spawn».
4. При красном required-CI на интеграционной ветке вернуть блокер с доказательством. Оркестратор запускает FIX-агента. Implementer не чинит интеграционную ветку и не трогает `main`.

Merger-сабагент не закрывает карточки. При терминальном вердикте `merged` карточку закрывает Beacon и пишет ссылку на PR.

## Draft PR после первого влития

До первого влития в интеграционную ветку PR не открывают: ветка без коммитов, опережающих `main`, не может открыть PR. После первого влития оркестратор открывает draft PR из интеграционной ветки в `main` и помечает его закрывающим спец и карточки волны.

Пока волна идёт, draft PR остаётся черновиком и следует за вершиной интеграционной ветки. Каждое влитие merger-сабагента попадает в этот PR. Статус draft снимают только после финального code-review и правок по нему. На этом шаге PR передаётся авто-мержу Beacon по `verdict=ready`.

## Финальный review и уборка worktree

Code-review идёт по интеграционной ветке после последнего влития, а не по отдельным PR карточек. Разбор ведётся по двум осям Standards и Spec из `docs/design/review-axes.md`, с точкой сравнения на вершине интеграционной ветки.

Все замечания review исправляет один свежий implementer-сабагент. Merger-сабагент влит его правку в интеграционную ветку и снова прогоняет required-CI. Только после зелёного CI оркестратор снимает статус draft с PR.

Уборка worktree обязательна. После снятия статуса draft оркестратор снимает блокировку и удаляет все worktree исполнителей. Merger проверяет, что ни в одном worktree не осталось невлитых коммитов. Работа в чужом worktree и повторное использование его ветки запрещены.
