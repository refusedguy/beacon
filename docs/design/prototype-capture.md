# Прототип как primary source

Прототип это одноразовый код, который отвечает на один дизайнерский вопрос. Вопрос определяет форму прототипа. Прототип не попадает в main: main хранит только проверенное решение. Такой подход описан в `skills/engineering/prototype/SKILL.md` (mattpocock/skills@abeeaf9), строки 12-26. В `skills/engineering/ask-matt/SKILL.md:87` прототип назван primary source.

## Измерение до выбора

На `origin/main` `0ce4ba29` запрос `git grep -i -c -E 'prototype/|primary source' -- AGENTS.md README.md GLOSSARY.md docs/templates .opencode docs/design docs/adrs internal cmd tools scripts` дал одно совпадение. Это строка `internal/infra/opencode/client.go:114` про источник данных агента, а не про прототипы. Совпадений по префиксу `prototype/` не было. Правила сохранения прототипа в дереве отсутствовали. Этот документ записывает правило целиком.

## Выбор ветки по типу вопроса

Сначала определи, на какой вопрос отвечает прототип. Вопрос решает форму артефакта. Ошибка на этом шаге расходует всю работу прототипа.

| Вопрос | Ветка | Артефакт |
| --- | --- | --- |
| «Правильна ли логика или state model?» | логика | Один HTML-файл с кнопками свободной игры и вкладками пошагового разбора. Файл прогоняет state machine по случаям, которые трудно обдумать на бумаге, и им может управлять человек без опыта разработки. |
| «Как это должно выглядеть?» | UI | Несколько радикально разных вариантов на одном маршруте. Переключение идёт через параметр URL и плавающую панель снизу. |

Если вопрос неоднозначен, а автор недоступен, выбери ветку по окружающему коду. Серверный модуль даёт логику, страница или компонент даёт UI. Принятое допущение напиши в начале прототипа.

## Шесть правил прототипа

Обе ветки подчиняются одним и тем же шести правилам.

1. **Одноразовый и явно помеченный.** Размести код рядом с модулем или страницей, которые он проверяет, чтобы контекст был виден. Назови его так, чтобы читатель сразу отличил прототип от продакшена. Для UI-маршрутов следуй принятому в проекте роутингу и не создавай новую структуру верхнего уровня.
2. **Запускается одной командой.** UI-прототип стартует командой раннера проекта, например `pnpm <name>`, `python <path>` или `bun <path>`. Логический прототип это один HTML-файл, который открывается двойным щелчком. Запуск не требует размышлений.
3. **Без сохранения состояния по умолчанию.** Состояние живёт в памяти. Сохранение это то, что прототип проверяет, а не то, от чего он зависит. Если вопрос явно про базу данных, возьми временную БД или локальный файл с понятным именем «PROTOTYPE, wipe me».
4. **Без полировки.** Не пиши тесты, не добавляй обработку ошибок сверх минимума для запуска, не вводи абстракции. Цель прототипа: быстро узнать ответ.
5. **Показывай состояние.** После каждого действия в логике и при каждом переключении варианта в UI выводи полное состояние. Читатель видит, что изменилось.
6. **Зафиксируй результат.** Перенеси проверенное решение в реальный код. Сам прототип сохрани как primary source: закоммить его в одноразовую ветку вне main и оставь указатель на неё в задаче. Вердикт запиши вместе с вопросом, на который он отвечает.

## Порядок завершения

1. Перенеси проверенное решение в реальный код. В main попадает только решение.
2. Закоммить прототип в ветку `prototype/<name>` и не мержи её в main. Ветка остаётся одноразовым источником ответа.
3. В карточке задачи оставь указатель на ветку `prototype/<name>` и вердикт вместе с вопросом. Запись вердикта сохраняет ответ, который иначе теряется в чате.
4. Прототип не заменяет тест на согласованном seam из CMx-05. Прототип отвечает на вопрос, тест закрепляет согласованный контракт на этом seam. Когда форма самого интерфейса остаётся под вопросом, сначала ответь на него прототипом, затем согласуй seam и только после этого пиши тест.
