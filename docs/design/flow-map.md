# Карта потоков beacon

Статус: контракт проекта. Карточка: `docs/tasks/CMx-03.md`. Источник схемы: `docs/research/comp-matt-skills.md`, раздел 5, и `mattpocock/skills@abeeaf9`, `skills/engineering/ask-matt/SKILL.md`.

Карта показывает один путь задачи через beacon. Путь идёт от карточки до слитого PR. Здесь нет правил claim, вердиктов и заполнения слотов. По каждому правилу дан указатель на шаблон или на `AGENTS.md`. Карта отвечает на два вопроса: с какого входа агент попадает в поток и где заканчивается основная ветка.

## Измерение до выбора

База карточки `origin/main` `0ce4ba29`. Команда из карточки:

```
git grep -i -c -E 'on-ramp|main flow|карта потоков' -- AGENTS.md README.md GLOSSARY.md docs/templates .opencode docs/design docs/adrs internal cmd tools scripts
```

Результат равен нулю. `AGENTS.md` описывает граф карточек и claim, но не показывает вход в поток и конец основной ветки. `README.md` даёт таблицу команд без маршрутизации. Поэтому карта лежит в отдельном файле, а не в `AGENTS.md` или `README.md`.

## Основной путь

Основной путь один. Карточка превращается в ветку и PR, PR получает вердикт, вердикт `merged` ведёт к слиянию в main. Ветвление внутри пути задано шагами исполнителя и оркестратора.

| Шаг | Кто | Указатель |
| --- | --- | --- |
| Взять карточку и зарегистрировать Watch | executor | `docs/templates/executor-task.md:290`, раздел «Цикл: claim, register, push PR, finish turn». На базе `0ce4ba29` это `:148-153`. |
| Сдать PR и завершить ход | executor | тот же раздел, шаги 3 и 4. |
| Прочитать вердикт и заполнить свободный слот | orchestrator | `docs/templates/orchestrator-task.md:288`, раздел «Заполнение слотов на каждом терминальном сигнале». На базе `0ce4ba29` это `:235-248`. |
| Назначить вердикт и сделать merge | Beacon | `AGENTS.md`, раздел «Авто-мерж». |

Основная ветка заканчивается вердиктом `merged`. После него агент отвязан от Watch, а карточку закрывает Beacon. Правила вердиктов, в том числе какие из них будят агента, лежат в `docs/templates/executor-task.md`, раздел «Вердикты и пробуждение», и в `GLOSSARY.md`.

## Три on-ramp

On-ramp это вход в основной путь со стороны. Их три. Каждый ведёт к шагу «взять карточку», но начинается по-разному.

1. **Входящая задача.** Владелец или индекс дают новую карточку со статусом `todo`. Агент получает её через `beacon_task_claim`. Это обычный старт основного пути. Поиск по каталогу `docs/tasks/` вместо claim запрещён, указатель в `AGENTS.md`, раздел «Задачи: индекс, граф и claim».
2. **Красный вердикт.** PR уже сдан, но проверка упала. Агент просыпается на `keep_working`, `rebase` или `retry`, читает `beacon_get_result` и сравнивает упавшую проверку со своим diff. Своя ошибка ведёт к исправлению ветки и новому headSHA. Чужая поломка main даёт `blocked:not_mine`. Указатель в `docs/templates/executor-task.md`, раздел «Действие после retry».
3. **Большой туманный объём.** Задача шире одной карточки и требует research и плана до правки. Агент сначала снимает измерение и пишет `PLAN.md` по режиму плана из карточки, затем входит в основной путь. Указатель в `AGENTS.md`, раздел «Режимы плана», и в `docs/templates/orchestrator-task.md`, раздел «Вертикальные срезы и expand-contract».

## Словарь снизу

Остальные потоки опираются на словарь. Термины живут в двух файлах, карта их не повторяет.

- `GLOSSARY.md` задаёт роли, Watch, вердикты и обязательства. Ссылка из любого потока ведёт туда.
- `docs/design/module-depth.md` задаёт три критерия глубины модуля: тест удаления, интерфейс как тестовая поверхность, правило одного и двух адаптеров. Карточка CMx-03 называла этот файл будущим, сейчас он есть в дереве.

Слои импорта и правила для кода лежат в `AGENTS.md`, раздел «Слои», а не здесь.
