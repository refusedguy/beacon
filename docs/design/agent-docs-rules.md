Этот файл задаёт правила для `AGENTS.md` и doc-указателей beacon. Изменения вносят в документ, на который указывает steering-файл, а не в копию текста внутри `AGENTS.md`.

## Четыре правила

### 1. Каждый шаг заканчивается критерием завершения

Критерий завершения задаёт условие, по которому агент отличает done от not-done. Без него агент заканчивает шаг раньше времени, потому что видит следующие шаги и стремится к ним. Сначала заостри границу шага. Прячь последующие шаги только когда граница неисчерпаемо расплывчата и ты наблюдаешь спешку. Сокрытие работает через реальную границу контекста: handoff или отправку сабагента. Встроенный вызов такую границу не создаёт.

Критерий должен быть проверяемым и исчерпывающим. Слабая формулировка вроде «достигнуто понимание» не годится. Сильная формулировка называет команду, файл или состояние, которое можно прочитать. Требовательность критерия задаёт объём работы: «каждый изменённый файл учтён» заставляет проверить все файлы, а «составить список изменений» не заставляет.

### 2. Одно значение живёт в одном месте

Каждое значение хранится в одной авторитетной точке. Повтор одного смысла в двух местах стоит поддержки и токенов и поднимает его ранг в иерархии выше реального. Если поведение меняется, правь одну точку. Вторая копия становится источником расхождения.

Это правило не отменяет намеренное повторение слова-якоря. Слово-якорь повторяет токен, а не смысл.

### 3. Окружение источник истины

Окружение тоже хранит значения: `package.json` со скриптами, конфиги, структура каталогов, вывод `--help`. Документ, который пересказывает команду или конфиг из окружения, хранит устаревающую копию. Такая копия оправдана, только если поиск в окружении дорог.

Кэшируй то, чего агент не найдёт в окружении: неписаную договорённость, причину выбора, подводный камень, который конфиг не открывает. Справки об одном файле или одной команде оставь в окружении. Там они не устареют.

Проверяй каждую строку на актуальность. Строка теряет смысл, когда не относится к задаче или когда изменилось поведение, которое она описывает. Без такой проверки документ обрастает осадком старых слоёв.

### 4. No-op предложение удаляй целиком

No-op это инструкция, которой агент и так следует по умолчанию. Она платит нагрузкой и ничего не меняет. Тест: изменит ли предложение поведение относительно значения по умолчанию? Тест относится к модели, а не к читателю. Два человека могут не согласиться о no-op, потому что спорят о поведении по умолчанию. Их спор решается прогоном документа, а не спором.

Когда предложение проваливает тест, удали его целиком. Не обрезай слова. Тест также оценивает слова-якоря. Слово, которое слабее значения по умолчанию, например «быть внимательным» для уже внимательного агента, это no-op. Замени его более сильным словом, а не новой техникой.

Утверждения в запретной форме смещают внимание к запрещённому действию. Формулируй целевое действие. Запрет оставляй только как жёсткий предохранитель, который нельзя выразить положительно, и рядом указывай, что делать вместо этого.

## Иерархия из четырёх уровней

Уровни расположены по тому, как скоро агенту нужен материал.

1. In-file step. Порядок действий в самом файле. Загружен всегда.
2. In-file reference. Определения и правила внутри того же файла. Агент читает их по запросу, без перехода в другой файл.
3. Disclosed reference. Отдельный файл в той же папке. Агент доходит до него по указателю контекста, когда указатель срабатывает.
4. External reference. Файл в любом месте репозитория или вне его. Указатель на него может написать любой документ.

Уровни 3 и 4 в исходном скилле образуют одну ступень disclosed reference. Здесь они разделены, потому что стоимость перехода и формулировка указателя для соседнего файла и для внешнего документа различны. Это разделение сохраняет разницу в цене загрузки.

Progressive disclosure это спуск по лестнице. Он защищает иерархию, а не только экономит токены. Верхний уровень остаётся читаемым. Правило перехода по ветвям: оставляй в файле то, что нужно каждой ветви, а остальное выноси за указатель. Когда документ содержит шаги, in-file reference, который следовало бы вынести, закапывает эти шаги и превращает внимание к ним в случайность.

Co-location работает внутри уровня. Держи определение правила, сами правила и оговорки под одним заголовком. Читающий один раздел получает соседние смыслы вместе с ним. Разделение смысла по разным местам не то же самое, что дублирование: дублирование повторяет смысл, а разбросанность дробит его.

## Два примера из `AGENTS.md`

### Пример 1. Критерий завершения в разделе «Своя ветка и PR»

Было:

```text
3. Только свои OwnerFiles.
```

Стало:

```text
3. Правь только файлы из поля «Владелец файлов» карточки. Критерий завершения: `git diff --name-only` в твоей ветке содержит только эти файлы, сторонний файл не изменён.
```

Критерий проверяем командой и исчерпывает набор изменённых файлов. `AGENTS.md` в этом PR не правится. Пример показывает правку формулировки.

### Пример 2. No-op в разделе «Оркестратору: заполнение слотов»

В `AGENTS.md` подряд идут две фразы:

```text
НЕ открывай карточки со статусом `dropped`.
...
Карточку `dropped` в работу не брать.
```

Вторая фраза повторяет первую и не добавляет поведения. Удали её целиком. Первая фраза продолжает действовать, агент теряет только лишнюю строку. Соседнее предложение про причину, что подтверждение карточки фиксирует брошенный дизайн или дубль кода, остаётся: оно объясняет причину запрета и не является no-op.
