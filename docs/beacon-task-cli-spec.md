# Спецификация подкоманды `beacon task`

Статус: спецификация для реализации. Поведение зафиксировано в ADR 0020, коды выхода в ADR 0016, требование самотеста в ADR 0005 и ADR 0010.

## 1. Назначение и границы

Подкоманда `beacon task` работает с карточками в `docs/tasks/*.md`. Бинарник `beacon` остаётся одним исполняемым файлом на стандартной библиотеке Go. Внешних модулей и внешних процессов подкоманда не вызывает. Источник: ADR 0020 («Команды работы с задачами живут в бинарнике beacon»), ADR 0016 («Только стандартная библиотека, без внешних модулей»).

В спецификации три команды:

- `beacon task list [flags]`
- `beacon task new [flags]`
- `beacon task take <id> [flags]`

Машинный поток идёт в stdout, диагностика в stderr. Это же правило ADR 0016 задаёт для `beacon list --format json`, каталога команд. Каталог команд из ADR 0016 и список задач из этой спецификации разные вещи: `beacon list --format json` печатает поля `name`, `summary`, `usage`, а `beacon task list --format json` печатает поля карточек, описанные в разделе 3.4.

## 2. Контракт карточки

Парсер читает файл по строкам. Поле занимает одну строку, начинается в первом столбце и имеет вид `Имя: значение`. Пробелы после двоеточия отбрасываются. Обязательные поля по ADR 0020:

| Поле | Допустимые значения |
|---|---|
| `Тип` | `epic` или `task` |
| `Статус` | `todo`, `in_progress`, `done`, `dropped` |
| `Фаза` | `P0`, `P1`, `P2`, `P3`, `P4` |
| `Владелец файлов` | список путей через запятую |
| `Зависимости` | список ID через запятую или `нет` |
| `Ссылка` | `ADR NNNN` или ID задачи-эпика |
| `Цель`, `Контекст`, `Шаги`, `Проверка`, `Приёмка` | произвольный текст |
| `Агент`, `Время` | `нет` до взятия задачи, затем имя агента и время |

Идентификатор задачи берётся из имени файла. Это регулярное выражение `^T[0-9]+\.[0-9]+`, применённое к началу имени файла. Суффикс после первого дефиса в имени файла не входит в ID. Например, файл `T3.7-executor-task-template.md` даёт ID `T3.7`. Заголовок берётся из первой строки `# ID. Заголовок`, префикс ID и точка после него отбрасываются. Допустимые дополнительные строки, например `Гейт: G2`, парсер сохраняет и не считает ошибкой.

Отсутствие обязательного поля, повтор обязательного поля или неизвестное значение перечисления считается нарушением формата. Команда печатает имя файла и имя поля в stderr и возвращает код 1. Молча пропускать такую карточку запрещено: агент, который читает JSON, должен видеть все карточки или получить ошибку. Источник: ADR 0020 («формат карточки читаем», «при провале файл не пишется и печатается причина»), ADR 0005 (правило без гейта считается долгом).

## 3. `beacon task list [flags]`

### 3.1. Синтаксис

```
beacon task list [flags]
```

### 3.2. Флаги

| Флаг | Значение | По умолчанию |
|---|---|---|
| `--status <todo\|in_progress\|done\|dropped>` | фильтр по статусу | все статусы |
| `--phase <P0\|P1\|P2\|P3\|P4>` | фильтр по фазе | все фазы |
| `--agent <строка>` | фильтр по значению поля `Агент` | без фильтра |
| `--file <путь>` | фильтр по владельцам файлов | без фильтра |
| `--format <table\|json>` | формат вывода | `table` |

Каждый фильтр можно повторить. Значения одного фильтра объединяются по «или», разные фильтры по «и». Неизвестное значение флага возвращает код 1. Пустой результат возвращает код 0: заголовок таблицы без строк или пустой массив `[]` в JSON.

Сравнение путей для `--file` использует ту же нормализацию, что и проверка пересечения владельцев в разделе 4.6. Флаг `--file internal/infra/mcp` находит карточку с владельцем `internal/infra/mcp/server.go`.

### 3.3. Пример

```
beacon task list --status todo --phase P2 --format json
```

### 3.4. Формат вывода

По умолчанию команда печатает таблицу с выравниванием по столбцам. Столбцы идут в порядке: ID, Тип, Статус, Фаза, Ссылка, Агент, Время, Владелец файлов, Заголовок. Источник: ADR 0020 («показывает текущие задачи с фильтром по статусу и фазе»).

При `--format json` stdout содержит только JSON-массив. Порядок объектов стабильный: по ID, сначала числовая часть фазы, затем номер задачи. Поля каждого объекта ровно следующие.

| Поле JSON | Источник в карточке | Тип |
|---|---|---|
| `id` | имя файла | строка, `T2.1` |
| `type` | `Тип` | строка, `task` или `epic` |
| `status` | `Статус` | строка |
| `phase` | `Фаза` | строка, `P2` |
| `ownerFiles` | `Владелец файлов` | массив строк |
| `dependencies` | `Зависимости` | массив строк, `[]` если `нет` |
| `reference` | `Ссылка` | строка, `ADR 0003` или `T1.1` |
| `agent` | `Агент` | строка, `нет` до взятия |
| `time` | `Время` | строка, `нет` до взятия |
| `title` | заголовок первого уровня | строка без префикса ID |

```json
[
  {
    "id": "T2.1",
    "type": "task",
    "status": "todo",
    "phase": "P2",
    "ownerFiles": [
      "internal/infra/mcp/server.go",
      "internal/infra/mcp/server_test.go"
    ],
    "dependencies": ["T1.1"],
    "reference": "ADR 0003",
    "agent": "нет",
    "time": "нет",
    "title": "MCP-сервер на go-sdk и реестр семи инструментов"
  }
]
```

Команда не меняет карточки. Блокировку `list` не берёт, потому что только читает файлы.

## 4. `beacon task new [flags]`

### 4.1. Синтаксис

```
beacon task new --phase <P0|P1|P2|P3|P4> --title <строка> --reference <ADR NNNN|T<g>.<n>> --owner-files <путь[,путь...]> [flags]
```

### 4.2. Флаги

| Флаг | Значение | По умолчанию |
|---|---|---|
| `--type <task\|epic>` | тип новой карточки | `task` |
| `--phase <P0\|...\|P4>` | фаза, обязателен | нет |
| `--title <строка>` | заголовок, обязателен | нет |
| `--reference <строка>` | ссылка на ADR или на эпик, обязателен | нет |
| `--owner-files <список>` | владельцы файлов через запятую, обязателен | нет |
| `--dependencies <список>` | ID через запятую | `нет` |
| `--goal <строка>` | поле `Цель` | `заполнить при работе` |
| `--context <строка>` | поле `Контекст` | `заполнить при работе` |
| `--steps <строка>` | поле `Шаги` | `заполнить при работе` |
| `--check <строка>` | поле `Проверка` | `заполнить при работе` |
| `--acceptance <строка>` | поле `Приёмка` | `заполнить при работе` |
| `--dry-run` | проверить и напечатать ID без записи файла | `false` |

Поля `Цель`, `Контекст`, `Шаги`, `Проверка`, `Приёмка` обязательны по ADR 0020, поэтому шаблон всегда содержит эти строки. Значение по умолчанию прямо говорит, что их заполнит исполнитель. Источник: ADR 0020 («создаёт карточку из шаблона с валидацией»).

### 4.3. Пример

```
beacon task new --type task --phase P2 --title "Атомарная запись карточки" --reference "ADR 0020" --owner-files "internal/task/store.go,internal/task/store_test.go" --dependencies "T1.8"
```

### 4.4. Выбор следующего ID

ID имеет вид `T<g>.<n>`, где `g` это номер фазы из `--phase`: `P0` даёт `0`, `P1` даёт `1`, и так до `P4`. Номер `n` считается так:

1. Команда берёт глобальную блокировку, описанную в разделе 5.3.
2. Команда читает все файлы `docs/tasks/*.md` и собирает номера `n` из файлов группы `T<g>`.
3. Команда читает счётчик группы из `$XDG_STATE_HOME/beacon/task-counter-<hash8>.json`. В файле лежит последний выданный номер для каждой группы. Если файла нет, счётчик равен нулю.
4. Новый номер равен `max(счётчик, max(n)) + 1`. Если файлов группы нет и счётчик нулевой, номер равен `1`.
5. Имя файла равно `T<g>.<n>.md`. Суффикс не добавляется, чтобы имя оставалось детерминированным.
6. Файл создаётся вызовом с флагом `O_CREATE|O_EXCL`, затем счётчик обновляется до `n` через временный файл и переименование.

Счётчик хранится в каталоге состояния из ADR 0011, а не в репозитории. Он нужен, чтобы не переиспользовать номер удалённой карточки. Если удалить `T2.4` и считать номер только по файлам, следующим снова будет `T2.4`. Старая ссылка на удалённую задачу станет указывать на другую. Счётчик убирает эту ошибку. Пропущенные номера допустимы, если запись карточки прервалась после обновления счётчика.

Два агента, которые вызвали `new` одновременно, не получат одинаковый ID по двум причинам. Блокировка сериализует чтение максимума, чтение счётчика, создание файла и обновление счётчика, поэтому второй агент видит файл и счётчик первого. Флаг `O_CREATE|O_EXCL` не даёт перезаписать файл, если блокировка устарела и была перехвачена. Второй случай заканчивается кодом 1 с сообщением о занятом ID, а не двумя карточками с одним ID. Сервера нет, поэтому другого источника уникальности нет. Источник: ADR 0020 («Обязательные поля карточки», ID из имени файла), ADR 0011 (каталог состояния), ADR 0016 (один бинарник без внешних процессов).

### 4.5. Валидация ссылки

Команда проверяет ссылку до записи файла. Порядок проверок фиксирован, чтобы сообщения об ошибках были предсказуемыми.

1. Ссылка на ADR задана строкой `ADR NNNN`. Команда проверяет регулярное выражение `^ADR [0-9]{4}$`, затем ищет файл `docs/adrs/NNNN-*.md`. Из найденного файла читается строка `Статус:`. Принимаются статусы `accepted` и `default`. Статус `open` отклоняется. Причина: ADR 0020 требует согласованного решения, а `open` по индексу ADR означает непринятое решение.
2. Ссылка на эпик задана строкой `T<g>.<n>`. Команда ищет карточку с этим ID, у которой `Тип: epic`. Эпик считается существующим, только если такой файл есть в `docs/tasks/` и поле `Тип` в нём равно `epic`. Затем команда проверяет, что у самого эпика есть ссылка на существующий ADR. Причина: ADR 0020 («Эпик обязан ссылаться на ADR»).
3. Карточка с `--type epic` принимает только ссылку на ADR. Карточка с `--type task` принимает ADR или эпик. Причина: ADR 0020 («Простая задача обязана ссылаться на ADR или на эпик. Эпик обязан ссылаться на ADR»).
4. Любая другая строка отклоняется с кодом 1.

По состоянию на эту спецификацию в `docs/tasks/` нет карточек с `Тип: epic`. Ссылка на эпик начнёт работать после того, как владелец создаст такую карточку.

### 4.6. Проверка пересечения владельцев файлов

Команда не пишет файл, если любой путь из `--owner-files` уже закреплён за карточкой со статусом `todo` или `in_progress`. Статусы `done` и `dropped` освобождают файлы. Источник: ADR 0020 («владелец файлов не занят другой карточкой со статусом todo или in_progress», «Статусы done и dropped освобождают файлы»).

Нормализация пути:

1. Заменить обратные слеши на прямые.
2. Убрать завершающий `/**` и завершающий `/`.
3. Привести путь к каноническому виду без `.` и `..`.

Два пути конфликтуют, если они равны или один является началом другого по границе сегмента. Так `cmd/beacon/**` превращается в `cmd/beacon` и конфликтует с `cmd/beacon/main.go`. Каталог `internal/infra/github/testdata/` конфликтует с любым файлом внутри него.

При конфликте команда печатает ID существующей карточки, её статус и спорный путь. Файл новой карточки не создаётся, код выхода 1.

### 4.7. Порядок операций и вывод

1. Проверить флаги. Ошибка даёт код 1.
2. Взять блокировку. Ошибка даёт код 2.
3. Прочитать и разобрать все карточки. Нарушение формата даёт код 1.
4. Проверить ссылку по разделу 4.5. Ошибка даёт код 1.
5. Проверить владельцев по разделу 4.6. Ошибка даёт код 1.
6. Посчитать ID по разделу 4.4.
7. При `--dry-run` напечатать ID и путь файла, отпустить блокировку и вернуть 0. Файл и счётчик не меняются.
8. Собрать карточку из шаблона, записать файл с `O_CREATE|O_EXCL`, записать на диск, отпустить блокировку.
9. Напечатать в stdout ID и путь, например `T2.18 docs/tasks/T2.18.md`, и вернуть 0.

Команда не заполняет `Агент` и `Время`. Эти поля остаются `нет` до вызова `take`.

## 5. `beacon task take <id> [flags]`

### 5.1. Синтаксис

```
beacon task take <id> [--agent <строка>] [--time <RFC3339>]
```

`<id>` это `T<g>.<n>`, например `T2.1`. Команда принимает ID с расширением `.md` и без него. Любой другой аргумент, а также отсутствие или дублирование аргумента дают код 1.

### 5.2. Флаги

| Флаг | Значение | По умолчанию |
|---|---|---|
| `--agent <строка>` | имя агента, которое пишется в поле `Агент` | переменная `BEACON_AGENT` |
| `--time <RFC3339>` | время взятия в UTC | текущее время в UTC |

Если `--agent` не задан и `BEACON_AGENT` пуста, команда возвращает код 1. Переменные окружения начинаются с `BEACON_`, как требует ADR 0011. Время печатается в формате `2026-11-19T14:03:21Z`. Источник: ADR 0020 («Агент и Время заполняются при взятии задачи»).

### 5.3. Атомарная смена статуса и защита от гонки

Команда использует один файловый замок на весь каталог карточек. Это простой механизм без сервера и без базы данных для статуса задач.

Путь замка это `$XDG_STATE_HOME/beacon/task-<hash8>.lock`, где `hash8` это первые восемь символов хеша абсолютного пути к корню проекта. Если `XDG_STATE_HOME` не задан, используется `~/.local/state/beacon`. Каталог создаётся с правами `0700`. Источник: ADR 0011 («Состояние живёт в $XDG_STATE_HOME/beacon», «Права на каталог состояния 0700»). Замок лежит в каталоге состояния, а не в `docs/tasks/`, поэтому не попадает в список карточек и не меняет репозиторий. Хеш корня не даёт двум разным проектам на одной машине мешать друг другу.

Захват замка:

1. Открыть файл замка с `O_CREATE|O_EXCL|O_WRONLY`, режим `0600`.
2. Записать в него PID процесса, время захвата и путь к проекту.
3. Если открытие вернуло `EEXIST`, прочитать владельца. Если процесс с этим PID жив и замок моложе 30 секунд, повторить через 100 мс. Всего до 50 попыток. Если время вышло, вернуть код 2.
4. Если процесс мёртв или замок старше 30 секунд, удалить замок и повторить захват. Это обработка остатка после падения агента.

Освобождение замка это удаление файла. Команда освобождает замок на каждом пути выхода, включая ошибки.

Изменение карточки под замком:

1. Прочитать целевую карточку и проверить, что `Статус: todo`. Другие статусы отклоняются с кодом 1. Причина: ADR 0020 («команда меняет Статус: todo на in_progress»).
2. Заменить в прочитанном тексте три строки: `Статус: todo` на `Статус: in_progress`, `Агент: нет` на `Агент: <имя>`, `Время: нет` на `Время: <время>`. Все остальные строки и порядок полей сохраняются.
3. Записать новый текст во временный файл в том же каталоге, вызвать синхронизацию, закрыть файл и переименовать его в целевую карточку. Переименование заменяет файл за одну операцию, поэтому читатель не увидит половину карточки.
4. Синхронизировать каталог, отпустить замок, напечатать в stdout `T2.1 in_progress <агент> <время>` и вернуть 0.

Гонка двух агентов разбирается так. Первый агент держит замок и меняет статус на `in_progress`. Второй агент ждёт замок, читает карточку и видит `in_progress`. Он возвращает код 1 с сообщением, которое содержит имя агента и время из карточки. Оба агента никогда не получают успех на одной карточке. Переименование закрывает второй возможный источник гонки, когда читатель успел открыть файл между записью и переименованием. Источник: ADR 0020 («занятыми считаются статусы todo и in_progress»), ADR 0015 (атомарная запись как рабочий пример в проекте).

### 5.4. Пример

```
beacon task take T2.1 --agent executor-1
```

## 6. Коды выхода

Коды выхода фиксированы ADR 0016. Команда обязана различать код 1 и код 2, поэтому запуск через `go run` или `just` не используется.

| Код | Смысл | Примеры |
|---|---|---|
| 0 | Команда выполнилась | `list` с пустым результатом, `new --dry-run`, успешный `take` |
| 1 | Нарушение или валидация не прошла | карточку нельзя разобрать, ссылки нет, владельцы пересекаются, задача уже взята, неизвестный флаг, отсутствует обязательный аргумент |
| 2 | Ошибка запуска | каталог `docs/tasks` недоступен, не создаётся каталог состояния, не взят замок, нет прав на запись |

Текст ошибки для обоих ненулевых кодов идёт в stderr. stdout при ошибке пустой, чтобы агент не принял диагностику за машинные данные. Источник: ADR 0016 («Машинный поток идёт в stdout, шум в stderr»).

## 7. Самотест с посаженным нарушением

У каждой команды есть тест с намеренно испорченными входными данными. Тест проверяет, что команда нашла нарушение, вернула нужный код и не изменила карточки. Если убрать нарушение, тот же тест должен пройти. Это доказывает, что тест не вакуумный. Источник: ADR 0005 («у каждого гейта посаженное нарушение, которое гейт обязан найти»), ADR 0016 («у каждого гейта есть self-test с посаженным нарушением»), ADR 0010 («задача без behavior-теста не считается готовой»).

Код хранит каталог карточек и каталог состояния как параметры. Тесты передают временные каталоги и не трогают рабочие `docs/tasks/`.

| Посаженное нарушение | Ожидаемый результат |
|---|---|
| В карточке удалена строка `Статус:` | `list` возвращает 1, stderr содержит имя файла, stdout пустой |
| `new` получает `Ссылка: ADR 0099`, файла нет | код 1, файл не создан |
| `new` получает `Ссылка: T9.9`, эпика нет | код 1, файл не создан |
| У ADR из поля `Ссылка` статус `open` | код 1, файл не создан |
| `--type epic` и ссылка на задачу | код 1, файл не создан |
| `--owner-files` совпадает с файлом карточки `todo` | код 1, файл не создан, stderr содержит ID карточки-владельца |
| `--owner-files` лежит внутри каталога карточки `in_progress` | код 1, файл не создан |
| Два `new` с одинаковыми флагами запущены одновременно | оба возвращают 0, созданы два файла с разными ID |
| Карточку `T2.4` удалили, счётчик сохранён | следующий `new --phase P2` даёт `T2.5`, а не `T2.4` |
| `take` на карточке `in_progress` | код 1, карточка не изменена |
| Два `take` одной карточки запущены одновременно | ровно один возвращает 0, второй возвращает 1, в карточке один агент и одно время |

Тест гонки повторяется не менее 20 раз, чтобы поймать редкий порядок вызовов. Тест блокировки дополнительно проверяет случай остатка после падения процесса: файл замка с мёртвым PID удаляется, следующая команда работает.

## 8. Простыми словами

Команда `beacon task` работает с обычными текстовыми файлами в `docs/tasks/`. Каждый файл это одна карточка задачи. Никакой скрытой базы для статуса этих карточек нет. Статус, агент и время лежат прямо в карточке, поэтому их видно в редакторе и в `git diff`.

`list` читает карточки и показывает их в таблице или в JSON. `new` проверяет три вещи до записи: есть ссылка на согласованное решение, файлы не заняты другой незакрытой задачей, формат карточки правильный. Если что-то не так, новой карточки не будет.

Номер задачи считается из уже существующих файлов и из небольшого счётчика в каталоге состояния. Всегда берётся следующий номер, и старые номера не переиспользуются даже после удаления карточки. Когда две команды запускаются одновременно, одна работает, вторая ждёт. Для этого используется один файл-замок в каталоге состояния. После окончания работы замок удаляется. Если агент упал и оставил замок, команда поймёт это по старому времени или мёртвому процессу и продолжит работу.

`take` меняет статус на `in_progress` и записывает агента и время. Второй агент, который попытается взять ту же задачу, увидит новый статус и получит отказ. Карточка при этом не испортится: команда сначала готовит новый текст, а потом заменяет файл целиком.

## 9. Что не делать

- Не добавлять Helm, чарты и манифесты. Задача работает с файлами репозитория. Источник: ADR 0020.
- Не ходить в сеть и не вызывать `gh` или GitHub API. Ссылка проверяется по локальным файлам ADR и карточек. Источник: ADR 0004 и ADR 0020.
- Не зависеть от GitHub, CI провайдера и имени пользователя в системе. Имя агента приходит из флага или `BEACON_AGENT`. Источник: ADR 0011.
- Не хранить статус задач в отдельном JSON файле. Владелец отклонил этот вариант в ADR 0020. SQLite из ADR 0015 хранит состояние Watch и не хранит статус карточек. Счётчик ID это не статус, он лежит в каталоге состояния по ADR 0011.
- Не запускать подкоманду через `just` или `go run ./tools/beacon`. Оболочка не различает коды 1 и 2. Источник: ADR 0016.
- Не подключать внешние Go модули. Источник: ADR 0016, ADR 0005.
- Не поднимать сервер, демон и фоновый процесс. Блокировки достаточно файла. Источник: ADR 0020, ADR 0011.
- Не писать замок в `docs/tasks/`. Он попадёт в список карточек. Источник: ADR 0011.
- Не пропускать карточку с полем, которое нельзя разобрать. Источник: ADR 0005, ADR 0020.
- Не менять карточки из общего кода в обход `new` и `take`. Владелец файлов и статус должны меняться в одном месте. Источник: ADR 0020.

## 10. Обоснование решений

| Решение | Аргумент | Источник |
|---|---|---|
| Три подкоманды в бинарнике `beacon` | Владелец попросил быстрый инструмент, один файл без внешних утилит | ADR 0020, ADR 0016 |
| Фиксированный набор полей карточки | Формат становится контрактом, все карточки приводятся к нему | ADR 0020 |
| Коды 0, 1, 2 и разделение stdout и stderr | Один скомпилированный бинарник передаёт коды в CI без потерь | ADR 0016 |
| ID `max(счётчик, максимум по файлам) + 1` под блокировкой и `O_CREATE|O_EXCL` | Два агента не получат одинаковый ID, номер удалённой карточки не переиспользуется | ADR 0020, ADR 0011, ADR 0016 |
| Ссылка на ADR со статусом `accepted` или `default` | Задача не создаётся без согласованного решения | ADR 0020, индекс ADR |
| Эпик существует, только если файл с `Тип: epic` есть на диске | Тип карточки явный, второго реестра эпиков нет | ADR 0020 |
| Заняты статусы `todo` и `in_progress` | `done` и `dropped` освобождают файлы | ADR 0020 |
| Один файловый замок и атомарное переименование | Простая защита от гонки без сервера и внешних пакетов | ADR 0020, ADR 0011, ADR 0015 |
| Замок в `$XDG_STATE_HOME/beacon` | Состояние машины лежит отдельно от конфига, права 0700 | ADR 0011 |
| Самотест с посаженным нарушением | Правило без гейта считается долгом, тест доказывает невакуумность | ADR 0005, ADR 0016, ADR 0010 |
