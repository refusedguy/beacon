# Red verdict triage

Исполнитель просыпается на вердикте `retry`, когда CI красный. Сначала он определяет причину, потом сообщает оркестратору через `beacon_ack`. До классификации он не меняет код и не трогает `main`.

## Процедура

1. Прочитать снимок вызовом `beacon_get_result`. В ответе есть `failedChecks`. Каждая запись несёт `name`, `conclusion`, `detailsUrl`, `required` и `flakyMatched`. Полные логи не нужны.
2. Сверить `failedChecks` со своим diff. Посмотреть `git status --short` и `git diff <baseRef>..HEAD` в своём worktree. Проверка считается твоей, когда её причина лежит в файлах, которые ты менял в этой ветке.
3. Выбрать одну из трёх причин.
   - Записи `failedChecks` лежат вне твоего diff, либо `main` красный на последнем коммите. Это флейк или сломанный `main`. Причина: `братан иди чини main`.
   - Причина падения лежит в твоём diff. Это твоя ошибка. Причина: `моя вина, чиню`. Исправь свою ветку и запушь новый headSHA.
   - Причину нельзя уверенно отнести ни к тому, ни к другому. Причина: `проверил, изменений моих нет`.
4. Для причин вне твоего diff (первая и третья) вызвать `beacon_ack` с `decision="blocked:not_mine"` на том же Watch. Передать `revision` из wake-указателя, как в примере ниже. Инструмент копирует упавшие проверки из снимка CI, записывает причину `not_mine` и будит оркестратора с текстом `spawn FIX-agent`. Для своей ошибки (вторая причина) блокировку не ставить: исправь код и запушь новый headSHA.
5. Завершить ход. Wake оркестратору не означает готовность PR. Мерж делает только оркестратор после своего `beacon_get_result` с `verdict=ready`.

### Пример вызова и stale-revision

Возьми `revision` из поля `revision` wake-указателя, на котором агент проснулся. Это ревизия Watch из события, а не `event.id`, который гасит повторную доставку вебхука. `beacon_ack` не принимает `event.id`. Когда событие выглядит старым, прочитай `beacon_get_result` и используй `revision` из свежего снимка.

Пример вызова для причины вне твоего diff:

```json
{
  "watchID": "<watchID из wake-указателя>",
  "obligationID": "<obligationID из beacon_get_result>",
  "revision": 7,
  "decision": "blocked:not_mine"
}
```

У `beacon_ack` нет поля `blockReason`. Причина блокировки приходит из `decision`: значение `blocked:not_mine` разбирается в `not_mine` и пишется в `BlockInfo` вместе с упавшими проверками и сессией блокировщика. Текст из шага 3 остаётся в отчёте агента и не становится аргументом вызова.

Если `revision` меньше ревизии, которую Watch уже зафиксировал, `beacon_ack` возвращает `ok:false` и `StaleRevisionError`. Записи нет: `claimedAt` не ставится, блок и wake не создаются. Прочитай свежий `beacon_get_result`, возьми его `revision` и повтори вызов. Повтор с тем же `revision` ничего не меняет.

## Доказательство находки

Блокирующая находка ревью несёт поле `evidence`. В нём четыре значения: команда, вывод прогона, ожидаемый вывод и ссылка на head, для которого команда запускалась. Команда воспроизводится агентом без человека. Вывод берётся из реального прогона.

Находка без команды и вывода не блокирует PR. Она уходит в follow-up. Три причины красного вердикта из раздела «Процедура» остаются в силе.

Правило не отменяет ADR 0022. Прогон идёт в CI через PR. Локальные тесты и гейты не запускаются. Кросс-вендорный судья остаётся необязательной проверкой.

## Исключение: вопрос к человеку

Консультация перед завершением хода не проводится, если ход заканчивается вопросом к человеку. В этом случае маркер правок остаётся, и консультация переносится на следующий ход. Исключение действует вместе с шагом 6 в `.opencode/skills/night-shift/SKILL.md`.

## Запрет

Не чинить `main` самому. Не пушить в `main`, не делать force-push в общие ветки и не править файлы вне своего worktree. Если `main` красный, оркестратор получает wake и сам решает, что делать.
