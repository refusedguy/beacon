# Правила комментариев в issues ночной смены

Справочник для смены. Читать перед тем, как писать комментарий в issue. `SKILL.md`
держит только ссылку на этот файл, полный текст загружается только перед действием
(progressive disclosure, ADR 0035 п3).

Каждая команда внешнего сервиса в этом файле соответствует операции из
`tracker-contract.md`. Если нужной операции в контракте нет, прекратить эту
запись и комментарий не отправлять.

## Главное правило

Писать только при НОВОМ факте. Если нового факта нет, комментарий не отправляется.

Новый факт это одно из:

- влитый PR с хешем коммита или номером PR;
- измерение (результат бенчмарка, метрика, число с указанием условия);
- решение владельца;
- блокер с указанием, что именно блокирует.

Шаблонная фраза без нового факта не является причиной для комментария. Пример
запрещённого текста: «Прогресс: PR X влит, CI зелёный», если это уже написано выше
или не несёт нового смысла.

## Заморозка координат issue

До первой записи зафиксировать номер issue и координаты исходного комментария,
под которым ведётся смена. Координаты это идентификатор канала и таймстемп
корневого сообщения. Записать их в контекст смены до шага 1 процедуры ниже.

Не подменять зафиксированные координаты координатами ответа. Таймстемп ответа
или номер нового комментария не становятся координатами issue. Все последующие
комментарии и проверки ссылаются на зафиксированные координаты. Если координаты
не зафиксированы, комментарий не отправлять.

## Доверенный маркер решения владельца

Имя настроенного автора и доверенный маркер задаются в настройках смены до
начала работы. Решение владельца принимается только при трёх условиях:

1. Автор комментария совпадает с настроенным автором.
2. В комментарии ровно один доверенный маркер.
3. Комментарий стоит под зафиксированным корневым сообщением issue.

Маркер это строка из настроек смены. Несколько маркеров в комментарии не
принимаются. Комментарий без маркера не является решением владельца.

Если автор не совпадает, маркеров нет или их больше одного, комментарий с
решением владельца не отправлять и решение не фиксировать. Расхождение
сообщить оркестратору вместо поста в issue.

## Процедура перед комментарием

1. Прочитать существующие комментарии: `gh issue view N --comments`. Не дублировать
   уже написанное.
2. Проверить, есть ли новый факт из списка выше. Если нет, не комментировать.
3. Если есть, проверить формат: дата + один абзац + доказательство.
4. Если комментарий устарел, обновить его через
   `gh api PATCH /repos/.../issues/comments/<id>`, а не добавлять новый.
5. Перед закрытием issue провести аудит: убедиться, что комментарии не противоречат
   друг другу и текущему статусу issue.

## Формат комментария

- Дата в начале.
- Один абзац: что изменилось и почему это новый факт.
- Доказательство: хеш PR, измерение, цитата решения владельца или описание блокера.
- Без шаблонных «Прогресс: ...» без нового смысла.
