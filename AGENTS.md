## Запреты

| Нельзя | Вместо этого |
| --- | --- |
| Коммитить или пушить в main | Ветка от origin/main, worktree, PR |
| `go test ./...`, `go build ./...`, `beacon gates` локально | GitHub Actions CI на PR; локально только `gofmt -w` на свои .go |
| `grep -r`, `grep -R`, `find /` | `rg <шаблон> <явный каталог>`; хук плагина отклоняет эти команды |
| Research-агенту вызывать `execute` или `tools.beacon.*` | Профиль `issue-scout` запрещает `execute`, `beacon_*` и `subagent`; для GitHub использовать webfetch |
| `gh pr checks --watch`, `sleep` в цикле | `waiting, <watchID>` и сон |
| Править чужую карточку или чужие OwnerFiles | Только своё поле «Владелец файлов»; задачу получаем через `beacon_task_claim`, статус карточки меняет Beacon при мерже |
| Добавлять зависимость, которая замыкает цикл | Граф отвергает цикл на записи |
| Закрывать карточку вручную | При `merged` Beacon ставит `done` и ссылку на PR |
| `batch-apply` без команды владельца | Ждать команды владельца |
| Закрывать чужие карточки в чужом PR | Не трогать |
| `notify.target: "<cardID>"` | Реальный `ses_...` |

## Порог правила

Порог правила отделяет наблюдение от правила в этом файле. Минимум для нового правила: два независимых наблюдения из разных сессий или карточек. Одиночный сигнал остаётся наблюдением и в таблицу запретов не попадает. Не считай источником ссылку на одного агента.

Для каждого правила в таблице «Запреты» запиши источник. Источник правила это две независимые карточки или ADR. Строка без источника уходит при ревью.

Не добавляй правило сразу после одного неудачного прогона. Сначала зафиксируй второе наблюдение в другой сессии или карточке.

## Граница инструмента

Плагин `beacon-project` ставит хук `ctx.tool.hook("execute.before")`. Хук отклоняет `grep -r`, `grep -R`, `find /`, локальные `go test`, `go build` и `beacon gates` до запуска команды. В сообщении указана замена: `rg` с явным каталогом или CI на PR. Переменная `BEACON_SHELL_GUARD=warn` включает режим наблюдения без блокировки. Режим по умолчанию блокирует команду.

Профиль `issue-scout` запрещает research-агенту `execute`, `beacon_*`, `subagent`, `edit`, `shell` и `write`. Запрет `execute` и `beacon_*` нужен вместе: при запрете только `execute` инструменты Beacon становятся прямыми.

## Измерение до выбора

Карточка или ADR предписывает подход. Не принимай его без измерения. Запиши в карточке поле `baseline` с числом или ссылкой на замер.

1. Найди в карточке измерение или ссылку на него.
2. Если измерения нет, сними замер или укажи источник, где он лежит.
3. Сравни замер с предписанным решением и только потом выбирай подход.

Решение без измерения проваливает карточку.

Число о скорости проходит семь вопросов из раздела «Семь вопросов к измерению производительности» в `docs/runbooks/verification.md`. Нужны названный лимитер, не менее пяти чередующихся прогонов A/B/A/B/A, медиана с размахом и счётчик ошибок. Без них число остаётся `inconclusive` и в решение не идёт. Источник: PSKX-03.

## Диагностика

Не грепать логи и не ждать в bash.

- `beacon_list_running`
- `beacon_stats`
- `beacon inspect`
- `beacon logs --tail 40 --errors`

Красная команда до первой гипотезы. Запусти одну команду, которая воспроизводит симптом пользователя и может упасть на этом баге. Это feedback loop. Без уже запущенной red-capable команды гипотезу не строй.

Команда подходит при четырёх условиях.

1. Задевает код, в котором лежит баг.
2. Проверяет точный симптом пользователя.
3. Даёт одинаковый вердикт при повторе.
4. Запускается агентом без человека.

До гипотезы достаточно одной команды и одного прогона. Вердикт прогона запиши как baseline по правилу «Измерение до выбора».

Если команду построить нельзя, остановись. Запроси доступ, артефакт с удалёнными секретами или разрешение на временную инструментацию. Вернись к гипотезе после того, как запустишь команду и запишешь её вердикт.

Состояние, в котором система оказалась, проверь перед первой гипотезой. Задай вопрос «состояние легитимно?» и выбери одну из двух веток.

- Да. Состояние легитимно. Обработай его там, где система его создала. Guard или retry ставь только в этом месте и только с доказательством.
- Нет. Состояние невозможно. Найди код, который его породил, и исправь причину. Guard, retry и обрезка значения у симптома баг не убирают.

Не ставь guard, retry и обрезку значения, пока не ответил на вопрос «состояние легитимно?». Guard без доказательства легитимности состояния не принимается.

Если нашёл шаблон, исправь его во всех местах, а не в одном экземпляре. Когда причина обнаружилась глубоким расследованием, добавь дешёвый сигнал. Держи его включённым постоянно, чтобы поймать повтор.

Правило дополняет контракт глубины в `internal/domain/depth.go`. Там остаются hypothesis, falsifier и evidence.

## Вторая инструкция

Порог в этом разделе считает повтор. Если ты пишешь в AGENTS.md или в шаблоне то же предупреждение, которое уже записано, остановись. Сначала найди структуру, которая делает ошибку невозможной: линт, флаг метаданных, runtime-проверку или скрипт. Повторяющуюся инструкцию надо закрепить структурой. Она сработает один раз и не зависит от того, прочитал ли агент текст.

Вторая инструкция без попытки кодификации не считается исправлением. Запиши, какую проверку ты рассмотрел, и почему она не подходит, если оставляешь текст.

Некоторые суждения не кодируются. Выбор между двумя корректными вариантами зависит от контекста и не сводится к проверке. В таком случае усиль текст и добавь пример сбоя: покажи ввод, при котором старая формулировка ведёт к ошибке, и ожидаемое действие. Без примера правило остаётся наблюдением и уходит при ревью по правилу «Порог правила».

Источник: `pstack/skills/principle-encode-lessons-in-structure/SKILL.md:11`, карточка PSKX-24. CM-04 и CM-05 задают конкретные проверки и здесь не повторяются.

## Своя ветка и PR

1. Сначала `git fetch origin main`. База ветки и worktree: свежий `origin/main`.
2. Ветка от `origin/main`, worktree.
3. Только свои OwnerFiles.
4. `git diff --stat` перед `gh pr create`.
5. `git push -u origin <ветка>`, `gh pr create --base main --head <ветка>`.
6. Отчёт: PR, headSHA, файлы.

Устаревшая база даёт ложный premise-check и конфликты при ребейзе.

### Минимальный diff (PSKX-28)

Не повторяй одно решение в нескольких местах. Держи его в одном источнике и передавай результат простым флагом. Держи минимальный diff.

Перед PR сверь `git diff --stat` и объясни каждую строку, которая не относится к задаче. Необъяснённая строка уходит из diff. Не добавляй абстракцию ради будущего расширения: абстракция без текущего вызывающего в PR не попадает.

Источник: `pstack/skills/principle-laziness-protocol/SKILL.md:9-10`, карточка PSKX-28. CM-04 и CM-05 задают конкретные проверки и здесь не повторяются.

## Задачи: индекс, граф и claim

Карточки в `docs/tasks/` остаются источником истины. Индекс в state dir пересобирается из них командой `beacon index build`. CI сверяет индекс побайтово с деревом карточек, а прекоммит блокирует устаревший индекс. Индекс вручную не правят.

### Кэш разбора (CA-18)

`beacon index build` прогревает версионируемый кэш разбора в state dir (`repomap-cache/vN/entries.json`). Запись keyed by path и проверяется по mtime и размеру: изменение файла инвалидирует запись. Рендер дерева keyed by `relative path + строки интереса + mtime`. При битом или недоступном хранилище кэш делает одну попытку пересоздания, затем работает в памяти без падения команды. `beacon index build` остаётся источником принудительной пересборки, вручную индекс не правят. Измерение: `beacon index cache-check --passes 100` печатает `parses` и `hits` по проходам; после первого прохода `parses=0`, флаг `--touch` меняет mtime и показывает инвалидацию, флаг `--break-cache` показывает работу в памяти.

- `beacon_task_claim` принимает agent ID и возвращает ID карточки, цель, зависимости, OwnerFiles, режим плана и handoff. Первая выдача помечает карточку `in_progress`, поэтому второй агент не возьмёт ту же карточку. Не ищите задачу вручную в `docs/tasks/`.
- Граф строится из четырёх типов рёбер: `blocks`, `depends-on`, `supersedes` и `related`. В граф попадают все семейства ID: T, RS, WIRING и BS. Цикл на записи отвергается. Не добавляйте зависимость, которая замыкает цикл.
- Поле «переносимые выводы» в шаблоне оркестратора объявляет, какие результаты upstream нужны downstream. Ребро `depends-on` переносит выводы в текст задачи до выдачи: воркеры на ветках сиблингов не читают чужие ветки, поэтому оркестратор сам вставляет тело upstream handoff в бриф. При этом необъявленное ребро при нужном контексте заставляет воркера догадываться. При большой области вывода оркестратор сжимает handoff, а не добавляет сырые логи в промпт.
- Маркер `graphReady` в ответе claim или в `beacon_stats` говорит, что граф собран и актуален.
- `beacon board` открывает локальный TUI без сети. Он показывает задачи из индекса, граф и фильтры по статусу и владельцу.
- При терминальном вердикте `merged` Beacon сам переводит связанную карточку в `done` и пишет ссылку на PR в подтверждение.

## Режимы плана

Перед фазой plan прочитай поле `Режим плана` в карточке. Значение `fast` или `full`. Пустое поле означает `fast`.

- `fast`: исполнитель не создаёт ветку и пишет `PLAN.md` в текущем дереве.
- `full`: исполнитель создаёт ветку или worktree и пишет тот же `PLAN.md`.

Оба режима создают проверяемый артефакт. План без `PLAN.md` проваливает карточку по правилу `no-artifact: fail`.

Для нетривиального изменения, которое пересекает границу функции, план содержит две формы проекта и таблицу «состояние, владелец состояния». Порядок задаёт раздел «Форма проекта до кода» в `docs/templates/executor-task.md`. `PLAN.md` без двух форм и таблицы владельцев проваливает фазу plan (PSKX-01). Протокол Watch и число MCP-инструментов не меняются.

## Обновление карты контекста

Флаг `--map-refresh` задаёт политику обновления ранжированной карты контекста (CA-20). Значения: `manual`, `files`, `always`, `auto`. Значение по умолчанию `auto`. Флаг не меняет существующие команды.

- `manual` возвращает последнюю карту и не строит новую.
- `files` повторно использует карту, пока набор файлов, их подписи и бюджет не изменились.
- `always` строит карту при каждом обновлении.
- `auto` повторно использует карту только после построения дольше одной секунды. В ключ кэша входят упомянутые файлы и идентификаторы.

Ключ кэша содержит набор файлов чата, набор остальных файлов, подписи файлов и бюджет. Модель не читает часы сама. Вызывающий код передаёт время построения через `MapBuildFunc` и решает, где хранить кэш между запусками.

## Авто-мерж

Beacon мержит зелёный PR по `verdict=ready` (ADR 0072). Исключения политики: `requireApproval`, `waitFor`, `waitForMain`. Исполнитель просыпается на `keep_working`, `rebase`, `retry` или ошибке мержа. При `ready` не вызывает `gh pr merge`.

## Блокеры main

Красная проверка на `main`: Beacon ставит `blocked`, пишет `BlockerIncident`. Исполнитель видит внешнюю поломку на `origin/main`: `beacon_ack` с `decision="blocked:not_mine"` и причиной. Оркестратор спавнит FIX-агента. main не чиним.

### Консультация перед завершением хода

Перед завершением хода агент проверяет маркер правок. Если файлы менялись после последней консультации, агент проводит консультацию и сообщает вердикт одной строкой. Если ход заканчивается вопросом к человеку, консультация переносится на следующий ход. Правило записано в `.opencode/skills/night-shift/SKILL.md` (шаг 6) и `.opencode/skills/red-verdict-triage/SKILL.md` (исключение). Карточка: `docs/tasks/CP-09.md`.

Консультация не становится обязательным гейтом CI. Состояние advisor хранится в четырёх артефактах: `state.json`, `pending`, `last-response.txt`, `log.md`. Стоп-хук проверяет флаг `nudge`, наличие маркера `pending` и последний символ ответа.

## Адверсариальный разбор

Ревью не принимает находку без запуска. Находка без команды и вывода не считается находкой.

Адверсарий пытается сломать изменение, а не улучшить его. Несколько адверсариев работают параллельно в отдельных worktree. Каждый получает одинаковый текст задачи и намерение изменения. Адверсарий не применяет правки к коду. Он возвращает только команду и её вывод, которые показывают поломку.

В отчёт попадает находка, у которой есть команда, вывод и объяснение, как поломка нарушает намерение. Замечания по стилю, именам и гипотетическим рискам без запуска в отчёт не попадают. Если подтверждённых finding нет, напиши «нет подтверждённых finding». Это допустимый результат разбора.

Протокол живёт в `docs/templates/executor-task.md`, раздел «Адверсариальный разбор». Он не меняет `beacon_watch_pr`, число MCP-инструментов и протокол Watch.

Источник: `docs/research/research-pstack-skills.md`, строка таблицы `interrogate`; карточка PSK-02.

## После сжатия

Плагин держит ключ `beacon/survival-rules` в instructions. Ключ стабильный, перезаписывается на старте и на хуке `compaction`. Правила выпали из контекста, читай ключ, а не гадай.

Ключ `beacon/survival-rules` входит в хвост истории и не сжимается. При бюджетном сжатии (CA-06) хвост из последних сообщений сохраняется дословно, разрез идёт по границе `assistant`, а сжимается только голова. Правила выживания поэтому остаются в контексте потомка после compaction.

## Стабильный префикс и точки кэша (CA-09)

Маркеры `cache:boundary` в этом файле задают границы кэша для повторных вызовов модели. Маркеры не меняют текст инструкций.

- `system` в начале файла. Правила и шаблон исполнителя образуют неизменный фрагмент. Его байты совпадают в каждом вызове потомка.
- `repo` перед разделом про свою ветку и PR. Текст карточки и множество файлов меняются от вызова к вызову и в кэш не входят.
- `chat` перед разделом про сжатие. Здесь начинаются правила выживания и история потомка.

Провайдер получает не более трёх точек кэша на запрос. Типы `CachePoint`, `CachePlan`, лимит `MaxCachePoints` и функция `PrefixFingerprint` лежат в `internal/app/session/delegation.go`. `PrefixFingerprint` помогает проверить побайтовое совпадение префикса между вызовами.

Подогрев префикса выключен по умолчанию. Нулевое значение `KeepaliveConfig` не шлёт фоновых запросов. При включении интервал равен пяти минутам, а лимит выходных токенов равен одному, как в aider (`aider/coders/base_coder.py:1340-1392`).

## Перезапуск после смерти

Агент оборвался, а его работа осталась в worktree и ветке. Новая сессия продолжает её, а не начинает с нуля.

1. Прочитай `git status --short --branch` в своём worktree. Ветка и незакоммиченные правки показывают, где остановился агент.
2. Прочитай общий журнал и собери сводку. Для файла или подсистемы прочитай связанные карточки, PR и issue за последние семь дней. Ограничь выборку именем подсистемы. Выпиши, что уже пробовали и что откатили. Сверь найденное живым состоянием через `git` и `gh`. Требуй, чтобы сводка состояния начинала открытые threads и следующий шаг.
3. Прочитай ключ `beacon/survival-rules` и continue-prompt. Продолжи с шага, на котором работа оборвалась.
4. Не создавай новый worktree и не повторяй уже сделанный коммит.

Продолжение без сводки общего журнала проваливает карточку. Симптом, который уже откатывали, не предлагай повторно без нового доказательства.

Работа в worktree не теряется. Перезапуск с нуля проваливает карточку.

Десять инструментов: `beacon_watch_pr`, `beacon_wait_result`, `beacon_get_result`, `beacon_list_running`, `beacon_ack`, `beacon_cancel_watch`, `beacon_stats`, `beacon_defer_wiring`, `beacon_task_claim` и `beacon_task_close`. `beacon_task_claim` берёт карточку в работу. `beacon_task_close` закрывает карточку с причиной.

`beacon_defer_wiring` вызывай сразу, как только понял, что часть фичи осталась неподключённой (OwnerFiles другого агента). Он возвращает готовую карточку `WIRING-<PR>`, которую надо добавить в свой PR. Не откладывай wiring на «потом»: без карточки работа теряется.

Шаблоны: `docs/templates/executor-task.md`, `docs/templates/orchestrator-task.md`.

## Оркестратору: заполнение слотов

Каждое `<beacon-event>` с `nextAction: report_to_orchestrator` (`wave item done`) означает один свободный слот. В том же ходе, без пинка владельца, запусти одного нового сабента. Один сигнал равен одному spawn. Не отвечай «тихо продолжаю» и не оставляй слот пустым.

Исключение: если main красный по required-проверке, новых сабентов не спавни. Дождись FIX-агента и зелёного main. Информационные проверки (`required: false`) main не ломают.

### Планировщик и воркеры

Оркестратор работает как планировщик. Планировщик публикует задачи и не правит код. Правка файлов, `git merge` и решение конфликтов не входят в его работу. Если планировщик хочет написать код, он публикует задачу для воркера.

Планировщик не знает, кто возьмёт его задачу. Скрипт направляет каждую задачу агенту. Планировщик думает задачами, а не агентами.

У воркера одна задача, одна копия репозитория и ни одного канала к другому агенту. По завершении воркер возвращает один структурированный handoff.

Сабпланировщик это рекурсивный планировщик. Планировщик публикует задачу «спланируй этот срез». Сабпланировщик полностью владеет срезом и возвращает один общий handoff.

Движение идёт непрерывно через handoffs. Планировщик, который решил, что закончил, может получить поздний handoff и перепланировать. Пока планировщик сам не перестанет публиковать задачи, состояния finished нет.

Распространение вместо синхронизации. Между соседями нет переписки. Между уровнями нет общего состояния. Каждый уровень видит только handoff своих детей.

| Узел | Ведёт цикл? | Область | Выход |
| --- | --- | --- | --- |
| Планировщик | да | Вся цель пользователя | Сообщение пользователю и опциональный PR |
| Сабпланировщик (↻) | да | Один срез области родителя | Handoff родителю |
| Воркер | нет | Одна конкретная задача | Handoff планировщику, выдавшему задачу |
| Верификатор | нет | Критерии приёмки одной цели | Handoff с вердиктом планировщику |
| Git | н/д | Общая среда | Ветки (код) и `handoffs/` (смысл) |

Раздел шаблона оркестратора: `docs/templates/orchestrator-task.md`. Правило «один сигнал равен одному spawn» из раздела заполнения слотов сохраняется.

### Необязательный протокол кандидатов (PSK-01)

Правило «один сигнал равен одному spawn» сохраняется для волны. Протокол кандидатов оркестратор включает отдельным решением и только для спорного проекта. К событию `wave item done` протокол не привязан. Для механической работы его не применяют.

Шесть фаз протокола описаны в `docs/templates/orchestrator-task.md`: рамка, разведение кандидатов, кросс-оценка, выбор основы, прививка, проверка. Рамка задаёт артефакт и 3-6 проверяемых критериев, которые видит только судья. Каждый кандидат работает в отдельном worktree и получает одинаковый текст задачи. Кросс-оценку делает судья из вендора, отличного от вендора исполнителя. Прививка переносит одну или две идеи от каждого проигравшего в отобранную основу с указанием источника. При согласии кандидатов прививка не нужна. При расхождении оркестратор пересматривает рамку и повторяет оценку.

Протокол не меняет `beacon_watch_pr`, число MCP-инструментов и число спавнов на сигнал. Карточка, которая ссылается на PSK-01, содержит рубрику и решение судьи.

Источник задач по приоритету: сначала `beacon deferred --format json` (отложенное wiring), затем индекс карточек через `beacon board` и граф без циклов, после чего вопросы владельца. `docs/ROADMAP_STATUS.md` и аудиты это подсказки, а не единственный путь. Перед запуском проверь непересечение OwnerFiles через `beacon task check-launch` / `PlanLaunch`. Каждый новый сабент получает задачу через `beacon_task_claim`, а не через ручную ссылку на карточку.

НЕ открывай карточки со статусом `dropped`. Их подтверждение фиксирует, что дизайн брошен или дублирует существующий код. Архивные S1-S7 карточки в大部分 dropped по ADR 0086/0094: серверные проекты, реестры, сессии, адаптеры и recovery уже сделаны в store/MCP или запрещены вторым протоколом. Агент обязан проверить premise перед кодом. Если функциональность уже есть в `internal/infra/store/*`, `internal/infra/mcp/*`, `internal/infra/registry/*` или `internal/domain/*`, НЕ пиши дубль, вернись с обоснованием (как агенты S3.001/S3.002/S3.003/S3.008/S4.001). Карточку `dropped` в работу не брать.

Тихий режим: на терминальный сигнал делай действие и не печатай в чат статусную строку «PR X влит». Пиши в чат только новую информацию: решение владельца, измерение, блокер, результат выборки.

### Список решений владельца

Если работа уперлась в решение, которое может принять только человек, напечатай короткий список с заголовком «ждут решения владельца». Каждая строка содержит ссылку на артефакт, вариант и рекомендацию, чего хватит для ответа с одного места. Не включай в список работу, которую агент может сделать сам. Если решений нет, строку «ждут решения владельца» не печатай. Статусные строки «PR влит» остаются запрещены.

Информационные проверки с `required: false` или `continue-on-error: true` не являются блокерами. По ним не вызывай `beacon_ack decision="blocked:not_mine"` и не спавни FIX-агента.

## Прозу пиши по unslop

Все тексты, которые ты пишешь (ответы, docs, README, PR body, commit messages, комментарии), пропускай через правила скилла `unslop`: без em dashes, простые слова, активный залог, одна мысль на предложение, без заполняющих фраз и без «rule of three». Загрузи скилл `unslop` перед написанием любой прозы.

## Аудит подавлений не заменяет unslop

unslop правит прозу: ответы, docs, README, тела PR, commit messages и комментарии. Второй проход, аудит подавлений из `docs/templates/executor-task.md`, читает код: комментарии и подавления правил линтера. Это разные проходы. unslop меняет текст. Аудит подавлений даёт только отчёт и не меняет файлы. Пометка `MUST KILL` из отчёта уходит в обычный цикл с OwnerFiles. Источник: карточка CP-17 и `pstack/agents/comment-sicko.md`.
