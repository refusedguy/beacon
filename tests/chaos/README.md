# T4.1. Хаос-тест: двойная доставка и indeterminate

Дата записи: 2026-11-22. Ветка: `feat/w41`. Карточка: `docs/tasks/T4.1-chaos-duplicate-delivery.md`.

Проверяемые решения: ADR 0017 (ветвление лестницы), ADR 0014 (нет квитанции, значит indeterminate), ADR 0015 (одна транзакция и `UNIQUE(watch_id, revision, subscriber_id)`), ADR 0019 (нет TTL как причины закрытия), ADR 0020 (формат карточки), ADR 0021 (изоляция worktree), ADR 0022 (проверка только в CI).

## Запуск

```
go test ./tests/chaos/...
```

Тест попадает в основной прогон `go test ./...` джобы `test` из `.github/workflows/ci.yml`. Отдельного шага в CI не нужно: пакет лежит в корневом модуле.

Имя файла `duplicate-delivery_test.go`, а не `duplicate-delivery.test.go` из поля «Владелец файлов». Go регистрирует функции `TestXxx` только из файлов с суффиксом `_test.go`. Под именем `.test.go` файл скомпилировался бы как обычный исходник, `go test` написал бы «no test files», и CI был бы зелёным при невыполненном тесте. Это нарушило бы требование карточки про реальный запуск теста в CI. Суффикс изменён минимально: дефис сохранён, заменён только разделитель.

## Изолированное окружение

- `state.db` это настоящая SQLite-база T1.2 (`internal/infra/store`), WAL, один писатель.
- `receipts.jsonl` это файловая граница с плагином T3.1 и квитанциями T3.6. `ImportReceipts` идемпотентен по `(obligationID, attempt)`.
- Ключ получателя считает `domain.ObligationKey(watchID, revision, subscriberID)` из T1.3 и T3.6. Он же служит ключом эскалации.
- Доставка указателя через канал T3.2 моделируется записью строки квитанции и импортом. Указатель несёт идентификаторы, не содержимое.
- Лестница (`internal/infra/ladder/transitions.go`) и эскалация (`internal/infra/ladder/escalation.go`) уже есть в `main`. Хаос-тест не импортирует их и использует маленькие детерминированные фейки `decideResend` и `escalationLedger`. Замена фейков реальными реализациями пока не сделана.

## Сценарии и числа

| Сценарий | Проверка | Ожидаемое число |
|---|---|---|
| Двойная доставка | deliveries | 2 |
| Двойная доставка | эффекты (wake и merge) | 1 |
| Двойная доставка | отброшенные дубли | 1 |
| Двойная доставка | строк в `receipts` и попыток | 1 и 1 |
| Indeterminate | повторных отправок | 0 |
| Indeterminate | строк в `receipts` и доставок | 0 и 0 |
| Indeterminate | эскалаций за эпизод | 1 |
| Indeterminate | обязательство осталось pending | да |
| Рестарт | обязательств сохранено | 2 |
| Рестарт | pending после рестарта | 1 |
| Рестарт | эффект после повторной доставки | 0 |
| Рестарт | лимит старта | не более 5 с |

Счётчик `Duplicates` у `ImportReceipts` считает дубли по всем строкам файла при каждом импорте, а не по одной доставке. Поэтому число отброшенных доставок тест считает как deliveries минус применённые эффекты: 2 минус 1 равно 1. Число строк в `receipts.jsonl` после двух доставок равно двум, а уникальных квитанций в базе одной.

Окно доказательства в тесте 30 мс вместо 15 минут из ADR 0017, чтобы прогон оставался быстрым в CI. Лимит рестарта 5 с взят из WORKER-PROMPT §5 без масштабирования. Фактическую длительность рестарта измеряет тест в CI. Локально число не фиксируется по ADR 0022.

## Результаты прогона

Числа в таблице это утверждения теста, которые он проверяет при каждом запуске. Дата записи 2026-11-19. Вывод `go test` и длительность рестарта фиксируются логами CI-джобы `test`. Локальный прогон по ADR 0022 не выполнялся.

## Стыковка с зависимостями

T3.6 и T2.6 уже в `main`. Реальные лестница и эскалация из `internal/infra/ladder/*` тоже есть в `main` (T3.9 и T3.10). Хаос-тест не импортирует их. Он по-прежнему использует фейки `decideResend`, `escalationLedger` и счётчик мержей вместо реальных вызовов лестницы, эскалации и оркестратора. Замена не сделана.
